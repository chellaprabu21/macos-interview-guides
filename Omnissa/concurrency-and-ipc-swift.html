Concurrency & IPC in Swift, From Scratch

Everything behind that JD line — why concurrency is hard, the Swift tools that tame it (GCD, async/await, actors, Sendable), and the two IPC mechanisms named: Unix domain sockets and XPC. Plain-English first, then interview depth.

Read me first

Same four beats per topic as the frameworks guide: one-sentence version → why it exists → how it works → in the interview (answers in commit-first-then-caveat style).

The build order matters. We start with the one problem all of concurrency is trying to solve — shared mutable state — because every tool after that (locks, queues, actors) is just a different answer to it. Then IPC, which is concurrency between separate processes instead of threads.

Swift-first, but honest about the boundaryYour day-to-day answers should be Swift: GCD and Swift Concurrency. But a macOS daemon lives at a boundary where C and POSIX still show up — sockets are a C API, ES/Network callbacks arrive on C threads, and XPC has both a Swift face (NSXPCConnection) and a C face. I'll keep Swift central and drop to C only where it genuinely lives. Naming that boundary is itself a senior signal.

Topic 01

The core problem: shared mutable state
Understand this one thing and every tool afterward makes sense as "a way to avoid it."
The one-sentence version

Concurrency is running multiple things at once; the entire difficulty is that when two of them touch the same piece of memory and at least one is writing, the result is unpredictable — a data race.

Why it's hard — the picture

A thread is an independent line of execution with its own stack, but sharing all the heap memory of its process. Two threads, one shared counter, both doing count += 1:

 count += 1  is really THREE steps:   read count → add 1 → write count

 Thread A          Thread B           count
 read (0)                              0
                   read (0)            0     ← both read the same old value
 add → 1                               0
                   add → 1             0
 write 1                               1
                   write 1             1     ← two increments, but count is 1, not 2

That lost update is a race condition. And it's worse than "sometimes wrong numbers": in Swift and C, a data race on most types is undefined behavior — the program is allowed to crash or corrupt memory, because the compiler and CPU reorder and cache operations assuming no other thread interferes. This is why Swift 6 added compile-time data-race checking: the whole language is now organized around proving races can't happen.

The three failure modes you must be able to name

Race conditionTwo threads touch shared state unsynchronized; result depends on timing. (The counter above.)
DeadlockTwo threads each wait for a resource the other holds; both freeze forever.
Priority inversionA high-priority thread waits on a low-priority thread that never gets scheduled — the high-priority work stalls.

The two ways out (the whole field, in two lines)

  • Don't share: give each thread its own copy. Swift's value types (structs) make this natural — hand another task a struct and there's no shared memory to race on.
  • Serialize access: if you must share, make sure only one thread touches it at a time — a lock, a serial queue, or an actor. Every synchronization tool is a flavor of this.
Why a daemon feels this acutelyYour agent has callbacks arriving from many sources at once — ES events on one thread, network flows on another, timers, XPC requests — all wanting to touch shared state like a config cache or an event queue. Getting this wrong is exactly the "complex concurrency issue" your resume says you've debugged with Instruments. Have one such story ready: the symptom, the tool, the fix.

In the interview

What's the difference between a race condition and a data race?

Commit: A data race is the specific low-level case — two threads access the same memory concurrently, at least one writing, with no synchronization — and it's undefined behavior. A race condition is the broader idea: any bug where correctness depends on timing or ordering, even if each individual access is safe.

Nuance: you can have a race condition without a data race — e.g. two properly-locked operations that are individually safe but wrong when interleaved (check-then-act on a value that changed in between). So fixing data races with locks isn't automatically enough; you sometimes need the whole compound operation to be atomic. In Swift, actors and value semantics eliminate a lot of data races structurally, which is the modern answer.

Why are value types (structs) relevant to concurrency in Swift?

Commit: Because they're copied on assignment, so passing a struct to another thread hands over an independent copy — there's no shared mutable state, and therefore no data race by construction. It's the "don't share" strategy baked into the type system.

Nuance: arrays/strings/dictionaries are structs with copy-on-write, so the copy is cheap until someone mutates. This is why a good pattern for an agent is to snapshot config or telemetry as an immutable struct and hand that to workers, rather than sharing a mutable object behind a lock.

Topic 02

Locks & the tools that serialize access
If you must share, only one thread at a time. Here are the tools, cheapest concept to richest.
The one-sentence version

A lock is a "talking stick": only the thread holding it may touch the protected data; everyone else waits their turn. Swift gives you several, from a raw low-level lock up to actors that do the locking for you.

The tools, and when each fits

1 · os_unfair_lock — the low-level mutex

The modern primitive lock on Apple platforms. A thread acquires it, does its short critical work, releases it; a second thread trying to acquire while it's held is put to sleep by the kernel until it's free.

final class Counter {
    private var lock = os_unfair_lock()
    private var value = 0
    func increment() {
        os_unfair_lock_lock(&lock)
        value += 1              // critical section: exactly one thread here at a time
        os_unfair_lock_unlock(&lock)
    }
}

The name "unfair" means it doesn't guarantee first-come-first-served ordering — a deliberate performance choice. In modern Swift you'd often use the newer Mutex type from the Synchronization framework, which wraps this safely and holds the protected value inside the lock so you can't forget to lock. Worth mentioning as the current best practice.

Never say OSSpinLockThe old OSSpinLock is deprecated and dangerous: it spins (busy-waits, burning CPU) and causes priority inversion — a low-priority thread holding it can be starved forever while a high-priority thread spins. os_unfair_lock fixed this by telling the kernel who owns it so the owner can be boosted. Knowing this specific history is a strong signal.

2 · The serial queue as a lock — the GCD way

A serial dispatch queue runs its work one item at a time, in order. That is mutual exclusion: route all access to shared state through one serial queue and it can never be touched concurrently. This was the idiomatic pre-async Swift pattern.

private let queue = DispatchQueue(label: "com.corp.agent.state")
func read() -> Config { queue.sync { config } }           // serialized read
func update(_ c: Config) { queue.async { config = c } }    // serialized write

3 · Reader-writer with a concurrent queue + barrier

When reads vastly outnumber writes (like a config cache), you want many readers at once but exclusive writes. A concurrent queue with a barrier on writes gives exactly that: reads run in parallel; a barrier write waits for in-flight reads to finish, runs alone, then lets reads resume.

4 · The actor — Swift's built-in answer (covered fully in Topic 04)

An actor is a type that automatically serializes access to its own mutable state — the compiler enforces that you can only touch it through await, one caller at a time. It's a serial queue and a lock rolled into the language, with compile-time safety. For new Swift code this is usually the right choice, and we'll go deep on it shortly.

Deadlock — how it happens and how to prevent it

The classic: thread 1 locks A then wants B; thread 2 locks B then wants A. Neither releases; both wait forever.

 Thread 1: hold A ──wants──▶ B          Fix: everyone acquires locks in the SAME
 Thread 2: hold B ──wants──▶ A                global order (always A before B).
                                              A cycle in "who waits for whom" = deadlock.

The #1 real macOS deadlock is simpler and worth stating outright: calling DispatchQueue.sync targeting the queue you're already running on. You block waiting for the queue to be free, but you're the one occupying it — instant self-deadlock.

In the interview

How would you make a shared config cache thread-safe in Swift?

Commit: For new code, I'd make it an actor — access is automatically serialized and the compiler guarantees no data race. If I'm in a GCD codebase, I'd route all access through a serial dispatch queue, or use a concurrent queue with a barrier on writes since a config cache is read-heavy.

Nuance: if it's a single value and hot, a plain os_unfair_lock or the newer Mutex type is lowest-overhead. The choice is really about read/write ratio and whether I'm in async code: actor for async and safety, barrier-queue for read-heavy, raw lock for a tiny hot path.

Explain a deadlock you could cause with GCD, and how to avoid it.

Commit: The most common one is calling .sync on the queue you're currently executing on — you block waiting for that queue, but you're what's occupying it, so it can never free up. Avoid it by never calling sync back onto your current queue, and preferring async for anything reentrant.

Nuance: the general form is circular waiting between multiple locks, which I prevent with a consistent global lock-acquisition order. Swift Concurrency helps here because actors avoid manual locking entirely, though you can still deadlock if you block a thread waiting on an actor from the same cooperative pool — which is why you don't mix blocking waits into async code.

Why is os_unfair_lock preferred over a spinlock?

Commit: A spinlock busy-waits — it burns the CPU in a loop while waiting — and worse, it causes priority inversion: if a low-priority thread holds it and a high-priority thread spins on it, the holder may never get scheduled to release it. os_unfair_lock sleeps the waiter and records the owner so the kernel can priority-boost it.

Nuance: spinlocks are only ever appropriate for extremely short critical sections where sleeping costs more than spinning, and even then Apple deprecated OSSpinLock for the inversion problem. On Apple platforms the safe default is os_unfair_lock or the Mutex wrapper.

Topic 03

GCD / Grand Central Dispatch
The workhorse before async/await — still everywhere in system code, and still asked about.
The one-sentence version

GCD lets you hand blocks of work to queues instead of managing threads yourself; a shared pool of threads underneath picks up the work, keeping roughly one thread busy per CPU core.

Why it exists

Creating and managing threads by hand is error-prone and wasteful — spawn too many and they thrash the CPU with context switches. GCD flips it: you describe units of work and which queue they belong to; the system owns the threads and reuses them. You stop thinking about threads and start thinking about queues.

How it actually works

Serial vs concurrent queues

Queue typeBehaviorUse for
SerialOne task at a time, in orderProtecting shared state (it's a lock); ordered work
ConcurrentMany tasks at onceIndependent parallel work (e.g. process N files)
MainSerial, on the main threadUI updates only

sync vs async — the distinction people fumble

  • async — "run this later, I'm not waiting." Returns immediately.
  • sync — "run this and block me until it's done." (This is what self-deadlocks if you target your own queue.)

Serial vs concurrent is about the queue (how many at once). sync vs async is about the caller (do I wait?). They're independent choices — a frequent point of confusion worth stating cleanly.

QoS — quality of service (and priority inversion again)

You tag work with a priority class — .userInteractive, .userInitiated, .utility, .background — so the system schedules important work first and defers background work (saving battery). If high-priority work waits on lower-priority work, GCD priority-boosts the lower work to prevent inversion.

DispatchSource — the daemon's event backbone

A DispatchSource turns low-level kernel events into queue callbacks: a timer firing, a signal arriving, a file descriptor becoming readable, or a monitored process exiting. This is how a daemon reacts to the world without a thread blocking in a read loop — you'll see it wrapping sockets and file watches.

Groups & semaphores

DispatchGroup — "run N tasks, notify me when all finish" (fan-out/fan-in). DispatchSemaphore — a counter gating access to a limited resource, or a bridge to make async work look synchronous. Both are legacy patterns that async/await often replaces more cleanly.

Thread explosionIf you dump lots of blocking work onto a concurrent queue and each block waits on I/O, GCD keeps spinning up new threads to stay busy — you can exhaust the thread limit and stall the whole app. The fix historically was limiting concurrency (semaphore) or a serial queue; the modern fix is Swift Concurrency's cooperative pool, which caps threads deliberately. Mentioning this shows you've hit real GCD limits.

In the interview

Serial vs concurrent queue, and sync vs async — aren't those the same thing?

Commit: No — they're independent axes. Serial vs concurrent is a property of the queue: how many tasks run at once. Sync vs async is a property of the call: whether the caller blocks until the work finishes. You can submit sync to a concurrent queue or async to a serial queue; any combination is valid.

Nuance: the common useful pairings are async-to-concurrent for parallel background work, and sync-to-serial when you need a value back from state protected by that serial queue. The dangerous combination is sync onto your own current queue, which deadlocks.

How does a daemon watch a socket or a file for activity with GCD?

Commit: With a DispatchSource — specifically a read source on the file descriptor. Instead of a thread blocking in a read() loop, the source fires a callback on my queue whenever the descriptor has data, so one queue can multiplex many descriptors with no dedicated blocked threads.

Nuance: dispatch sources also handle timers, Unix signals, and process-exit events, which makes them the natural event backbone for a daemon. It's the same efficiency idea as kqueue underneath — GCD is exposing kernel event notification as queue callbacks.

Topic 04 · The centerpiece

Swift Concurrency: async/await & actors
The modern model. Since you're Swift-first, this is where you should be strongest.
The one-sentence version

Swift Concurrency lets you write asynchronous code that reads like normal top-to-bottom code (async/await), organizes it into a tree of cancellable tasks, and protects shared state with actors — with the compiler checking for data races at build time.

Why it exists

The old world was callbacks and completion handlers: nested, hard to read, easy to forget an error path, and with no help from the compiler about threading. Swift Concurrency replaces all of it with three connected ideas — async/await for readability, structured tasks for lifetime and cancellation, and actors for safe shared state — unified by the Sendable type system that makes data races a compile error rather than a 2am crash.

How it actually works

1 · async / await — suspension, not blocking

An async function can suspend at an await — pause, free its thread to do other work, and resume later when the awaited thing is ready. This is the crucial distinction from blocking:

 BLOCKING (old):   thread sits idle, held hostage, while waiting for I/O
 SUSPENDING (new): at `await`, the function steps aside and RELEASES the thread;
                   the thread runs other tasks; your function resumes when ready

func loadPosture() async throws -> Posture {
    let device = try await readDeviceState()   // suspends here; thread is freed
    let signed  = try await sign(device)        // suspends again
    return Posture(device, signed)          // reads like sync code, runs async
}

2 · Structured concurrency — tasks form a tree

A Task is a unit of async work. "Structured" means child tasks are tied to their parent's scope: the parent can't finish until its children do, and cancelling a parent cancels the whole subtree. This solves the old problem of orphaned background work that outlives what started it.

// Run three checks in parallel, all cancelled together if the parent is
try await withThrowingTaskGroup(of: Signal.self) { group in
    group.addTask { try await checkDisk() }
    group.addTask { try await checkNetwork() }
    group.addTask { try await checkCerts() }
    for try await signal in group { collect(signal) }
}

Cancellation is cooperative: a cancelled task isn't force-killed; it keeps running until it checks Task.isCancelled or hits a cancellation-aware await. So long-running work must check for cancellation to be responsive — a common interview follow-up.

3 · Actors — the safe-shared-state primitive

This is the concept to nail. An actor is like a class, but the compiler guarantees only one task touches its mutable state at a time.

actor VerdictCache {
    private var cache: [String: Verdict] = [:]
    func verdict(for hash: String) -> Verdict? { cache[hash] }   // serialized
    func store(_ v: Verdict, for hash: String) { cache[hash] = v } // serialized
}
// Callers must await — the await is where serialization happens:
let v = await cache.verdict(for: h)

The actor is doing internally what you'd do manually with a serial queue — but the compiler enforces it: you literally cannot access cache from outside without going through await, so a whole class of data-race bugs becomes impossible to write.

Actor reentrancy — the classic senior trapActors are reentrant: when an actor method hits an await and suspends, the actor is free to run other calls in the meantime. So state you read before an await may have changed after it. The rule: never assume your actor's state is unchanged across an await — re-check invariants afterward. This is the #1 "gotcha" question about actors; knowing it marks you as someone who's actually used them.

4 · MainActor

@MainActor is a special global actor meaning "this runs on the main thread." You annotate UI code with it and the compiler guarantees main-thread execution — replacing manual DispatchQueue.main.async and its easy-to-forget mistakes.

5 · Sendable — the type system that makes it safe

Sendable is a protocol marking types that are safe to pass between concurrency domains (between tasks/actors). Value types are automatically Sendable; a mutable class is not, because sharing it would allow a race. The compiler checks this at every boundary — this is Swift 6's data-race safety. A @Sendable closure similarly can't capture unsafe mutable state. When you can't prove safety but know it's fine, @unchecked Sendable is your explicit "trust me" escape hatch — use sparingly and say so.

6 · Bridging old callbacks into async — continuations

Real systems have C and Objective-C callback APIs (ES completion handlers, socket callbacks). You wrap them into async with a continuation: it suspends the async function and hands you a token to resume it when the callback fires.

func connect() async throws -> Session {
    try await withCheckedThrowingContinuation { cont in
        legacyConnect { session, error in          // old callback API
            if let error { cont.resume(throwing: error) }
            else { cont.resume(returning: session!) }  // resume EXACTLY once
        }
    }
}

Rule: resume the continuation exactly once — zero times leaks the task forever; twice crashes. The "checked" variant traps if you get it wrong, which is why you use it during development.

The Swift-first agent story"At the boundary I bridge C callbacks — ES messages, socket readiness — into async with continuations; above that boundary I use actors to protect the shared verdict cache and event buffer, so the compiler proves there's no data race; and I keep the ES handler itself off the cooperative pool because it has a hard deadline and I must never block a pool thread." That single answer shows you understand where each model belongs — which is the whole point of being Swift-first on a systems team.
Never block the cooperative poolSwift Concurrency runs async work on a small pool sized to your cores. If you do a blocking call (a synchronous socket read, a semaphore wait, sleep) inside async code, you starve that pool and can hang the app — the modern version of GCD thread explosion. Blocking/syscall work belongs on a dedicated thread or GCD queue, bridged in via continuation. Saying this preempts a favorite follow-up.

In the interview

What's the difference between suspending and blocking?

Commit: Blocking holds a thread hostage — the thread sits idle doing nothing while it waits. Suspending, at an await, releases the thread back to the pool to run other work, and resumes your function later. Same waiting from your code's view, completely different cost to the system.

Nuance: that's exactly why you must never do a blocking call inside async code — it defeats the model by tying up a pooled thread that suspension was designed to free, and can deadlock the whole cooperative pool. Blocking work gets pushed to a dedicated thread and bridged back with a continuation.

How does an actor prevent data races, and what's the catch?

Commit: An actor serializes all access to its mutable state — the compiler forces every external access to go through await, so only one task is inside the actor's state at a time. It's a serial queue plus a lock, enforced at compile time.

Nuance: the catch is reentrancy — when an actor method suspends at an await, the actor can run other calls meanwhile, so state can change across that suspension point. You can't assume anything you read before an await is still true after it; you re-validate. That's the subtle bug actors don't save you from.

You have an old C API with a completion callback. How do you use it from async Swift?

Commit: I wrap it in a continuation — withCheckedThrowingContinuation — which suspends the async function and gives me a token I resume from inside the callback, returning the value or throwing the error. That turns a callback API into a clean await.

Nuance: the one hard rule is resuming exactly once — never zero (the task leaks forever) and never twice (it crashes). I use the checked variant in development because it traps on misuse. This is exactly how I'd bring an Endpoint Security or socket callback into structured Swift concurrency.

What is Sendable and why did Swift add it?

Commit: Sendable marks types that are safe to move between concurrency domains — tasks and actors. The compiler checks that only Sendable things cross those boundaries, which turns data races from a runtime mystery into a compile-time error. Value types are Sendable automatically; mutable reference types aren't.

Nuance: it's the foundation of Swift 6's complete concurrency checking. When I have a type I know is safe but can't be proven — say a class guarded internally by a lock — I mark it @unchecked Sendable and take responsibility for that guarantee, which is an explicit, greppable decision rather than a silent assumption.

async/await vs GCD — when would you still reach for GCD?

Commit: For new application logic I default to async/await and actors — safer and more readable. I reach for GCD when I'm at the low-level systems boundary: DispatchSource for file-descriptor, signal, and timer events, or a dedicated serial queue for work that must not touch the cooperative pool, like a hard-deadline ES handler or blocking socket I/O.

Nuance: they interoperate — I bridge GCD/callback work into async with continuations. So it's not either/or; it's async/await for the structured, cancellable business logic and GCD for the kernel-event plumbing underneath.

Topic 05

IPC & Unix domain sockets
Concurrency between separate processes. First the fundamentals, then the socket the JD names.
The one-sentence version

IPC (inter-process communication) is how two separate processes — which don't share memory — talk to each other. A Unix domain socket is one of the main ways: a fast, local, bidirectional pipe between processes on the same machine, addressed by a filesystem path.

Why it exists — and why an agent needs it

Threads share memory; processes don't — each has its own isolated address space (that isolation is a security and stability feature). So processes need an explicit channel to communicate. An endpoint agent is naturally multi-process: a privileged root daemon does the sensitive work, a System Extension hosts the ES/NE code, and a menu-bar app talks to the user. These pieces must exchange messages — that's IPC.

The macOS IPC menu (know the landscape)

MechanismBest for
XPCApple-native process talking to Apple-native process — the default on macOS (Topic 06)
Unix domain socketsLocal IPC, especially when one end is portable C/C++ or non-Apple — the JD names this
Mach portsThe low-level primitive XPC is built on; rarely used directly
Pipes, shared memory, filesSimple streams, bulk data, persistence

Unix domain sockets, from scratch

They use the same socket API as network sockets (socket, bind, listen, accept, read, write) but with the AF_UNIX family and a filesystem path instead of an IP address and port. Because they never touch the network stack, they're faster than a localhost TCP connection and can't be reached from off-machine.

 SERVER                              CLIENT
 socket(AF_UNIX)                     socket(AF_UNIX)
 bind("/var/run/agent.sock")         connect("/var/run/agent.sock")
 listen()                                 │
 accept() ◀───────────────────────────────┘   now a bidirectional byte stream
 read()/write() ◀──────────────────────▶ write()/read()

Two things you must handle — and interviewers check for

  • Message framing. A stream socket is a river of bytes with no message boundaries — two writes can arrive as one read, or split across reads. So you impose your own frames: the standard trick is a length prefix — write a 4-byte length, then the payload; the reader reads 4 bytes, then exactly that many. Cap the max length so a bad/hostile peer can't make you allocate gigabytes.
  • Peer identity. Since any local process could connect, you check who's on the other end: getpeereid gives the peer's user/group ID, and LOCAL_PEERCRED gives more. For real security you verify the peer's code signature (the Security.framework technique) — trusting the connection because your team signed the peer, not because of its path or PID.
Why a portable-core team likes UDSOmnissa's DEX agent has a cross-platform C++ core. Unix domain sockets are the natural IPC there because they're not Apple-specific — the same socket code works on Linux. XPC would lock that boundary to Apple. So the honest, senior answer to "XPC or sockets?" is: XPC when both ends are Apple-native and I want launchd lifecycle and typed messages; Unix sockets when a portable C/C++ core or non-Apple tool needs in. You run both at JumpCloud — say which carries what.

Reading a socket the Swift way

You don't sit a thread in a blocking read loop. You make the descriptor non-blocking and attach a DispatchSource read source (Topic 03) — it calls you back on a queue when bytes are ready, so one queue handles many connections. Above that, you can expose the whole thing as an AsyncStream of decoded messages so the rest of your Swift code just does for await message in connection.

In the interview

You're sending messages over a Unix domain socket and they're arriving merged or split. Why, and how do you fix it?

Commit: Because a stream socket doesn't preserve message boundaries — it's a byte stream, so the kernel is free to coalesce or split your writes. The fix is application-level framing: I prefix each message with its length, typically a 4-byte header, so the reader reads the length then exactly that many bytes to reconstruct one message.

Nuance: I cap the maximum frame size so a malformed or hostile length can't make me allocate unbounded memory, and I add a small version field in the header so the daemon and client can be upgraded independently — which is a real concern at fleet scale where the two halves update at different times.

Any local process can connect to your socket. How do you make sure only your app does?

Commit: I verify the peer's code signature. From the connection I get the peer's identity and build a SecCode, then check it against a requirement pinning my Team ID and signing identifier — so only a binary my team signed is accepted.

Nuance: peer credentials like getpeereid tell me the uid, which is a start, but uid alone is spoofable in the sense that any process of that user could connect — the signature check is what actually establishes trust. This is the same identity principle as XPC connection validation; I apply it regardless of transport.

Would you use a Unix socket or localhost TCP for local IPC?

Commit: Unix domain socket. It's faster because it skips the entire TCP/IP stack, and it's inherently local — nothing off-machine can reach it, so there's no accidental network exposure. TCP on localhost adds protocol overhead and an attack surface for no benefit here.

Nuance: the one case for localhost TCP is if a component genuinely can't do Unix sockets or needs to be relocatable across machines later — but for a same-machine daemon-to-helper channel, Unix sockets are the right default.

Topic 06

XPC
Apple's own IPC — the default for Mac-native processes, with a clean Swift face.
The one-sentence version

XPC is macOS's built-in, secure IPC: you call methods on an object that actually lives in another process, as if it were local, with the system managing launching, crash-recovery, and message serialization for you.

Why it exists

Sockets give you a raw byte pipe — you build framing, serialization, and lifecycle yourself. XPC gives you all of that for free when both ends are Apple-native: you define a protocol, call methods on a proxy, and the system handles marshaling arguments, launching the other side on demand, and restarting it if it crashes. It's built on Mach ports and integrated with launchd (the system's service manager), which is where the lifecycle magic comes from.

How it actually works

The shape of it in Swift (NSXPCConnection)

You share a @objc protocol between both processes describing what can be called. The client gets a proxy; calls on it execute in the server process.

// Shared protocol (both processes have this)
@objc protocol AgentControl {
    func currentPosture(reply: @escaping (Posture) -> Void)
}

// Client side
let conn = NSXPCConnection(machServiceName: "com.corp.agentd", options: .privileged)
conn.remoteObjectInterface = NSXPCInterface(with: AgentControl.self)
conn.resume()
let proxy = conn.remoteObjectProxy as? AgentControl
proxy?.currentPosture { posture in use(posture) }   // runs in the daemon, replies back

launchd lifecycle — why XPC services "just start"

You register the daemon with launchd (via a plist declaring its MachServices name, or modern SMAppService). Then: the daemon starts on demand when the first message arrives, and launchd relaunches it if it crashes — you never manage its process yourself. This on-demand + crash-recovery behavior is XPC's headline advantage over rolling your own socket server.

The security question — asked in every agent interview

An XPC listener must not trust connections by default. In the accept handler you validate the caller by its code signature, using the connection's audit token:

func listener(_ l: NSXPCListener,
              shouldAcceptNewConnection c: NSXPCConnection) -> Bool {
    // Take c.auditToken → build a SecCode → SecCodeCheckValidity against
    // a requirement pinning YOUR Team ID + signing identifier.
    return verifyCodeSignature(auditToken: c.auditToken)   // reject if not ours
}

Why the audit token and not the PID: PIDs get reused, so a check on PID alone can be defeated by a process that inherits a recycled PID. The audit token includes a pid-version that distinguishes a dead process from its replacement, and it's kernel-verified — you can't forge it. This ties straight back to Security.framework and is the XPC senior signal.

Connection lifecycle handlers

Set an invalidationHandler (connection permanently dead — clean up) and an interruptionHandler (server crashed but connection can be re-established — reconnect logic). Handling these is what makes an agent resilient when its helper restarts.

Validate every input, it's a trust boundaryEven after signature-checking the peer, treat every argument arriving over XPC as untrusted input — define narrow protocol methods, bound sizes, and never assume the caller is well-behaved. An IPC endpoint in a privileged daemon is an attack surface; the interviewer wants to hear you think of it that way.

In the interview

How do you secure an XPC connection?

Commit: In the listener's shouldAcceptNewConnection, I verify the connecting process's code signature. I take the connection's audit token, build a SecCode from it, and check it against a requirement that pins my Team ID and signing identifier — rejecting anything my team didn't sign.

Nuance: I use the audit token rather than the PID because PIDs are reused and thus spoofable; the token is kernel-verified and carries a pid-version. And I still validate every argument on every method — signature-checking the peer establishes who it is, but a privileged daemon treats all IPC input as untrusted regardless.

Why choose XPC over a Unix socket, and when would you not?

Commit: XPC when both ends are Apple-native — it hands me typed method calls, argument marshaling, and launchd-managed lifecycle: on-demand launch and automatic crash relaunch, none of which I'd get from a raw socket. It's the macOS default for a reason.

Nuance: I'd choose Unix domain sockets when one end is a portable C/C++ core or a non-Apple tool, because XPC ties me to Apple frameworks — a cross-platform agent core can't speak XPC but speaks sockets everywhere. So it's a boundary decision: XPC for the Mac-native pieces, sockets where portability or a foreign runtime is involved.

How does an XPC daemon start, and what happens if it crashes?

Commit: launchd manages it. I register the service with launchd declaring its Mach service name, and it starts on demand — the daemon isn't running until the first client message arrives, at which point launchd launches it. If it crashes, launchd relaunches it under the same name.

Nuance: on the client side I handle the interruption and invalidation handlers so I reconnect cleanly after a restart. That on-demand and self-healing lifecycle is exactly why XPC beats a hand-rolled socket server for Apple-native components — I'm not writing my own supervision.

The through-lines interviewers reward

  • One problem, many tools. Everything — locks, serial queues, actors — exists to serialize access to shared mutable state. Lead with that and each tool is just a point on a spectrum from manual (locks) to compiler-enforced (actors).
  • Suspend, don't block. The modern model frees threads at await instead of holding them. The cardinal sin — blocking the cooperative pool — is where most Swift-concurrency follow-ups go.
  • Identity is the same across IPC transports. Whether XPC or a Unix socket, you authenticate the peer by verifying its code signature via the audit token — the Security.framework link. One idea, both transports.
  • Right tool per layer. C/GCD at the kernel-event boundary (deadlines, sockets, DispatchSource), Swift Concurrency for structured business logic above it, bridged by continuations. Showing you know where each belongs is the senior signal for a Swift-first systems role.
