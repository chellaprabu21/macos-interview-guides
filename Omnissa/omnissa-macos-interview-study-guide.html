1 · C++ Deep Dive HEAVY

The #1 required qualification. Expect "under the hood" chains: they ask a simple question, then drill three levels down. Answer patterns below give the committed first sentence, then the depth.

1.1 Memory & object lifetime

COREStack vs heap; what does new actually do?

Commit: new does two things — calls operator new to allocate raw memory (ultimately from the heap via malloc-like machinery), then invokes the constructor on that memory. delete reverses it: destructor first, then operator delete.

Depth: placement new separates the two (new (ptr) T(...) constructs without allocating — how std::vector builds elements in reserved capacity). Array new[] must be paired with delete[]; mismatching is UB because the compiler may stash the element count in a header before the array.

CORERAII — explain it and why it matters in an agent

Commit: RAII ties resource lifetime to object lifetime: acquire in the constructor, release in the destructor, so cleanup runs deterministically on every exit path including exceptions. It's the single most important C++ idiom.

Agent hook: in a long-running daemon, leaked file descriptors, mach ports, or ES clients accumulate until the process is killed. Wrap every OS handle — es_client_t, sockets, CFTypes — in RAII wrappers (std::unique_ptr with custom deleter is the quickest). Your Instruments leak-hunting stories slot here.

CORERule of Three / Five / Zero

Commit: If you write any one of destructor, copy constructor, or copy assignment, you almost certainly need all three (Rule of Three); with move semantics add move constructor and move assignment (Five). Best is Rule of Zero — own resources only via members that already manage themselves (smart pointers, containers) so you write none.

Trap follow-up: declaring a destructor suppresses implicit move operations — the class silently falls back to copies. Classic hidden-perf-bug question.

DEEPSmart pointers — unique_ptr vs shared_ptr vs weak_ptr, and costs

Commit: unique_ptr is sole ownership, zero overhead vs a raw pointer, move-only. shared_ptr is shared ownership via an atomically ref-counted control block. weak_ptr observes without owning — it breaks reference cycles and is the answer to "how do you prevent shared_ptr leaks."

Depth: shared_ptr costs two pointers (object + control block), atomic inc/dec on every copy (contention on hot paths), and a heap allocation for the control block — make_shared fuses object+block into one allocation but keeps memory alive until the last weak_ptr dies. Only the ref-count is thread-safe; concurrent writes through the pointer still need synchronization. enable_shared_from_this for handing out shared ownership from this (async callbacks in an agent — keep-alive pattern: capture shared_from_this() in the lambda).

DEEPMove semantics — what actually happens; std::move

Commit: A move transfers ownership of resources instead of copying them — the move constructor steals the source's internals (pointer, size, capacity for a vector) and leaves it valid-but-unspecified. std::move does nothing at runtime; it's a cast to rvalue reference that makes overload resolution pick the move.

Depth: rvalue vs lvalue references; forwarding references (T&& in a deduced context) plus std::forward for perfect forwarding; moved-from objects must remain destructible; RVO/NRVO means return std::move(local) is a pessimization — it blocks copy elision.

TRAPCommon UB they probe: dangling refs, ODR, strict aliasing, data races

Ready list: use-after-free / dangling reference from returning a ref to a local; iterator invalidation (push_back reallocation while iterating); signed integer overflow is UB; data race = two threads, same memory, at least one write, no synchronization → UB, not "just stale reads"; reinterpret_cast type punning violates strict aliasing (use memcpy or std::bit_cast).

1.2 Polymorphism & object layout

COREHow do virtual functions work?

Commit: Each polymorphic class gets a vtable — a static array of function pointers; each object carries a hidden vptr to its class's vtable, set by the constructor. A virtual call loads vptr → indexes vtable → indirect call.

Depth chain they follow: cost = one extra indirection plus lost inlining/branch prediction, negligible unless in a tight loop; why virtual destructors — deleting a derived object through a base pointer without one is UB (derived destructor never runs); calling virtuals in constructors dispatches to the class under construction, not the eventual derived type; pure virtual (=0) makes the class abstract.

DEEPvtable follow-ups: multiple inheritance, virtual inheritance, RTTI

Multiple inheritance → multiple vptrs and this-pointer adjustment thunks. Virtual inheritance solves the diamond by sharing one base subobject, paid for with vbase offsets. dynamic_cast uses RTTI stored via the vtable; cross-casts and downcasts return nullptr (pointers) or throw (references). If they ask "how would you avoid virtual dispatch": CRTP / static polymorphism, or std::variant + std::visit.

COREconst correctness, static, inline, extern "C"

Rapid-fire set: const member functions promise not to mutate observable state (mutable escapes for caches/mutexes); static members are per-class; function-local statics are initialized thread-safely on first use since C++11 (Meyers singleton — likely relevant to agent singletons); inline today mostly means "multiple identical definitions allowed" (ODR), not "please inline"; extern "C" disables name mangling — exactly how a C++ core exposes a C ABI for Swift/Obj-C to call. That last one is your interop bridge — volunteer it.

DEEPTemplates: instantiation, specialization, SFINAE vs concepts

Commit: Templates are compile-time code generation — each unique argument set instantiates a distinct concrete type/function. Definitions must be visible at instantiation (why templates live in headers).

Depth: full vs partial specialization; two-phase lookup; SFINAE ("substitution failure is not an error") as the pre-C++20 way to constrain overloads via enable_if; C++20 concepts as the readable replacement (template<typename T> requires std::integral<T>). Mention constexpr/if constexpr for compile-time branching. You don't need metaprogramming wizardry — clear fundamentals + honesty about depth beats bluffing.

COREExceptions vs error codes in systems code; noexcept

Commit: Exceptions for truly exceptional, non-local failures with RAII doing cleanup; error codes / std::optional / expected-style returns on hot paths and across module or language boundaries — and never let exceptions cross a C ABI or into Swift/Obj-C frames: catch at the boundary and translate. That boundary rule is the agent-engineering answer they want.

noexcept: promise not to throw; violating it calls std::terminate. Move constructors should be noexcept or vector falls back to copying on reallocation — sneaky perf question.

2 · Swift Depth HEAVY

You're strong here — the risk is under-preparing the "explain precisely" versions of things you do by instinct.

COREARC — how it works, and vs C++ smart pointers

Commit: ARC is compile-time automatic reference counting: the compiler inserts retain/release at ownership boundaries; when count hits zero, deinit runs immediately. It's deterministic — no garbage collector, no pauses.

Great comparative answer for this JD: ARC ≈ intrusive shared_ptr semantics baked into the language; weak ≈ weak_ptr (auto-nils via side tables); unowned ≈ non-owning raw pointer (crash if dangling, no nil-check cost). Retain cycles = the shared_ptr cycle problem: closures capture self strongly → [weak self]. Know that ARC applies to classes/closures, not structs/enums.

COREValue vs reference types; copy-on-write

Commit: Structs/enums are value types — copied on assignment, no shared mutable state, no ARC traffic; classes are reference types. Standard collections (Array, String, Dictionary) are structs with copy-on-write: cheap copies share storage until a mutation on non-uniquely-referenced storage triggers a real copy (isKnownUniquelyReferenced).

Systems angle: value types kill a whole class of data races by construction — thread-safety by copying. That's why agent config/telemetry snapshots as structs is a good design answer.

DEEPProtocols, generics, existentials — static vs dynamic dispatch

Commit: Generic constraints (func f<T: Proto>(_ t: T)) are resolved statically — specialization, inlining, no boxing. Existentials (any Proto) use a witness table + boxed storage — dynamic dispatch, heap allocation if the value doesn't fit the inline buffer (3 words).

Depth: protocol witness tables vs class vtables; some (opaque types) = static type hidden from caller, zero existential cost; PATs (associated types) historically forced generics — any lifted that in Swift 5.7+. This maps directly to the C++ question "templates vs virtual dispatch" — draw the parallel out loud; interviewers for a dual-language role reward exactly that.

COREClosures: capture semantics, escaping, @Sendable

Closures capture variables by reference by default (capture list [x] copies at creation); @escaping means outliving the call — requires explicit self, hence retain-cycle discipline. @Sendable closures forbid capturing non-thread-safe state — the compiler enforcing what you enforce by review in C++.

DEEPGCD vs Swift structured concurrency — when each, in an agent

Commit: GCD: queues + blocks, manual discipline — serial queues as locks, target hierarchies, DispatchSource for kernel events. Structured concurrency: async/await + actors — compiler-checked isolation, cancellation, task trees. In a daemon that talks to C++ and ES callbacks, GCD/pthreads still dominate at the boundary; actors shine for shared state above it.

Know cold: actor reentrancy (state can change across an await), Task.detached vs child tasks, cooperative thread pool ≠ unlimited threads (never block it with sync waits — thread-pool starvation), continuations (withCheckedThrowingContinuation) to wrap callback APIs — exactly how you bridge a C++ completion callback into async Swift.

COREError handling; optionals under the hood

throws/do-catch is sugar over typed error returns (not stack unwinding like C++ — cheap); Result for stored/async errors. Optionals are enum Optional { case none, some(Wrapped) } — pattern matching, not null pointers; ! force-unwrap traps deterministically.

3.2 The questions they'll actually ask

CORE"How did you bridge C++ into Swift in a real product?"

Your story, structured: WebRTC is a C++ codebase; the app layer was Swift/Obj-C. You wrapped the C++ session/track/stats APIs in Objective-C++ facade classes (.mm) — C++ members hidden via pimpl so no C++ types leaked into headers Swift could see. Ownership rule: the Obj-C wrapper owns the C++ object (unique_ptr in the impl), created in init, destroyed in dealloc — ARC lifetime drives C++ lifetime. Callbacks from C++ threads were marshaled onto known dispatch queues before touching Swift/ObjC state. Stats polling fed your RTT/jitter tuning work.

DEEPMemory ownership across the boundary — the rules

Commit: One side owns; the boundary documents it. Patterns: (1) ARC owns wrapper, wrapper's unique_ptr owns C++ object; (2) C++ core owns, hands Swift opaque handles + explicit destroy function; (3) ref-counted C++ objects retained/released through the shim. Never let a raw C++ pointer outlive its owner into a Swift closure — copy the data or retain the owner into the callback context.

CoreFoundation angle they may chain into: CF ownership rules — "Create/Copy" names return +1 you must CFRelease; in Swift, Unmanaged with takeRetainedValue() (consumes the +1) vs takeUnretainedValue(). Toll-free bridging (CFString ↔ NSString ↔ String).

TRAPExceptions, threads, and strings across the boundary

Three traps, one answer each: Exceptions — C++ exceptions crossing into Swift/Obj-C frames are UB; catch in the shim, convert to error codes/NSError. Threads — C++ callback threads have no autorelease pool and no main-actor guarantees; wrap in @autoreleasepool (Obj-C++) and dispatch to a queue. Strings — std::string ↔ String copies via UTF-8; watch lifetime of c_str() pointers (dies with the string); NSString interior pointers likewise.

DEEP"What does the Obj-C runtime add?" (message dispatch vs C++ calls)

Obj-C method calls go through objc_msgSend — dynamic selector lookup with caching; slower than a C++ virtual call but enables swizzling, KVO, dynamic proxies. Swift calls into Obj-C use the same machinery; pure Swift uses vtables/witness tables/static dispatch. Good closing line: pick the boundary so hot paths stay inside C++ or inside Swift, and cross it coarsely (batched telemetry, not per-event chatter).

4 · macOS Frameworks HEAVY

The JD names six: Endpoint Security, Network Extension, Security, SystemConfiguration, CoreFoundation, IOKit. This is your home turf at JumpCloud — the prep goal is precise vocabulary, not new learning.

4.1 Endpoint Security (ES)

COREES architecture: client, events, AUTH vs NOTIFY

Commit: ES is the userspace replacement for kernel-auditing kexts: you create an es_client_t (es_new_client) from a process holding the com.apple.developer.endpoint-security.client entitlement (restricted — Apple approval), subscribe to event types, and receive messages on a handler block. Two flavors: NOTIFY (observe after the fact) and AUTH (the kernel blocks the operation until you respond allow/deny).

Key events to name: ES_EVENT_TYPE_AUTH_EXEC, AUTH_OPEN, NOTIFY_FORK, NOTIFY_EXIT, file events (create/rename/unlink), NOTIFY_XP_MALWARE_DETECTED. Process info arrives in es_process_t: audit token, signing ID, Team ID, CDHash, path.

DEEPAUTH deadlines, muting, and performance — the senior questions

Deadlines: every AUTH message carries a deadline (in the message); miss it and the kernel decides for you — and repeated misses get your client killed (ES_CLIENT_RESULT_ERR_... / watchdog). So: respond fast, never block the handler on network/disk; copy the message (es_retain_message) if deferring, decide on another queue, respond with es_respond_auth_result. Use caching (allow-verdict cache keyed by CDHash) so repeat exec of the same binary is O(1).

Muting: es_mute_process / es_mute_path to drop noisy known-good sources (your own agent!) — the difference between 3% and 30% CPU on a busy Mac. Also mention inversion (mute-all-except) for targeted monitoring.

DEX angle: for an experience/telemetry agent, prefer NOTIFY subscriptions and aggressive muting; AUTH is for security posture enforcement — you've done both sides at JumpCloud.

5 · System Extensions, Signing, Notarization, TCC LIGHT

You own this daily — skim for vocabulary precision.

CORESystem Extension lifecycle & why they replaced kexts

Kexts ran in kernel space — one bug panics the machine, and they weakened platform security. System Extensions (ES clients, NE providers, DriverKit) run in userspace with entitlements, installed via OSSystemExtensionRequest from the containing app in /Applications, approved by the user (or silently via MDM profile — the fleet answer), activated/upgraded/deactivated through systemextensionsctl-visible state machine. Extension survives app deletion until deactivated. Delivery for fleets: MDM pushes the SysExt + TCC/notification payloads → zero-touch activation — say this; it's the enterprise-agent differentiator.

CORESigning chain: certificates → entitlements → hardened runtime → notarization → Gatekeeper

The 60-second narrative: Developer ID signs the binary (codesign, secure timestamps); entitlements are baked into the signature; hardened runtime restricts dylib injection/debugging unless exception entitlements are present; notarization (notarytool) submits to Apple for automated malware scan → staple the ticket to the pkg/app; Gatekeeper checks quarantine-flagged first launches: valid Dev ID + notarization ticket, else blocked. Verification: codesign -dv --verify, spctl -a -vvv. TCC: privacy database gating Full Disk Access, screen recording etc. — for agents, granted via MDM PPPC profiles instead of user prompts.

6 · Concurrency & IPC HEAVY

JD: "multi-threading, concurrency, and inter-process communication (Unix domain sockets, XPC)." Expect at least one full question chain here.

6.1 Threads, locks, atomics

COREMutex vs spinlock vs read-write lock vs semaphore

Mutex: sleeps the thread on contention — default. Spinlock: burns CPU waiting — only for tiny critical sections where sleep/wake costs more; on macOS use os_unfair_lock (never the deprecated OSSpinLock — priority-inversion prone). RW lock: many readers or one writer — read-heavy state like agent config. Semaphore: counting resource gate; dispatch_semaphore. Condition variable: wait-for-predicate with a mutex, always in a while loop (spurious wakeups).

DEEPDeadlock — conditions, and one you actually debugged

Commit: Four Coffman conditions — mutual exclusion, hold-and-wait, no preemption, circular wait; break any one, classically by global lock ordering. Then go concrete: dispatch_sync onto the queue you're already on is the #1 macOS deadlock; lock inversion between a callback thread and main thread is #2. Have your own Instruments/LLDB war story ready (you listed concurrency defects on the resume — pick one, 60 seconds, symptom → hypothesis → tool → fix → prevention).

DEEPAtomics & memory ordering — how deep to go

Safe depth: std::atomic gives race-free single-variable access; default seq_cst ordering is safest; acquire/release pairs synchronize "everything before the release-store is visible after the acquire-load" — the basis of lock-free flags and double-checked locking done right. Relaxed = counters only. If pushed further: say you reach for proven primitives over hand-rolled lock-free structures in a shipping agent — that's the senior answer, not a dodge.

COREGCD mechanics rapid-fire

Serial vs concurrent queues; queues ≠ threads (thread pool underneath, ~1 thread per core plus overcommit); dispatch_async vs sync; target queue hierarchies to serialize subsystems; QoS classes and priority inversion (sync wait from high-QoS on low-QoS work gets boosted); DispatchSource for signals/timers/fd events — a daemon's event backbone; barriers on concurrent queues for reader-writer patterns.

6.2 IPC: XPC and Unix domain sockets

COREXPC — architecture and the security question they always ask

Commit: XPC is macOS's structured IPC over Mach messages: NSXPCConnection exposes a protocol-typed remote object (or the C xpc_connection_t API); launchd owns service lifecycle — on-demand launch, crash relaunch — via MachServices in the daemon's plist.

The security follow-up (guaranteed for an agent role): never trust the connection by default. In listener(_:shouldAcceptNewConnection:), take the connection's audit token, build SecCode from it, and verify a designated requirement (your Team ID + signing identifier + hardened runtime); optionally check entitlements. PID checks are race-prone (PID reuse) — audit token is the correct identity. Also: define narrow protocols, validate every input (it's a trust boundary), and set interruption/invalidation handlers for reconnect logic.

COREUnix domain sockets — and when you'd pick them over XPC

Commit: UDS = socket API (AF_UNIX) with a filesystem path endpoint; kernel-buffered byte stream (or datagrams), works with kqueue/dispatch sources, and crucially is cross-platform-friendly — the natural transport when your agent core is portable C++ (Omnissa's world). XPC when both ends are Apple-native and you want launchd lifecycle + typed protocols; UDS when the C++ core, CLI tools, or non-Apple components need in. Peer credentials via getpeereid/LOCAL_PEERCRED; permissions via socket file mode + directory perms. You run both at JumpCloud — say which carries what and why.

DEEPFraming, versioning, and backpressure on a UDS protocol

Streams don't preserve message boundaries → length-prefixed frames (4-byte LE length + payload, cap max size); version field in a header for rolling upgrades (daemon and UI updated at different times — fleet reality); backpressure: bounded queues + drop/coalesce telemetry rather than ballooning memory — a DEX agent must degrade gracefully, never become the experience problem it measures. This paragraph is design-round gold; reuse it in §12.

7 · Networking & TLS MEDIUM

CORETLS 1.3 handshake — the 90-second version

ClientHello (supported suites, key share via ECDHE, SNI) → ServerHello + certificate + CertVerify + Finished → client verifies chain to trusted root, checks hostname, sends Finished → symmetric session keys derived (HKDF) → application data. 1.3 = 1-RTT, forward secrecy mandatory (ephemeral keys), old suites gone. mTLS adds a client certificate — tie to your device-trust cert work. Certificate pinning: pin SPKI hash, plan rotation.

COREOpenSSL vs Apple stacks — the JD says OpenSSL

Commit: Cross-platform C++ cores use OpenSSL because Secure Transport/Network.framework are Apple-only. Know the object model: SSL_CTX (per-process config: cert, key, verify mode, min TLS version) → SSL per connection → SSL_connect/read/write; verify callback + SSL_get_verify_result; BIO abstraction for memory/socket I/O. Honest framing if probed: your shipped TLS work used Apple's stacks and WebRTC's built-in (BoringSSL-based) crypto; you know the OpenSSL API shape and the concepts are identical. Commit, then caveat.

COREHTTP client in an agent: pooling, retries, backoff

DEEPSockets rapid-fire (they may go old-school)

9.1 CMake in two hours

COREMental model + the file you should be able to sketch

CMake is a build-system generator: CMakeLists.txt → generates Ninja/Make/Xcode projects. Modern CMake is target-based: everything hangs off targets, and properties propagate via PUBLIC/PRIVATE/INTERFACE.

cmake_minimum_required(VERSION 3.20)
project(agent CXX)
set(CMAKE_CXX_STANDARD 17)

add_library(agent_core STATIC src/core.cpp src/telemetry.cpp)
target_include_directories(agent_core PUBLIC include)   # consumers get it too
target_link_libraries(agent_core PRIVATE OpenSSL::SSL)  # impl detail, not propagated

add_executable(agentd src/main.cpp)
target_link_libraries(agentd PRIVATE agent_core)

if(APPLE)
  target_link_libraries(agentd PRIVATE "-framework SystemConfiguration" "-framework IOKit")
endif()

Vocabulary to have: out-of-source builds (cmake -B build -G Ninja, cmake --build build); find_package + imported targets (OpenSSL::SSL); CMAKE_BUILD_TYPE Debug/Release/RelWithDebInfo; toolchain files for cross-compiling; FetchContent for vendoring deps (how you'd pull googletest); generator expressions ($<$<CONFIG:Debug>:...>) — recognize, don't memorize; CTest as the test runner. PUBLIC vs PRIVATE vs INTERFACE is the most-asked conceptual bit: PRIVATE = build me only, INTERFACE = consumers only, PUBLIC = both.
