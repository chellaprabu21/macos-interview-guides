Design 01

SOLID principles
Five rules for maintainable OO code (Robert C. Martin). One crisp line + one Swift example each — say them applied, not recited.

S — Single Responsibility

"A class should have only one reason to change." One job per type.

class UserManager {           // 3 reasons to change: DB, validation, email
    func save(_ u: User) {}
    func validate(_ u: User) -> Bool { true }
    func sendWelcome(to u: User) {}
}
class UserRepository { func save(_ u: User) {} }       // persistence
class UserValidator  { func isValid(_ u: User) -> Bool { true } }
class EmailService   { func sendWelcome(to u: User) {} }

O — Open/Closed

"Open for extension, closed for modification." Add behavior without editing existing code — via protocols + polymorphism.

func discount(type: String, price: Double) -> Double {
    if type == "student" { return price * 0.9 }        // new type = edit this fn
    else if type == "veteran" { return price * 0.8 }
    return price
}
protocol DiscountStrategy { func apply(to p: Double) -> Double }
struct Student: DiscountStrategy { func apply(to p: Double) -> Double { p * 0.9 } }
struct Veteran: DiscountStrategy { func apply(to p: Double) -> Double { p * 0.8 } }
// new discount = new struct, zero edits to existing code

L — Liskov Substitution

"Subtypes must be substitutable for their base type" — without breaking behavior.

class Bird { func fly() {} }
class Penguin: Bird { override func fly() { fatalError("can't fly") } }  // breaks the contract
protocol Bird { func move() }
struct Sparrow: Bird { func move() { /* fly */ } }
struct Penguin: Bird { func move() { /* swim */ } }  // both honor "move"

I — Interface Segregation

"Don't force clients to depend on methods they don't use." Split fat protocols.

protocol Machine { func print(); func scan(); func fax() }
class SimplePrinter: Machine {        // forced to stub scan + fax
    func print() {}; func scan() {}; func fax() {}
}
protocol Printable { func print() }
protocol Scannable { func scan() }
class SimplePrinter: Printable { func print() {} }        // only what it needs
class MFP: Printable, Scannable { func print() {}; func scan() {} }

D — Dependency Inversion

"Depend on abstractions, not concretions." High-level code depends on a protocol; concrete types are injected.

protocol Database { func save(_ d: String) }
struct MySQL: Database { func save(_ d: String) {} }
struct Mongo: Database { func save(_ d: String) {} }

class UserService {
    let db: Database
    init(db: Database) { self.db = db }   // inject any DB → testable, flexible
    func add(_ u: String) { db.save(u) }
}
LetterOne-linerSwift tool
SOne responsibility per typeSplit into focused types

LSubtypes honor the contractProtocols over broken inheritance

The move that wins the VMware questionWhen asked "parse this JSON with a design pattern," reach for SOLID out loud: "Codable model (SRP), a Parser protocol so I depend on an abstraction (DIP) and can swap JSON for CSV (OCP), injected into the service for testability." That single sentence answers "parser" and "design pattern" and "SOLID" at once — see §14.

Architecture & patterns
MVC, MVVM, dependency injection, protocol-oriented programming — the vocabulary for "how would you structure this?"

MVC vs MVVM

LayersModel · View · ControllerModel · View · ViewModel

TestabilityHard — logic tangled with UIKitEasy — ViewModel is plain, UIKit-free, unit-testable

MVVM binding with a simple Box (no Combine needed)

final class Box<T> {
    var value: T { didSet { listener?(value) } }
    private var listener: ((T) -> Void)?
    init(_ v: T) { value = v }
    func bind(_ l: @escaping (T) -> Void) { listener = l; l(value) }
}

class LoginViewModel {
    let isValid = Box(false)                // VM exposes observable state
    func update(email: String, pass: String) {
        isValid.value = email.contains("@") && pass.count >= 6
    }
}
// In the VC: viewModel.isValid.bind { [weak self] ok in self?.button.isEnabled = ok }

Dependency Injection

Passing a type's dependencies in (via init, property, or method) instead of it creating them itself. Enables swapping real/mock — the backbone of testable code and the "D" in SOLID. Three forms: initializer injection (preferred — dependencies explicit and immutable), property injection, method injection.

Protocol-Oriented Programming (POP)

Swift's preference for composing behavior via protocols + protocol extensions (default implementations) over class inheritance. Benefits: value types can adopt behavior, no single-inheritance limit, better testability. "Prefer protocol + extension over a base class" is the POP one-liner.

protocol Identifiable { var id: String { get } }
extension Identifiable { var shortID: String { String(id.prefix(8)) } }  // default impl, shared

In the interview

Why MVVM over MVC?

Commit: MVVM moves presentation logic and state out of the view controller into a ViewModel that has no UIKit dependency, so it's unit-testable and the VC shrinks to binding. It directly fixes the "massive view controller" problem where networking, formatting, and state all pile into the controller.

Nuance: MVVM needs a binding mechanism — Combine, a closure-based observable, or a small Box type — and it's not free; for a trivial screen MVC is fine. I reach for MVVM when a screen has real state and logic worth testing in isolation.

What is dependency injection and why does it matter?

Commit: It's providing a type's dependencies from outside rather than having it construct them, usually through the initializer. It matters because it decouples the type from concrete implementations — I can inject a real network service in production and a mock in tests — which is the Dependency Inversion principle in practice.

Nuance: initializer injection is my default because it makes dependencies explicit and lets them be immutable. It's also what makes the parser design in the VMware question testable — the service depends on a Parser protocol I inject, not a concrete JSON decoder.

Swift fundamentals
Struct vs class, closures, property attributes, lazy — the rapid-fire questions.

Struct vs Class — the most-asked question

struct (value type)class (reference type)
Copy semanticsCopied on assignment (independent copies)Shared reference (both point to same instance)
MemoryUsually stack; no ARCHeap; ARC-managed
InheritanceNo (composition/protocols instead)Yes
Mutabilitymutating needed to change selfMutate freely
IdentityNo === (only equality)=== compares identity
Use whenData, models, thread-safe snapshots — the Swift defaultShared mutable state, identity, UIKit/inheritance needs

Rule of thumb: start with a struct; switch to a class only when you need reference semantics (shared mutable state, identity, or inheritance). Standard library favors structs — Array, String, Dictionary are all structs with copy-on-write.

Closures — escaping vs non-escaping

  • Non-escaping (default): the closure is used within the function call and doesn't outlive it. No retain-cycle risk, no explicit self.
  • @escaping: the closure is stored and called later (async callbacks, completion handlers) — it outlives the function, so it captures self strongly and needs [weak self] discipline.
func fetch(completion: @escaping (Data) -> Void) {   // stored until network returns
    URLSession.shared.dataTask(with: url) { data, _, _ in
        completion(data ?? Data())
    }.resume()
}

Capture lists

[weak self] / [unowned self] at the start of a closure controls how captured references are held — the fix for retain cycles (see §04). [weak self] makes self optional inside; [unowned self] assumes it's alive (crashes if not).

lazy var vs computed property

lazy varcomputed var

Use forExpensive one-time setupValues derived from other state

In the interview

Struct or class — how do you decide?

Commit: I default to struct. Value semantics mean copies are independent, so there's no accidental shared mutable state and no data races from sharing — which is why Swift's own collections are structs. I switch to a class only when I specifically need reference semantics: shared mutable state, object identity, or class inheritance, or when interoperating with UIKit which is class-based.

Nuance: structs also skip ARC overhead since they're typically stack-allocated. The one cost is that large structs copy on assignment, but copy-on-write in the standard library types handles that for collections. So: struct first, class when I have a concrete reason.

What does @escaping mean?

Commit: It marks a closure that outlives the function it's passed to — it gets stored and called later, like a network completion handler. Because it escapes, it captures self strongly, so I use [weak self] to avoid retain cycles, and Swift forces explicit self to make that capture visible.

Nuance: non-escaping is the default and is cheaper — the compiler knows the closure won't outlive the call, so there's no cycle risk and no explicit-self requirement. The distinction exists precisely so the compiler can warn you where lifetime and capture actually matter.

Language 04

Memory management & ARC
The ARC question sank the VMware loop for many — nail the retain-cycle mechanics, not just "it manages memory."

What ARC is

Automatic Reference Counting: the compiler inserts retain/release calls so each class instance is freed the moment its reference count hits zero. It's deterministic (no garbage collector, no pauses) and happens at compile time. ARC applies to classes and closures — not structs/enums (value types have nothing to count).

Retain cycles — the mechanism

If A holds a strong reference to B and B holds a strong reference back to A, neither count ever reaches zero → both leak forever. The two classic sources:

// 1. Two objects referencing each other
class Parent { var child: Child? }
class Child  { var parent: Parent? }   // strong ↔ strong = cycle

// 2. A closure capturing self, while self stores the closure
class VC {
    var onDone: (() -> Void)?
    func setup() { onDone = { self.reload() } }  // closure retains self, self retains closure
}
class Child { weak var parent: Parent? }        // break with weak
onDone = { [weak self] in self?.reload() }         // break with capture list

weak vs unowned

weakunowned
OptionalityOptional — auto-set to nil when target diesNon-optional — assumes target outlives it

Use whenTarget may become nil (delegates, parent refs)Target is guaranteed to live as long or longer (e.g. closure tied to self's lifetime)

Safe default: weak. Use unowned only when you're certain of the lifetime and want to avoid the optional.

Property attributes (Obj-C heritage, still asked)

strongDefault; keeps the object alive (owning)
weakNon-owning, auto-nils; breaks cycles

In the interview

Explain ARC and how a retain cycle happens.

Commit: ARC is compile-time automatic reference counting — the compiler inserts retain and release so each class instance is deallocated the instant its reference count drops to zero, deterministically, with no garbage collector. A retain cycle happens when two objects hold strong references to each other, so neither count ever reaches zero and both leak. The most common case in iOS is a closure capturing self strongly while self stores that closure.

Nuance: I break cycles with weak or unowned — weak for references that can legitimately become nil like delegates and parent pointers, unowned only when the target is guaranteed to outlive the reference. In closures that's the [weak self] capture list. ARC applies to classes and closures, not value types, since structs have nothing to reference-count.

weak vs unowned — which and when?

Commit: weak is optional and automatically becomes nil when its target is deallocated, so accessing it is always safe. unowned is non-optional and assumes the target still exists — if it doesn't, accessing it crashes. I default to weak; I use unowned only when the reference's lifetime is guaranteed to be within the target's, to avoid an unnecessary optional.

Nuance: a common correct unowned is a closure that can't outlive self because self owns it and they die together. But if I'm unsure, weak is the safe choice — a nil is recoverable, a crash isn't.

Language 05

Static vs dynamic dispatch
How Swift decides which method to call — a performance + correctness question.

Dispatch = how the runtime picks which implementation to run for a call.

TypeHowCostWhen Swift uses it
Static (direct)Address known at compile time; can inlineCheapeststructs, final classes, private, non-overridable
Table (vtable/witness)Look up in a per-type tableOne indirection, no inlineNon-final class methods; protocol methods
Message (objc_msgSend)Dynamic runtime lookup by selectorSlowest, but enables KVO/swizzling@objc dynamic, Obj-C interop

Practical lever: marking a class or method final (or using structs) lets the compiler use static dispatch and inline — a real optimization for hot paths. Marking something @objc dynamic opts into message dispatch, needed for KVO.

How can you make method dispatch faster in Swift?

Commit: Give the compiler enough information to use static dispatch. Marking a class or method final, using private, or using structs all let the compiler resolve the call at compile time and inline it, versus a class method that goes through a vtable. For a hot code path that's a measurable win.

Nuance: the trade is flexibility — final and static dispatch mean no overriding and no runtime features like KVO or swizzling, which require @objc dynamic message dispatch. So I optimize with final where I don't need dynamism, and accept the slower path only where I actually need runtime behavior.

Concurrency 06

Threads, GCD & async/await
The core concurrency model — and the two axes people always confuse.

Threads vs queues

A thread is a line of execution you'd otherwise manage by hand (create, schedule, tear down — error-prone). GCD flips it: you submit work to queues, and a managed thread pool runs it. You think in queues, not threads.

The two independent axes (the classic confusion)

 QUEUE TYPE  (how many at once)      CALL TYPE  (does the caller wait?)
 ─────────────────────────────      ────────────────────────────────
 Serial     one task at a time      sync   block caller until done
 Concurrent many tasks at once      async  return immediately

 These are INDEPENDENT. Any combination is valid.
 sync-on-your-own-serial-queue = DEADLOCK (you wait for a queue you're occupying)

DispatchQueue.global(qos: .userInitiated).async {   // background work
    let data = heavyDecode()
    DispatchQueue.main.async { self.render(data) }  // UI back on main
}

QoS (quality of service)

Priority hints so the system schedules important work first and defers the rest (saving battery): .userInteractive → .userInitiated → .utility → .background. The main queue is serial and runs UI.

GCD vs Operation Queues

GCD (DispatchQueue)OperationQueue
LevelLightweight, C-based, closuresHigher-level, object-based (Operation)
DependenciesManual (groups)Built-in (addDependency)
CancellationManual (DispatchWorkItem)Built-in (cancel())
Max concurrencyNot directlymaxConcurrentOperationCount
Use whenSimple async dispatchComplex dependency graphs, cancellable, throttled work

Modern: async/await

Lets async code read top-to-bottom. An await suspends (frees the thread) rather than blocks. Actors serialize shared state with compile-time safety. Bridge old callbacks with continuations.

func loadUsers() async throws -> [User] {
    let (data, _) = try await URLSession.shared.data(from: url)  // suspends
    return try JSONDecoder().decode([User].self, from: data)
}

In the interview

Serial vs concurrent vs sync vs async?

Commit: Serial vs concurrent describes the queue — how many tasks run at once. Sync vs async describes the call — whether the caller blocks until the work finishes. They're independent: I can submit sync to a concurrent queue or async to a serial one.

Nuance: the dangerous combination is calling sync onto the serial queue I'm already running on — I block waiting for a queue I'm occupying, which deadlocks. In practice I use async-to-background for heavy work and always hop back to the main queue for UI updates.

GCD or OperationQueue?

Commit: GCD for simple, fire-and-forget async work — it's lightweight and closure-based. OperationQueue when I need dependencies between tasks, cancellation, or a concurrency limit, because those are built in as addDependency, cancel(), and maxConcurrentOperationCount.

Nuance: a good example is image loading in a table view — OperationQueue lets me cap concurrent downloads and cancel a cell's operation when it scrolls off. For new code I'd increasingly use async/await with task groups, which gives structured cancellation natively.

Concurrency 07

Thread safety
Race conditions, deadlocks, and the read/write problem — the "make this safe" question.

The three problems

  • Race condition — two threads touch shared state unsynchronized; result depends on timing (e.g. two threads both do count += 1 and one update is lost).
  • Deadlock — each thread waits on a resource the other holds; both freeze.
  • Readers-writers — many can read safely at once, but a write must be exclusive.

The tools (Swift)

Serial queueRoute all access through it → one-at-a-time. Simple, idiomatic.
Concurrent queue + barrierReads run in parallel; barrier makes writes exclusive. Best for read-heavy state.
os_unfair_lock / NSLockLow-level mutex for a small hot section. (Never OSSpinLock — priority inversion.)
actorCompiler-enforced serialized access. The modern answer.

Reader-writer with a barrier — the pattern to memorize

final class SafeCache {
    private var store: [String: Data] = [:]
    private let q = DispatchQueue(label: "cache", attributes: .concurrent)

    func value(_ k: String) -> Data? {
        q.sync { store[k] }                          // concurrent reads
    }
    func set(_ k: String, _ v: Data) {
        q.async(flags: .barrier) { store[k] = v }    // exclusive write
    }
}
The UIKit rule that's easy to forget under pressureAll UIKit updates must happen on the main thread. A background completion handler that touches a label, table view, or any UI without DispatchQueue.main.async is a bug — sometimes a crash, sometimes silent corruption. In the "load API into table view" question, forgetting this is an instant red flag. Always say it out loud.
How do you make a shared resource thread-safe?

Commit: I serialize access. The idiomatic GCD way is routing all reads and writes through a serial queue, or for a read-heavy resource like a cache, a concurrent queue where reads run in parallel with sync and writes are exclusive using an async(flags: .barrier). For new code, an actor gives the same guarantee with compile-time enforcement.

Nuance: for a tiny hot critical section a plain os_unfair_lock is lowest-overhead — but never a spinlock, because of priority inversion. And separately, any UI mutation must be dispatched to the main thread regardless of how I protect the model.

Concurrency 08

Barrier · Semaphore · Group · WorkItem
The four GCD tools your notes flagged — each solves one specific coordination problem.

Dispatch Barrier — a synchronization point in a concurrent queue

Submitted with .barrier, the block waits for all prior tasks to finish, runs alone, then lets subsequent tasks resume. This is what makes exclusive writes in the reader-writer pattern (§07).

Dispatch Semaphore — gate a limited resource

A counter. wait() decrements (blocks if zero); signal() increments. Use to limit concurrency (e.g. max 3 downloads) or to make async work look synchronous.

let sem = DispatchSemaphore(value: 3)   // allow 3 at once
for url in urls {
    sem.wait()                             // blocks if 3 already running
    download(url) { sem.signal() }         // release a slot when done
}

DispatchGroup — wait for N tasks to all finish

Your exact note: "2 network calls, proceed only when both are over." enter()/leave() bracket each task; notify() fires when the count returns to zero.

let group = DispatchGroup()
group.enter(); fetchProfile { group.leave() }
group.enter(); fetchSettings { group.leave() }
group.notify(queue: .main) { self.render() }   // runs after BOTH complete

DispatchWorkItem — cancellable work (debounce)

Your note: "API call in a work item, cancel it, only fire after the user stops typing 1 sec" — the classic search debounce.

var pending: DispatchWorkItem?
func searchTextChanged(_ text: String) {
    pending?.cancel()                              // cancel the previous
    let item = DispatchWorkItem { self.search(text) }
    pending = item
    DispatchQueue.main.asyncAfter(deadline: .now() + 1, execute: item)  // fire after 1s idle
}
ToolSolvesKey calls
BarrierExclusive write in a concurrent queue.barrier
SemaphoreLimit concurrency / gate a resourcewait / signal
GroupWait for many tasks to completeenter / leave / notify
WorkItemCancellable / debounced workcancel / asyncAfter
You need to make two network calls and continue only when both finish. How?

Commit: A DispatchGroup. I call enter() before each request and leave() in each completion handler, then notify(queue: .main) to run the continuation once both have left — which fires only after both complete, back on the main thread for UI.

Nuance: the discipline is balancing every enter with exactly one leave on every path including errors, or notify never fires. With async/await this becomes cleaner — an async let for each call and a single await on both, which also gives me structured cancellation for free.

How would you debounce a search field?

Commit: A DispatchWorkItem I cancel and recreate on every keystroke, scheduled with asyncAfter a second out. Each new character cancels the pending item and schedules a fresh one, so the search only actually runs after the user pauses typing for a second.

Nuance: this avoids firing a network request per keystroke, which saves bandwidth and backend load. The modern equivalent is Combine's debounce operator or an async Task I cancel, but the WorkItem version is the clearest to write on a whiteboard.

Named pipe (FIFO) — sender & receiver

// WRITER
mkfifo("/tmp/my_fifo", 0666);

// READER

Unix domain socket — the local go-to

// SERVER
int s = socket(AF_UNIX, SOCK_STREAM, 0);
struct sockaddr_un a = { .sun_family = AF_UNIX };
strcpy(a.sun_path, "/tmp/sock"); unlink(a.sun_path);
bind(s, (struct sockaddr*)&a, sizeof a);
listen(s, 5);
int c = accept(s, NULL, NULL);
read(c, buf, sizeof buf);

// CLIENT
int s = socket(AF_UNIX, SOCK_STREAM, 0);
connect(s, (struct sockaddr*)&a, sizeof a);
write(s, "hello", 6);

Shared memory — fastest, but you sync it yourself

// WRITER: create, size, map, write
int fd = shm_open("/shm", O_CREAT | O_RDWR, 0666);
ftruncate(fd, 1024);
char *m = mmap(NULL, 1024, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
strcpy(m, "hello");

// READER: open, map read-only, read
int fd = shm_open("/shm", O_RDONLY, 0666);
char *m = mmap(NULL, 1024, PROT_READ, MAP_SHARED, fd, 0);
printf("%s", m);
shm_unlink("/shm");
The shared-memory follow-up VMware would ask"Shared memory is fastest — why?" Because there's no kernel copy on each message: both processes access the same physical pages directly, whereas pipes/sockets copy data through the kernel. The catch: the kernel gives you no synchronization, so you must add your own — a semaphore or mutex in the shared region — or you'll get exactly the race conditions from §07. Naming that trade-off is the whole point of the question.

Signals & XPC (quick reference)

// SIGNAL — notification only, no payload
// receiver: signal(SIGUSR1, handler); while(1) pause();
// sender:   kill(pid, SIGUSR1);

// XPC — typed dictionaries over Mach, launchd-managed (see the Concurrency/IPC deep-dive doc)
xpc_connection_t c = xpc_connection_create_mach_service("com.x.svc", NULL, 0);

In the interview

Compare pipes and shared memory.

Commit: A pipe is a kernel-managed byte stream — one process writes, another reads, and the data is copied through the kernel on each transfer, so it's simple and safe but has copy overhead. Shared memory maps the same physical pages into both processes, so they read and write the same bytes directly with no kernel copy — the fastest IPC — but the kernel provides no synchronization, so I have to coordinate access myself with a semaphore or mutex.

Nuance: so I'd choose a pipe or socket when I want simplicity and built-in flow control, and shared memory when I'm moving large volumes and can't afford the copy — accepting that I now own the race-condition problem. On macOS specifically, for structured app-to-helper communication I'd usually reach for XPC over raw pipes.

TLS & chain of trust

TLS gives privacy (encryption), integrity (tamper detection), and identity (certificates). The handshake: client and server agree a shared symmetric key via ephemeral Diffie-Hellman (forward secrecy) and the server proves identity with a certificate. Chain of trust: the server's cert is signed by an intermediate CA, signed by a root CA in your device's trust store — the client walks that chain to a trusted root, and checks the hostname and expiry. (Full depth in the dedicated Networking doc.)

NAT (Network Address Translation)

Lets many devices on a private network share one public IP: the router rewrites source addresses/ports on the way out and maps replies back. Relevant to peer-to-peer (WebRTC) because it hides devices behind the router — solved with STUN (discover your public address) and TURN (relay when direct connection fails). This is your Zoho Assist territory.

JSON parsing with Codable — the bread-and-butter question

struct User: Codable {           // maps JSON keys → properties automatically
    let id: Int
    let name: String
    let email: String
}

URLSession.shared.dataTask(with: url) { data, _, error in
    guard let data = data, error == nil else { return }
    do {
        let users = try JSONDecoder().decode([User].self, from: data)
        DispatchQueue.main.async { self.update(users) }   // UI on main!
    } catch { print("decode error:", error) }
}.resume()                                                // don't forget .resume()
Codable follow-ups to have readyCustom key names via CodingKeys; nested objects (nest Codable structs); dates via decoder.dateDecodingStrategy; snake_case via .convertFromSnakeCase; a mismatched type throws DecodingError — always wrap in do/catch. And the modern form: let (data, _) = try await URLSession.shared.data(from: url).
Walk me through calling an API and parsing the response.

Commit: I define a Codable model matching the JSON, create a URLSession data task with the URL, and in the completion I guard against error and nil data, then JSONDecoder().decode into my model inside a do/catch. Any UI update from the result goes back on the main queue, and I call .resume() to start the task.

Nuance: for a cleaner design I'd put this behind a protocol-based service so it's injectable and testable rather than calling URLSession inline — which is exactly the "parser with a design pattern" the VMware round wanted. And I'd prefer the async/await form, try await URLSession.shared.data(from:), which removes the callback nesting.

Systems 11

Code signing & security
Signing, entitlements, hardened runtime — the macOS distribution chain your notes flagged.
Code signingCryptographically signs your binary with your Developer ID → proves who built it and that it hasn't been tampered with. Verify: codesign -dv --verify.
EntitlementsCapability claims baked into the signature (e.g. keychain access groups, network client, the Endpoint Security entitlement). The system grants privileges based on them; they can't be forged because they're inside the signature.
Hardened runtimeOpt-in protections: blocks code injection, DYLD hijacking, and unsigned memory execution unless you declare specific exception entitlements. Required for notarization.
NotarizationApple scans your signed app for malware and issues a ticket you staple to it. Separate from signing — signing = identity, notarization = Apple's scan.
GatekeeperOn first launch of a downloaded (quarantined) app, checks valid Developer ID + notarization; else blocks. Verify: spctl -a -vvv.

The chain in order: sign (identity) → hardened runtime (protections) → notarize (Apple's malware scan) → staple ticket → Gatekeeper allows launch. Don't blur signing, notarization, and Gatekeeper — they're three different checks answering three different questions (who made it / did Apple scan it / may it launch).

What's the difference between code signing and notarization?

Commit: Code signing proves identity and integrity — my Developer ID signed this binary and it hasn't been altered. Notarization is a separate step where Apple scans the already-signed app for malware and returns a ticket I staple to it. Signing says who built it; notarization says Apple checked it.

Nuance: Gatekeeper is yet a third thing — the runtime check at first launch that a downloaded app is both validly signed and notarized before it's allowed to run. All three are required for smooth distribution, and the hardened runtime is a prerequisite for notarization because Apple requires those protections.

The trapviewDidLoad runs once; viewWillAppear runs every appearance. Putting per-appearance refresh in viewDidLoad (so it only updates the first time) is a classic bug they probe.
Where do you put a network refresh — viewDidLoad or viewWillAppear?

Commit: It depends on whether the data can change between appearances. One-time setup goes in viewDidLoad since it runs once. A refresh that should happen every time the screen is shown — like re-fetching a list that another screen might have modified — goes in viewWillAppear, because viewDidLoad would only fire on the first load.

Nuance: I'm careful not to kick off heavy work in viewWillAppear that runs on every appearance and janks the transition — for that I'd start it in viewDidAppear after the view is on screen, or debounce it.

KVO & NotificationCenter (quick reference)

  • KVO — observe a specific property's changes on a specific object (@objc dynamic property). Fine-grained, one-to-one.
  • NotificationCenter — broadcast named events to any number of observers. Decoupled, one-to-many; remember to remove observers (or use the block API with tokens).
Delegate or closure — how do you choose?

Commit: A delegate when there are several related callbacks or I want a formal contract — like a table view's data source and delegate methods. A closure for a single, one-off result, like "here's the fetched user" — it's more concise and keeps the logic inline at the call site.

Nuance: both need cycle discipline — a weak delegate and [weak self] in an escaping closure. For one-to-many or fully decoupled communication I'd instead use NotificationCenter or Combine. The choice is really about how many callbacks and how tight the coupling should be.

Practice 14 · The one that mattered

The VMware problem, solved end-to-end
"Parse JSON/CSV with a design pattern, design the classes, and load it into a table view with concurrency." Rehearse this until it's automatic.

Step 1 — Model + a parser abstraction (SOLID: SRP, DIP, OCP)

struct User: Codable { let id: Int; let name: String; let email: String }

protocol Parser {                                // DIP: depend on abstraction
    func parse<T: Decodable>(_ data: Data, as: T.Type) throws -> T
}
struct JSONParser: Parser {                          // OCP: add CSVParser without editing
    func parse<T: Decodable>(_ data: Data, as t: T.Type) throws -> T {
        try JSONDecoder().decode(t, from: data)
    }
}

Say out loud: "Codable model is the single-responsibility data type; a Parser protocol lets me depend on an abstraction and swap JSON for CSV without changing the service — that's DIP and OCP." That sentence alone answers "parser + design pattern + SOLID."

Step 2 — An injectable service (DIP + testability)

final class UserService {
    private let parser: Parser
    private let session: URLSession
    init(parser: Parser = JSONParser(), session: URLSession = .shared) {
        self.parser = parser; self.session = session   // inject → mockable in tests
    }
    func loadUsers() async throws -> [User] {
        let (data, _) = try await session.data(from: url)  // off main automatically
        return try parser.parse(data, as: [User].self)     // decode off main
    }
}

Step 3 — Table view load with the four concurrency beats

func refresh() {
    Task {
        do {
            let users = try await service.loadUsers()   // 1 fetch + 2 decode: off main
            await MainActor.run {                     // 3 UI update: on main
                self.users = users
                self.tableView.reloadData()
            }
        } catch { showError(error) }
    }
}
// 4 cell reuse + cancellation for per-cell async (e.g. images):
func tableView(_ t: UITableView, cellForRowAt i: IndexPath) -> UITableViewCell {
    let cell = t.dequeueReusableCell(withIdentifier: "c", for: i) as! UserCell
    cell.tag = i.row                                     // guard against reuse race
    cell.imageTask?.cancel()                             // cancel stale work on reuse
    cell.imageTask = Task {
        let img = await loadImage(users[i.row].id)
        if cell.tag == i.row { await MainActor.run { cell.imageView?.image = img } }
    }
    return cell
}
Why this wins the roundYou've hit every part they were testing, in order, out loud: a design pattern (protocol + DI), SOLID applied to the actual problem, GCD/concurrency done correctly (off-main decode, on-main UI), and the two things most candidates miss — cell reuse race (the tag guard) and cancellation on scroll. Landing all four concurrency beats is exactly the senior signal that was missing before. Memorize this shape; it generalizes to any "load data into a list" question.
