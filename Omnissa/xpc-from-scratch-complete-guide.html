XPC, From Scratch

Everything about XPC, built up from zero — what it is, the problem it solves, how it works underneath, and how to actually use it safely. No prior XPC knowledge assumed. Plain-English explanations, small steps, and one full worked example at the end.

Start here

This guide assumes you know Swift and the basics of macOS apps, but nothing about XPC. Read it top to bottom — each chapter builds on the last.

The shape of the journey: first what XPC is and why it exists (the ideas), then what's underneath it so the API stops feeling magic, then the practical parts — the two flavors, the API, building a connection, lifecycle, and the security you must get right. The one sentence to hold in your headXPC lets your program call a function that actually runs in a different process, almost as easily as calling a local method — and the system handles launching that other process, restarting it if it crashes, and moving the data back and forth.

Chapter 01

What XPC actually is
Before any code — get the picture clear.
In plain words

XPC is a way for two separate programs (processes) on the same Mac to talk to each other. One side offers some functionality; the other side calls it. Apple built XPC so this feels like calling methods on an object, even though that object lives in another process entirely.

The core idea: processes are isolated islands

Every running program is a process, and each process has its own private memory. Process A cannot reach into process B's memory and read a variable — that isolation is a deliberate safety and security feature of the operating system. So if two processes need to cooperate, they need an explicit, official channel to pass messages. That channel is what "IPC" (inter-process communication) means, and XPC is Apple's preferred IPC mechanism on macOS.

 ┌─────────────────┐                          ┌─────────────────┐
 │   Process A     │      XPC connection       │   Process B     │
 │  (your app)     │  ◀══════════════════════▶ │  (a helper)     │
 │                 │   "please do X and reply" │                 │
 │  own memory     │                           │  own memory     │
 └─────────────────┘                          └─────────────────┘
        two isolated processes, talking over a managed channel

What makes XPC special (vs a raw pipe or socket)

You could make two processes talk with a raw socket, but then you would have to build everything: a message format, how to know when the other side is ready, how to serialize your data, and how to restart the helper if it dies. XPC gives you all of that:

  • Typed method calls — you define a Swift protocol, and calling the remote side looks like calling methods on an object.
  • Automatic data marshaling — XPC packs up your arguments, sends them across, and unpacks them on the other side.
  • Lifecycle management — the system (launchd) starts the helper when it's first needed and restarts it if it crashes. You don't manage that process yourself.
The mental model to carry forwardThink of XPC as "remote method calls between two processes, with the OS doing the plumbing." Everything technical in this guide is a detail of how that plumbing works and how to make it secure.

Chapter 02

Why XPC exists — the problem it solves
If you understand the "why," every design decision in XPC makes sense.

XPC exists for two big reasons. Both come down to: splitting one program into multiple processes on purpose.

Reason 1 — Crash isolation & safety

Imagine your app parses a risky file format (a PDF, an image, untrusted data). If that parsing code has a bug and crashes — or worse, is exploited — it takes your whole app down with it. But if you move that risky work into a separate helper process and talk to it over XPC, then a crash there only kills the helper. Your main app keeps running, and the system just relaunches the helper. You've contained the blast radius.

You can also give that helper process fewer privileges (a tighter sandbox), so even if it's compromised, the attacker gains very little. This is "privilege separation."

Reason 2 — Privilege separation (the agent case)

This is the one most relevant to endpoint/security software. Some work needs administrator (root) privileges — installing things, touching protected system areas. But you never want your big user-facing app running as root; that's a huge attack surface. So the standard pattern is:

 ┌────────────────────────┐        ┌─────────────────────────────┐
 │  Main app / menu bar   │  XPC   │  Privileged helper (daemon) │
 │  runs as the USER      │ ◀────▶ │  runs as ROOT               │
 │  does UI, no power     │        │  does the powerful work     │
 │  (large, exposed)      │        │  (tiny, careful, locked)    │
 └────────────────────────┘        └─────────────────────────────┘

The unprivileged app asks the small, carefully-written privileged helper to do the sensitive operations over XPC. The helper is tiny and exposes only a few narrow, well-guarded methods. This keeps the powerful code small and auditable — exactly how a well-designed macOS agent is structured.

Why this matters for youA macOS endpoint agent is naturally multi-process: a root daemon does privileged work, system extensions host the security frameworks, and a menu-bar app talks to the user. XPC is the glue between these pieces. So learning XPC isn't academic — it's the communication backbone of the exact kind of software you build.

The through-line: every XPC feature serves these two goals

Keep this in mind as you read on. On-demand launching, crash recovery, the strict security checks, the sandboxing — all of it exists to make "split your program into cooperating processes" safe and practical. When a detail seems fussy (like verifying who's connecting), it's because XPC is often the doorway to privileged code, and that doorway must be guarded.

Chapter 03

What's underneath (gently)
A little of the machinery, so the API stops feeling like magic. You don't need to use any of this directly.

You can use XPC without ever touching the layers below — but knowing they exist makes the behavior make sense. Two pieces sit under XPC: Mach ports and launchd.

Mach ports — the actual pipes

At the lowest level, macOS's kernel (XNU) provides Mach ports: think of a Mach port as a secure, kernel-guarded mailbox. A process that holds a "send right" to a port can drop messages into it; the process holding the "receive right" collects them. Crucially, you can't fake one — you can only use a port if the kernel gave you permission. XPC messages ultimately travel over Mach ports; XPC is a friendlier layer on top so you deal with dictionaries and method calls instead of raw kernel messaging.

launchd — the manager that starts things

launchd is the very first process macOS starts (process ID 1) and the manager of all system services. Here's the key part: services register their name with launchd, and launchd holds the "receive right" for them. So when your app wants to talk to a helper, it asks launchd for that helper by name — and launchd does two magical things:

  • Starts the helper on demand. The helper doesn't need to be running. The moment your first message arrives, launchd launches it. When idle, it can be shut down. This saves resources.
  • Restarts it if it crashes. If the helper dies, launchd brings it back under the same name the next time it's needed.
 your app: "connect me to com.corp.helper"
        │
        ▼
   ┌─────────┐   holds the name, launches on demand,   ┌──────────────┐
   │ launchd │ ─────────────────────────────────────▶ │  the helper  │
   └─────────┘   relaunches if it crashes              └──────────────┘
Why this mattersThat "starts on demand and restarts on crash" behavior is XPC's biggest advantage over a hand-built socket server — and it comes from launchd, not from XPC code you write. When we get to lifecycle (Chapter 7), this is why your helper can be "not running" yet still reachable.

Chapter 04

The two flavors of XPC
"XPC" is used for two related-but-different things. Know which you're building — this trips up beginners.

When people say "XPC," they might mean one of two setups. They share the same communication API but differ in what the helper is and who manages it.

Flavor A — XPC Services (the simple one)

An XPC Service is a small helper bundle that lives inside your app (in YourApp.app/Contents/XPCServices/). It's private to your app, runs unprivileged (often in a tight sandbox), and is fully managed by the system. You use these for crash isolation — moving risky work (parsing, plugins, media decoding) into a separate process so a crash there doesn't take down your app.

  • Created almost automatically — Xcode has an "XPC Service" target template.
  • Addressed by a service name; connected with NSXPCConnection(serviceName:).
  • Lifecycle is entirely automatic; you barely think about it.

Flavor B — Mach services / privileged helpers & daemons (the powerful one)

This is a separately-installed helper registered with launchd system-wide — often running as root. This is the privilege-separation pattern from Chapter 2, and the one an endpoint agent uses. It's more work to set up (you register it with launchd and must handle security carefully) but it's how you do privileged operations.

  • Registered with launchd via a property list declaring a MachServices name, or on modern macOS via SMAppService (macOS 13+) — the current way to install login items and daemons. (Older code used SMJobBless.)
  • Addressed by a Mach service name; connected with NSXPCConnection(machServiceName:options:).
  • You are responsible for security — this doorway may lead to root, so verifying the caller is essential (Chapter 8).
XPC Service (Flavor A)Mach service / daemon (Flavor B)
Where it livesInside your app bundleInstalled system-wide via launchd
PrivilegeUnprivileged, sandboxedOften root
PurposeCrash isolation, sandbox risky workPrivilege separation — do powerful work safely
Connect withNSXPCConnection(serviceName:)NSXPCConnection(machServiceName:options:)
Setup effortLow (Xcode template)Higher (register + secure)
Security burdenLightHeavy — you must validate callers
Which should you learn first?Understand both, but the communication code — protocols, connections, method calls — is identical between them. Only the setup and security differ. So learn the connection mechanics once (next chapters), then apply them to whichever flavor you need. For agent work, Flavor B is your world.

Chapter 05

The two API layers
There's a low-level C API and a friendly Swift/Obj-C API. Use the friendly one — but recognize the other.

The low-level C API (recognize it, don't reach for it)

The original XPC API is pure C. You work with xpc_connection_t and pass dictionaries (xpc_object_t) of key-value data. You'll see it in older code and Apple's C samples:

// Low-level C style — messages are dictionaries you build by hand
xpc_connection_t conn = xpc_connection_create_mach_service("com.corp.helper", NULL, 0);
xpc_connection_set_event_handler(conn, ^(xpc_object_t event) { /* handle reply */ });
xpc_connection_resume(conn);

xpc_object_t msg = xpc_dictionary_create(NULL, NULL, 0);
xpc_dictionary_set_string(msg, "command", "status");
xpc_connection_send_message(conn, msg);

It works, but it's verbose and untyped — you're manually building dictionaries and reading them back with string keys. Fine for tiny C tools; painful for real apps.

The high-level API: NSXPCConnection (use this)

NSXPCConnection (Objective-C, fully usable from Swift) is the modern, recommended layer. Instead of dictionaries, you define a Swift protocol describing what the remote side can do, and then you just call its methods. XPC turns those calls into messages for you. This is dramatically cleaner and type-safe, so the rest of this guide uses it.

Three types make up the high-level API — meet them now, use them next chapter:

NSXPCConnectionThe connection itself — one per link between two processes
NSXPCInterfaceWraps your protocol so XPC knows the shape of the calls
NSXPCListenerOn the server side — listens for incoming connections
The rule of thumbUse NSXPCConnection for anything you write in Swift or Obj-C. Only drop to the C API if you're in a pure-C context or need something the high-level API doesn't expose. Everything from here uses NSXPCConnection.

Chapter 06

Build a connection, step by step
The heart of XPC. We'll go one small step at a time — this is the pattern you'll reuse everywhere.

Every NSXPCConnection setup has the same shape. There's a server side (the helper that offers functionality) and a client side (whoever calls it). Let's build both, slowly.

Step 1 — Define the shared protocol (the contract)

Both processes need to agree on what can be called. You write a protocol, marked @objc (XPC is Objective-C underneath), and share the same file in both targets. This is the entire "API" between them.

// SharedProtocol.swift — compiled into BOTH the app and the helper
@objc protocol HelperProtocol {
    func currentStatus(reply: @escaping (String) -> Void)
    func install(package: String, reply: @escaping (Bool) -> Void)
}
Why every method has a "reply" closureXPC calls are asynchronous — the other process runs the work and calls you back. So instead of returning a value directly, each method takes a reply closure that the remote side invokes with the result. A method that returns nothing and expects no reply is "fire and forget"; a method with a reply block waits for an answer. (In newer Swift you can also use async methods, but reply blocks are the classic form to understand first.)

Step 2 — The server: create a listener

The helper process sets up an NSXPCListener and becomes its delegate. The listener waits for incoming connections.

class HelperMain: NSObject, NSXPCListenerDelegate {
    let listener: NSXPCListener

    override init() {
        listener = NSXPCListener(machServiceName: "com.corp.helper")  // Flavor B
        super.init()
        listener.delegate = self
    }
    func run() {
        listener.resume()      // start listening
        RunLoop.current.run()  // keep the process alive
    }
}

Step 3 — The server: accept a connection and expose an object

When a client connects, the delegate method shouldAcceptNewConnection is called. This is where you (1) decide whether to accept — the security checkpoint, covered in Chapter 8 — and (2) tell XPC which object actually handles the calls.

func listener(_ listener: NSXPCListener,
              shouldAcceptNewConnection newConnection: NSXPCConnection) -> Bool {

    // (security check goes here — see Chapter 8)

    // Tell XPC the shape of the calls...
    newConnection.exportedInterface = NSXPCInterface(with: HelperProtocol.self)
    // ...and the object that implements them:
    newConnection.exportedObject = HelperImplementation()

    newConnection.resume()   // activate the connection
    return true              // accept
}

And the implementation object is just a normal class conforming to the protocol:

class HelperImplementation: NSObject, HelperProtocol {
    func currentStatus(reply: @escaping (String) -> Void) {
        reply("healthy")                    // call the reply to send the answer back
    }
    func install(package: String, reply: @escaping (Bool) -> Void) {
        let ok = doPrivilegedInstall(package)
        reply(ok)
    }
}

Step 4 — The client: connect and get a proxy

Now the app side. You create a connection to the same service name, tell it the interface, resume it, and ask for a proxy object. The proxy looks like something conforming to your protocol — but calling its methods actually sends messages to the helper.

let connection = NSXPCConnection(machServiceName: "com.corp.helper", options: .privileged)
connection.remoteObjectInterface = NSXPCInterface(with: HelperProtocol.self)
connection.resume()

let proxy = connection.remoteObjectProxy as? HelperProtocol
proxy?.currentStatus { status in
    print("Helper says:", status)     // this runs when the helper replies
}
The whole thing in one breathServer: make a listener → accept connections → hand XPC an object that implements the protocol. Client: make a connection → get a proxy → call methods on it. XPC ships each call to the helper, runs it there, and delivers the reply back. That's the entire model — everything else is lifecycle and security around this core.

A note on error handling the proxy

Use remoteObjectProxyWithErrorHandler instead of the plain proxy so you catch connection failures (helper unavailable, crashed mid-call):

let proxy = connection.remoteObjectProxyWithErrorHandler { error in
    print("XPC call failed:", error)   // e.g. helper couldn't be reached
} as? HelperProtocol

Chapter 07

Lifecycle: launch, crash, reconnect
What happens over time — and the two handlers that make your client resilient.

The helper starts on demand

Remember launchd from Chapter 3: your helper does not need to be running when your app starts. The first time your client sends a message, launchd launches the helper, which sets up its listener and accepts the connection. When idle, the helper may be shut down again. You never call "start the helper" yourself — connecting is starting it.

Two things can go wrong, and each has a handler

Connections don't live forever. Set these two handlers on the client's connection right after creating it:

HandlerFires whenWhat to do
interruptionHandlerThe helper crashed, but the connection can be re-established (launchd will relaunch on the next call)Log it; expect to retry. The connection object is still usable.
invalidationHandlerThe connection is permanently dead — it will never work again (helper removed, or you called invalidate())Clean up; don't reuse this connection. Create a fresh one if needed.
connection.interruptionHandler = {
    print("Helper crashed — will reconnect on next call")
}
connection.invalidationHandler = {
    print("Connection permanently invalid — discard it")
}
The distinction, made simpleInterruption = temporary (the helper fell over but can come back). Invalidation = permanent (this connection is finished forever). A robust client logs interruptions and keeps going, and on invalidation throws the connection away and builds a new one if it still needs the helper.

Tearing down cleanly

When you're done, call connection.invalidate(). This ends the connection and triggers the invalidation handler. Always invalidate connections you no longer need so resources are released.

The lifecycle, start to finish

 app launches (helper NOT running)
   │
   ├─ client creates connection, sets handlers, resume()
   ├─ client calls a method  ──▶ launchd LAUNCHES the helper on demand
   │                             helper accepts, runs the call, replies
   │
   ├─ helper crashes  ──▶ interruptionHandler fires; next call relaunches it
   │
   └─ app done  ──▶ connection.invalidate()  ──▶ invalidationHandler fires

In the interview

What's the difference between the interruption and invalidation handlers?

Commit: The interruption handler fires when the remote process crashes but the connection can still be recovered — launchd will relaunch the helper on the next message, so I can keep using the connection. The invalidation handler fires when the connection is permanently dead and will never work again, so I discard it and, if needed, create a new one.

Nuance: in practice I log interruptions and let the next call transparently relaunch the helper, while on invalidation I tear down any state tied to that connection. I also call invalidate() myself when I'm done, which triggers that same handler, so cleanup lives in one place.

Does the helper need to be running before the app connects?

Commit: No. launchd manages the helper and starts it on demand — the first message from my app causes launchd to launch it. That's a core XPC advantage: I don't supervise the helper's process myself, and it can stay shut down while idle.

Nuance: the same mechanism restarts the helper if it crashes, so my client just needs to handle the brief interruption and retry. This on-demand-launch-and-relaunch behavior is exactly why XPC is preferable to a hand-rolled socket server for a helper.

Chapter 08 · The most important chapter

Security — verifying who's connecting
If your helper is privileged, this doorway leads to root. Guarding it correctly is the difference between a helper and a vulnerability.
The core danger, in plain words

Any process on the machine can try to connect to your helper's service. If your helper does privileged things and you accept every connection, then any app — including malware — can ask your root helper to do those privileged things for it. You must verify that the connecting process is really your app before accepting.

The wrong way: trusting the PID

A beginner's instinct is to check the connecting process's ID (PID) and see if it "looks right." Don't. PIDs are recycled — the OS reuses them — so a malicious process can end up with a PID you previously trusted. Checking the PID alone is a well-known vulnerability, not a defense.

The right way: verify the code signature

The correct check is: "was the connecting process built and signed by my team?" You verify the connecting process's code signature against a requirement that pins your Team ID and signing identity. Only a binary your team signed can pass — malware can't forge your signature.

The modern, easy way (macOS 13+): setCodeSigningRequirement

Apple added a one-line API that does the whole check for you. You give the listener (or connection) a requirement string, and XPC rejects any peer that doesn't match — before your delegate even sees it:

// On the helper's listener — reject anyone not signed by my team, automatically
listener.setCodeSigningRequirement(
    "anchor apple generic and certificate leaf[subject.OU] = \"YOURTEAMID\""
)

That requirement string reads as: "signed with a certificate chaining to Apple, whose leaf certificate's organizational unit (your Team ID) is YOURTEAMID." If you're on macOS 13 or later, this is the recommended approach — one line, and XPC enforces it for you.

The manual way (older systems): check the audit token yourself

On older macOS, or for finer control, you verify inside shouldAcceptNewConnection using the connection's audit token — a kernel-verified identity token (much stronger than a PID; it can't be forged or confused by PID reuse). You build a code object from it and check it against your requirement:

func listener(_ l: NSXPCListener,
              shouldAcceptNewConnection c: NSXPCConnection) -> Bool {

    var token = c.auditToken                 // kernel-verified identity of the caller
    let tokenData = Data(bytes: &token, count: MemoryLayout.size(ofValue: token))

    var code: SecCode?
    let attrs = [kSecGuestAttributeAudit: tokenData] as CFDictionary
    SecCodeCopyGuestWithAttributes(nil, attrs, [], &code)

    var requirement: SecRequirement?
    SecRequirementCreateWithString(
        "anchor apple generic and certificate leaf[subject.OU] = \"YOURTEAMID\"" as CFString,
        [], &requirement)

    let status = SecCodeCheckValidity(code!, [], requirement)
    return status == errSecSuccess          // accept ONLY if the signature matches
}
Why the audit token, not the PIDThe audit token is stamped by the kernel and carries a version number that distinguishes a live process from a dead one whose PID got reused. It's unforgeable. The PID is just a number that gets recycled. So the audit token answers "who is really on the other end," which is exactly what you need before doing privileged work for them.

Two more security habits

  • Keep the interface tiny. Expose only the few methods the helper truly needs. Every exposed method is attack surface.
  • Validate every argument. Even after verifying the caller, treat every value they send as untrusted — check ranges, sizes, and paths. A trusted caller can still be buggy or send bad data.

In the interview

How do you secure an XPC connection?

Commit: I verify the connecting process's code signature, not its PID. On macOS 13 and later I use setCodeSigningRequirement on the listener with a requirement pinning my Team ID, so XPC rejects any peer my team didn't sign before my code even runs. On older systems I do it manually in shouldAcceptNewConnection using the connection's audit token to build a SecCode and checking it against that requirement.

Nuance: I avoid the PID because PIDs are recycled, so a malicious process could inherit one I trusted — the audit token is kernel-verified and unforgeable, so it's the correct identity. Beyond authenticating the caller, I keep the exposed interface minimal and validate every argument, since a privileged helper's method surface is an attack surface even for a legitimate caller.

Why is checking the process ID (PID) not enough?

Commit: Because PIDs are reused by the operating system. A process can exit and its PID can be reassigned to a different, possibly malicious process — so a PID I checked and trusted a moment ago might now belong to something else. It's a classic time-of-check-to-time-of-use problem.

Nuance: the audit token solves this because it's kernel-verified and includes a PID-version that distinguishes a live process from a reincarnated PID. So identity checks should always be based on the audit token and the code signature it lets me verify, never the raw PID.

Chapter 09

What data can cross
Not everything can be sent between processes. Here's what's allowed and how to enable custom types.

The basics: only serializable data crosses

Because the two processes have separate memory, XPC has to serialize your arguments — turn them into bytes, send them, and rebuild them on the other side. So you can only pass things that know how to serialize themselves. Out of the box: strings, numbers, booleans, dates, data, arrays, and dictionaries of those. Under the hood these conform to NSSecureCoding.

Passing your own custom types

To send a custom class, it must conform to NSSecureCoding, and — for security — you must explicitly whitelist which classes are allowed as arguments to a given method. XPC won't just accept any class; you declare the expected ones so a malicious sender can't smuggle an unexpected object type in. You do this on the NSXPCInterface:

let interface = NSXPCInterface(with: HelperProtocol.self)
// Allow MyReport objects as the argument to this method's reply:
interface.setClasses(
    [MyReport.self, NSArray.self],
    for: #selector(HelperProtocol.fetchReport(reply:)),
    argumentIndex: 0,
    ofReply: true)          // true = it's in the reply; false = it's an argument
The beginner surpriseYou can't send arbitrary Swift structs or classes over XPC. If a value won't serialize (conform to NSSecureCoding) it can't cross the boundary. The usual fix is to send simple data — a string, a Data blob, or a Codable type you encode to Data yourself and decode on the other side — rather than fighting to make a complex object NSSecureCoding-compliant.
Practical tipFor anything beyond simple values, a clean pattern is: define a Codable struct, encode it to Data with JSONEncoder/PropertyListEncoder before sending, and decode it on the other side. Then your XPC methods only ever pass Data — which always crosses cleanly — and you keep the rich types in Swift on each end.

Chapter 10

Full worked example
Everything so far, assembled into one complete privileged-helper setup. Read it as the summary of the whole guide.

A menu-bar app that asks a root helper to report status and install a package. Three files: the shared protocol, the helper, and the client.

File 1 — Shared protocol (in both targets)

// HelperProtocol.swift
@objc protocol HelperProtocol {
    func currentStatus(reply: @escaping (String) -> Void)
    func install(package: String, reply: @escaping (Bool, String) -> Void)
}

File 2 — The helper (runs as root, managed by launchd)

// main.swift of the helper
import Foundation

class HelperImpl: NSObject, HelperProtocol {
    func currentStatus(reply: @escaping (String) -> Void) {
        reply("healthy · v2.4.0")
    }
    func install(package: String, reply: @escaping (Bool, String) -> Void) {
        guard package.hasSuffix(".pkg") else {        // validate input!
            return reply(false, "not a pkg")
        }
        let ok = runInstaller(package)                // the privileged work
        reply(ok, ok ? "installed" : "failed")
    }
}

class Delegate: NSObject, NSXPCListenerDelegate {
    func listener(_ l: NSXPCListener,
                  shouldAcceptNewConnection c: NSXPCConnection) -> Bool {
        c.exportedInterface = NSXPCInterface(with: HelperProtocol.self)
        c.exportedObject = HelperImpl()
        c.resume()
        return true
    }
}

let listener = NSXPCListener(machServiceName: "com.corp.helper")
let delegate = Delegate()
listener.delegate = delegate
if #available(macOS 13, *) {                          // SECURITY: one-line caller check
    listener.setCodeSigningRequirement(
        "anchor apple generic and certificate leaf[subject.OU] = \"YOURTEAMID\"")
}
listener.resume()
RunLoop.current.run()                                // keep the helper alive

File 3 — The client (the app)

// In the app
final class HelperClient {
    private var connection: NSXPCConnection?

    private func makeConnection() -> NSXPCConnection {
        let c = NSXPCConnection(machServiceName: "com.corp.helper", options: .privileged)
        c.remoteObjectInterface = NSXPCInterface(with: HelperProtocol.self)
        c.interruptionHandler = { print("helper crashed; will relaunch") }
        c.invalidationHandler = { print("connection dead; discard") }
        c.resume()
        return c
    }

    func status(_ done: @escaping (String) -> Void) {
        if connection == nil { connection = makeConnection() }
        let proxy = connection?.remoteObjectProxyWithErrorHandler { err in
            done("error: \(err.localizedDescription)")
        } as? HelperProtocol
        proxy?.currentStatus(reply: done)
    }
}
// usage: HelperClient().status { print("Helper:", $0) }

Reusing an invalidated connectionCalls silently failOn invalidation, discard and create a fresh connection
The two that bite everyone(1) Forgetting resume() — connections are born suspended, so nothing happens until you resume, and there's no error to tell you why. (2) The reply block contract — call it exactly once. Zero calls hangs the caller; two calls crashes. When you have multiple code paths (success, validation failure, error), make sure every single one calls reply once.

The 30-second explanation of XPC

"XPC is macOS's IPC framework for letting separate processes talk. You define a Swift protocol, and calling the remote side looks like calling methods on an object — XPC marshals the arguments and delivers the reply. It's built on Mach ports and integrated with launchd, so the helper starts on demand and relaunches if it crashes. It's used mainly for two things: crash isolation, by moving risky work into a sandboxed helper, and privilege separation, where a small root helper does powerful work for an unprivileged app."

The must-know facts, ranked

  1. Security is the headline. Verify the caller's code signature, not its PID — via setCodeSigningRequirement on macOS 13+, or the audit token manually. PIDs are recycled and unsafe.
  2. launchd gives on-demand launch and crash recovery — the reason XPC beats a hand-rolled socket server.
  3. The connection model: server exposes an object via a listener; client gets a proxy and calls methods; XPC ships the call and reply.
  4. Interruption (temporary) vs invalidation (permanent) — handle both; discard invalidated connections.
  5. Reply blocks fire exactly once; only serializable (NSSecureCoding) data crosses.

How this connects to your bigger pictureXPC is one of the two IPC mechanisms named in macOS agent roles (the other is Unix domain sockets). The honest senior framing: XPC when both ends are Apple-native and you want typed calls plus launchd lifecycle; Unix sockets when a portable C/C++ core or non-Apple component needs in. You now understand XPC deeply enough to make and defend that choice — which is exactly what a systems interviewer wants to hear.
