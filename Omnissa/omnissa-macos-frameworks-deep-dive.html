Framework 01

CoreFoundation
The plumbing under everything else. Master this and four other frameworks get easier.
The one-sentence version

CoreFoundation (CF) is a C library that gives macOS its basic building-block types — strings, arrays, dictionaries, numbers, dates — plus the memory rules and the event loop that older system APIs are built on.

Why it exists

Long before Swift, Apple needed a set of fundamental data types that both C-based system code and Objective-C apps could share without conversion. So they wrote CoreFoundation in C: CFStringRef, CFArrayRef, CFDictionaryRef, CFNumberRef, and so on. Foundation's Objective-C classes (NSString, NSArray…) are, under the hood, often the very same objects — a trick called toll-free bridging: you can cast a CFStringRef to an NSString* for free because they're literally the same thing in memory.

You care about CF because the low-level frameworks in this document — Security, SystemConfiguration, IOKit — are C APIs that hand you and expect CF objects. You can't use them without speaking CF.

How it actually works

1 · Everything is a "CFType" with a reference count

Every CF object (CFStringRef, CFDictionaryRef, etc.) is a chunk of heap memory with a retain count — a number tracking how many owners it has. When the count drops to zero, the object is freed. This is manual: you adjust the count.

  • CFRetain(obj) — "I want to keep this." Count +1.
  • CFRelease(obj) — "I'm done with this." Count −1. At zero, it's destroyed.

2 · The one rule that governs all of CF: the Create/Get rule

This is the single most-tested CF concept. It answers "do I own this object, i.e. must I release it?" — just by looking at the function name:

If the function name contains…You own the resultSo you must…
Create or Copy
CFStringCreateWithCString		Yes — it came to you with a +1 retain countcall CFRelease when done
Get
CFDictionaryGetValue		No — you're just borrowing itdo nothing; releasing it is a bug (over-release → crash)
The mental shortcut"Create/Copy = you clean up. Get = hands off." Interviewers love this because getting it wrong is the source of a huge fraction of real CF crashes — either a leak (forgot to release a Created object) or a crash (released a Got object you didn't own).

3 · How this looks from Swift: Unmanaged

Swift's ARC wants to manage retain counts for you, but C functions don't tell the compiler their ownership rules. So at the boundary, Swift gives you Unmanaged<T> and makes you state the rule explicitly:

// A C function returned a CFStringRef. Did it "Create" it?
let name = SecCopyErrorMessageString(status, nil)   // "Copy" → we own +1
// takeRetainedValue: "I own it, ARC — consume the +1 for me"
let str = name?.takeRetainedValue() as String?

// If it were a "Get" (borrowed), we'd use:
// .takeUnretainedValue()  → "I don't own it, don't touch the count"

Say it in one line: takeRetainedValue consumes a +1 (for Create/Copy); takeUnretainedValue borrows (for Get). Matching the wrong one leaks or crashes.

4 · The run loop (why old APIs need it)

A run loop (CFRunLoop) is a thread's event pump: it sleeps until something happens — a timer fires, a network source has data, a system notification arrives — then wakes and dispatches it. Many older C APIs (SystemConfiguration, IOKit notifications) deliver their callbacks by attaching a "source" to a run loop.

The modern move — and a good thing to volunteer — is that most of these APIs now let you deliver callbacks to a dispatch queue instead (e.g. SCDynamicStoreSetDispatchQueue), which is cleaner in a daemon than running a CFRunLoop by hand.

In the interview

Explain CoreFoundation memory management.

Commit: CF is manually reference-counted, and the ownership rule is encoded in the function name — the Create Rule. Functions with "Create" or "Copy" in the name return an object you own with a +1 retain count, so you must CFRelease it. Functions with "Get" return a borrowed reference you must not release.

Then the nuance: from Swift this surfaces as Unmanaged, where you pick takeRetainedValue for Create/Copy results and takeUnretainedValue for Get results. And CF toll-free bridges with Foundation, so a CFStringRef and an NSString are often the same object — which is why bridging is free.

Why this lands

You named the rule, gave the Swift consequence, and connected to bridging — three layers in thirty seconds.

What is toll-free bridging?

Commit: It's the fact that certain CoreFoundation types and their Foundation counterparts are implemented as the same underlying object, so you can cast between them with zero cost — CFStringRef ↔ NSString, CFArrayRef ↔ NSArray, CFDictionaryRef ↔ NSDictionary.

Nuance: not every CF type bridges, and the historical reason it exists is that CF (C) and Foundation (Obj-C) were designed to share one object model so system code and app code didn't pay conversion costs.

You call a CF function and the app leaks memory. How do you reason about it?

Commit: First thing I check is whether I'm holding onto a Created/Copied object without releasing it — the most common CF leak. I read the function names: any "Create" or "Copy" result I'm keeping needs a matching CFRelease on every exit path.

Nuance: in Swift I'd verify the Unmanaged choice — a takeUnretainedValue on something I actually own leaks; the reverse over-releases. And I'd confirm with Instruments' Allocations tool, which interposes on the allocator and shows me the retain/release history and backtraces for the leaked object.

Framework 02

Security
Keychain, certificates, cryptographic keys, and verifying who signed a piece of code. The heart of "device trust."
The one-sentence version

The Security framework is macOS's vault and its notary: it stores secrets (passwords, keys, certificates) safely in the Keychain, performs cryptography using keys that can live inside secure hardware, and lets you verify the identity of code — proving a running process was signed by who you think.

Why it exists

Two very different needs, one framework. First, apps need somewhere safe to keep secrets — you don't want passwords sitting in a plain file. The Keychain is an encrypted, access-controlled database for exactly that. Second, the OS needs to answer "can I trust this?" — is this certificate valid, was this app signed by a legitimate developer, is the process on the other end of my connection really my own helper tool? Those are the code-signing and trust APIs.

For an endpoint / zero-trust product this framework is central: device trust means proving a device is who it claims to be, using a cryptographic key that only that device holds. That's built directly on Security.framework.

How it actually works

1 · Keychain items and the SecItem API

The Keychain stores items — a password, a key, a certificate, an identity. You interact with it through four C functions that all take a dictionary of attributes:

SecItemAddstore a new item
SecItemCopyMatchinglook one up (note "Copy" → you own the result)
SecItemUpdatemodify
SecItemDeleteremove

You describe the item with attribute keys: its class (kSecClass — generic password, key, certificate…), a service name, an account, and crucially an accessibility setting.

2 · Accessibility: when is a secret readable?

Every keychain item carries a policy for when it can be unlocked — this is a favorite interview probe:

  • kSecAttrAccessibleWhenUnlocked — readable only while the device is unlocked. The safe default.
  • kSecAttrAccessibleAfterFirstUnlock — readable after the first unlock following a boot, even if later locked. This is what a background daemon needs, because it must function while the screen is locked.
  • The …ThisDeviceOnly variants — never migrate to a new device via backup. Right choice for a device-identity key that should be non-portable.

3 · The Secure Enclave — keys that can't be stolen

This is the concept that makes device trust actually secure, so understand it precisely.

The Secure Enclave is a separate security chip (a coprocessor) isolated from the main CPU. You can ask it to generate a private key inside itself, and here's the key property: the private key never leaves the enclave — it never exists in normal memory, not even for a moment. Your app only ever gets a handle to it. When you need to sign something, you hand the data to the enclave and it returns the signature; the key itself is untouchable.

// Generate a key that lives and dies inside the Secure Enclave
var attrs: [String: Any] = [
    kSecAttrKeyType as String: kSecAttrKeyTypeECSECPrimeRandom,
    kSecAttrTokenID as String: kSecAttrTokenIDSecureEnclave,   // ← the magic line
    kSecAttrKeySizeInBits as String: 256,
]
let privateKey = SecKeyCreateRandomKey(attrs as CFDictionary, &error)
// privateKey is a HANDLE. The actual key material is inside the chip.
Your device-trust story, in one breath"On the device I generate an elliptic-curve key inside the Secure Enclave — the private key never touches host memory. I put a certificate proving the device's identity in the Keychain with after-first-unlock, this-device-only accessibility so the daemon can use it while locked and it can't be exfiltrated to another machine. To access a protected resource, the device signs a challenge with the enclave key; possession of that hardware-bound key plus posture signals is what the zero-trust backend checks." — This single answer covers Secure Enclave, Keychain, certificates, and zero-trust at once. Rehearse it.

4 · Certificates, identities, and trust evaluation

Three related objects you should distinguish cleanly:

  • SecCertificate — a public certificate (identity + public key, signed by a CA).
  • SecKey — a cryptographic key (public or private).
  • SecIdentity — a certificate paired with its matching private key. This is what you present for client authentication (mTLS).

To decide whether a certificate is trustworthy, you build a SecTrust object (the cert plus a policy, e.g. "SSL for hostname X") and evaluate it — the system walks the chain up to a trusted root and checks validity and revocation.

5 · Code-signing verification — the agent-security superpower

Separate from keychains: Security.framework lets a privileged process ask "who signed the code that's running as this other process?" This is how you harden an IPC connection — you don't trust a peer because of its PID, you trust it because it was signed by your team.

 another process connects to your daemon
        │  you have its audit token (kernel-verified identity)
        ▼
 SecCodeCopyGuestWithAttributes(auditToken) ──▶ a SecCode for the peer
        │
        ▼
 SecCodeCheckValidity(peer, requirement)
        requirement string, e.g.:
        anchor apple generic and certificate leaf[subject.OU] = "YOURTEAMID"
        │

The requirement string is a mini-language describing "what must be true of the signature." SecStaticCode is the on-disk equivalent (verify a file); SecCode is the running-process version.

In the interview

How does the Secure Enclave make a key more secure than storing it in the Keychain?

Commit: A Secure Enclave key's private material is generated inside the enclave chip and never leaves it — it's never in main memory, so even code that fully compromises the host process can't read the key; it can only ask the enclave to sign, which it can't do without the device. A plain Keychain item, by contrast, is decrypted into process memory when you use it.

Nuance: the two combine — you keep the enclave key handle and its certificate in the Keychain for lookup, and you can attach a SecAccessControl requiring biometrics or the device passcode at use-time for an extra gate. The trade-off is that enclave keys are limited to specific algorithms (EC, not arbitrary key types) and can't be exported or backed up — which for device identity is exactly what you want.

Your daemon needs a secret while the Mac is locked. Which keychain accessibility do you choose and why?

Commit: kSecAttrAccessibleAfterFirstUnlock — a background daemon must keep working when the user locks the screen, and this makes the item readable from the first post-boot unlock onward, including while locked.

Nuance: I'd add ThisDeviceOnly if it's a device-bound secret that must never migrate via backup. I would not use WhenUnlocked for a daemon — it'd fail the moment the screen locks. Choosing accessibility is really about matching the secret's lifetime and threat model to the daemon's runtime.

How would you make sure only your own app can connect to your privileged helper?

Commit: I verify the peer's code signature, not its PID. From the connection's audit token I build a SecCode and call SecCodeCheckValidity against a requirement that pins my Team ID and signing identifier — so only a binary my team signed passes.

Nuance: PID-based checks are unsafe because PIDs get reused — a malicious process could inherit a PID. The audit token includes a pid-version that defeats that, and the signature check defeats impersonation entirely. This is the correct way to secure an XPC or socket connection, and I'll come back to it in the IPC discussion.

Common trapDon't confuse notarization (Apple scanning your app for malware before distribution) with code signing (proving who built it) or trust evaluation (validating a TLS certificate chain). Three different things people blur together. Signing = identity; notarization = Apple's malware scan; trust eval = is this cert chain valid.

Framework 03

SystemConfiguration
The live map of the Mac's network state — and how to react to it without polling.
The one-sentence version

SystemConfiguration (SC) is a live database of the machine's network and system configuration — current IP addresses, DNS servers, proxies, the active network interface, who's logged in — that you can both read and subscribe to for change notifications.

Why it exists

Network conditions on a laptop change constantly: Wi-Fi drops, the user plugs in Ethernet, a VPN comes up, they walk into an office and hit a proxy. Software that cares about the network — and an endpoint agent very much does — needs to know the moment this happens, not discover it by failing. SystemConfiguration is the OS's authoritative, push-based source for that state.

How it actually works

1 · SCDynamicStore — the reactive state store

The core object is SCDynamicStore: a key-value store the system keeps up to date. You watch keys (using pattern matching, e.g. "all IPv4 state keys") and register a callback that fires whenever a matching value changes. No polling — the system pushes to you.

// Watch for any change to network global state, deliver on a queue
let store = SCDynamicStoreCreate(nil, "com.corp.agent" as CFString, callback, &ctx)
let keys = ["State:/Network/Global/IPv4", "State:/Network/Global/DNS"]
SCDynamicStoreSetNotificationKeys(store, keys as CFArray, nil)
SCDynamicStoreSetDispatchQueue(store, myQueue)   // modern: no manual run loop
// callback now fires on myQueue whenever the primary IPv4 route or DNS changes

2 · What lives in there

  • Network state — primary interface, IP addresses, router, DNS servers (the example above).
  • Proxy settings — SCDynamicStoreCopyProxies gives the system proxy config, including PAC-file URLs. Essential for an enterprise agent whose uploads must respect corporate proxies.
  • Console user — who's currently logged in at the screen, and login/logout transitions.

3 · Reachability, and its modern replacement

SCNetworkReachability answers "is this host potentially reachable, and would connecting need Wi-Fi/cellular?" It's classic but dated. The senior move is to mention that Apple now steers you toward NWPathMonitor in Network.framework for path/reachability monitoring — saying this signals you're current, not stuck on 2015 APIs.

Where an agent uses thisNetwork transitions are first-class experience and security telemetry. A DEX agent reports connectivity changes; a security agent re-evaluates posture when the network changes (e.g., left the trusted network → tighten access). Doing it event-driven via SCDynamicStore instead of a polling timer is both correct and battery-friendly — and battery is something a fleet agent gets blamed for, so it's worth saying.

In the interview

How would your agent detect that the network changed, efficiently?

Commit: I'd subscribe to SCDynamicStore for the network state keys — primary IPv4/IPv6 route and DNS — and get a push callback the instant they change, delivered to a dispatch queue. No polling.

Nuance: for simple "can I reach this host" checks I'd use NWPathMonitor from Network.framework, which is the modern replacement for SCNetworkReachability. Event-driven matters at fleet scale — a polling timer that wakes the CPU every few seconds across millions of devices is a measurable battery and energy cost, and an agent that drains battery gets uninstalled.

Your telemetry uploads work at home but fail on the corporate network. Where do you look?

Commit: Proxies. Enterprise networks route outbound traffic through an HTTP proxy, often configured by a PAC file. I'd read the system proxy configuration via SCDynamicStoreCopyProxies and make sure my HTTP client honors it, including evaluating the PAC file for the destination.

Nuance: I'd also consider TLS-inspecting middleboxes — if I pin certificates, an enterprise's inspection proxy will break the connection, so pinning needs an enterprise-aware exception path. This is exactly the kind of real-world networking an endpoint agent has to survive.

Framework 04

IOKit
The window into hardware — devices, power, sleep/wake, and the device tree.
The one-sentence version

IOKit is macOS's driver framework. Drivers live in the kernel side of it, but from a normal app you use IOKit to read the live tree of hardware devices — serial numbers, USB devices, battery state — and to get notified when hardware changes or the machine sleeps and wakes.

Why it exists

The OS needs a structured way to represent every piece of hardware — the built-in ones and everything plugged in — and to let drivers attach to them. That structure is the IORegistry: a live tree of device objects, each with properties. Drivers are the kernel half; the userspace half (what you'll be asked about for an agent role) is querying that tree and watching it.

How it actually works

1 · The IORegistry: a tree of devices with properties

Picture a live tree. The root is the machine; branches are buses (PCI, USB); leaves are individual devices. Each node has a class (what kind of thing it is) and a dictionary of properties (serial number, vendor ID, capacity…). You explore it by matching.

2 · Matching — how you find a device

You build a matching dictionary ("find me all IOUSBHostDevice objects"), hand it to IOServiceGetMatchingServices, and iterate the results, reading properties off each:

// Enumerate USB devices and read a property from each
let matching = IOServiceMatching("IOUSBHostDevice")
var iter: io_iterator_t = 0
IOServiceGetMatchingServices(kIOMainPortDefault, matching, &iter)

while case let dev = IOIteratorNext(iter), dev != 0 {
    var props: Unmanaged<CFMutableDictionary>? = nil
    IORegistryEntryCreateCFProperties(dev, &props, kCFAllocatorDefault, 0)
    // props now holds vendor, product, serial, etc. (note "Create" → release it)
    IOObjectRelease(dev)
}

Notice CoreFoundation everywhere — CFMutableDictionary, the Create rule, Unmanaged. This is why CF came first.

3 · What an agent actually reads from IOKit

Hardware inventorymodel, serial number (via IOPlatformExpertDevice), UUID — device identity for asset tracking
Power & batterycharge, health, on-AC-or-battery (IOPMPowerSource) — experience telemetry
USB monitoringwatch for device insert/remove — a security signal (data exfiltration via USB)
Sleep / wakeIORegisterForSystemPower — get notified before sleep and after wake

4 · Notifications — watching for change

Beyond one-time queries, you can register for events: device added/removed, or system power transitions. These historically deliver via a run loop source (IONotificationPort) — which ties back to the CoreFoundation run-loop concept.

Say this and sound currentKernel extensions (kexts) are deprecated. Real drivers now use DriverKit (running in userspace, safer). And for the monitoring an agent does, you don't need a kext at all — you use IOKit's userspace query/notification APIs plus Endpoint Security. Volunteering "I'd never ship a kext for this today" signals you know the modern platform.

In the interview

How would your agent get the device's serial number and detect USB drives being plugged in?

Commit: For the serial, I query the IORegistry — match IOPlatformExpertDevice and read the platform serial property. For USB, I register an IOKit notification for device-published events on USB device matching, so I get a callback each time one is attached or removed.

Nuance: USB insert/remove is a genuine security signal — removable media is a classic exfiltration and malware vector — so an endpoint agent surfaces it as an event. All of this is userspace IOKit; no kernel extension needed, which matters because kexts are deprecated in favor of DriverKit and userspace monitoring.

Why does your daemon care about sleep/wake notifications?

Commit: Because a laptop sleeps constantly, and the agent needs to behave correctly around it — flush pending telemetry before sleep, and re-establish connections and re-check posture on wake. I register with IORegisterForSystemPower to get those transitions.

Nuance: sleep/wake is itself experience telemetry (how often, how long), and getting it wrong causes bugs like stale network connections after wake or wakeups that drain battery. Handling power events cleanly is part of being a well-behaved fleet agent.

Framework 05 · Headline framework

Network Extension
Legitimately see and control network traffic — VPNs, content filters, DNS proxies — from userspace.
The one-sentence version

Network Extension (NE) is Apple's official, sandboxed way to intercept and control network traffic: build a VPN, filter or block connections, proxy DNS, or route specific apps' traffic — all from a userspace system extension, no kernel code.

Why it exists

Before NE, doing this meant kernel network hooks (kexts) — powerful but dangerous: a bug took down the whole machine, and Apple couldn't guarantee privacy. NE replaces all of that with a set of provider classes that run in userspace with specific entitlements. You subclass the right provider for your use case; the system delivers traffic to you and enforces your verdicts.

How it actually works

1 · Pick the right provider — this is the core knowledge

NE isn't one thing; it's a family. Interviewers test whether you can choose the correct provider for a goal:

ProviderWhat it sees / doesClassic use
NEFilterDataProvider
(content filter)		Every network flow, inline; you allow / drop / ask-for-more per flowFirewall, per-app visibility, DLP
NEDNSProxyProviderAll DNS queries on the systemDNS security & telemetry
NEPacketTunnelProviderRaw IP packets via a virtual interfaceFull VPN (your own protocol)
NEAppProxyProviderPer-app TCP/UDP flows (not raw packets)Per-app VPN, ZTNA
NETransparentProxyProviderSelected flows, intercepted transparently — app doesn't knowModern ZTNA / selective interception

The one-line way to remember the split: packet tunnel = whole-device VPN at the IP layer; app proxy / transparent proxy = per-app at the flow layer; content filter = observe/allow/deny; DNS proxy = just DNS.

2 · Flows, and per-app attribution

A content filter delivers flows — NEFilterFlow objects representing one connection. The powerful part: each flow carries the identity of the app that created it (its signing identifier and audit token), so you can make decisions like "block this app from reaching that host." That per-process attribution is what turns raw traffic into meaningful security policy.

3 · The privacy design you should name

The content-filter data provider — the one that sees actual traffic — runs in a sandbox with no ability to send data off the device. Apple did this deliberately: an extension that can read all your traffic must not also be able to phone it home. Configuration and any "call home" happens in a separate control provider / the containing app. Knowing this privacy split is a senior signal.

Your Zscaler/ZPA prep transfers directlyPer-app VPN and ZTNA (zero-trust network access) is exactly NEAppProxyProvider / NETransparentProxyProvider territory. If you did the ZPA data-path work, you can speak to how selected flows get intercepted, tunneled to a broker, and policy-checked — that's the same mental model, just Apple's framing.

4 · How it's deployed to a fleet

An NE provider ships as a system extension bundled in an app. On one Mac the user approves it; across a fleet, the MDM pushes a profile that pre-approves and activates it silently — zero-touch. That MDM angle is the enterprise differentiator and worth mentioning.

In the interview

You need to block a specific app from reaching certain domains. Which NE provider, and how?

Commit: An NEFilterDataProvider — a content filter. It sees every flow inline with the originating app's identity, so I match the app's signing identifier and the destination and return a drop verdict for the ones I want blocked.

Nuance: if I only needed to control it at the DNS level I could use an NEDNSProxyProvider instead, which is lighter — but that's bypassable via hardcoded IPs, so a true block belongs at the flow layer. And the filter data provider is sandboxed with no network egress by design, so any "report this block to the server" happens in the control provider, not the data provider.

Full VPN vs per-app VPN — which provider for each, and why does it matter?

Commit: Full device VPN uses NEPacketTunnelProvider — you get raw IP packets through a virtual interface and tunnel everything. Per-app is NEAppProxyProvider (or NETransparentProxyProvider) — you operate on individual apps' TCP/UDP flows, so only chosen apps are routed.

Nuance: the layer is the real difference — packet tunnel works at L3 (IP packets, protocol-agnostic), app proxy works at the flow/socket layer with app attribution. For a zero-trust product you usually want per-app or transparent proxying so you route corporate apps to the broker without tunneling the user's personal traffic — better privacy and performance.

Why is Network Extension better than the old kernel approach?

Commit: It runs in userspace, so a bug crashes and restarts the extension instead of panicking the whole machine, and it's constrained by entitlements and sandboxing so it can't abuse the traffic it sees.

Nuance: that safety is why Apple deprecated network kexts entirely. The content-filter data provider even has no network egress, so an extension that reads all traffic structurally cannot exfiltrate it — a privacy guarantee the kernel approach couldn't make.

Framework 06 · Headline framework

Endpoint Security
Watch — and optionally block — security-relevant events on the system: process launches, file operations, and more.
The one-sentence version

Endpoint Security (ES) lets a privileged userspace program subscribe to a stream of security events — a process is about to exec, a file is being opened, a process forked — and either just observe them or authorize them (allow/deny before they happen).

Why it exists

Security products (EDR, antivirus, DLP) need to see everything happening on a machine, and sometimes stop it. This used to require kernel extensions hooking syscalls — the same panic-the-machine risk as network kexts. ES is the userspace replacement: Apple emits the events to you from the kernel, over an entitled client, safely.

How it actually works

1 · The client and the two event modes

You create an es_client_t (requires a restricted Apple-granted entitlement), subscribe to the event types you care about, and receive them in a handler. Every event is one of two modes — this distinction is the most important thing to know about ES:

ModeWhat happensYour job
NOTIFYThe event already happened; you're told after the factObserve, log, report. Nobody's waiting.
AUTHThe kernel has paused the operation and is waiting for your verdictDecide allow or deny — and fast (see deadlines)
// Subscribe to: block-capable exec, plus notify-only fork/exit
es_subscribe(client, [ES_EVENT_TYPE_AUTH_EXEC,
                      ES_EVENT_TYPE_NOTIFY_FORK,
                      ES_EVENT_TYPE_NOTIFY_EXIT], 3)

// In the handler, for an AUTH event you MUST respond:
es_respond_auth_result(client, msg, ES_AUTH_RESULT_ALLOW, false)

2 · The deadline — the concept that shapes all ES design

Every AUTH event carries a deadline. If you don't respond in time, the kernel decides for you — and if you're chronically late, it kills your client.

Think about what this forces: your AUTH handler must be fast. You cannot make a network call, hit a slow database, or block on a lock inside it. Everything needed to decide must be in memory. This single constraint drives the whole architecture of an ES agent:

  • Cache verdicts. Keyed by the binary's CDHash (its cryptographic identity), so the second launch of an already-approved app is an instant memory lookup, not a re-evaluation.
  • Never block in the handler. If a decision genuinely needs slow work, you retain the message (es_retain_message), decide on another queue, and respond before the deadline — or design so the common case never needs that.

3 · What's in an event

Each message carries rich, kernel-verified process info in an es_process_t: the audit token, the path, the signing ID and Team ID, and the CDHash (the code-directory hash — the binary's true fingerprint). Because it's from the kernel, it's trustworthy — you're not asking the process to identify itself.

4 · Muting — the performance lever

A busy Mac generates a firehose of events. If you process all of them you'll burn CPU (and you'll see your own agent's activity too). Muting tells the kernel to stop sending you events from specific processes or paths (es_mute_process, es_mute_path) — including muting your own agent so you don't watch yourself.

Why muting beats filteringMuting happens in the kernel — muted events are never generated for you at all. Filtering in your handler means the event was already produced, copied, and delivered before you throw it away. At tens of thousands of events per second the difference between "never sent" and "sent then discarded" is the difference between 3% and 30% CPU. This is a favorite senior probe.
You've built both sides of thisNOTIFY for experience/telemetry (what's running, what changed), AUTH for enforcement (block untrusted binaries). If you've shipped an ES client at JumpCloud, the strongest possible answer to any ES question is to describe your real design: which events, how you cache verdicts against the deadline, how you mute your own agent, and how events flow into a bounded queue for enrichment. Lead with that.

In the interview

Walk me through what happens when a process tries to launch and your ES client is watching exec.

Commit: If I subscribed to ES_EVENT_TYPE_AUTH_EXEC, the kernel pauses the exec and sends me a message with a deadline. My handler inspects the es_process_t — path, Team ID, CDHash — decides allow or deny, and calls es_respond_auth_result before the deadline. If I only need to observe, I use the NOTIFY variant and the exec isn't blocked at all.

Nuance: the deadline is the design driver — the verdict must come from an in-memory cache keyed by CDHash, never a network call, or I'll miss the deadline and eventually get my client killed. First launch of an unknown binary might do heavier work off the handler thread by retaining the message; repeat launches are cache hits.

Your ES agent is using 30% CPU on a busy build machine. First move?

Commit: Muting. A build machine spawns thousands of short-lived processes and does massive file I/O, so I'm drowning in events. I mute the known-noisy, trusted sources — the compiler toolchain, my own agent's processes — at the kernel level with es_mute_path / es_mute_process, so those events are never generated for me.

Nuance: muting in the kernel is far cheaper than filtering in my handler, because muted events aren't produced, copied, or delivered at all. I'd also make sure I'm not doing per-event work that belongs batched, and that my verdict cache is actually hitting. Muting first, though — it's the biggest lever.

Why is Endpoint Security in userspace an improvement over the old kernel extensions it replaced?

Commit: Stability and security. An ES client runs in userspace (typically inside a system extension), so a bug crashes just the extension — which the system restarts — instead of kernel-panicking the entire Mac the way a faulty kext would.

Nuance: it's also gated by a restricted entitlement Apple must grant, and it gives structured, kernel-verified event data rather than fragile syscall hooking. That's why Apple deprecated the kext-based approach — same story as Network Extension replacing network kexts.

NOTIFY vs AUTH — when would you deliberately choose NOTIFY even for a security feature?

Commit: When I only need to record or react after the fact and don't need to block — NOTIFY has no deadline pressure, so it's cheaper and can't accidentally freeze the system if my client is slow.

Nuance: AUTH is only justified when I genuinely must prevent the operation, because every AUTH subscription adds latency to that operation system-wide and risks the deadline. A well-designed agent uses AUTH sparingly for true enforcement and NOTIFY broadly for visibility — over-using AUTH is how agents make Macs feel sluggish.

Putting it together

How the six fit in one agent
If you can draw this, you can answer almost any "how would you build X" question.

These aren't six unrelated topics — they're layers of one system. Here's how they stack inside an endpoint agent, which is also a clean thing to sketch on a whiteboard:

 ┌──────────────────────────────────────────────────────────────┐
 │  THE AGENT  (a LaunchDaemon + one or more System Extensions)  │
 ├──────────────────────────────────────────────────────────────┤
 │                                                              │
 │  SENSING LAYER — what's happening on this device?           │
 │   • Endpoint Security ....... processes, file events         │
 │   • Network Extension ....... network flows, DNS             │
 │   • IOKit ................... hardware, USB, power, sleep     │
 │   • SystemConfiguration ..... network/proxy/DNS changes      │
 │                                                              │
 │  TRUST LAYER — who is this device, who can I trust?         │
 │   • Security ................ Secure Enclave device key,     │
 │                               Keychain, code-sign checks     │
 │                                                              │
 │  FOUNDATION — the types & rules all of the above speak      │
 │   • CoreFoundation .......... CFTypes, Create/Get rule,      │
 │                               run loops                      │
 └──────────────────────────────────────────────────────────────┘

The connections interviewers love

  • CoreFoundation is the language the C frameworks (Security, SystemConfiguration, IOKit) speak — CFTypes in, CFTypes out, Create/Get ownership throughout. Getting CF right is a prerequisite, not a side topic.
  • Security is the trust anchor for everything else: the code-signing checks that validate an ES event's process, the device key behind zero-trust access, the identity you present for mTLS.
  • ES and NE are the same idea in two domains — userspace system extensions that replaced dangerous kernel hooks, both gated by entitlements, both delivering kernel-verified events you observe or block.
  • The audit token ties it together: ES gives you one per process, NE flows carry one, and you feed it to Security's SecCode APIs to verify who signed the code. One identity primitive, three frameworks.
Your closing move in any framework questionZoom out to this map. "Endpoint Security tells me what's executing, Network Extension what's connecting, IOKit what hardware's present, SystemConfiguration how the network's changing — all keyed to kernel-verified process identity that I validate through Security.framework, all built on CoreFoundation types. At JumpCloud I've built agents that combine these." That shows you see the platform as a system, which is exactly the level this role is hiring for.
