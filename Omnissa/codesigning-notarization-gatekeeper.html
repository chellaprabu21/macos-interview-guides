Code Signing, Notarization & Gatekeeper

The complete chain that decides whether your Mac app is allowed to run — from cryptographic first principles, in the order the concepts build. No prior knowledge assumed, ending with a full CI pipeline and an interview question bank.

Start here

These three things get blurred together constantly — including by experienced engineers. The most valuable thing this guide gives you is knowing exactly which question each one answers.

Chapter 01

The big picture
See the whole journey before zooming into any one part.

The problem macOS is solving

You download an app from the internet. Your Mac has no idea what it is. Three dangers:

  1. Impersonation — is this really from the developer it claims to be from?
  2. Tampering — did someone modify the app after the developer built it, injecting malware into an otherwise legitimate app?
  3. Outright malware — the developer is real, but the software is malicious.

Signing solves #1 and #2. Notarization addresses #3. Gatekeeper is the guard at the door who checks the results of both before letting the app in.

What each step buys you

And notarization requires the Hardened Runtime. These dependencies are exactly why the pipeline in Chapter 12 has the order it does — the order isn't arbitrary, it's forced.

Chapter 02 · Foundations

Hashes & digital signatures
Three ideas. Get these and code signing becomes obvious rather than mysterious.

Idea 1 — A hash is a fingerprint of data

A hash function (like SHA-256) takes any amount of data and produces a fixed-size fingerprint. Three properties matter:

  • The same input always gives the same hash.
  • Change even one bit and the hash changes completely.
  • You can't reverse it, and you can't find two inputs with the same hash.

So if you know the correct hash of a file, you can detect any tampering by re-hashing and comparing. That's the integrity half of code signing.

Idea 2 — A digital signature proves who created something

You have a key pair: a private key (secret, only you) and a public key (published). The math works so that:

 SIGNING (you, private key)            VERIFYING (anyone, public key)
 ─────────────────────────            ─────────────────────────────
 hash the data      → H                hash the data        → H'
 encrypt H with                        decrypt signature
 your private key   → SIGNATURE        with the public key  → H

                                       H == H' ?
                                         ✓ untampered AND signed by the
                                           holder of that private key

Only your private key could produce a signature that your public key correctly decrypts. So a valid signature proves the data hasn't changed and you signed it — both at once.

Idea 3 — Certificates: who vouches for the public key?

One gap remains: anyone can generate a key pair and claim to be "Acme Corp." A certificate closes it. A trusted authority — here, Apple — signs a document saying "this public key belongs to Acme Corp, Team ID ABC123." Every Mac already trusts Apple's root, so it can verify that chain.

 Apple Root CA ──signs──▶ Apple Developer ID CA ──signs──▶ Your certificate
 (pre-trusted by             (intermediate)                (your public key +
  every Mac)                                                your Team ID)

 The CHAIN OF TRUST. Verification walks up it to a root the Mac trusts.
Code signing is just these three ideas appliedHash the code (integrity) → sign the hashes with your private key (identity) → include your Apple-issued certificate so anyone can verify the chain (trust). Everything in the next chapters is a detail of how Apple structures this.

In the interview

At a cryptographic level, what does code signing actually do?

Commit: It hashes the code, encrypts those hashes with the developer's private key to produce a signature, and bundles the developer's certificate alongside. To verify, the system re-hashes the code, decrypts the signature using the public key from that certificate, and compares — a match proves both that the code is unmodified and that it was signed by the holder of the private key.

Nuance: the certificate is itself signed by Apple, chaining to a root every Mac already trusts, which is what binds the public key to a real developer identity. So signing gives integrity and authenticity together — but it says nothing about whether the code is safe. That's precisely why notarization exists as a separate step.

Chapter 03

Inside a code signature
What Apple actually stores when you sign — and the term you'll hear constantly: CDHash.

A signature isn't one hash — it's a tree of them

An app isn't one file; it's a bundle with an executable, resources, frameworks, plists. Apple hashes everything, in layers:

 ┌──────────────────────────────────────────────────────┐
 │  CODE DIRECTORY  (the heart of the signature)        │
 │                                                      │
 │   · identifier    com.corp.myapp                     │
 │   · Team ID       ABC123XYZ                          │
 │   · page hashes   [h1][h2][h3]… ← the executable is  │
 │                                   hashed PAGE BY PAGE│
 │   · hash of the resource seal (CodeResources file)   │
 │   · entitlements hash                                │
 └──────────────────────────────────────────────────────┘
              │
              │  hash the whole Code Directory
              ▼
         ★ CDHash ★   ← the app's unique cryptographic identity
              │
              │  sign this with your private key
              ▼
      SIGNATURE + your certificate chain

Three things to remember from that diagram

  • Page hashes. The executable is hashed in small pages, not as one blob. Why? So the kernel can verify each page as it's loaded into memory. If someone modifies code on disk while the app runs, the next page load fails validation and the process is killed. Signing protects code at runtime, not just at launch.
  • The CDHash (Code Directory hash) is the fingerprint of the whole signature structure. It's the binary's true identity — it's what Endpoint Security events report, what verdict caches key on, and how you refer to "this exact build" unambiguously.
  • The resource seal. Non-code files (images, plists, nibs) are hashed into a CodeResources file, which is itself hashed into the Code Directory. That's why adding a file to a signed bundle breaks the signature.

Where the signature lives

For a Mach-O executable, the signature is embedded inside the binary as a special segment (LC_CODE_SIGNATURE). For a bundle, the resource hashes live in Contents/_CodeSignature/CodeResources. So a signed app carries its own proof — no external file needed.

Why CDHash matters to you specificallyIn an endpoint agent, ES events give you each process's CDHash. It's a stable, forgery-proof identifier for "exactly this binary." Caching an allow/deny verdict keyed on CDHash is how you meet ES's deadline (a memory lookup instead of re-verifying). If someone asks "how do you identify a binary?" — CDHash, not path, not name, both of which are trivially changed.

In the interview

What is a CDHash?

Commit: It's the hash of the Code Directory — the structure inside a code signature that contains the binary's identifier, Team ID, page-by-page hashes of the executable, and hashes of its resources and entitlements. Because it covers all of that, the CDHash uniquely and unforgeably identifies one exact build of a binary.

Nuance: it's the identifier I'd use in a security agent, since Endpoint Security reports it per process — path and name are trivially spoofed, but you can't produce a different binary with the same CDHash. It's also what I'd key a verdict cache on to answer authorization events within their deadline.

Why does the signature hash the executable page by page instead of as a whole?

Commit: So the kernel can verify code lazily, as each page is paged into memory at runtime. Hashing the whole binary once would only let you validate at launch; page hashes let macOS check every page on load, so modifying code on disk after launch causes the next page fault to fail validation and the process gets killed.

Nuance: that's what makes code signing a runtime protection and not just a launch-time check, and it's the foundation the Hardened Runtime builds on when it blocks unsigned executable memory and code injection.

Chapter 04

Certificates & identities
Which certificate for which purpose — a genuinely common source of confusion and build failures.

The certificates you'll encounter

CertificateSignsDistribution channel
Developer ID ApplicationApps, binaries, .dmgOutside the App Store (your website, MDM). The one you need for notarization.
Developer ID Installer.pkg installer packagesOutside the App Store
Apple DevelopmentLocal dev buildsYour machines only
Apple DistributionApp Store submissionsMac App Store (Apple re-signs it)
Mac Installer DistributionApp Store .pkgMac App Store
The classic build failureUsing Developer ID Application to sign a .pkg, or Developer ID Installer to sign an app. They're not interchangeable. App/binary → Application cert. Installer package → Installer cert. If productsign mysteriously fails, this is usually why.

Team ID and Signing Identifier — two different names

  • Team ID — a 10-character code identifying your organization (e.g. ABC123XYZ9). Every certificate your team gets carries it. It's the "who" in "who signed this."
  • Signing Identifier (bundle identifier) — identifies the specific app, like com.corp.agent.

Together they say "app com.corp.agent, made by team ABC123XYZ9." That pair is what you pin in security checks — such as validating an XPC caller.

Designated Requirement (DR) — a rule about acceptable signatures

A requirement string is a tiny language for expressing "what must be true of a signature." Every signed binary has a default one, and you write your own when validating others:

# "signed by Apple's chain, and the leaf cert's OU is my Team ID"
anchor apple generic and certificate leaf[subject.OU] = "ABC123XYZ9"

# tighter: also require a specific app identifier
identifier "com.corp.agent" and anchor apple generic
  and certificate leaf[subject.OU] = "ABC123XYZ9"

This is the exact string you'd hand to setCodeSigningRequirement when securing an XPC listener, or to SecRequirementCreateWithString when verifying a peer process. Chapter 13 connects the dots.

Timestamps & revocation

  • Secure timestamp (--timestamp) — a trusted third-party record of when you signed. Without it, your app stops validating when the certificate expires. With it, the signature stays valid because it proves you signed while the cert was live. Required for notarization.
  • Revocation — Apple can revoke a Developer ID certificate (e.g. it was used for malware). Revocation kills all apps signed with it, retroactively. This is why certificates are guarded carefully and CI signing keys live in secured keychains.

In the interview

Which certificate signs an app vs a .pkg?

Commit: Developer ID Application signs the app and its binaries; Developer ID Installer signs the .pkg. They're distinct certificates for distinct artifacts, and swapping them is a common cause of signing failures. Both are for distribution outside the App Store.

Nuance: if I were shipping through the Mac App Store I'd instead use Apple Distribution and Mac Installer Distribution, and Apple re-signs the app on delivery. For a fleet agent distributed via MDM or download, it's the Developer ID pair plus notarization.

Why use --timestamp when signing?

Commit: It records a trusted, independent proof of when the signature was made. Without a secure timestamp, the signature becomes invalid once the signing certificate expires; with one, the app keeps validating because the system can see it was signed while the certificate was still valid.

Nuance: it's also mandatory for notarization, so it isn't really optional for anything you distribute. It matters practically for long-lived software like an agent that stays deployed on fleets for years past its build date.

Chapter 05

Entitlements
Capabilities baked into the signature — how macOS knows your app is allowed to do powerful things.
In plain words

An entitlement is a permission your app claims, written into a plist and then sealed inside its code signature. Because it's inside the signature, it can't be added or edited afterwards without invalidating the signature — so the system can trust it.

Why sealing them inside the signature is the whole point

Imagine entitlements were a separate file. Malware could just add "give me Endpoint Security access" to any app's file and gain kernel-level visibility. Instead, entitlements are hashed into the Code Directory (Chapter 3). Change them → the CDHash changes → the signature breaks → macOS refuses to run it. An entitlement is an unforgeable claim, which is why the OS can grant real power based on it.

What they look like

<!-- app.entitlements -->
<dict>
  <key>com.apple.security.app-sandbox</key>               <true/>
  <key>com.apple.security.network.client</key>           <true/>
  <key>com.apple.developer.endpoint-security.client</key><true/>  <!-- restricted! -->
</dict>

The three tiers of entitlement

TierExamplesHow you get it
Freenetwork client, file access, sandboxJust declare them
CapabilityiCloud, push notifications, App GroupsEnable in your developer account; provisioning profile grants them
Restrictedendpoint-security.client, system-extension.installApple must approve you — you request it and justify the use case
The one your JD cares aboutcom.apple.developer.endpoint-security.client is a restricted entitlement — Apple individually approves companies to have it, because it grants visibility into every process launch and file operation on the machine. That approval process is why endpoint security vendors are a small club. Knowing this detail signals real familiarity with the space.

Reading entitlements from a binary

codesign -d --entitlements :- /Applications/MyApp.app

In the interview

What are entitlements and why can't they be forged?

Commit: Entitlements are capabilities an app declares — network access, sandbox membership, Endpoint Security access — and they're sealed inside the code signature. Because they're hashed into the Code Directory, editing them changes the CDHash and invalidates the signature, so the app won't run. That unforgeability is what lets the OS grant genuinely privileged capabilities based on them.

Nuance: some entitlements are free to declare, some require enabling a capability in your developer account, and a few — like the Endpoint Security client entitlement — are restricted and require Apple's explicit approval per developer. So an entitlement is simultaneously a claim by the app and, for restricted ones, an authorization from Apple.

Chapter 06

Hardened Runtime
Opt-in runtime protections. Required for notarization — so effectively mandatory.
In plain words

Hardened Runtime is a flag you enable at signing time that tells macOS to enforce a set of runtime protections on your process — blocking code injection, debugger attachment, and loading unsigned libraries — unless you explicitly declare an exception.

What it actually blocks

ProtectionWhat it prevents
Library validationLoading libraries not signed by you or Apple — blocks dylib hijacking / injection
No DYLD_INSERT_LIBRARIESInjecting code via environment variables
No unsigned executable memoryWriting code into memory and running it (JIT-style attacks)
No debugger attachmentAnother process attaching to and inspecting yours
Resource-access promptsCamera, mic, etc. require declared entitlements

Exceptions — when your app legitimately needs one

Some apps genuinely need these behaviors. You declare an exception as an entitlement, which means it's visible in the signature and Apple sees it at notarization:

<key>com.apple.security.cs.allow-jit</key>                        <true/>
<key>com.apple.security.cs.allow-unsigned-executable-memory</key> <true/>
<key>com.apple.security.cs.disable-library-validation</key>       <true/>
<key>com.apple.security.cs.debugger</key>                         <true/>

Example: a browser or a language runtime needs JIT. A plugin host needs to load third-party libraries, so it disables library validation. Each exception weakens your security, so declare only what you need — and be able to say why in an interview.

Sandbox ≠ Hardened RuntimeThese are different and independent. The App Sandbox restricts what resources your app can reach (files, network, hardware) — it's about containment. The Hardened Runtime protects your process's integrity from tampering and injection. App Store apps must be sandboxed; notarized apps must use Hardened Runtime. An app can have both, either, or (for local dev) neither.

How to enable it

codesign --options runtime --sign "Developer ID Application: Corp (ABC123XYZ9)" MyApp.app
#          ^^^^^^^^^^^^^^^^^ this is what turns on Hardened Runtime

In the interview

What is the Hardened Runtime and how is it different from the sandbox?

Commit: The Hardened Runtime is a set of runtime protections you opt into at signing with --options runtime — it blocks code injection, DYLD_INSERT_LIBRARIES, unsigned executable memory, debugger attachment, and loading unsigned libraries. The sandbox is a different thing: it restricts which resources the app can reach, like files and network. Hardened Runtime protects the process's integrity; the sandbox contains what it can touch.

Nuance: they're independent — you can have one, both, or neither. In practice notarization requires Hardened Runtime, and the App Store requires the sandbox. If my app legitimately needs JIT or third-party plugins, I declare a specific exception entitlement, which Apple sees at notarization, and I'd only add the ones I actually need since each one weakens the protection.

Chapter 07

Signing in practice
The commands, and the one ordering rule that trips everyone up.

The basic command, dissected

codesign --sign "Developer ID Application: Corp (ABC123XYZ9)" \
         --options runtime \                     # enable Hardened Runtime
         --entitlements app.entitlements \       # seal capabilities into signature
         --timestamp \                           # secure timestamp (required to notarize)
         --force \                               # replace any existing signature
         MyApp.app

The ordering rule: sign inside-out

This is the single most common source of "why is my signature invalid?"

Because a bundle's signature includes hashes of everything inside it, you must sign nested items first, then the outer bundle. If you sign the app first and then a framework inside it, you've just changed the app's contents after sealing them — the outer signature is now broken.

 WRONG                              RIGHT (inside-out)
 ─────                              ──────────────────
 sign MyApp.app                     1. sign each embedded framework
 sign frameworks inside it          2. sign each helper / XPC service
 → outer signature broken           3. sign the main executable
                                    4. sign MyApp.app  (seals everything)

codesign --deep exists but Apple discourages it — it applies the same entitlements everywhere and skips nuance. Sign each component explicitly with its own entitlements.

Signing a .pkg — a different tool and a different certificate

# build the component package (payload + scripts)
pkgbuild --root ./payload --identifier com.corp.agent --version 2.4.0 \
         --scripts ./scripts --install-location / Agent.pkg

# wrap into a distribution package
productbuild --distribution Distribution.xml --package-path . Installer.pkg

# sign it with the INSTALLER certificate (not Application!)
productsign --sign "Developer ID Installer: Corp (ABC123XYZ9)" \
            Installer.pkg Installer-signed.pkg
Remember the pairingcodesign + Developer ID Application → apps, binaries, .dmg.
productsign + Developer ID Installer → .pkg installers.

In the interview

In what order do you sign a bundle with embedded frameworks, and why?

Commit: Inside-out: sign the embedded frameworks and helper tools first, then the main executable, then the outer app bundle last. Because the bundle's signature seals hashes of everything inside it, signing a nested item after the outer bundle changes the bundle's contents and invalidates its signature.

Nuance: I avoid codesign --deep even though it looks convenient — Apple discourages it because it applies the same entitlements to every nested component, which is wrong when a helper needs different entitlements than the app. Explicit per-component signing is the correct approach.

Chapter 08

Notarization
Apple scans your signed app for malware and issues a ticket. Not a code review — an automated scan.
In plain words

You upload your signed app to Apple. An automated service scans it for known malware and checks it was signed correctly with Hardened Runtime. If it passes, Apple issues a ticket — a signed record saying "Apple examined this exact build and found nothing malicious."

What notarization is NOT

Beginners assume it's a human review like App Store review. It isn't:

  • Not App Store review. No human looks at your app. No design guidelines, no rejection for UX.
  • Not a security audit. It's an automated scan for known malicious content and misconfiguration.
  • Not a signature. Apple doesn't sign your app; it issues a separate ticket referencing your app's CDHash.

It's fast — typically minutes.

What Apple checks

Malware scanKnown malicious content
Valid Developer ID signatureSigned with a real, unrevoked cert
Hardened Runtime enabledMandatory — fails without it
Secure timestampMandatory
No overly-broad entitlementsSuspicious exception entitlements get flagged

The commands (notarytool — the modern tool)

# One-time: store credentials in the keychain so CI doesn't hold secrets in scripts
xcrun notarytool store-credentials "notary-profile" \
      --apple-id "dev@corp.com" --team-id ABC123XYZ9 --password <app-specific-password>

# Submit and wait for the result
xcrun notarytool submit Installer-signed.pkg \
      --keychain-profile "notary-profile" --wait

# If it fails, get the detailed log — this tells you exactly what's wrong
xcrun notarytool log <submission-id> --keychain-profile "notary-profile"
altool is goneThe old altool notarization workflow is deprecated and no longer accepted. If you see it in a tutorial, it's outdated — notarytool is the current tool, and it's much faster. Mentioning this shows you're current.

What you submit

Notarization accepts a container: a .zip, .dmg, or .pkg. Everything signable inside it must already be signed. Apple examines all nested code.

The ticket is tied to the exact buildThe ticket references your app's CDHash. Change one byte, rebuild, and the CDHash changes — the old ticket no longer applies and you must notarize again. There's no "notarize once, ship forever" for changed builds.

In the interview

What is notarization and how does it differ from code signing?

Commit: Code signing is something I do — it proves who built the app and that it hasn't been altered. Notarization is something Apple does: I upload the signed app, Apple runs an automated malware scan and checks it uses a valid Developer ID and the Hardened Runtime, and if it passes, Apple issues a ticket for that exact build. Signing says who made it; notarization says Apple scanned it.

Nuance: notarization isn't App Store review — no human looks at it, it takes minutes, and Apple doesn't sign my app; the ticket is a separate record keyed to my binary's CDHash. It requires Hardened Runtime and a secure timestamp, which is why those two come earlier in the pipeline.

Notarization fails. How do you debug it?

Commit: I fetch the detailed log with xcrun notarytool log <submission-id>, which lists exactly which files failed and why. The most common causes are a nested binary or framework that wasn't signed, Hardened Runtime not enabled, or a missing secure timestamp.

Nuance: the log points at individual paths inside the bundle, which usually reveals I missed signing a helper tool or an embedded dylib. That connects back to the inside-out signing order — if a nested component is unsigned or signed after the outer bundle, notarization catches it even when local verification looked fine.

Chapter 09

Stapling
A small step with an important reason: offline users.

The problem stapling solves

After notarization, Apple has a ticket for your app on their servers. When a user launches your app, Gatekeeper can ask Apple's servers "is there a ticket for this CDHash?" — but only if the user is online. What if they're not?

The fix

Stapling attaches a copy of the ticket to your app (or dmg/pkg) so it travels with the artifact. Now Gatekeeper finds the ticket locally — no network needed.

xcrun stapler staple Installer-signed.pkg
xcrun stapler validate Installer-signed.pkg   # confirm it worked
 WITHOUT stapling                       WITH stapling
 ────────────────                       ─────────────
 user launches app                      user launches app
   Gatekeeper → asks Apple's servers      Gatekeeper → finds ticket inside the app
   offline? → may fail / warn             works offline. Always.
The one-line reason to stapleSo your app validates even when the user has no internet. It's technically optional (Gatekeeper can check online) but you should always do it — first launches often happen right after install, on flaky networks, or on machines behind restrictive firewalls. For a fleet-deployed agent, offline validation is essential.

In the interview

What is stapling and is it required?

Commit: Stapling attaches the notarization ticket to the app or installer so it ships with the artifact. It's not strictly required — Gatekeeper can query Apple's servers for the ticket at launch — but you should always staple, because otherwise a user who's offline at first launch may see a failure or warning.

Nuance: for software deployed across a fleet, offline first-launch is common — machines behind firewalls, freshly imaged laptops, restricted networks. Stapling makes verification fully local and deterministic, which removes an entire class of "it works on my machine" install failures.

Chapter 10

Gatekeeper & the quarantine flag
The guard at the door. Understand quarantine and Gatekeeper's behavior stops being mysterious.
In plain words

Gatekeeper is the macOS feature that checks, before an app runs for the first time, that it's properly signed and notarized. If it isn't, macOS blocks it and shows the user a warning.

The key that unlocks everything: the quarantine flag

Gatekeeper doesn't check every app on every launch. It checks apps that arrived from the internet. How does it know? The quarantine flag.

When a browser, email client, or messaging app downloads a file, it attaches an extended attribute to it: com.apple.quarantine. This is a marker meaning "this came from outside — treat it with suspicion." Gatekeeper's checks trigger on quarantined files at first launch.

# see the quarantine flag on a downloaded file
xattr -l ~/Downloads/MyApp.app
# com.apple.quarantine: 0081;65f0a1b2;Safari;...

# remove it (for local testing only — never tell users to do this)
xattr -dr com.apple.quarantine ~/Downloads/MyApp.app
This explains the #1 confusing symptom"It runs fine on my machine but users get 'app is damaged and can't be opened'." Your locally-built app has no quarantine flag, so Gatekeeper never checks it. The downloaded copy does have one, so Gatekeeper checks — and finds it unsigned or un-notarized. To reproduce a user's experience, download your own artifact (or set the flag manually) rather than testing the build directory.

What Gatekeeper checks at first launch

  1. Is the file quarantined? (If not, generally no check.)
  2. Is the code signature valid and intact?
  3. Is the signing certificate valid and not revoked?
  4. Is there a valid notarization ticket — stapled locally, or found online?

All pass → the app launches, and macOS removes the quarantine flag so subsequent launches are fast. Any fail → blocked, with a dialog.

The error messages, decoded

User seesActually means
"…is damaged and can't be opened"Usually not corruption — the signature is invalid, or it's not notarized
"…can't be opened because Apple cannot check it for malicious software"Signed but not notarized
"…can't be opened because it is from an unidentified developer"Not signed with a Developer ID at all
"Damaged" almost never means damagedThis misleading message is the most common Gatekeeper confusion. If a user reports it, check signing and notarization — not file corruption. Being able to say this in an interview shows you've actually shipped Mac software.

Related notions worth knowing

  • The user override. A user can right-click → Open, or approve in System Settings → Privacy & Security, to run a blocked app. Newer macOS versions have made this deliberately harder.
  • XProtect — Apple's built-in signature-based malware scanner. It runs independently of Gatekeeper and blocks known-malicious files at launch. Distinct from notarization.
  • spctl --master-disable — turns Gatekeeper off entirely (the "Anywhere" option). Useful in a test VM, never on user machines.

In the interview

What is Gatekeeper and when does it run?

Commit: Gatekeeper is macOS's launch-time check that a downloaded app is validly signed with a Developer ID and has a notarization ticket. It triggers on the first launch of a quarantined file — the com.apple.quarantine extended attribute that browsers and other apps attach to downloads. If the checks pass, the app runs and the flag is cleared; if not, macOS blocks it.

Nuance: this is why an app runs fine locally but fails for users — a locally-built app has no quarantine flag, so Gatekeeper never inspects it. To reproduce a user's experience I download my own artifact or set the flag manually. Gatekeeper is also distinct from XProtect, which is Apple's separate signature-based malware scanner.

A user says your app "is damaged and can't be opened." What's wrong?

Commit: Almost certainly not damage. That message usually means the code signature is invalid or the app isn't notarized, and Gatekeeper is blocking it on first launch because it's quarantined. I'd verify with codesign --verify --deep --strict and spctl -a -vvv on the downloaded copy, and check whether the ticket is stapled with stapler validate.

Nuance: a common root cause is that the artifact was modified after signing — for example, a build script touched a file inside the bundle, or the zip was rebuilt after notarization, which invalidates the seal. The message is misleading; the fix is nearly always in the signing or notarization pipeline, not the file transfer.

Chapter 11

Verifying & debugging
The commands you'll actually type when something breaks. Memorize the first three.

The essential four

# 1. What is this signed with? (identity, Team ID, CDHash)
codesign -dvvv /Applications/MyApp.app

# 2. Is the signature intact and internally consistent?
codesign --verify --deep --strict --verbose=4 /Applications/MyApp.app

# 3. Would GATEKEEPER let it run? (the real user-facing answer)
spctl -a -vvv -t execute /Applications/MyApp.app     # for apps
spctl -a -vvv -t install Installer.pkg               # for pkgs

# 4. Is the notarization ticket stapled?
xcrun stapler validate /Applications/MyApp.app

Reading the output

# codesign -dvvv output, annotated
Identifier=com.corp.agent                ← signing identifier (bundle ID)
TeamIdentifier=ABC123XYZ9                ← your Team ID
CDHash=a1b2c3...                         ← the build's unique fingerprint
Authority=Developer ID Application: Corp ← the leaf certificate
Authority=Developer ID Certification Authority   ← intermediate

A healthy signature shows all three Authority lines (chain to Apple Root), a Timestamp, and a Runtime Version. Missing Timestamp or Runtime Version → notarization will fail.

Other useful checks

codesign -d --entitlements :- MyApp.app     # show entitlements

The debugging orderWork outward: (1) codesign --verify — is the signature itself sound? (2) stapler validate — is the ticket attached? (3) spctl -a -vvv — would Gatekeeper accept it? Each answers a different layer, so whichever fails first tells you which stage of the pipeline broke.

Chapter 12

The full pipeline
Everything assembled. This is the CI script — and the answer to "walk me through shipping a Mac app."
#!/bin/bash
set -e
APP="MyApp.app"
PKG="Installer.pkg"
APP_CERT="Developer ID Application: Corp (ABC123XYZ9)"
INST_CERT="Developer ID Installer: Corp (ABC123XYZ9)"

# ── 1. SIGN, inside-out: nested code first, bundle last ─────────────
for f in "$APP"/Contents/Frameworks/*; do
  codesign --force --options runtime --timestamp --sign "$APP_CERT" "$f"
done
codesign --force --options runtime --timestamp \
         --entitlements helper.entitlements --sign "$APP_CERT" \
         "$APP"/Contents/XPCServices/Helper.xpc          # own entitlements!
codesign --force --options runtime --timestamp \
         --entitlements app.entitlements --sign "$APP_CERT" "$APP"

# ── 2. VERIFY locally before wasting a notarization round-trip ──────
codesign --verify --deep --strict --verbose=4 "$APP"

# ── 3. PACKAGE ──────────────────────────────────────────────────────
pkgbuild --root ./payload --identifier com.corp.agent --version 2.4.0 \
         --scripts ./scripts --install-location / Component.pkg
productbuild --distribution Distribution.xml --package-path . "$PKG"

# ── 4. SIGN THE PKG with the INSTALLER cert ─────────────────────────
productsign --sign "$INST_CERT" "$PKG" "signed-$PKG"

# ── 5. NOTARIZE (blocks until Apple answers) ────────────────────────
xcrun notarytool submit "signed-$PKG" --keychain-profile "notary-profile" --wait

# ── 6. STAPLE the ticket so it validates offline ────────────────────
xcrun stapler staple "signed-$PKG"
xcrun stapler validate "signed-$PKG"

# ── 7. FINAL CHECK: would Gatekeeper accept it? ─────────────────────
spctl -a -vvv -t install "signed-$PKG"
Why the order is forced, not arbitrarySign inside-out (outer seal covers inner contents) → verify locally (cheap, before a slow round-trip) → package → sign the pkg with the installer cert → notarize (needs a signed artifact with Hardened Runtime + timestamp) → staple (needs a ticket to exist) → spctl (the final "would a real user's Mac accept this?"). Each step depends on the one before. Say this dependency chain out loud in an interview and you've demonstrated real understanding, not memorization.

CI considerations

  • Signing certificates live in a dedicated keychain on the build machine; unlock it in the script rather than embedding secrets.
  • notarytool store-credentials keeps the Apple ID and app-specific password out of your scripts.
  • Always run spctl as the last gate — it's the only check that mimics the actual user experience.

Chapter 13

Related: TCC, SIP, and XPC
Where signing connects to the rest of macOS security — the "so what" for an agent engineer.

TCC — a different question again

TCC (Transparency, Consent, and Control) is the privacy layer: the prompts asking "MyApp wants to access your Camera / Full Disk / Screen Recording." It's keyed to your signing identity, which is why re-signing an app can reset its permissions.

Now you can place all four layers cleanly — each answers a distinct question:

LayerThe question
Code signingWho made this, and is it unmodified?
NotarizationDid Apple scan it for malware?
GatekeeperMay it launch on this Mac?
TCCWhat may it access once running?

For fleets, TCC permissions are pre-granted by MDM using PPPC profiles (Privacy Preferences Policy Control), which reference your app's signing requirement — no user prompts. That's how an agent gets Full Disk Access silently on 10,000 Macs.

SIP — System Integrity Protection

Protects system files and processes from modification even by root. Unrelated to your app's signature, but often mentioned alongside — it's why you can't just write into /System.

Where signing meets XPC (the tie-back)

Everything in Chapter 4 about requirement strings pays off here. When your privileged helper validates who's connecting to it, it checks the caller's code signature against a requirement pinning your Team ID:

// macOS 13+: one line, XPC enforces it for you
listener.setCodeSigningRequirement(
    "anchor apple generic and certificate leaf[subject.OU] = \"ABC123XYZ9\"")

And Endpoint Security events carry each process's Team ID, signing ID, and CDHash (Chapter 3), so an agent can make policy decisions like "only allow binaries signed by approved teams."

The insight that ties this document to your workCode signing isn't just a distribution chore — it's the identity system for code on macOS. Every security decision (can this XPC client talk to my root helper? should I allow this process to exec? which app gets Full Disk Access?) is ultimately answered by "what signature does this code carry?" That's why an endpoint engineer needs this material cold.

Chapter 15

Interview question bank
Everything above, as the questions you'll be asked. Commit first, then caveat.
Explain the difference between code signing, notarization, and Gatekeeper.

Commit: They answer three different questions. Code signing is done by me at build time and proves who built the app and that it hasn't been tampered with. Notarization is done by Apple — I upload the signed app, Apple scans it for malware and issues a ticket for that exact build. Gatekeeper runs on the user's Mac at first launch of a downloaded app and verifies both: valid signature, valid notarization ticket.

Nuance: the ordering is forced — signing must precede notarization, notarization requires the Hardened Runtime and a secure timestamp, and you staple the resulting ticket so Gatekeeper can verify offline. People conflate the three, but each is a distinct check performed by a different party at a different time.

Walk me through shipping a signed, notarized Mac app.

Commit: Build, then sign inside-out — embedded frameworks and helpers first with their own entitlements, then the main bundle — using a Developer ID Application certificate with --options runtime and --timestamp. Verify locally with codesign --verify --deep --strict. Package with pkgbuild and productbuild, sign the pkg with the Developer ID Installer cert via productsign. Submit to notarytool and wait, then stapler staple the ticket, and finally confirm with spctl -a -vvv.

Nuance: the order isn't arbitrary — the outer signature seals inner contents so nested code must be signed first; notarization requires an already-signed artifact with Hardened Runtime and a timestamp; stapling needs a ticket to exist. And nothing may touch the artifact after notarization, since any byte change alters the CDHash and orphans the ticket.

What is the quarantine flag and why does it matter?

Commit: It's an extended attribute, com.apple.quarantine, that browsers and other apps attach to files downloaded from the internet. Gatekeeper's checks trigger on quarantined files at first launch — that's how macOS distinguishes something that came from outside from something you built locally.

Nuance: this explains the most common confusion in Mac distribution — an app runs fine on the developer's machine because the local build has no quarantine flag, so Gatekeeper never inspects it, but the downloaded copy is blocked. To reproduce a user's experience I test the actual downloaded artifact, or set the attribute manually with xattr.

Why is the Hardened Runtime required for notarization?

Commit: Because Apple wants notarized software to be resistant to tampering at runtime, not just at install. The Hardened Runtime blocks code injection, DYLD_INSERT_LIBRARIES, unsigned executable memory, and debugger attachment — so a notarized app can't be easily hijacked into running malicious code after Apple scanned it.

Nuance: without it, a scan at notarization time would prove little, since an attacker could inject code into the running process afterwards. If my app legitimately needs one of those behaviors — JIT for a runtime, or loading third-party plugins — I declare a specific exception entitlement, which is sealed into the signature and visible to Apple during notarization.

How would you verify that another running process is trustworthy?

Commit: I'd verify its code signature against a requirement string pinning my Team ID and signing identifier — using its kernel-provided audit token to build a SecCode and calling SecCodeCheckValidity. On macOS 13+ for XPC specifically, setCodeSigningRequirement does this in one line.

Nuance: I never trust the PID, because PIDs are recycled — a malicious process can inherit one I previously trusted. The audit token is kernel-verified and unforgeable. This is the same identity mechanism Endpoint Security uses when it reports each process's Team ID, signing ID, and CDHash, which is what makes code signing the real identity system for code on macOS.

What happens if Apple revokes your Developer ID certificate?

Commit: Every app signed with it stops passing Gatekeeper — retroactively, across all users. Revocation is checked at launch, so previously working apps get blocked. It's the nuclear option Apple uses when a certificate has been used to sign malware.

Nuance: that's why signing certificates and private keys are guarded like production secrets — kept in a locked keychain on a dedicated build machine, never in a repo. It's also an argument for stable, well-controlled CI signing rather than developers signing release builds from their laptops.

What's a CDHash, and why not just identify a binary by its path?

Commit: The CDHash is the hash of the Code Directory — covering the binary's identifier, Team ID, page hashes, and entitlements — so it's an unforgeable fingerprint of one exact build. A path is just a string: anyone can name a malicious binary anything and put it anywhere, so path-based identity is meaningless for security decisions.

Nuance: in an Endpoint Security agent, the CDHash is what I key verdict caches on, because the kernel hands it to me per process and it can't be spoofed. That lets me answer an authorization event from memory within its deadline rather than re-evaluating the signature each time.

The 60-second summary to have ready

"Code signing hashes the app and signs those hashes with my Developer ID private key, sealing in the Team ID and entitlements — that gives integrity and identity, and the CDHash uniquely fingerprints the build. Notarization is Apple's automated malware scan of that signed app; it requires the Hardened Runtime and a secure timestamp, and produces a ticket which I staple to the artifact so it verifies offline. Gatekeeper is the check on the user's Mac at first launch of any file carrying the quarantine flag — it validates the signature, the certificate's revocation status, and the notarization ticket. Signing says who made it, notarization says Apple scanned it, Gatekeeper decides whether it runs."
