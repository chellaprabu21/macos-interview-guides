Why does any of this matter?

Your laptop or server runs a small program called the JumpCloud agent. It talks to JumpCloud's cloud servers constantly — to get policies, run commands, check passwords, and report status.

The cloud needs to answer one critical question every time: "Is this really one of our customer's devices, or is someone pretending?"

Certificates and mTLS are how we answer that question — securely, automatically, without you typing a password every five minutes.

Part 1: HTTPS — the locked envelope

You've seen HTTPS in your browser (the padlock icon). It's the same idea here. When the agent sends data to JumpCloud, the data travels inside an encrypted tunnel so nobody on the network can read or tamper with it.

Think of it like…

Mailing a letter inside a locked box. Only the recipient has the key. Even if someone intercepts the package, they can't read what's inside.

With regular HTTPS (like visiting a website), you check that the website is real (the padlock proves it's really your bank, not a fake site). But the website doesn't check who you are — unless you log in separately.

Part 2: Digital certificates — a device ID card

A digital certificate is like a government-issued ID card, but for computers. It says: "This device is device #ABC123, issued by JumpCloud, valid until next year."

Think of it like…

A company badge. It has your photo (identity), your employee number (unique ID), the company logo (who issued it), and an expiry date. Security at the building entrance checks the badge before letting you in.

Two pieces that always go together

Every certificate comes as a pair:

Private key 🔑
Stays secret on the device forever. Like the PIN for your badge — never shared, never sent over the network. Stored in a protected file on disk.
Certificate (public part) 📇
Can be shown to anyone. Proves the device owns the matching private key. Contains a unique ID (certuuid) and is signed by JumpCloud's authority.
Important

If someone steals your certificate, it's annoying but fixable — you revoke it. If someone steals your private key, they can impersonate your device. That's why the private key never leaves the machine and is stored with strict file permissions.

Deep Dive: How the certificate is created on the device

This section walks through exactly what happens on your machine during first install — no jargon where we can avoid it, but enough detail to understand the mechanics.

Files the agent creates on disk

After setup completes, three security-related files live in the agent config directory (e.g. /opt/jc/ on Linux):

/opt/jc/ (or equivalent)
├── client.key   ← private key (secret, never leaves device)
├── client.crt   ← certificate (public ID card)
└── ca.crt       ← trust bundle (how to verify JumpCloud servers)

The config file jcagent.conf also stores the device's account number (systemKey) and its certificate ID (certuuid) — but the actual cryptographic secrets live in those three files.

What's printed on the certificate?

Think of these as the fields on an ID card:

Common Name (CN)
The device's unique ID — a random certuuid like a3f8b2c1…. This never changes, even when the certificate is renewed.
Organization (O)
Always JumpCloud — who the certificate belongs to.
Issuer
JumpCloud's Certificate Authority (CA) — the "government" that signed the ID.
Valid from / until
Start and expiry dates. After expiry, the agent renews automatically.
Digital signature
Proof that JumpCloud's CA officially issued this card — tampering breaks the signature.

Creation — step by step on the device

  1. 1

    Generate a unique device name (certuuid)

    The agent creates a random UUID (like a serial number) using secure randomness. This becomes the device's permanent identity — its name on the certificate. Example: a3f8b2c1d4e5… (32 hex characters).

  2. 2

    Generate the private key — entirely on the device

    The agent uses cryptography (RSA 2048-bit) to create a key pair. The private key is written to client.key with restricted file permissions (only root/admin can read it).

  3. 3

    Create a Certificate Signing Request (CSR) — "please make me an ID card"

    The agent builds a CSR using the private key. The CSR says: "Please issue a certificate for device ID a3f8b2c1…, organization JumpCloud."

    Crucially: the CSR proves the requester owns the private key (via math), but the private key itself is not included in the CSR.

  4. 4

    Send the CSR to JumpCloud Kickstart (with Connect Key)

    The CSR is uploaded to POST /SignCsr along with the Connect Key (to prove enrollment is authorized). At this point the connection is encrypted (HTTPS) but the device does not yet have a certificate — it's asking for one.

  5. 5

    JumpCloud signs the CSR and returns the certificate

    JumpCloud's CA stamps the CSR as official and returns client.crt. The server also stores the signed cert temporarily (until registration finishes) and checks the certuuid isn't already used by another device.

  6. 6

    Download the trust bundle (ca.crt)

    The agent downloads JumpCloud's CA certificates so it knows which servers to trust. Without this, it couldn't verify it's talking to the real JumpCloud — not an impostor.

The private key never travels over the network. It is born on the device, lives on the device, and dies on the device. JumpCloud never sees it. Only the CSR (the application) and the resulting certificate (the ID card) are exchanged.
CSR explained simply

A CSR is like filling out a form at the DMV: "My name is a3f8b2c1, please print a license." You sign the form with your personal signature (private key math) to prove you're really asking. The DMV (JumpCloud CA) prints the license (certificate) and gives it back. Your signature style (private key) stays with you — it's not printed on the license.

Why keep the same private key forever?

On renewal, JumpCloud issues a new client.crt but keeps the same client.key and same certuuid. This is intentional: the agent uses the private key to encrypt local secrets (like FileVault recovery keys). Changing the key would break access to those stored secrets.

Deep Dive: How the certificate is used for authentication

Once client.crt and client.key exist, every call to JumpCloud uses them automatically. You don't "log in" with the certificate — the agent's HTTP client loads both files and presents them during the TLS connection setup.

The TLS handshake — proving you own the certificate

When the agent connects to agent.jumpcloud.com, this happens before any API data is sent:

Server proves itself. JumpCloud sends its server certificate. The agent checks it against ca.crt — "Is this really JumpCloud, or a fake?"

Server asks for the device's certificate. Because this is mTLS, the server says: "Now show me your ID card."

Agent sends client.crt. The public certificate travels over the wire. Still no private key.

Server sends a random challenge. "Prove you own the private key that matches this certificate."

Agent signs the challenge with client.key. The signature is sent back. This is the cryptographic equivalent of entering your PIN — done in milliseconds, invisibly.

Server verifies the signature. If it matches the certificate → the device truly owns the private key. The encrypted tunnel opens. If not → connection rejected.

Why the challenge matters

Showing the certificate alone isn't enough — anyone could copy the public ID card file. The challenge-response step proves the device still has the matching secret key right now, not just a photocopy of the badge from yesterday.

After TLS — the second identity check

mTLS gets the request through the front door. The application then does one more check to bind the certificate to a specific device record:

  1. A

    Load balancer reads the certificate

    After mTLS succeeds, the load balancer extracts the certificate's Common Name (the certuuid) and forwards it as headers like X-SSL-CLIENT-DN and X-SSL-CLIENT-CN to the application server.

  2. B

    Agent includes its account number

    Every request also carries x-system-id — the systemKey assigned during registration (stored in jcagent.conf).

  3. C

    Server cross-checks in the database

    Query: find system where _id = systemKey AND certuuid = CN from certificate. Match found → request proceeds, policies/commands flow. No match → 401 Unauthorized.

Two locks on the door

Lock 1 (TLS/mTLS): Cryptography proves you physically hold the private key that matches a valid JumpCloud-issued certificate.

Lock 2 (application): The database confirms that certificate ID and account number belong to the same, still-active device.

An attacker needs to defeat both — steal the private key and know the systemKey, and the device must still be registered in JumpCloud.

What the agent code actually does (simplified)

On every API call, the agent's HTTP client:

  • Loads client.crt + client.key into the TLS stack
  • Loads ca.crt as trusted roots (minimum TLS 1.2)
  • Attaches headers: x-system-id, x-ssl-client-cn (certuuid), agent version
  • Opens the connection — TLS handshake + mTLS challenge happen automatically
  • Sends the API payload (JSON) inside the encrypted tunnel

Certificate renewal — same identity, new expiry date

Before the certificate expires, the agent:

  1. 1

    Uses the existing certificate to authenticate

    Renewal goes to the private kickstart server — you must already have a valid cert to get in.

  2. 2

    Creates a new CSR with the same private key and same certuuid

    Same device identity, new application for a fresh expiry date.

  3. 3

    Receives a new client.crt, replaces the old one

    client.key unchanged. certuuid unchanged. systemKey unchanged. Seamless to the user.

Think of it like…

Who checks the ID?

A load balancer (a front-door server) sits in front of JumpCloud's services. It terminates the encrypted connection, inspects the device's certificate, and checks:

  • Was this certificate signed by JumpCloud's Certificate Authority (CA)?
  • Is it still valid (not expired)?
  • Does the unique ID on the certificate match a known device in our database?

Only if all checks pass does the request reach the actual application server.

Part 4: Connect Key vs Certificate — two different keys for two different jobs

This is the part that confuses most people. JumpCloud uses two separate authentication mechanisms, each for a different moment in the device's life.

Connect Key — the "invitation code"
A short-lived secret code (like a one-time invite link) that says "this device is allowed to join organization X." Used only during initial setup — when the agent is first installed. An admin, MDM system, or user portal provides it. Once the device is registered, the Connect Key's job is done.
Certificate — the "permanent badge"
Issued during setup and used forever after (renewed periodically). Every single API call the agent makes for the rest of its life is authenticated with this certificate. No Connect Key needed anymore.
Think of it like…

Getting hired at a company. The Connect Key is your job offer letter — it gets you in the door on day one. The certificate is your employee badge — you swipe it every morning for years. You don't bring your offer letter to work every day.

Part 5: What happens when a device is first installed — the full story

Here's the entire registration process told as a simple story, step by step.

  1. 1

    Someone installs the agent and provides a Connect Key

    An IT admin runs the installer with a key from the Admin Console, or MDM pushes the agent with an auto-generated key, or a user downloads it from the User Portal.

  2. 2

    The agent creates its own secret key (private key)

    Generated locally on the device. Never sent anywhere. This is the "PIN" that will prove ownership of the certificate forever.

  3. 3

    The agent asks JumpCloud to make an ID card (certificate)

    It sends a Certificate Signing Request (CSR) — basically "please issue an ID card for device #XYZ" — along with the Connect Key to prove it's allowed to ask.

  4. 4

    JumpCloud signs and returns the certificate

    JumpCloud's Certificate Authority stamps the ID card as official. The signed certificate is temporarily stored server-side until registration completes (prevents someone from grabbing a cert and never finishing setup).

  5. 5

    The agent tests that its new badge works

    A quick "can I get in the door?" check — the agent connects using its new certificate and Connect Key. If this fails, registration stops here.

  6. 6

    The agent officially registers as a system

    Using its new certificate (mTLS), the agent tells JumpCloud: "I'm device #XYZ, here's my hardware info (hostname, serial number, OS, etc.). Please add me to the organization's device list." JumpCloud creates the device record and sends back a systemKey — the device's permanent account number.

  7. 7

    Done — the Connect Key is retired, the certificate takes over

    From now on, every conversation uses mTLS with the certificate. The device shows up in the Admin Console. Policies start flowing.

Part 6: Every day after registration — how the agent stays authenticated

Once registered, the agent never asks for a Connect Key again. Every time it calls JumpCloud (which is constantly — every few minutes), this happens automatically:

Agent opens an encrypted connection (TLS)

The tunnel is established. Data will be encrypted.

Agent presents its certificate

"Hi, I'm device #XYZ. Here's my signed ID card."

Load balancer verifies the certificate

Signed by JumpCloud CA? Not expired? ✓

Agent also sends its systemKey

"And here's my account number: 507f1f77bcf86cd799439011"

Server cross-checks both pieces

Does account number 507f… belong to a device whose certificate ID is XYZ? If yes → request allowed. If no → rejected (400/401).

Business happens

Policies downloaded, commands executed, metrics sent — all over the encrypted mTLS channel.

Why check both the certificate AND the systemKey?

It's like requiring both your badge (certificate) and typing your employee number (systemKey) at the gate. If someone somehow got a copy of a certificate, they'd also need to know which account number it belongs to. Two pieces of identity are harder to fake than one.

Part 7: Certificate renewal — getting a new badge, keeping the same PIN

Certificates expire (typically after a year or so). Before that happens, the agent automatically renews its certificate. Important details:

  • The private key stays the same — like keeping your PIN when you get a new physical badge
  • The device ID (certuuid) stays the same — same employee number on the new badge
  • Renewal requires the existing certificate — you must already be authenticated to renew
  • Renewal happens over the private kickstart server, which only accepts mTLS connections
Think of it like…

Your company badge expires annually. You go to HR (using your current badge to get in), they print a new one with the same employee number, and you keep using the same PIN. You can't walk in off the street and ask for a badge — you need to already be an employee.

Part 8: Device auth vs User auth — two different questions

mTLS answers: "Which device is this?"
User authentication answers: "Which person is using this device?"

These are completely separate. When you log into your Mac or enter your password at the Windows login screen, a second authentication happens:

  1. A

    Device is already authenticated (mTLS)

    The agent's certificate already proved this is a managed JumpCloud device.

  2. B

    User enters username + password (or MFA)

    The agent sends credentials to JumpCloud over the already-secure mTLS channel.

  3. C

    JumpCloud checks: is this user allowed on this device?

    The user must be "bound" to the system. Random users can't log in even with valid passwords.

  4. D

    Login granted (or denied)

    JumpCloud returns a token; the agent unlocks the session locally.

Think of it like…

Entering a secure office building. The building's security system (mTLS) verifies the building itself is a legitimate JumpCloud-managed site. Then the reception desk (user auth) checks your personal ID and confirms you're on the visitor list for this specific building.

Part 9: What happens when things go wrong?

Device is removed from JumpCloud
The system record is deleted. The next time the agent connects, the server recognizes the device is gone and sends an uninstall command instead of policies. The certificate alone isn't enough — the account must still exist.
Certificate expires without renewal
mTLS handshake fails. The agent can't connect. It will attempt to renew automatically; if that fails too, the agent stops functioning until an admin intervenes.
Agent cloned from a golden image
Two devices can't share the same certificate ID. During registration, JumpCloud checks that the certuuid is unique. A cloned image with a duplicate ID will be rejected.
Someone intercepts network traffic
They see encrypted gibberish (TLS). They can't decrypt it without the keys. They can't impersonate the device without the private key, which never left the machine.
Connect Key is stolen before use
Connect Keys are short-lived and single-purpose. An attacker could potentially register a rogue device if they get the key before the legitimate device does — which is why keys should be treated as secrets and MDM enrollment is preferred over shared keys.

The whole thing in five sentences

  • A Connect Key is a one-time invitation that lets a new device join your organization.
  • During setup, the device creates a private key (secret) and gets a certificate (ID card) signed by JumpCloud.
  • After setup, the Connect Key is retired. The certificate + systemKey authenticate every request forever.
  • mTLS means both the device and server prove their identity before any data is exchanged — inside an encrypted tunnel.
  • User login is a separate step on top: the device must already be trusted before a person's credentials are checked.
