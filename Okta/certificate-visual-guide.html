❌ A certificate is NOT…

A password you type in. A secret key. Something you memorize. Something that alone unlocks the server.

✅ A certificate IS…

A public ID document + a mathematical link to a private key stored separately on the device. Like a driver's license that only works if you also know the PIN.

2. Two linked pieces — only one is secret

Created together on the device. They match like a lock and key. The certificate is the lock (public). The private key is the key (secret).

4b. What is the "random challenge"? (deep dive)

Steps 4–6 of the handshake — what actually happens, in plain language.

The problem we're solving

Sending client.crt only says "I claim to be device XYZ." Anyone could copy that file from another machine. The challenge proves you hold the matching secret key right now — not just a photocopy of the ID.

Simple analogy

A bouncer asks you to sign a random napkin they just handed you. They verify the signature against the sample on your ID card. Copying someone's license doesn't help — you can't forge their handwriting without practice (the private key).

What TLS actually does (inside the handshake)

It's not a separate JumpCloud API call. The "challenge" is built into the TLS protocol itself. Both sides have been exchanging handshake messages; together those messages form a transcript. The server effectively says: sign this transcript hash to prove you own the key.

Key insight: The certificate embeds the public half of the key pair. Only the matching private key can produce a signature the public key will accept. This is one-way math — you can't derive the private key from the certificate.

Step by step — who does what

  1. 4
    Server builds the "challenge"

    During TLS, server and client have exchanged several messages. TLS combines them into one hash — a fixed-length fingerprint unique to this exact conversation. Because it includes random values from both sides, it's different every connection (like a fresh napkin each time).

  2. 5
    Agent signs with the private key

    The agent's TLS stack reads client.key from disk and runs a sign operation: signature = Sign(private_key, hash). The private key never leaves the device — only the signature bytes are sent back. (In TLS 1.3 this is the CertificateVerify message.)

  3. 6
    Server verifies — pass or reject

    The load balancer extracts the public key from the client's certificate and runs: Verify(public_key, hash, signature). If the math checks out → the signer owns the private key paired with that certificate → connection allowed. If not → handshake fails, connection dropped. No API data ever flows.

What if someone only steals the certificate?

❌ Attacker has client.crt only

Can claim the device ID. Cannot produce a valid signature. Verification fails. Connection rejected.

✅ Real device has both files

Has client.crt + client.key. Signs the hash correctly. Verification passes. Tunnel opens.

Why a fresh hash every time?

The transcript includes random numbers from both server and client. An attacker can't replay yesterday's signature — it was for a different hash. Each connection requires a new proof, right now, with the private key.
