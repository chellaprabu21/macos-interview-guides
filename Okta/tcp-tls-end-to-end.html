End to end · DNS → TCP → TLS → data → teardown

What actually happens when you open an https:// URL.

Every layer, in order, with animated packet flows. By the end you should be able to narrate a connection from a cold DNS cache to the encrypted first byte of HTML — and explain what breaks at each step.

01

The whole journey

Five phases. Everything in this document expands one of them.

The complete sequence
Roughly what each phase costs on a typical connection with ~30 ms round-trip time.
The framing that makes this stick

Each layer solves exactly one problem the layer below doesn't. IP can deliver a packet somewhere but may lose, duplicate, or reorder it. TCP turns that into a reliable, ordered byte stream — but in plaintext, to whoever happens to answer. TLS adds confidentiality, integrity, and proof of identity. HTTP then defines what the bytes mean.

02

The layers

Where TLS actually sits, and why that placement matters.

Encapsulation
Your data gets wrapped by each layer on the way down, unwrapped on the way up.
Why TLS sits above TCP

TLS assumes a reliable, ordered byte stream — it needs its records to arrive intact and in sequence, because decryption and integrity checking depend on order. TCP provides exactly that, so TLS doesn't have to reimplement retransmission or sequencing. The cost is layering: a lost TCP packet stalls the TLS stream even if later data has arrived, which is head-of-line blocking.

This is precisely what QUIC changes — it runs over UDP and integrates the transport with the crypto, so a lost packet only blocks its own stream, and connection setup takes fewer round trips. HTTP/3 is HTTP over QUIC.

What an observer sees at each layer

Visible to an eavesdropperHidden by TLS
Your IP and the server's IPThe URL path and query string
Port numbers (443 → it's HTTPS)Headers, cookies, tokens
Packet timing and sizesRequest and response bodies
The hostname, via SNI or DNS (unless ECH/DoH)The certificate itself, in TLS 1.3

Worth knowing: TLS hides content, not metadata. Traffic analysis on sizes and timing can reveal a surprising amount even without decryption.

03

DNS resolution — before any connection exists

You typed a name. TCP needs an address.

The lookup chain

  1. Browser cache → OS cache → hosts file — all local, microseconds.
  2. Recursive resolver (your ISP, or 1.1.1.1 / 8.8.8.8) — if it has the answer cached, you're done in one round trip.
  3. Otherwise the resolver walks the hierarchy: root servers → TLD servers (.com) → authoritative nameserver for the domain.
  4. The answer comes back with a TTL and is cached at every level on the way.
Why it matters operationally

A cold DNS lookup can add 20–100 ms before a single packet reaches the server. TTLs control how long stale answers persist — which is why a DNS-based failover is only as fast as the TTL you set before the incident. And DNS is traditionally unencrypted UDP, so it leaks every hostname you visit; DoH and DoT fix that, and Encrypted Client Hello closes the matching leak in TLS's SNI field.

Modern browsers also run Happy Eyeballs — resolving both A (IPv4) and AAAA (IPv6) records and racing connection attempts, so a broken IPv6 path doesn't stall the page.

04

What TCP gives you

IP delivers packets unreliably. TCP builds a reliable stream on top.

GuaranteeMechanism
DeliveryAcknowledgements plus retransmission on timeout or duplicate ACKs
OrderingSequence numbers; the receiver buffers and reorders
No duplicatesSequence numbers let the receiver discard repeats
Flow controlReceive window — don't overwhelm a slow receiver
Congestion controlCongestion window — don't overwhelm the network
Integrity (weak)16-bit checksum — catches corruption, not tampering
What TCP does NOT give you

No confidentiality — every byte is readable by anyone on the path. No authentication — you're connected to whatever answered at that IP, which may not be who you intended. No real integrity — the checksum catches accidental corruption but an attacker can recompute it trivially. Those three gaps are precisely what TLS fills.

The header fields that matter

FieldPurpose
Source / dest portWhich process on each machine. 443 = HTTPS by convention.
Sequence numberPosition of this segment's first byte in the stream
Ack numberNext byte expected — implicitly acknowledges everything before it
FlagsSYN synchronise · ACK acknowledge · FIN finish · RST reset · PSH push
WindowHow many more bytes the receiver can accept right now

A connection is identified by the four-tuple: source IP, source port, destination IP, destination port. That's why one client can hold many simultaneous connections to the same server — each gets a different source port.

05

The TCP three-way handshake

Before any data flows, both sides must agree they're connected and synchronise sequence numbers.

SYN → SYN-ACK → ACK
Step through it. Watch the connection state change on each side.
Server is listening on port 443. Client has nothing yet.

Why three messages, not two

Each side must know that its own sequence number was received. Message 1 tells the server the client's starting sequence. Message 2 acknowledges it and carries the server's own. Message 3 acknowledges the server's. Two messages would leave the server unsure whether its sequence number arrived.

Sequence numbers are random, and that's a security control

Initial sequence numbers are randomised. If they were predictable, an off-path attacker could forge segments that the receiver would accept as part of an existing connection — TCP sequence prediction, a real historical attack. Randomisation means an attacker must be on-path to inject.

SYN flood — the classic DoS

The server allocates state when it receives a SYN and sends SYN-ACK, then waits. An attacker sends thousands of SYNs from spoofed addresses and never completes the handshake, exhausting the server's half-open connection table. The defence is SYN cookies: the server encodes the connection state into its own sequence number and allocates nothing until the final ACK arrives — which proves the client actually received the SYN-ACK, so the address wasn't spoofed.

The socket API mapping

// Server                          // Client
socket()                           socket()
bind()      // port 443
listen()    // → LISTEN
                                   connect()   // → sends SYN, blocks
accept()    // returns once the
            // handshake completes
// Both now have a connected socket; read()/write() move bytes.
06

Reliability, flow control & congestion

What TCP does continuously once the connection is up.

Retransmission

The sender keeps unacknowledged data buffered. If an ACK doesn't arrive within the retransmission timeout — derived from measured round-trip time plus variance — it resends. It also resends early on three duplicate ACKs (fast retransmit), because repeated ACKs for the same byte mean later segments arrived but one is missing.

Flow control vs congestion control — don't conflate them

Flow controlCongestion control
ProtectsThe receiver from being overwhelmedThe network from being overwhelmed
MechanismReceive window advertised in every ACKCongestion window, inferred from loss and delay
SignalExplicit — the receiver tells youImplicit — you deduce it from packet loss or rising latency

The sender may have in flight only the minimum of the two windows.

Slow start — why the first bytes are slow

A new connection doesn't know the network's capacity, so it starts conservatively (typically 10 segments, about 14 KB) and doubles the congestion window every round trip until it detects loss. That means a fresh connection cannot deliver a large response at full speed immediately — it has to ramp.

The practical consequence

This is why connection reuse matters so much. A warm connection has already discovered the network capacity; a cold one restarts slow start. It's the argument for HTTP keep-alive, connection pooling, and HTTP/2 multiplexing — and why your agent's daemon should hold a warm connection rather than opening one per request.

Head-of-line blocking

Because TCP guarantees ordering, one lost segment stalls delivery of everything behind it — even data that already arrived. With HTTP/2 multiplexing many streams over one TCP connection, a single loss stalls all of them. QUIC solves this by tracking streams independently over UDP.

07

What TLS adds

Three guarantees, layered onto TCP's reliable stream.

GuaranteeMeaningMechanism
ConfidentialityObservers see only ciphertextAES-GCM or ChaCha20-Poly1305 with a session key
IntegrityTampering is detectedAEAD authentication tag on every record
AuthenticationYou're talking to who you thinkX.509 certificate chain signed by a trusted CA
Authentication is the one people undervalue

Encryption without authentication is nearly worthless — you'd have a perfectly private conversation with an attacker. That's why certificate validation is the load-bearing part of TLS, and why "disable certificate checking to make it work" is one of the most damaging things a developer can ship.

The handshake's job, in one line

Prove the server's identity, agree on a shared symmetric key without transmitting it, and negotiate which algorithms to use — all over a channel the attacker can read and modify.

Why both crypto families appear

Asymmetric crypto solves identity and key agreement but is far too slow for bulk data and size-limited. Symmetric is fast and unlimited but can't distribute its own key. So TLS uses asymmetric briefly to authenticate and derive a session key, then symmetric for every byte after. That's hybrid encryption, and it's the entire architecture of the protocol.

08

The TLS 1.3 handshake

One round trip. Step through what's in each flight and when encryption begins.

TLS 1.3 — full handshake
Note the moment the connection goes encrypted: earlier than you might expect.
TCP is established. TLS now negotiates on top of it.

What's inside each flight

MessageContents & purpose
ClientHelloSupported TLS versions, cipher suites, a random nonce, SNI (which hostname — needed because one IP hosts many sites), ALPN (which protocol: h2, http/1.1), and key_share — the client's ephemeral public key, sent optimistically to save a round trip.
ServerHelloChosen version and cipher suite, server random, and the server's key_share. After this message both sides can derive keys — so everything following is encrypted.
{Certificate}The server's certificate chain. Encrypted in TLS 1.3, unlike 1.2 where it was sent in the clear.
{CertificateVerify}A signature over the handshake transcript using the certificate's private key. This is what proves the server actually holds the key, not just a copy of someone's certificate.
{Finished}A MAC over the entire handshake transcript. If any earlier message was tampered with, this check fails — which is what defeats downgrade attacks.
The trick that makes it one round trip

The client guesses which key-exchange group the server will pick and sends its ephemeral public key in the very first message. Usually it guesses right, so the server can immediately compute the shared secret and send its own key share back — key agreement completes in one exchange. If the guess is wrong, the server sends a HelloRetryRequest and you pay an extra round trip. TLS 1.2 always needed two, because key exchange only began after the hellos.

TLS 1.2 vs 1.3 — what changed and why

AspectTLS 1.2TLS 1.3
Round trips21 (0 on resumption)
Key exchangeRSA transport or (EC)DHEEphemeral only — forward secrecy mandatory
Cipher suitesDozens, many weakFive, all AEAD
CertificateSent in plaintextEncrypted
Removed—RC4, 3DES, CBC modes, MD5/SHA-1 signatures, compression, renegotiation
Why static RSA key transport had to go

In old TLS, the client could encrypt a pre-master secret with the server's RSA public key. Simple — but it means anyone who later obtains the server's private key can decrypt every recorded session, retroactively. Removing it makes forward secrecy non-optional, which is the single most important change in TLS 1.3.

0-RTT resumption — and its caveat

On a repeat connection the client can send application data in its very first packet using a pre-shared key from the previous session. Zero round trips. The catch: 0-RTT data is replayable — an attacker can capture and resend it, and the server has no way to tell. So it's only safe for idempotent requests. Naming that trade-off is a strong signal.

09

Certificate validation — the part that actually protects you

Encryption without this is a private conversation with an attacker.

Walking the chain of trust
Step through what the client checks before it will proceed.
The server has presented a certificate chain. The client must decide whether to trust it.
Step 5 is the one people miss

A certificate is public — anyone can download bank.com's certificate. So presenting it proves nothing. CertificateVerify is a signature over the handshake transcript made with the certificate's private key, which only the legitimate server holds. That's what turns "I have a certificate" into "I am the entity this certificate names."

Revocation — the weakest link

MethodProblem
CRLA list of every revoked certificate — large, slow, often stale
OCSPA live query per certificate — adds latency, leaks browsing to the CA, and typically fails open if unreachable
OCSP staplingThe server presents a recent signed status itself — fixes latency and privacy. The practical answer.
Short-lived certsValidity measured in days, so revocation matters less. Increasingly the direction of travel.

Pinning & mTLS

Certificate pinning — trust only a specific certificate or public key rather than any valid chain. It defeats a rogue or compromised CA, which matters for an agent talking to a known backend. The costs are real: rotation must be planned far ahead or you brick clients, and pinning breaks under corporate TLS inspection. Pin an intermediate or include a backup key.

mTLS — the server also requests a client certificate, so both sides authenticate. This is the natural pattern for a device with a hardware-backed key, and the basis of service-to-service auth in zero-trust networks.

10

How the session keys are derived

No key is ever transmitted. Both sides compute the same values independently.

From key shares to traffic keys
The pipeline both sides run in parallel.
  • ECDHE produces a shared secret from the two key shares. Neither side transmits it; both compute it.
  • HKDF expands that into several distinct keys — separate handshake keys and application keys, and separate keys per direction. Using one key everywhere would be a weakness.
  • The derivation mixes in the handshake transcript, so if any handshake message was altered, the two sides derive different keys and the Finished check fails.
  • Key update lets long-lived connections rotate traffic keys without a new handshake.
Why forward secrecy falls out of this

The key shares are ephemeral — generated for this connection and discarded afterwards. The server's certificate private key authenticates the exchange but never encrypts anything. So stealing that long-term key later gives an attacker no way to recover past session keys: the ephemeral keys that produced them no longer exist. Recorded traffic stays unreadable.

11

Sending data over the established connection

What happens to a single HTTP request on its way down and back up the stack.

One request, all the way down and back
Step through the encapsulation and reversal.
The application hands an HTTP request to the TLS layer.

TLS records

TLS doesn't encrypt a byte stream continuously — it splits data into records (up to 16 KB), each independently encrypted with its own nonce and carrying its own authentication tag. A sequence number is mixed into the nonce, which is what prevents an attacker reordering or replaying records even though each is individually valid.

Record boundaries leak information

Sizes and timing are visible even though contents aren't. Traffic analysis on record sizes has been used to infer which page was loaded, or even which characters were typed in an interactive session. TLS 1.3 supports record padding to blunt this, though most deployments don't use it aggressively.

What the application actually experiences

// Everything above is invisible at this level.
let (data, response) = try await URLSession.shared.data(from: url)

// URLSession has already: resolved DNS, opened TCP, completed the
// TLS handshake, validated the certificate chain, and decrypted
// the response — possibly reusing a pooled warm connection.

Which is why the settings that matter are the ones controlling that machinery: timeoutIntervalForRequest, waitsForConnectivity, httpMaximumConnectionsPerHost, and a URLSessionDelegate if you need pinning.

12

Closing the connection

Graceful and abrupt, and why one socket state lingers.

Four-way teardown
TCP connections close in each direction independently.
The client has finished. It closes TLS first, then TCP.

Why close_notify matters

TLS sends an explicit close_notify alert before the TCP close. Without it, a receiver can't distinguish a legitimate end-of-data from an attacker cutting the connection early — a truncation attack, where the attacker removes the tail of a response and you accept the truncated version as complete.

TIME_WAIT — the state everyone asks about

Why it exists

The side that closes first waits 2× the maximum segment lifetime (typically 60 s) before releasing the socket. Two reasons: a delayed duplicate packet from this connection must not be delivered to a new connection reusing the same four-tuple; and if the final ACK is lost, the peer will retransmit its FIN and someone must still be there to answer.

The practical consequence: a server that closes many connections accumulates thousands of sockets in TIME_WAIT and can exhaust its port range. Fixes: let the client close where possible, use connection reuse so you close far less often, and tune SO_REUSEADDR / kernel parameters carefully rather than blindly.

FIN vs RST

  • FIN — graceful. "I have no more data to send," while still able to receive. That's why it's four messages: each direction closes independently.
  • RST — abrupt. "This connection is dead, discard everything." Sent on error, on connecting to a closed port, or when an application aborts. Any buffered data is lost.

Tools worth naming

# Full timing breakdown — DNS, connect, TLS, first byte

     -o /dev/null -s https://example.com

# Packet level — handshakes are visible even when payloads aren't

# macOS: connection states, TIME_WAIT counts
netstat -an | grep 443 | awk '{print $6}' | sort | uniq -c
The debugging instinct to state

"I isolate the layer first. Does DNS resolve? Does TCP connect — refused instantly is a different problem from timing out. Does the TLS handshake complete, and if not, which check failed? Only then do I look at the application. curl's timing breakdown gives me all four boundaries in one command, which usually points straight at the layer before I've opened a packet capture."

14

Interview answers

Two or three sentences each, then depth if invited.

Walk me through what happens when I type an https:// URL and press enter.

The browser resolves the hostname to an IP via DNS — checking local caches first, then a recursive resolver that may walk from root to TLD to authoritative servers. Then TCP's three-way handshake: SYN, SYN-ACK, ACK, which synchronises sequence numbers and establishes a reliable ordered byte stream.

Then the TLS handshake on top. The client sends a ClientHello with supported ciphers, SNI, and an ephemeral key share; the server replies with its chosen cipher, its own key share, and — already encrypted in TLS 1.3 — its certificate, a signature over the transcript, and Finished. The client validates the chain to a trusted root, checks expiry and hostname, and verifies that signature to confirm the server actually holds the private key. Both sides derive the same session keys via ECDHE and HKDF without transmitting them.

From there it's HTTP over symmetric AES-GCM. Roughly three round trips plus DNS to the first byte of HTML.

Why is the TCP handshake three messages rather than two?

Each side needs confirmation that its own sequence number was received. The SYN carries the client's initial sequence; the SYN-ACK acknowledges it and carries the server's; the final ACK acknowledges the server's. With only two messages the server would never know its sequence number arrived. The sequence numbers are randomised, incidentally, because predictable ones historically allowed off-path attackers to inject forged segments.

What does TLS actually give you that TCP doesn't?

Three things. Confidentiality — TCP is entirely plaintext to anyone on the path. Authentication — TCP connects you to whatever answered at that IP, with no proof of identity, whereas TLS validates a certificate chain. And real integrity — TCP's 16-bit checksum catches accidental corruption but an attacker can recompute it, while TLS uses an AEAD authentication tag per record. Of those, authentication is the one people undervalue: encryption without it just means a private conversation with an attacker.

How does TLS 1.3 manage one round trip?

The client guesses which key-exchange group the server will choose and sends its ephemeral public key in the ClientHello. Usually it guesses correctly, so the server can compute the shared secret immediately and send its own key share plus the certificate and Finished in one flight — all encrypted, since keys are derivable after the ServerHello. TLS 1.2 needed two round trips because key exchange only started after the hellos. If the guess is wrong you get a HelloRetryRequest and pay the extra trip.

What is forward secrecy and why did TLS 1.3 mandate it?

Session keys are derived from ephemeral key pairs generated per connection and discarded afterwards, so the server's long-term certificate key authenticates the exchange but never encrypts anything. An attacker who records traffic today and steals that key later still can't decrypt the recordings, because the keys that protected them no longer exist. TLS 1.2 permitted static RSA key transport, where the pre-master secret was encrypted to the server's public key — meaning one stolen key retroactively decrypted every recorded session. Removing that is the most important change in 1.3.

How does certificate validation work?

The client verifies the signature chain from the leaf up through intermediates to a root already in the OS trust store, checks each certificate is within its validity period, checks the hostname matches a SAN entry — CN is legacy — and checks revocation, ideally via OCSP stapling. Then the crucial step people forget: CertificateVerify is a signature over the handshake transcript using the certificate's private key, which proves the server actually holds it rather than just presenting a public certificate anyone could download.

What is TIME_WAIT and why does it exist?

The side that closes first holds the socket for twice the maximum segment lifetime before releasing it. Two reasons: a delayed duplicate from the old connection must not be delivered to a new one reusing the same four-tuple, and if the final ACK is lost the peer retransmits its FIN and someone must still be there to answer. Operationally it means a server that closes many short-lived connections can exhaust its port range, which is an argument for connection reuse and for letting the client close where you can.

What's head-of-line blocking?

TCP guarantees ordered delivery, so a single lost segment stalls everything behind it even though that data already arrived. With HTTP/2 multiplexing many streams over one TCP connection, one loss stalls all of them — you removed application-level blocking but inherited transport-level blocking. QUIC fixes it by running over UDP and tracking streams independently, so a loss only affects its own stream. That's the main motivation for HTTP/3.

How would you debug a TLS handshake failure?

Isolate the layer first — curl with a timing breakdown tells me whether DNS, TCP connect, or TLS is where it stops. If it's TLS, openssl s_client shows the served chain and the exact verification error. The common causes in order: a missing intermediate certificate so the chain can't be built, an expired certificate or a wrong client clock, a hostname not covered by the SAN, no shared cipher because one side is old or the other is hardened, and pinning failures after a rotation. Also worth checking whether a corporate TLS-inspection proxy is in the path, since that breaks pinned clients specifically.

Why is 0-RTT resumption risky?

The client sends application data in its very first packet using a pre-shared key from a previous session, so there's no round trip at all. But that data isn't tied to a fresh handshake exchange, so an attacker who captures it can replay it and the server can't distinguish the replay from the original. It's therefore only safe for idempotent requests — a GET is fine, a POST that transfers money is not. Most implementations restrict which requests may use it.

The compressed version

DNS turns a name into an address. TCP turns unreliable packets into a reliable ordered stream. TLS turns a reliable stream into a private, tamper-evident, authenticated one — using asymmetric crypto briefly to prove identity and agree a key, then symmetric crypto for everything after. HTTP then decides what the bytes mean.
