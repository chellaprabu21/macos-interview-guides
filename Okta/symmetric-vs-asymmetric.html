Symmetric vs asymmetric encryption.

Two families of encryption that solve different problems — and every real system uses both together. This starts with locks and mailboxes, ends with the mathematics and the Apple platform APIs, and animates the flows where seeing the movement makes it click.

01

Why encryption exists

One sentence of setup before any mechanism.

You want to send a message across a channel someone else can observe — a network cable, the air, a disk that might be stolen. Encryption transforms the message so that observing it reveals nothing, and only the intended party can transform it back.

The transformation is done by an algorithm (public, published, scrutinised for decades) parameterised by a key (secret). That split matters:

Kerckhoffs's principle

The security must rest entirely on the key, never on the algorithm being secret. Assume the attacker has your source code, knows the algorithm, and has seen a million encrypted messages. If the system still holds, it's secure. If it only works because nobody knows how it works, it's not encryption — it's obscurity, and it fails the moment someone reverse-engineers your binary.

The two families differ in one respect only: whether the key that locks is the same key that unlocks. Everything else follows from that.

02

Symmetric encryption — one shared key

The intuitive kind. Same key both directions.

The picture

A lockbox with one key, and you and your friend each have an identical copy. You put the message in, lock it, send the box. Your friend unlocks it with their copy. Anyone who intercepts the box sees only a locked box.

Symmetric encryption
Watch the same key do both jobs. Alice locks; Eve sees nothing useful; Bob unlocks.
Alice has a message. Both parties already share an identical key.

What's actually happening

The algorithm takes the plaintext and the key and produces ciphertext through many rounds of substitution and permutation — swapping bytes according to lookup tables, shuffling their positions, and mixing in the key. Reverse the rounds with the same key and you recover the plaintext. AES does this in 10–14 rounds depending on key size.

Its great virtue

Speed. AES is implemented in hardware on every modern CPU (AES-NI instructions), so it runs at gigabytes per second. That's why symmetric encryption carries all the actual data in every real system — your TLS session, your encrypted disk, your database at rest.

03

The two problems symmetric can't solve

Both are structural, not implementation flaws. They're why the second family had to be invented.

Problem 1 — key distribution

Alice and Bob both need the same key. How does it get to both of them? If Alice sends it over the channel, Eve captures it and can read everything. You need a secure channel to establish a secure channel — which is circular.

Historically this was solved by physical means: couriers, code books, meeting in person. That works for embassies. It does not work for a browser connecting to a website it has never contacted before.

Problem 2 — it scales terribly

Every pair of people needs their own key, otherwise everyone can read everyone's messages.

Problem 3 — no identity

A shared key proves nothing about who you're talking to. Anyone holding the key can encrypt and decrypt, so a message that decrypts successfully only tells you it came from someone with the key — which is at least two people, and possibly anyone who stole it.

The summary to say in an interview

"Symmetric encryption has the key-distribution problem — both parties need the same secret and there's no safe way to get it to them over an untrusted channel — plus quadratic key growth and no notion of identity. Asymmetric cryptography exists to solve exactly those three."

04

Asymmetric encryption — a pair of keys

The idea that seems impossible until you see the mechanism.

The picture

A mailbox on a public street with a slot in the top. Anyone can drop a letter in — the slot is public. But only the person with the mailbox key can open it and read what's inside. Dropping in and taking out are different capabilities, requiring different things.

Each person generates a key pair: a public key they publish freely, and a private key they never share with anyone. The two are mathematically linked such that what one key does, only the other can undo — and crucially, knowing the public key doesn't let you compute the private one.

Asymmetric encryption — sending Bob a secret
Bob publishes his public key. Alice uses it to lock. Only Bob's private key opens it — and Eve has the public key too, which doesn't help her at all.
Bob has generated a key pair. His public key can go anywhere; his private key never moves.
What this solved
  • Key distribution — the public key can be shouted from a rooftop. There's nothing secret to transport.
  • Scaling — n people need n key pairs, not n(n−1)/2 shared keys. Linear, not quadratic.
  • Identity — see the next section; this is the part people find surprising.
05

The two superpowers

The same key pair does two completely different jobs depending on which key you start with. This is the most commonly muddled point in cryptography.

Same pair, opposite directions
Toggle between the two uses. Notice which key is used first each time.
Direction 1 of 2 — confidentiality.

Why direction 2 gives you identity

If a message can be un-transformed with Alice's public key, then it must have been transformed with Alice's private key — and only Alice has that. So the message provably came from her. That's a digital signature, and it's the foundation of every certificate, code signature, and authentication token in existence.

In practice you sign a hash, not the message

Asymmetric operations are slow and size-limited, so real signing hashes the message first (producing a fixed-size digest) and signs that. Verification re-hashes the received message and checks it matches. Same guarantee, vastly more efficient — and it works on a 4 GB file just as well as on a sentence.

The mnemonic that keeps them straight

Encrypt with the key you can give away. Sign with the key you keep.

Or: lock the box with the recipient's public key; stamp the seal with your own private key.

06

The mathematics — why this actually works

You don't need to derive RSA in an interview, but understanding why the asymmetry exists separates real comprehension from analogy.

The core requirement: a one-way function with a trapdoor

Asymmetric cryptography needs an operation that is easy in one direction and infeasible in reverse — unless you know a secret piece of information (the trapdoor), which makes the reverse easy again. The public key describes the forward operation; the private key is the trapdoor.

Trapdoor 1 — factoring (RSA)

  • Easy: multiply two large primes. p × q = n. A computer does this instantly, even for 1024-bit primes.
  • Infeasible: given only n, recover p and q. For a 2048-bit n, no known classical algorithm does this in reasonable time.
  • The trapdoor: knowing p and q lets you compute the private exponent. The public key is derived from n; the private key needs the factors.

Try it intuitively: 391 — what are its factors? You'd have to search. (17 × 23.) Now imagine that number with 617 digits.

Trapdoor 2 — discrete logarithm (Diffie-Hellman, ECC)

  • Easy: compute g^a mod p — even for enormous exponents, via repeated squaring.
  • Infeasible: given g, p, and g^a mod p, find a. The modular arithmetic destroys the ordering that would let you search efficiently.

The reason ordering matters: without mod p, larger exponents give larger results, so you could binary search. The modulus wraps values around unpredictably, so the output tells you nothing about the size of the input.

Elliptic curves — the same idea, better geometry

ECC uses points on a curve like y² = x³ + ax + b with a defined "addition" operation on points. Adding a point to itself k times is easy; recovering k from the result is the elliptic-curve discrete logarithm problem, and it's much harder per bit than the classical version.

Why that matters practically

Because the underlying problem is harder, you need far smaller keys for equivalent security:

Security levelRSA keyECC key
~112-bit2048-bit224-bit
~128-bit3072-bit256-bit
~256-bit15360-bit512-bit

Smaller keys mean less storage, less bandwidth, and far less computation — which is exactly why constrained hardware like the Secure Enclave uses P-256 and doesn't support RSA at all.

Why symmetric needs no trapdoor

AES doesn't rely on a hard mathematical problem. It relies on confusion and diffusion — each output bit depends on many input bits and key bits in a way that's statistically indistinguishable from random. There's no clever shortcut to attack; the only known approach is trying every key, and 2^128 keys is beyond physical possibility. That's also why symmetric crypto is far less threatened by quantum computers: there's no structure for Shor's algorithm to exploit.

The RSA size limit — a real constraint

RSA can only encrypt data smaller than its modulus — a 2048-bit key encrypts at most about 256 bytes, less with padding. So you literally cannot encrypt a file with RSA. This isn't just a performance preference; it's a hard limit, and it's one of the concrete reasons hybrid encryption exists.

08

Modes of operation — and why ECB fails

A block cipher encrypts one fixed-size block. The mode defines how you handle a longer message — and the choice is where real implementations break.

ModeHowVerdict
ECBEach block encrypted independentlyNever use. Identical plaintext blocks produce identical ciphertext, so structure leaks straight through.
CBCEach block XORed with the previous ciphertext; needs an IVWorkable but fragile — padding-oracle attacks, and no integrity on its own.
CTRTurns the block cipher into a stream cipherFine, parallelisable, but no integrity and nonce reuse is catastrophic.
GCMCTR plus an authentication tagThe default. AEAD — confidentiality and integrity in one primitive.
Why ECB leaks — the famous demonstration

Encrypt an image of a penguin with AES-ECB and you can still see the penguin. Every white pixel block encrypts to the same ciphertext block, every black block to another — so the pattern survives perfectly even though every individual value is scrambled. The encryption is mathematically sound; the mode destroys it. This is the clearest illustration that a correct algorithm used wrongly gives no security.

The answer to "how would you encrypt data?"

"AES-256-GCM, with a unique nonce per message that is never reused under the same key. GCM is authenticated encryption, so I get integrity along with confidentiality rather than bolting on a MAC and risking the composition order. Nonce reuse with GCM is catastrophic — it leaks the authentication key and enables forgery — so nonce generation is part of the design, not an afterthought. And I'd use the platform implementation rather than my own."

09

Diffie-Hellman — agreeing a secret in public

A third thing asymmetric maths gives you: two parties derive a shared secret over a fully monitored channel, without ever transmitting it.

The paint analogy

Alice and Bob publicly agree on a common colour (yellow) — Eve sees it. Each privately picks a secret colour and mixes it with the yellow. They swap mixtures publicly — Eve sees both. Each then adds their own secret colour to the other's mixture, and both arrive at the same final colour. Eve has both mixtures and the yellow, but separating a mixture back into components is prohibitively hard, so she can't reach the final colour.

The numbers above are toy-sized so you can verify them by hand. Real Diffie-Hellman uses a prime p of 2048+ bits, or elliptic curve points, where recovering the private exponent is infeasible.

Forward secrecy — the reason this matters so much

Use a fresh, ephemeral key pair for every session (ECDHE) and discard it afterwards. Then an attacker who records your encrypted traffic today and steals the server's long-term private key a year later still cannot decrypt those recordings — the keys that protected them no longer exist anywhere. That's forward secrecy, and it's why TLS 1.3 made ephemeral key exchange mandatory and removed static RSA key transport entirely.

The critical weakness — always volunteer this

Raw Diffie-Hellman is completely vulnerable to man-in-the-middle. It establishes a shared secret with someone, but proves nothing about who — an attacker can run DH separately with each party and relay between them. That's exactly why DH is always paired with authentication: a certificate signature proving the server is who it claims. Key agreement and identity are separate problems.

10

Hybrid encryption — how real systems work

Neither family is used alone. This is the synthesis, and it's what TLS does every time you load a page.

The insight

Asymmetric solves key distribution and identity but is slow and size-limited. Symmetric is fast and handles any amount of data but can't distribute its own key. So use asymmetric briefly to establish a symmetric key, then use symmetric for everything else. Best of both, and the reason "which is better?" is the wrong question.

Key wrapping — the related pattern

The same idea applied to data at rest. Encrypt the data with a random symmetric data key, then encrypt that small key with a key-encryption key held in hardware. Rotating the outer key means re-wrapping a few bytes rather than re-encrypting terabytes. This is exactly how disk encryption and cloud KMS work — and it's a strong thing to mention when asked how you'd encrypt data at rest.

Choosing between them

The comparison table, and the decision rules.

SymmetricAsymmetric
KeysOne shared secretPublic + private pair
SpeedVery fast — hardware accelerated100–1000× slower
Data sizeUnlimitedLimited — RSA can't exceed its modulus
Key distributionThe hard problemSolved — publish the public key
Key count for n partiesn(n−1)/2 — quadraticn pairs — linear
Identity / authenticationNo — anyone with the keyYes — via signatures
Non-repudiationNoYes
Quantum resistanceGood — double the key sizeBroken by Shor's algorithm
Typical useBulk data, disk, sessionsKey exchange, signatures, certificates

Decision rules

  • Bulk data? → symmetric (AES-GCM). Always.
  • Parties who've never met? → asymmetric to bootstrap, then symmetric.
  • Need to prove who sent it? → asymmetric signature. Symmetric cannot do this.
  • Both parties equally trusted and a secure channel already exists? → symmetric alone is fine and simpler.
  • Data at rest with a hardware-protected key? → symmetric data key, wrapped by an asymmetric or hardware key.
Post-quantum, in one paragraph

Shor's algorithm on a large enough quantum computer breaks RSA and ECC, because factoring and discrete logs are exactly what quantum computers do well. Symmetric crypto is far less affected — Grover's algorithm roughly halves the effective key length, so AES-256 remains comfortable. NIST has standardised post-quantum algorithms (ML-KEM for key encapsulation, ML-DSA for signatures), and current practice is hybrid deployment — classical plus post-quantum together — because of "harvest now, decrypt later." Not urgent for short-lived session data; genuinely relevant for anything that must stay confidential for a decade.

On Apple platforms

Where this becomes code you'd actually ship.

CryptoKit — both families

import CryptoKit

// ─── SYMMETRIC — bulk data ───────────────────────────────
let key = SymmetricKey(size: .bits256)
let sealed = try AES.GCM.seal(plaintext, using: key)   // nonce auto-generated
let opened = try AES.GCM.open(sealed, using: key)

// ─── ASYMMETRIC — signing (identity) ─────────────────────
let signingKey = P256.Signing.PrivateKey()
let signature  = try signingKey.signature(for: data)
let ok = signingKey.publicKey.isValidSignature(signature, for: data)

// ─── ASYMMETRIC — key agreement (ECDH) ───────────────────
let myKey  = P256.KeyAgreement.PrivateKey()
let shared = try myKey.sharedSecretFromKeyAgreement(with: theirPublicKey)

// ─── THE HANDOVER — derive a symmetric key from the agreement
let sessionKey = shared.hkdfDerivedSymmetricKey(
    using: SHA256.self, salt: salt, sharedInfo: Data(), outputByteCount: 32)
// From here on: AES.GCM with sessionKey. That's hybrid encryption.
Why CryptoKit over CommonCrypto

CryptoKit deliberately doesn't expose ECB or unauthenticated modes — the unsafe options aren't reachable. That's API design as a security control, and it's a good thing to say: "I prefer CryptoKit precisely because you can't easily make the classic mistakes."

The Secure Enclave — asymmetric with hardware backing

// A P-256 private key that NEVER leaves the hardware
let access = SecAccessControlCreateWithFlags(
    nil,
    kSecAttrAccessibleWhenUnlockedThisDeviceOnly,
    [.privateKeyUsage, .userPresence],          // biometric gate
    nil)!

let attrs: [String: Any] = [
    kSecAttrKeyType as String:      kSecAttrKeyTypeECSECPrimeRandom,
    kSecAttrKeySizeInBits as String: 256,
    kSecAttrTokenID as String:      kSecAttrTokenIDSecureEnclave,
    kSecPrivateKeyAttrs as String: [
        kSecAttrIsPermanent as String:   true,
        kSecAttrAccessControl as String: access
    ]
]
let key = SecKeyCreateRandomKey(attrs as CFDictionary, &error)!
// You can ask it to sign. You can never read it. Not even as root.
Why the Enclave is asymmetric-only, and why that's the point

The SEP supports P-256, not RSA — elliptic curves give equivalent security with far less computation and storage, which suits constrained hardware. And it's asymmetric by design: the private key stays inside and only signs or agrees, while the public key goes out into the world. That asymmetry is exactly what makes a credential device-bound — there is nothing extractable to steal.

This is the same primitive underneath FIDO2 platform authenticators and MDM device attestation: a hardware-held private key signing an origin-bound or server-issued challenge.

13

Interview answers

Two or three sentences each, then depth if invited.

Explain the difference between symmetric and asymmetric encryption.

Symmetric uses one shared key for both encryption and decryption — it's fast and handles unlimited data, but it has the key-distribution problem: both parties need the same secret and there's no safe way to send it over an untrusted channel. It also scales quadratically and proves nothing about identity.

Asymmetric uses a mathematically linked key pair. Encrypt with someone's public key and only their private key can decrypt — that gives confidentiality. Sign with your private key and anyone can verify with your public key — that gives authenticity and non-repudiation. It solves distribution and identity, but it's orders of magnitude slower and size-limited.

So real systems use both: asymmetric briefly to authenticate and agree on a session key, then symmetric for the actual data. That's exactly what TLS does.

Which key encrypts and which decrypts?

Depends on the goal. For confidentiality, encrypt with the recipient's public key so only their private key opens it. For authenticity, sign with your own private key so anyone with your public key can verify it came from you. The mnemonic: encrypt with the key you can give away, sign with the key you keep.

Why not just use asymmetric for everything?

Two reasons, and the second is a hard limit rather than a preference. It's 100 to 1000 times slower, so encrypting a video stream with RSA is impractical. And RSA can only encrypt data smaller than its modulus — a 2048-bit key handles about 256 bytes — so you literally cannot encrypt a file with it. Hence hybrid: asymmetric to establish the key, symmetric to move the data.

How would you encrypt data at rest?

AES-256-GCM with a unique nonce per message, never reused under the same key — GCM gives integrity as well as confidentiality, so I'm not composing a cipher and a MAC by hand and risking the order. The interesting question is key management rather than the cipher: I'd use a random data key for the content and wrap it with a key-encryption key held in hardware — on Apple platforms a Secure Enclave key. Rotating then means re-wrapping a few bytes instead of re-encrypting everything.

Explain Diffie-Hellman.

It lets two parties derive a shared secret over a completely public channel without ever transmitting it, based on the discrete logarithm problem — the exchanged values are cheap to compute forward and infeasible to reverse. ECDH is the elliptic-curve version used today, and the ephemeral variant gives forward secrecy, so recorded traffic stays safe even if the long-term key later leaks. The crucial caveat is that raw DH is entirely vulnerable to man-in-the-middle — it establishes a secret with someone but proves nothing about who — which is why it's always paired with certificate-based authentication.

Why does the Secure Enclave use elliptic curves rather than RSA?

Equivalent security with far smaller keys — a 256-bit ECC key is roughly a 3072-bit RSA key — which means much less computation, storage, and power. That suits a constrained coprocessor. More importantly the asymmetric model is what makes the credential device-bound: the private key is generated inside and never leaves, so it can only sign or perform key agreement, and there's nothing extractable for an attacker to steal even with root. That's the primitive underneath FIDO2 platform authenticators and device attestation.

What's AEAD and why does it matter?

Authenticated Encryption with Associated Data — it encrypts the payload and authenticates it in one primitive, plus authenticates additional unencrypted context like headers. It matters because encryption alone gives confidentiality but not integrity: with CBC, an attacker can flip bits in the ciphertext and produce predictable changes in the plaintext. Composing a separate MAC works but the order matters (encrypt-then-MAC), and people get it wrong. AES-GCM and ChaCha20-Poly1305 make the question disappear.

What breaks under quantum computing?

Asymmetric takes the hit. Shor's algorithm efficiently solves factoring and discrete logarithms, which is exactly what RSA and ECC rest on. Symmetric is much safer — Grover's algorithm roughly halves the effective key length, so AES-256 stays comfortable. NIST has standardised post-quantum algorithms and current practice is hybrid deployment, classical plus post-quantum, because of harvest-now-decrypt-later. It's not urgent for short-lived session keys; it matters for anything needing decade-long confidentiality.

The one-sentence version

If you remember nothing else: symmetric is fast but can't distribute its own key; asymmetric solves distribution and identity but is slow and size-limited; every real system uses asymmetric to bootstrap symmetric.
