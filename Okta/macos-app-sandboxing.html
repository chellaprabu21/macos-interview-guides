App Sandbox · entitlements · TCC · SIP · hardened runtime

macOS sandboxing, and the layers around it.

Sandboxing is one of five distinct protection systems on macOS that people routinely conflate. This builds the App Sandbox from first principles, then separates it cleanly from TCC, SIP, the hardened runtime, and code signing — and shows how a security agent lives inside all of them.

01 / ★

The problem it solves

Start with why the default behaviour of an operating system is dangerous.

The traditional Unix model

Classic Unix permissions are based on who you are. If you're user chella, every process you run has full access to everything chella can reach.

a text editor you downloadedcan read your SSH keys · your browser cookies · your Documents · your Keychain items · and can talk to any network host
Nothing about being a text editor limits what it may do.

This made sense on a multi-user timesharing system in 1975, where the threat was other users. It makes no sense today, where the threat is the software you yourself installed — because it inherits all your authority the moment you run it.

The core mismatch

Unix asks "who is running this?" The question you actually need answered is "what should this particular program be allowed to do?"

A calculator and a backup tool run as the same user, but should clearly have wildly different powers. Unix has no way to express that difference.

The principle being applied

Least privilege: every program gets the minimum access needed for its job, and nothing more. Then a compromise of that program is contained — an attacker who exploits your text editor gets a text editor's powers, not your entire account.

Sandboxing is macOS's mechanism for expressing and enforcing that.

02

What the App Sandbox actually is

A precise definition, and what it's not.

Definition

The App Sandbox is a kernel-enforced restriction on what a process may do — which files it can open, whether it can use the network, whether it can access hardware — applied at process launch based on the app's declared entitlements.

Two properties that matter

  • Deny by default. Once sandboxed, the process starts with almost nothing. Every capability must be explicitly requested. This is the inverse of Unix, where you start with everything your user has.
  • Kernel-enforced. It isn't a library the app links or a policy it agrees to follow. The check happens in the kernel, below the app. A compromised app cannot decide to opt out — the restriction is applied to it, not by it.

What a sandboxed app loses by default

CapabilityDefault state
Read/write arbitrary filesDenied — only its own container
Outgoing network connectionsDenied
Incoming connections (act as a server)Denied
Camera, microphoneDenied
Contacts, Calendar, PhotosDenied
USB, Bluetooth, printingDenied
Launching other processesHeavily restricted
Inspecting other processesDenied
Its own container directoryAllowed — this is all you start with
What it is NOT
  • Not a VM or a container. The process runs natively on the same kernel; only its permitted operations are narrowed.
  • Not the same as TCC. TCC is the consent dialogs. Different system — see §08.
  • Not SIP. SIP protects the OS from root. Different system — see §09.
  • Not mandatory outside the App Store. Directly-distributed apps may choose not to sandbox.
  • Not protection against a root attacker who can modify the system itself.
03

How it works underneath

Enough mechanism to reason about it, without needing kernel source.

The enforcement point

macOS has a kernel subsystem called the Mandatory Access Control framework (MACF), inherited from TrustedBSD. It places hooks at security-relevant kernel operations — opening a file, creating a socket, sending a Mach message — where a policy module can approve or deny.

1 · app calls open("/Users/chella/.ssh/id_rsa")
↓
2 · kernel begins handling the syscall
↓
3 · MACF hook consults the sandbox policy for this process
↓
4 · not permitted → syscall returns EPERMthe app sees an ordinary "operation not permitted" error
The app can't distinguish a sandbox denial from a normal permission error — which is deliberate.

Where the policy comes from

At launch, the system reads the app's code signature, which contains its entitlements. If com.apple.security.app-sandbox is present, the kernel applies a sandbox profile derived from the full entitlement set. That profile is attached to the process for its entire lifetime.

Two consequences worth knowing

Entitlements are signed. They live inside the code signature, so editing them invalidates the signature and the app won't launch. You cannot grant yourself capabilities by editing a plist.

The sandbox is inherited and can only tighten. Child processes inherit the parent's restrictions. A sandboxed process cannot spawn an unsandboxed helper to do its dirty work — that would defeat the entire mechanism.

Profiles

Underneath, sandbox policies are written in a Scheme-like language (you can see Apple's own in /System/Library/Sandbox/Profiles/). Third-party apps don't write these directly — your entitlements select and parameterise a profile. Knowing they exist explains why the model is more expressive than the entitlement list suggests.

04 / ★

Entitlements

The vocabulary of capabilities. This is the part you'd actually work with.

An entitlement is a key-value pair embedded in the code signature. Some grant capabilities; others assert identity or opt into behaviours.

<?xml version="1.0" encoding="UTF-8"?>
<plist version="1.0">
<dict>
    <!-- Turn the sandbox on -->
    <key>com.apple.security.app-sandbox</key>
    <true/>

    <!-- Then request back only what you need -->
    <key>com.apple.security.network.client</key>
    <true/>

    <key>com.apple.security.files.user-selected.read-write</key>
    <true/>
</dict>
</plist>

The common ones

EntitlementGrants
network.clientOutgoing connections
network.serverListening for incoming connections
files.user-selected.read-writeAccess to files the user picks in an open panel — see §06
files.downloads.read-writeThe Downloads folder
files.bookmarks.app-scopePersisting access across launches
device.camera / device.microphoneHardware — still subject to TCC consent on top
personal-information.locationLocation services
printPrinting
application-groupsA shared container between your own apps

Three categories — the distinction matters

ordinaryyou just declare them · network, files, printing · no approval needed
provisioned / capabilitytied to your developer account · push notifications, iCloud, app groups
restrictedApple must explicitly grant them to your team · Endpoint Security, Network Extension, DriverKit
Restricted entitlements are how Apple gates powerful capabilities to vetted vendors.
Why this matters in your world

com.apple.developer.endpoint-security.client is a restricted entitlement. You apply to Apple, they assess your use case, and only then can your System Extension observe process and file events fleet-wide. That gate is deliberate — an ES client sees essentially everything happening on the machine, so Apple controls who can build one. Being able to explain that shows you understand the platform's trust model, not just its API.

The temptation to resist

com.apple.security.temporary-exception.* entitlements exist to ease migration — broad file access, arbitrary Mach lookups. They are called temporary for a reason: App Review scrutinises them heavily, they widen your attack surface, and they signal that the app hasn't been designed for the sandbox. Treat any temporary exception as technical debt with a deadline.

05

The container

Where a sandboxed app actually lives.

Every sandboxed app gets a private directory, keyed by its bundle identifier:

~/Library/Containers/com.example.MyApp/Data/
    ├── Documents/
    ├── Library/
    │   ├── Preferences/
    │   ├── Caches/
    │   └── Application Support/
    ├── Desktop  → symlink into the container, NOT the real Desktop
    └── Downloads → also redirected
The redirection that surprises people

Inside the sandbox, NSHomeDirectory() returns the container path, not /Users/chella. Standard paths like ~/Documents silently resolve inside the container.

This is why an app that worked fine unsandboxed suddenly "can't find its files" after sandboxing — it's looking in the right place by name, but that name now points somewhere else. Nothing failed; the namespace moved.

What this buys you

  • Isolation — apps can't read each other's data by default
  • Clean uninstall — delete the container, the app's data is genuinely gone
  • Containment — a compromised app's file access is bounded to its own data

App groups — controlled sharing

When your app and its extension genuinely need shared storage, an app group creates a container both can reach:

<key>com.apple.security.application-groups</key>
<array><string>TEAMID.com.example.shared</string></array>

// → ~/Library/Group Containers/TEAMID.com.example.shared/

The group identifier is prefixed with your Team ID, so only your own signed code can join. It's sharing with a boundary, not a hole.

06

Powerbox & security-scoped bookmarks

How a sandboxed app opens a file outside its container — the elegant part of the design.

The problem

A text editor must be able to open ~/Documents/notes.txt. But it can't be granted access to ~/Documents, because that would let it read everything there without the user knowing.

The solution — Powerbox

When you show an NSOpenPanel, the panel isn't drawn by your app. It's drawn by a separate trusted system process (Powerbox), outside your sandbox. Your app cannot see or manipulate it.

1app calls NSOpenPanel — the request goes to Powerbox
↓
2Powerbox draws the dialog · the app can't read it or preselect anything
↓
3user picks notes.txt — a deliberate human act
↓
4kernel extends the app's sandbox to allow that one file
The user's choice IS the permission grant. No dialog was needed, because opening a file already means "I want this app to have it."
Why this design is genuinely good

The user grants access by doing the thing they already wanted to do. There's no separate consent dialog to click through mindlessly, and the grant is precisely scoped to one file. Compare with a system that asks "allow access to Documents?" — the user says yes and the app gets everything, forever.

This is a good example to cite if you're ever asked about designing security UX: the best consent is the one embedded in an action the user was taking anyway.

Security-scoped bookmarks — persisting access

That grant disappears when the app quits. To reopen a recent file next launch, you need a security-scoped bookmark — an opaque token encoding both the file's location and the permission.

// Save: after the user picks a file
let bookmark = try url.bookmarkData(
    options: .withSecurityScope,
    includingResourceValuesForKeys: nil,
    relativeTo: nil)
UserDefaults.standard.set(bookmark, forKey: "lastFile")

// Restore: on next launch
var stale = false
let url = try URL(resolvingBookmarkData: data,
                  options: .withSecurityScope,
                  relativeTo: nil,
                  bookmarkDataIsStale: &stale)

guard url.startAccessingSecurityScopedResource() else { return }
defer { url.stopAccessingSecurityScopedResource() }   // ← always pair these
let contents = try String(contentsOf: url)
The bug people hit

Forgetting stopAccessingSecurityScopedResource() leaks a kernel resource, and there's a hard limit. Enough leaks and all subsequent access fails, usually long after the leak, making it painful to diagnose. Always pair with defer.

The five layers — separated

These get conflated constantly. Getting them straight is the single most useful thing here.

SystemProtectsFromControlled by
Code signingCode integrityTampering, unknown originDeveloper certificate
App SandboxThe rest of the systemThe app itselfEntitlements, at launch
TCCThe user's private dataAny app, sandboxed or notThe user, via consent dialogs
SIPThe operating systemrootApple; disabled only in recoveryOS
Hardened runtimeThe app's own processInjection, debugging, patchingOpt-in at signing
The distinction that clears up most confusion

The sandbox protects the system from the app. TCC protects the user from the app. SIP protects the OS from root. The hardened runtime protects the app from other processes.

Four different directions of protection. They're independent and they compose — an operation must pass all applicable layers.

How they stack for one operation

An app tries to read ~/Documents/report.pdf:

1 · code signingis this app validly signed and unmodified?
↓
2 · sandboxdoes the entitlement set permit this path?
↓
3 · TCChas the user consented to Documents access for this app?
↓
4 · Unix permissionsdoes the file mode allow it?
↓
allowedonly if every layer said yes
Any single "no" denies. This is defence in depth made concrete.
08

TCC — the consent system

Transparency, Consent, and Control. The dialogs everyone recognises, and the system people most often mistake for sandboxing.

What it is

TCC governs access to the user's private data and sensitive hardware, and it applies to every app — sandboxed or not. That last point is the key difference: sandboxing is something an app opts into; TCC applies regardless.

TCC-protectedExample
Camera, microphone, screen recordingVideo call apps
Contacts, Calendar, Reminders, PhotosPersonal data stores
Desktop, Documents, DownloadsEven unsandboxed apps are gated on these
Full Disk AccessBackup and security tools
AccessibilityControlling other apps — a very powerful grant
Input MonitoringReading keystrokes globally
Location

How it works

  • Decisions are stored in a TCC database, keyed on the app's code signature, not its path — so replacing the binary invalidates the grant, which prevents an attacker swapping in malicious code to inherit permissions.
  • The prompt string comes from your Info.plist (NSCameraUsageDescription and friends). Omit it and the app crashes on first access rather than showing an empty dialog.
  • The TCC database itself is protected by SIP, so even root can't simply grant itself permissions by editing it.
  • Users manage grants in System Settings → Privacy & Security.
The sandbox / TCC relationship

They're independent and both apply. A sandboxed app needs the camera entitlement (sandbox) and user consent (TCC). An unsandboxed app needs no entitlement but still needs consent.

So: entitlements are what the developer declares; TCC is what the user decides. That one sentence separates them permanently.

Enterprise nuance

Some TCC grants can be pre-approved by MDM via a Privacy Preferences Policy Control profile — which is how a security agent gets Full Disk Access on 50,000 Macs without asking every user. It requires supervised devices and only works for specific services. This is a practical detail worth knowing if fleet deployment comes up.

09

SIP — System Integrity Protection

Sometimes called "rootless." A different problem entirely.

The insight behind it

Historically, root could do anything — including modifying the operating system itself. So any root compromise was total and often permanent: malware could patch system binaries, install a rootkit, and survive reinstallation of applications.

SIP's premise: even root should not be able to modify the OS. Protection is enforced by the kernel based on file and process attributes, not on user identity.

What SIP protects

  • Filesystem: /System, /usr (except /usr/local), /bin, /sbin, and Apple-shipped apps — read-only even to root. On modern macOS the system volume is additionally a signed, sealed snapshot, cryptographically verified at boot.
  • Runtime: Apple system processes can't be attached to with a debugger or have code injected, even by root.
  • Kernel extensions: must be signed and approved.
  • Certain data: including the TCC database.

The comparison that fixes it in your head

SandboxSIP
ProtectsThe system from an appThe system from root
ScopeOne processSystem-wide
Opt-in?Yes, by the developerNo — always on unless disabled in recoveryOS
Can root bypass it?Root isn't sandboxed to begin withNo — that's the entire point
Disabling it

csrutil disable only works from recoveryOS, which requires physical presence and the user's credentials. Malware running on a booted system cannot turn SIP off. That physical-presence requirement is what makes the guarantee meaningful.

10

Hardened runtime & notarization

The last two layers, and the ones most often confused with sandboxing.

Hardened runtime — protecting the app from others

Every layer so far restricts what the app can do to the system. The hardened runtime is the opposite direction: it protects your process from other processes.

ProtectionBlocks
No DYLD_INSERT_LIBRARIESLibrary injection at launch
No unsigned executable memoryRuntime code patching
Not debuggable by defaultAttaching a debugger to inspect or modify your process
Validates linked librariesLoading a substituted framework

Exceptions exist as entitlements — com.apple.security.cs.allow-jit for JavaScript engines, disable-library-validation for plugin hosts — each widening the surface, so each needs justification.

Notarization

You upload your signed app to Apple, which scans it for known malware and issues a ticket. Gatekeeper checks that ticket on first launch. It is not App Review — no human evaluates your app — but it does mean Apple can revoke the ticket if the software is later found malicious, which effectively kills it across every Mac.

The hardened runtime is a prerequisite for notarization, which is why these two are usually mentioned together.

The five-layer summary sentence

"Code signing proves who wrote it and that it's unmodified. Notarization proves Apple scanned it. The hardened runtime protects the process from injection. The sandbox limits what the process can do. TCC gates the user's private data. And SIP protects the OS from root. Six mechanisms, six distinct jobs."

11 / ★ YOUR GROUND

Security agents and the sandbox

How a product like yours lives inside all of this — and where the interesting design decisions are.

The tension

A security agent needs to see everything — process launches, file writes, network flows — which is precisely what sandboxing exists to prevent. Apple's resolution isn't an exemption; it's a different, more tightly controlled path: System Extensions with restricted entitlements.

The component split

ComponentSandboxed?Notes
Main app (UI, settings)Usually yesLargest attack surface, parses untrusted input, needs no privilege
System Extension (ES / Network)Yes — a dedicated profileSandboxed and holds restricted entitlements. Not an escape hatch.
LaunchDaemon (root)Typically notRuns as root; often needs Full Disk Access via TCC
LaunchAgent (per user)VariesUser-context work, notifications
XPC helpersYesSandboxing individual helpers is a strong pattern
The design principle to state

"I design around trust boundaries first, then decide what code goes where. The UI is large and parses untrusted input, so it gets no privilege and stays sandboxed. The daemon has root, so it stays small and boring with a narrow XPC interface — the client requests, the daemon decides. The System Extension holds a restricted entitlement, so it does one job and nothing else. The architecture limits what a compromise can reach, rather than relying on the code being bug-free."

Sandboxing your own helpers — a strong pattern

Even outside the App Store, you can sandbox individual components. The parser that reads untrusted policy files, the component that handles network responses — these can run in a tightly sandboxed XPC service with no network, no file access beyond what's passed in, and no ability to spawn processes. A parsing bug then becomes a contained crash rather than a foothold.

That's applying the sandbox as a design tool rather than an App Store requirement, and it's a genuinely senior thing to describe.

The deployment reality

A security agent needs: a restricted entitlement approved by Apple, a System Extension the user or MDM approves, TCC grants (often Full Disk Access), and notarization. Every one of those is a place a fleet deployment can stall — which is why MDM pre-approval of extensions and PPPC profiles matters so much at scale. That operational detail is worth mentioning; it's what separates shipping from prototyping.

The trade-offs

Sandboxing isn't free, and having a view on the costs reads as experience.

BenefitCost
A compromise is containedLegitimate features become harder or impossible
Clear, auditable capability declarationEvery capability needs justification and often review
Users can see what an app may doExtra consent friction, which some users click through blindly
Required for App Store distributionSome app categories simply can't be sandboxed
Forces least-privilege designRetrofitting an existing app is genuinely painful
Clean uninstall, isolated dataFile paths change; migration code needed

What can't reasonably be sandboxed

  • Developer tools that compile and run arbitrary code
  • System utilities — disk tools, cleaners, backup software needing whole-disk access
  • Automation tools that drive other applications
  • Virtualisation software
  • Anything requiring kernel-adjacent access beyond the System Extension model

These distribute outside the App Store, and rely on notarization plus the hardened runtime plus TCC instead — which is a coherent alternative posture rather than an absence of security.

The balanced position

"Sandboxing is the right default for most applications — least privilege genuinely limits blast radius, and it forces you to be explicit about what the app needs. But it's a poor fit for tools whose purpose is broad system access, and forcing it there produces either a crippled product or a pile of temporary exceptions that defeat the point. The honest answer is that macOS supports two postures — sandboxed App Store apps, and notarized hardened-runtime apps gated by TCC — and choosing the right one is a design decision, not a compliance checkbox."

Debugging sandbox denials

Practical, and a good thing to be able to describe.

The symptom

Denials surface as ordinary errors — EPERM, "file not found", a socket that won't connect — with nothing saying "the sandbox blocked this." That's deliberate, and it makes the first encounter confusing.

The tools

# Watch sandbox denials live
log stream --predicate 'subsystem == "com.apple.sandbox" AND
                        eventMessage CONTAINS "deny"'

# Historical denials
log show --last 10m --predicate 'eventMessage CONTAINS "Sandbox"'

# What entitlements does this binary actually have?
codesign -d --entitlements :- /Applications/MyApp.app

# Full signature detail — team ID, flags, runtime version
codesign -dvvv /Applications/MyApp.app

# Is it notarized and will Gatekeeper accept it?
spctl -a -vvv /Applications/MyApp.app

# Reset TCC grants for testing (per-service or all for a bundle)
tccutil reset All com.example.MyApp

A denial in the log looks roughly like:

Sandbox: MyApp(1234) deny(1) file-read-data /Users/chella/Documents/x.txt

Which tells you the process, the operation class (file-read-data, network-outbound, mach-lookup), and the target — enough to identify the missing entitlement.

The common causes, in order
  1. Path assumptions — hardcoded ~/Documents now resolves into the container
  2. Missing entitlement — most often network.client, forgotten because it worked unsandboxed
  3. Bookmark not started — you have the bookmark but forgot startAccessingSecurityScopedResource()
  4. Leaked scoped resources — hit the limit, and everything fails later with no obvious cause
  5. Mach service lookup — talking to an XPC service you haven't declared
  6. TCC, not the sandbox — the entitlement is present but the user hasn't consented. Check both.
14

macOS vs iOS

Same underlying technology, very different posture — and the difference is instructive.

iOSmacOS
SandboxingMandatory for every appRequired for App Store; optional otherwise
DistributionApp Store (plus enterprise/regional alternatives)App Store or direct download
Filesystem visibilityEssentially none outside the containerFull filesystem exists and is navigable
Root accessNot availableAvailable to the user
System extensionsTightly limited extension pointsSystem Extensions, DriverKit, and more
Why the difference exists

iOS was designed sandboxed from day one, with no legacy of unrestricted apps. macOS has forty years of software that assumes full filesystem access, and remains a general-purpose development machine — you must be able to compile and run arbitrary code, which is fundamentally incompatible with mandatory sandboxing.

So Apple's macOS strategy has been to strengthen the other layers — notarization, hardened runtime, TCC, SIP, the signed system volume — for the large population of apps that can't be sandboxed. The direction of travel is clear: each release tightens the unsandboxed path.

Interview answers

Two or three sentences each, then depth if invited.

What is the macOS App Sandbox?

A kernel-enforced restriction on what a process may do — file access, networking, hardware — applied at launch based on entitlements embedded in the app's code signature. It's deny-by-default: a sandboxed app starts with access to essentially nothing beyond its own container, and every capability must be explicitly requested.

The point is least privilege. Traditional Unix permissions ask "who is running this," so any app you run inherits all your authority. The sandbox asks "what should this program be allowed to do," which is the question that actually matters when the threat is software you installed yourself.

Sandbox vs TCC vs SIP?

Different directions of protection. The sandbox protects the system from the app, based on entitlements the developer declares. TCC protects the user's private data from any app — sandboxed or not — based on consent the user gives. SIP protects the operating system from root, and can only be disabled from recoveryOS with physical access.

They're independent and compose: a sandboxed app wanting camera access needs the entitlement and the user's TCC consent. Entitlements are what the developer declares; TCC is what the user decides.

How does a sandboxed app open a file outside its container?

Through Powerbox. The open panel is drawn by a separate trusted system process outside the app's sandbox, so the app can't read or manipulate it. When the user picks a file, the kernel extends the sandbox to allow that specific file — the user's choice is the permission grant.

To keep that access across launches you store a security-scoped bookmark and call startAccessingSecurityScopedResource, always paired with a defer'd stop — leaking those hits a kernel limit and causes failures much later that are painful to trace.

Worth adding

It's a nice piece of security UX: no separate dialog to click through, and the grant is scoped to one file rather than a whole folder.

Why can't a security agent just be sandboxed normally?

Because it needs exactly what sandboxing exists to prevent — visibility into process launches, file writes, and network flows across the whole system. Apple's answer isn't an exemption but a separate controlled path: System Extensions with restricted entitlements like com.apple.developer.endpoint-security.client, which Apple grants only after reviewing your use case.

The extension is still sandboxed, just with a profile matching its job. In practice a real agent splits across components — a sandboxed UI with no privilege, a small root daemon, and the extension — with XPC between them, so each piece holds only what it needs.

What's the hardened runtime and how is it different?

Opposite direction from the sandbox. The sandbox limits what your app can do to the system; the hardened runtime protects your process from other processes — blocking library injection, unsigned executable memory, and debugger attachment. It's a prerequisite for notarization, which is why the two come up together.

Exceptions exist as entitlements — allow-JIT for a JavaScript engine, disable-library-validation for a plugin host — and each one widens your attack surface, so each needs a reason.

How would you debug a sandbox denial?

Stream the unified log filtered on the sandbox subsystem — denials show the process, the operation class like file-read-data or network-outbound, and the target path, which usually identifies the missing entitlement directly. Then codesign -d --entitlements to check what the binary actually has, since a build-configuration mistake is common.

The trap is that denials surface as ordinary errors — EPERM or "file not found" — with nothing indicating the sandbox. And I'd check whether it's actually TCC rather than the sandbox: the entitlement can be present while the user simply hasn't consented.

What are the downsides of sandboxing?

Some legitimate functionality becomes impossible — developer tools, disk utilities, automation software genuinely can't be sandboxed, and forcing it produces either a crippled product or a pile of temporary-exception entitlements that defeat the point. Retrofitting an existing app is painful, mainly because container path redirection breaks assumptions everywhere.

The balanced view is that macOS supports two coherent postures: sandboxed App Store apps, and notarized hardened-runtime apps gated by TCC. Choosing between them is a design decision rather than a compliance checkbox.
