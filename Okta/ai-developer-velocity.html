AI for developer velocity — what actually works.

Not a tools list. This is about where engineering time genuinely goes, which of it AI can compress, how you'd know whether it worked, and the failure modes that make teams slower. Section 11 connects it to security, which is where your two worlds meet.

01 / ★

What "velocity" actually means

Get this wrong and every subsequent decision optimises the wrong thing.

The trap

Velocity is not lines of code, commits, or PRs merged. AI can inflate all three enormously while making the organisation slower — more code to review, more surface to maintain, more subtle bugs to chase later. Output is not throughput.

The definition worth using

Velocity is how quickly a validated idea reaches production safely. That's a pipeline, and AI can compress some stages far more than others:

understandthe problem
and the code
→
writethe change
→
verifytests, review
→
shipCI, rollout
→
operatedebug, respond
Most tooling targets "write" — which is often the shortest stage.
The counter-intuitive point

For a senior engineer on a mature codebase, typing was never the bottleneck. Understanding the system, deciding what to change, and getting it reviewed dominate. So a tool that doubles typing speed moves a small fraction of the total — while a tool that halves the time to understand an unfamiliar subsystem moves a much larger one. That's why the highest-leverage uses are often comprehension and review, not generation.

The framing to open with

Say this

"I'd start by asking what's actually slow. On most teams it isn't typing — it's understanding unfamiliar code, waiting for review, debugging production issues, and the long tail of migrations nobody wants to do. AI helps unevenly across those, and the mistake is optimising the visible stage rather than the slow one."

The two rows to emphasise

03

Technique 1 — inline assistance

The baseline. Real gains, but the smallest of the techniques here.

What it covers

  • Completion — multi-line suggestions as you type
  • Transform selection — "extract this into a function," "convert to async/await," "add error handling"
  • Explain this — what does this regex / this bit-twiddling / this legacy function do
  • Inline chat — questions scoped to the file you're in

Where it genuinely helps

StrongWeak
Boilerplate — Codable conformances, protocol stubs, mock objectsNovel algorithms with subtle invariants
Repetitive patterns the file already establishesAnything requiring cross-file architectural context
Unfamiliar API syntax you'd otherwise look upSecurity-sensitive code where a plausible-looking mistake is costly
Test fixtures and parameterised casesConcurrency — a suggestion can look right and race
The honest assessment

Published studies show real but modest gains, concentrated in less experienced developers and unfamiliar territory. For a Staff engineer in a codebase they know well, inline completion is a convenience, not a transformation. Saying that plainly is more credible than quoting a vendor's percentage.

The hidden cost

Review load shifts, it doesn't disappear. Generated code still has to be read, understood, and owned. A developer who accepts suggestions without fully understanding them has moved work from writing to debugging — and debugging is more expensive. The discipline is: if I couldn't have written it, I shouldn't merge it.

04

Technique 2 — agentic workflows

The bigger shift: the model reads the repo, runs commands, iterates on failures.

What changes

Inline assistance operates on the file you're looking at. An agent operates on the repository — it can search, read many files, run the build, run tests, read the failures, and try again. That closes a feedback loop, which is qualitatively different from generating text.

1 · exploresearch the repo, read relevant files, build a picture
2 · planpropose an approach — reviewable before code exists
3 · implementmake the change across files
4 · verifyrun build and tests, read failures, iterate
5 · presenta diff with reasoning, for human review
Step 4 is what makes this different — the agent can tell whether it was wrong.

Where it works best

high value
Well-specified, verifiable

Bug with a failing test · dependency upgrade · mechanical migration · adding a case to an existing pattern. The success criterion is machine-checkable.

moderate
Bounded features

A new endpoint following existing conventions. Works when the codebase has strong patterns to imitate.

low value
Design-heavy or novel

Architecture, security-critical logic, performance work needing profiling judgment. The bottleneck is deciding, not typing.

The principle that predicts success

Agentic work succeeds in proportion to how machine-verifiable "done" is. A failing test is a perfect specification — the agent knows when it's finished. "Make this faster" or "improve the architecture" has no such signal, and that's exactly where results get unreliable.

A useful consequence: investing in your test suite is investing in AI leverage. Teams with strong tests get far more from agents than teams without, which is a nice argument for something you wanted anyway.

The practical patterns

  • Plan first, then execute — review the approach before any code is written. Catching a wrong direction at the plan stage costs a minute; catching it in a 40-file diff costs an hour.
  • Small scoped tasks beat large vague ones. "Add rate limiting to this endpoint following the pattern in X" works; "improve our API" doesn't.
  • Parallel exploration — run several approaches to a hard problem and compare, which is cheap in a way it never was with humans.
  • Sandboxed execution — agents that run commands need a container, not your laptop with production credentials in the environment.
05 / ★

Technique 3 — context engineering

The highest-leverage and least-discussed technique. It's the difference between a generic assistant and one that knows your system.

The core insight

Model quality is roughly the same for everyone. Context quality is not. The organisations getting real value are the ones that invested in making their conventions, architecture, and institutional knowledge available to the model — not the ones with a better subscription.

The layers of context

LayerWhat it provides
Repo conventions fileA committed document stating architecture, patterns, "we use X not Y," testing approach, and the things reviewers always ask for. Cheapest, highest-return investment available.
Codebase indexingSemantic search so the model finds relevant code rather than guessing from filenames
Internal docs & ADRsWhy decisions were made — the context that's otherwise only in senior engineers' heads
Issue & PR historyWhat's been tried, what broke, what got reverted and why
Runtime signalsLogs, traces, metrics — essential for debugging assistance to be grounded rather than speculative
Internal tool accessVia MCP or equivalent: issue tracker, CI, observability, feature flags — so the model can look things up rather than assume
The single best investment

A conventions file in the repo. It costs an afternoon, applies to every interaction afterwards, and encodes exactly the things reviewers repeat: "use the injected clock, never Date()," "logic goes in the core package, not the daemon," "every new dependency needs an ADR." That's institutional knowledge made machine-readable — and it improves human onboarding at the same time.

The subtle failure — context rot

Stale context is worse than none, because it's confidently wrong. A conventions file describing an architecture you migrated away from will actively steer people wrong. Treat it as code: review it in PRs, and update it when the pattern changes. Otherwise it decays exactly like documentation always has.

06

Technique 4 — review and quality gates

Often the highest-leverage place to apply AI, because review latency is frequently the biggest single delay.

The problem with human review

Review serves two purposes that get tangled: catching mistakes and transferring design judgment. The first is mechanical and repetitive; the second is why senior engineers should be in the loop. In practice the first crowds out the second — reviewers spend attention on naming, missing tests, and style, then rubber-stamp the architecture because they're tired.

beforeauthor waits hours or days · reviewer spends effort on trivia · design discussion happens last, if at all
↓
afterautomated pass catches trivia immediately · author fixes before a human looks · human attention goes to design
The win is reallocating human attention, not replacing the human.

What automated review does well

  • Convention adherence — the things your team says every time
  • Missing test coverage for new branches
  • Error paths unhandled, force-unwraps, ignored return values
  • Security patterns — string concatenation into queries, disabled certificate validation, secrets in code
  • Consistency with adjacent code the reviewer might not have open
  • PR summarisation for large diffs, so the reviewer starts oriented

What it doesn't do

  • Judge whether the approach is right
  • Know the organisational context — the deprecation coming next quarter
  • Weigh trade-offs that depend on business priorities
  • Notice the thing that isn't in the diff but should be
The failure mode to design against

Noisy automated review destroys itself. If half the comments are irrelevant, developers learn to dismiss all of them — including the one real finding. Precision matters far more than recall here. Start with a narrow, high-confidence rule set and expand only when the signal-to-noise holds.

07

Technique 5 — tests, migrations & debt

The least glamorous applications, and probably the highest actual return.

Tests — the strongest use case

Test writing is well-specified, repetitive, verifiable, and chronically under-done because it's tedious. That combination is close to ideal.

  • Characterisation tests for legacy code — generate tests capturing current behaviour before refactoring, which is exactly the work nobody does and everybody needs.
  • Edge-case enumeration — "what am I not testing?" is a question models are genuinely good at.
  • Parameterised cases from a description of the input space.
  • Test data and fixtures, including realistic malformed inputs.
The caveat

A generated test that asserts current behaviour locks in bugs as well as intent. Characterisation tests are for detecting change, not for validating correctness — and someone has to review whether the captured behaviour is actually desirable. Say that distinction; it shows you've thought past the demo.

Migrations — mechanical and endless

The work that's individually trivial and collectively enormous: a deprecated API across 400 call sites, Objective-C to Swift, XCTest to Swift Testing, completion handlers to async/await, a logging framework swap.

Historically you either wrote a script (brittle, edge cases everywhere) or did it by hand over months. Agentic tooling handles the long tail of "this call site is slightly different" that defeats mechanical rewriting — which is precisely why these migrations stall.

The debt this unlocks

WorkWhy it never happened before
Test coverage on legacy modulesNobody wants to spend a sprint on it
Deprecated API cleanupIndividually trivial, collectively weeks
Consistent error handlingTouches everything, benefits nothing visibly
Documentation refreshStale the moment it's written
Dependency upgradesBoring until it's a CVE
The reframe worth offering

"The most interesting effect isn't doing existing work faster — it's that work which was never economically viable becomes viable. Nobody was going to spend three weeks adding characterisation tests to a legacy module. If that becomes two days, it happens, and the compounding benefit is larger than the direct time saved."

Technique 6 — beyond writing code

Several of these have better return than code generation and get discussed far less.

ApplicationWhy it works
Codebase comprehension"How does authentication flow through this system?" Onboarding to an unfamiliar 200k-line codebase is a genuine multi-week cost, and this compresses it substantially.
Incident triageCorrelate logs, traces and recent deploys; generate hypotheses ranked by plausibility. During an incident the bottleneck is where to look, and breadth is exactly what a model offers.
Failure-mode brainstorming"What could go wrong with this design?" Not authoritative, but excellent at surfacing the case nobody in the room considered.
Threat modelling assistanceWalk STRIDE across a data-flow diagram. Structured, checklist-driven, and usually skipped for lack of time.
Flaky-test diagnosisCorrelate failures across runs to find the shared factor — tedious pattern-matching humans do badly.
Build & CI diagnosisObscure linker and toolchain errors have known causes buried in forums. High-frustration, low-skill work.
Commit and PR summariesBetter change descriptions with no author effort, which improves review speed and archaeology later.
Log and error analysis at scaleClustering and summarising crash reports across a fleet — directly relevant to your world.
The one to lead with

Codebase comprehension. It's the largest hidden cost in mature organisations, it's what makes engineers slow in their first months on a team, and it's the stage where a model's ability to read enormous amounts of code quickly is a genuine structural advantage rather than a marginal speedup.

Measuring whether it worked

The question that separates a serious programme from enthusiasm — and the one he's most likely to have opinions about.

Metrics that mislead
MetricWhy it's wrong
Lines of codeMore code is a liability, not an achievement
Suggestion acceptance rateMeasures the tool's agreeableness, not value delivered
PRs mergedSmaller PRs inflate it with no change in output
Self-reported time savedSystematically overestimated; people remember the wins
Tool usage / seats activeAdoption isn't impact

Metrics worth tracking

MetricWhat it captures
Cycle time (first commit → production)The end-to-end pipeline, which is what velocity actually means
Review latencyOften the largest single delay; direct target of §06
Change failure rateThe guardrail. If speed rises and this rises with it, you've bought nothing.
Time to restoreWhether AI-assisted debugging is real
Time to first meaningful PR for new joinersThe clearest signal that comprehension assistance works
Test coverage trendWhether the "unlocked debt work" is actually happening
Escaped defect rateThe slow-moving quality signal that matters most
The framing that will land

"I'd measure with DORA-style outcome metrics, always paired: cycle time and review latency for speed, change failure rate and escaped defects as the guardrail. Speed without the guardrail is meaningless — you can always ship faster by testing less. And I'd be sceptical of self-reported time saved; people remember the win and forget the twenty minutes debugging a plausible-looking suggestion."

The honest measurement problem

Attribution is genuinely hard. Cycle time moves for many reasons — team changes, project mix, seasonality. A clean A/B is impractical and arguably unethical if you believe the tool helps. So the realistic approach is directional metrics plus qualitative signal, and being honest that you're building a case rather than proving causation. Saying that is more credible than claiming a precise percentage.

How it goes wrong

Naming the failure modes is what makes you sound like someone who's done this rather than read about it.

FailureMechanismMitigation
Review debtGeneration outpaces review capacity; PRs get rubber-stampedCap PR size; automated pre-review; treat review as the real constraint
Plausible-but-wrongOutput looks idiomatic and is subtly incorrect — harder to spot than obviously broken codeVerification loops; strong tests; the "could I have written this?" rule
Comprehension decayNobody understands the code they shipped; debugging later is far more expensiveOwnership norms — you merge it, you own it, you can explain it
Convention driftGenerated code follows generic patterns, not yours; codebase fragmentsConventions file; automated review on adherence
Context rotStale guidance actively misleadsVersion the context; review it in PRs
Over-applicationUsed for design and architecture where judgment is the pointExplicit norms about where it's appropriate
Skill atrophyJuniors don't build debugging intuition because they never struggleDeliberate practice; encourage understanding before accepting
Security regressionsGenerated code reproduces insecure patterns from training dataSee §11 — this is the one your background speaks to
The one to name first

Review becomes the bottleneck. If you double code production and review capacity is unchanged, you haven't sped up delivery — you've built a queue, and queues degrade quality because reviewers under load approve rather than engage. Any serious velocity programme has to address review capacity at the same time as generation, or it makes things worse.

11 / ★ YOUR GROUND

The security angle

Where your Endpoint AI Governance work and his velocity work genuinely meet — and the most valuable thing you can contribute to this conversation.

The risks, concretely

RiskDetail
Insecure patterns reproducedTrained on public code, which contains a lot of string-concatenated SQL, disabled certificate validation, and weak crypto defaults. Plausible-looking and wrong.
Secrets leaving the boundaryDevelopers paste config, logs, and credentials into prompts. This is a data-exfiltration path that didn't exist before.
Proprietary code in promptsWhere does it go, is it retained, is it used for training? A real procurement question, not a theoretical one.
Prompt injection via repo contentAn agent reading files can encounter instructions embedded in a README, a dependency, or an issue comment. Untrusted content becoming instructions is a genuine new attack surface.
Hallucinated dependenciesA model suggests a package that doesn't exist; an attacker registers that name. Slopsquatting — a supply-chain attack created by the tooling itself.
Agent permissionsAn agent that runs commands has whatever access the developer has. On a machine with production credentials, that's a very large blast radius.
Licence contaminationGenerated code resembling GPL sources in a proprietary product
The one that's genuinely new

Prompt injection through repository content. An agent that reads files, issues, and dependency documentation is processing untrusted input as potential instructions. A malicious dependency's README could contain text directing the agent to exfiltrate environment variables or modify unrelated code. This is a novel attack surface with no mature defence, and naming it demonstrates you're thinking about the system rather than the feature.

Governance that doesn't destroy the benefit

  • Sandboxed execution — agents run in containers with scoped credentials, never on a laptop holding production access.
  • Secrets scanning on prompts, not just on commits — the leak happens earlier now.
  • Dependency verification — every suggested package checked against a registry before install, which kills slopsquatting.
  • Security-focused automated review on all code, with generated code getting no lighter treatment.
  • Data-residency clarity — enterprise agreements about retention and training, documented for audit.
  • Audit trail — what the agent read, what it ran, what it changed. Non-negotiable for a security product's codebase.
  • Human approval for irreversible actions — an agent may propose a migration; a human runs it against production.
The framing that positions you

"My team works on endpoint AI governance, so I see this from the other side: the same properties that make agents useful — reading broadly, executing commands, acting autonomously — are exactly the properties that make them a governance problem. An agent with repo access and shell execution has a blast radius comparable to a compromised developer account, and the industry is deploying them faster than it's instrumenting them.

The two questions I'd want answered before scaling: what can it reach, and what does it leave behind. Sandboxing bounds the first, audit trails address the second. Neither slows anyone down, and without them you can't answer an auditor asking who changed what."

Why this is your best contribution to the conversation

He's optimising for velocity. You bring the governance perspective he needs but may not have prioritised — and you bring it as an enabler rather than a blocker. That's a peer contribution, and it's genuinely your domain rather than something you've read up on.

Discussing it with him

His stated current focus. Aim for a real exchange rather than a survey of tools.

The question to lead with

"You mentioned you're working on developer velocity through AI — what's actually worked, and where has it disappointed? I'm curious partly because my team does endpoint AI governance, so I see the risk side, and partly because I'd expect the wins to be in less obvious places than code generation."

It's his current focus, it invites a genuine answer including the disappointments, and it flags your relevant experience without claiming his.

Positions worth having

  1. Velocity isn't typing speed. "For a senior engineer on a mature codebase, understanding the system and waiting for review dominate. So the leverage is in comprehension and review, not autocomplete."
  2. Verifiability predicts success. "Agentic work succeeds in proportion to how machine-checkable 'done' is. A failing test is a perfect spec. 'Improve the architecture' isn't — which is why investing in tests is investing in AI leverage."
  3. Context beats model choice. "Everyone has similar models. The differentiator is whether your conventions, architecture decisions, and institutional knowledge are available to it. A conventions file in the repo is the cheapest high-return thing available."
  4. Review is the bottleneck that appears. "Double generation without addressing review capacity and you've built a queue. Queues degrade quality, because reviewers under load approve rather than engage."
  5. Measure with paired metrics. "Cycle time and review latency for speed, change failure rate as the guardrail. And I'd distrust self-reported time saved."
  6. The governance angle. "The properties that make agents useful are the ones that make them a governance problem. Sandbox what they reach; audit what they leave behind."
