Assumes nothing · builds every concept from the ground up

Databases, from absolute scratch.

Starting with what a table physically is on a disk — because indexes, keys, and every performance decision only make sense once you can picture that. Each section builds on the last, and every concept comes with its trade-off.

01

What a database actually is

Strip away the mystique first.

A database is a program that stores data in files on a disk and answers questions about it. That's it. It's software, running as a process, reading and writing files — like any other program.

You could store your data in a text file. People do. A database exists because a text file fails at four things once data gets large or shared:

ProblemWhat a database provides
Finding things fastIndexes — you don't scan the whole file to find one row
Many users at onceConcurrency control — two people editing simultaneously don't corrupt each other
CrashesDurability — a power cut mid-write doesn't leave half a record
Related dataRelationships and joins — combining data that lives in different places
Hold this picture

Everything in this document is machinery for one of those four problems. When a concept feels arbitrary, ask which of the four it's solving — there's always an answer.

02

Tables, rows, and columns

The vocabulary, made concrete.

A table is like a spreadsheet. It has named columns with fixed types, and rows of actual data.

idnameemailcitycreated_at
1Priyapriya@ex.comBengaluru2026-01-15
2Arunarun@ex.comChennai2026-02-03
3Meerameera@ex.comBengaluru2026-02-11
4Karthikkarthik@ex.comMadurai2026-03-02

Creating that table:

CREATE TABLE users (
    id          INTEGER       PRIMARY KEY,
    name        VARCHAR(100)  NOT NULL,
    email       VARCHAR(255)  NOT NULL UNIQUE,
    city        VARCHAR(100),
    created_at  TIMESTAMP     DEFAULT now()
);

What each part means

PieceMeaning
INTEGER, VARCHAR(100)The type — what kind of value, and how much space it may take
NOT NULLThis column must always have a value
UNIQUENo two rows may share this value
DEFAULT now()If you don't supply a value, use this
PRIMARY KEYSee §04 — the most important one

These are constraints — rules the database enforces on every write. Their value is that they can't be forgotten. Application code can have a bug that inserts a duplicate email; a UNIQUE constraint rejects it regardless of which application, script, or human tries.

The trade-off — constraints

For: guaranteed data integrity, enforced no matter what writes. Bugs become errors rather than corruption.

Against: every constraint is a check on every write, so writes cost more. And changing a constraint later on a large table can require a lengthy migration.

Verdict: use them. Corrupt data is far more expensive than slightly slower writes, and it's often unrecoverable.

03 / ★ THE FOUNDATION

How a table is actually stored

This is the section that makes indexes obvious later. Take it slowly.

Rows live in pages

The disk isn't read one row at a time. The database reads and writes in fixed-size blocks called pages — typically 8 KB. A page holds as many rows as fit.

page 1 · 8 KBrows 1, 2, 3, … up to ~50 rows
page 2 · 8 KBrows 51, 52, 53, …
page 3 · 8 KBrows 101, 102, …
… thousands more pages …
The table file is just a long sequence of pages.
The consequence that matters

Reading one row costs a whole page. If you want row 52, the database reads all 8 KB of page 2 into memory. There's no way to read less — that's how disks and the OS work.

So the real currency of database performance is how many pages you touch, not how many rows you want.

The buffer pool — memory as a cache

Reading from disk is roughly 100,000× slower than reading from RAM. So the database keeps recently-used pages in memory, in an area called the buffer pool.

in buffer pool~100 nanoseconds
vs
from SSD~100 microseconds
(1000× slower)
vs
from spinning disk~10 milliseconds
(100,000× slower)
Most database tuning is really about keeping the pages you need in memory.
The trade-off — buffer pool size

Bigger: more of your data stays in RAM, dramatically faster reads.

Smaller: leaves memory for other things, but more disk reads.

The rule of thumb: if your working set — the data actually being accessed — fits in the buffer pool, everything is fast. Once it doesn't, performance falls off a cliff. That cliff is the single most important thing to know about database performance.

The heap — rows are unordered

By default rows are stored in a heap: essentially insertion order, with no sorting. New rows go wherever there's space, including gaps left by deletions.

This matters enormously. Because rows are unordered, finding a specific row means checking every page unless you have help. That "help" is an index — which is where §07 comes in.

The write-ahead log (WAL)

A problem: if a crash happens mid-write, a page could be half-updated and the data corrupt.

The solution: before changing any data page, the database first writes a description of the change to a sequential log file, and flushes that to disk. Only then does it modify the actual pages, which can happen later and lazily.

1you commit
→
2write to WAL,
flush to disk
→
3commit returns —
you're safe now
→
4data pages updated
later, lazily
Durability comes from step 2, not step 4.
Why this design is clever

Writing to the WAL is sequential — the disk head doesn't move, or on an SSD it's one contiguous write. Updating data pages is random — scattered across the file. Sequential writes are vastly faster. So the WAL lets you get durability at sequential-write speed, and defer the expensive random writes.

After a crash, the database replays the WAL to reconstruct any changes that hadn't reached the data pages. Nothing committed is ever lost.

04 / ★

Keys

The word "key" gets used for several different things. Here they are, separated.

Primary key

The column (or columns) that uniquely identifies each row. Every table should have one.

id ← primary keynameemail
1Priyapriya@ex.com
2Arunarun@ex.com

Properties enforced automatically:

  • Unique — no two rows share a value
  • Not null — every row must have one
  • Indexed — the database creates an index on it automatically, because it knows you'll look rows up by it

Which column should be the primary key?

ChoiceProsCons
Auto-increment integer
1, 2, 3…		Small (4–8 bytes), sequential so new rows pack neatly, fast to compareGuessable — /users/1, /users/2 lets anyone enumerate. Awkward across multiple servers.
UUID v4
random 128-bit		Unguessable, generatable anywhere without coordinationLarge (16 bytes), and random order causes page splits — see below
UUID v7
time-ordered		Unguessable and roughly sequential — best of bothStill 16 bytes; newer, less universally supported
Natural key
e.g. email		No extra columnAvoid. Real-world values change — people change emails — and then every reference breaks
Why random UUIDs hurt — an important detail

Index entries are stored sorted. With sequential IDs, every new row appends to the end of the index — one page stays hot in memory and fills neatly.

With random UUIDs, each insert lands in a random position. That means touching a random page (probably not in memory), and often splitting a full page into two half-full ones. The index becomes bloated and insert throughput drops noticeably. UUID v7 fixes this by embedding a timestamp so values sort roughly by creation time.

Foreign key

A column that points at another table's primary key. It's how tables relate.

orders
id (PK)user_id (FK → users.id)total
1011450.00
1021120.00
1033890.00

Order 101 belongs to user 1. The database can enforce that: insert an order with user_id = 999 when no such user exists, and it's rejected. That's referential integrity.

CREATE TABLE orders (
    id      INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    total   DECIMAL(10,2)
);

ON DELETE CASCADE means deleting a user deletes their orders. Alternatives: RESTRICT (refuse to delete a user who has orders) or SET NULL.

The trade-off — foreign keys

For: orphaned data becomes impossible. You can't have an order pointing at a deleted user, no matter what buggy code runs.

Against: every insert into orders requires a check against users, so writes are slower. They complicate bulk loading, and they make sharding hard — a foreign key can't span servers.

Verdict: use them in normal applications. Very large distributed systems sometimes drop them and enforce integrity in the application, accepting the risk for write throughput. Know that it's a deliberate trade, not an oversight.

The other "keys"

TermMeaning
Composite keyA primary key made of multiple columns together, e.g. (order_id, product_id)
Candidate keyAny column that could serve as primary key (unique and not null). You pick one; the rest stay as unique constraints.
Surrogate keyAn artificial ID with no business meaning — the auto-increment or UUID. Preferred, because it never needs to change.
Natural keyA real-world identifier (email, ISBN). Avoid as primary key — real-world values change.
Index keyConfusingly, the column(s) an index is built on. Nothing to do with uniqueness.
05

Relationships & joins

Why data is split across tables, and how you put it back together.

Why not one big table?

Suppose you stored users and orders together:

order_idtotaluser_nameuser_emailuser_city
101450Priyapriya@ex.comBengaluru
102120Priyapriya@ex.comBengaluru
103890Meerameera@ex.comBengaluru

Three problems, and they're the classic ones:

  • Update anomaly — Priya changes her email; you must update every row that mentions her, and if you miss one the data is now inconsistent.
  • Insertion anomaly — you can't record a user who hasn't ordered yet, because there's no row to put them in.
  • Deletion anomaly — delete Meera's only order and you lose her details entirely.

Splitting into users and orders fixes all three: each fact lives in exactly one place.

The three relationship types

TypeExampleHow it's built
One-to-manyOne user, many ordersForeign key on the "many" side (orders.user_id)
One-to-oneOne user, one profileForeign key with a unique constraint. Often just merge into one table unless you're splitting rarely-used columns.
Many-to-manyStudents ↔ coursesA junction table — enrolments(student_id, course_id). There's no other way.

Joins

A join combines rows from two tables by matching a column.

SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id;

For each order, find the user with the matching id, and output both.

Join typeReturns
INNER JOINOnly rows with a match on both sides. The default.
LEFT JOINAll rows from the left table; NULLs where there's no match. Use for "all users and their orders, including users with none."
RIGHT JOINMirror of left. Rarely used — people flip the table order instead.
FULL OUTER JOINEverything from both sides, nulls where unmatched.
CROSS JOINEvery combination. Usually an accident — n × m rows.

How joins actually execute

Worth knowing, because it explains why some joins are slow:

AlgorithmHow it worksGood when
Nested loopFor each row on the left, look up matches on the rightOne side is small, and the other has an index on the join column
Hash joinBuild a hash table from the smaller side, then scan the larger and probe itBoth sides are large, no useful index. Needs memory.
Merge joinSort both sides, then walk them in stepBoth already sorted on the join column
The classic slow join

A nested loop over two large tables with no index on the join column. For every one of a million left rows it scans a million right rows — a trillion comparisons. This is what people mean when they say "joins are slow." Joins aren't slow; unindexed joins are.

06

Why queries get slow

The problem indexes exist to solve. Build the intuition before the solution.

You have a table with 10 million users, and you run:

SELECT * FROM users WHERE email = 'meera@ex.com';

The database has no idea where that row is. Rows are stored in a heap, unordered. So it does the only thing it can: a full table scan.

read page 1check ~50 rows · none match
read page 2check ~50 rows · none match
… 200,000 pages …
page 137,442found it
10M rows ÷ 50 per page ≈ 200,000 pages read. At 8 KB each, that's 1.6 GB of I/O to find one row.
Two things to notice

1. It's O(n). Double the table, double the work. Ten million rows means ten million rows examined.

2. It gets worse with concurrency. One such query is slow. A hundred at once evict everything useful from the buffer pool, and the whole database grinds — a single missing index can take down a service.

What you want instead: some structure that lets you jump straight to the right page. That's an index.

07 / ★ THE KEY IDEA

Indexes — the idea

If you understand a book's index, you already understand this.

The analogy

A 900-page textbook. You want everything about "photosynthesis." You could read all 900 pages — that's a full table scan. Or you flip to the index at the back, which is sorted alphabetically, find "photosynthesis → p. 412," and go straight there.

A database index is exactly this: a separate, sorted structure that maps values to row locations.

What it looks like

CREATE INDEX idx_users_email ON users(email);

This builds a second structure alongside the table:

INDEX (sorted by email)
email→ location
arun@ex.compage 2, slot 7
karthik@ex.compage 9, slot 2
meera@ex.compage 4, slot 1
priya@ex.compage 1, slot 3
TABLE (unordered heap)
pagerows
1Priya, …
2Arun, …
4Meera, …
9Karthik, …
The index is sorted. The table isn't. That's the entire trick.

Why sorting changes everything

Because the index is sorted, you can binary search it: look at the middle, decide left or right, discard half, repeat.

RowsFull scan (checks)Index lookup (checks)
1,0001,000~10
1,000,0001,000,000~20
1,000,000,0001,000,000,000~30

That's O(log n) versus O(n). A billion rows costs only 50% more work than a million — this is why indexes feel like magic.

The one-sentence version

An index trades extra storage and slower writes for dramatically faster reads on the indexed column. Every trade-off in §10 follows from that sentence.

Inside a B-tree

The actual structure. Understanding it explains several behaviours that otherwise seem arbitrary.

Databases don't use a flat sorted list — they use a B-tree (specifically a B+tree). A tree of pages, where each page holds many keys.

root page< 500 | 500–999 | ≥ 1000
↓ pick one branch
internal<200 | 200–499
internal500–749 | 750–999
internal1000–1499 | ≥1500
↓
leafactual keys
+ row pointers
↔
leafkeys →
↔
leafkeys →
Leaves hold the data and are linked sideways. Internal pages are signposts only.

Properties, and what each one buys you

PropertyConsequence
Very wide — each page holds hundreds of keysThe tree is shallow. Even a billion rows is only 3–4 levels deep, so a lookup is 3–4 page reads.
Always balancedEvery lookup costs the same. No worst case where the tree degenerates into a list.
Leaves are linked sidewaysRange queries are fast. Find the start, then walk sideways. This is why B-trees beat hash indexes.
Leaves are sortedORDER BY on an indexed column needs no sort step — just read the leaves in order.

Page splits — why insert order matters

When a leaf page fills and a new key must go in the middle, the page splits into two half-full pages.

The practical consequence

Sequential inserts (auto-increment IDs, timestamps) always append to the rightmost leaf. One page stays hot in memory, fills completely, then a new one starts. Efficient and compact.

Random inserts (UUID v4) land anywhere, splitting pages all over the tree. The index grows larger than necessary, pages sit half-empty, and inserts touch cold pages. This is the concrete reason UUID v7 exists.

Other index types, briefly

TypeUseLimitation
B-treeEquality, ranges, sorting, prefix matching. The default for good reason.—
HashEquality only, O(1)No ranges, no sorting. Rarely worth it — B-trees are nearly as fast and far more flexible.
GIN / invertedFull-text search, JSON containment, array membershipLarge, slower to update
GiST / R-treeGeographic and geometric queriesSpecialised
Partial indexIndex only some rows: WHERE deleted_at IS NULLOnly helps queries with the same condition

Clustered vs non-clustered — an important distinction

ClusteredNon-clustered (secondary)
What it isThe table rows are stored inside the index, in key orderA separate structure pointing at rows in the heap
How many per tableOne — data can only be sorted one wayAs many as you like
Lookup costFind the leaf — the row is right thereFind the leaf, then a second read to fetch the row
Range queriesVery fast — matching rows are physically adjacentSlower — rows scattered across the heap

MySQL InnoDB clusters on the primary key always. PostgreSQL uses heaps with all indexes secondary. That extra row fetch is why the planner sometimes chooses a table scan even when an index exists — see §11.

09 / ★

Composite indexes

An index on several columns. The rules here are the most commonly-tested database knowledge.

CREATE INDEX idx_orders ON orders(user_id, created_at, status);

The phone-book analogy

A phone book is sorted by surname, then first name. So:

  • Find everyone named Sharma → easy, they're together
  • Find Sharma, Priya → easy, within the Sharmas it's sorted by first name
  • Find everyone named Priya (any surname) → you must read the whole book

A composite index behaves identically. It's sorted by the first column, then by the second within that, and so on.

The leftmost-prefix rule

With an index on (user_id, created_at, status):

-- ✓ USES the index
WHERE user_id = 42
WHERE user_id = 42 AND created_at > '2026-01-01'
WHERE user_id = 42 AND created_at > '...' AND status = 'paid'

-- ✗ CANNOT use it (no leftmost prefix)
WHERE created_at > '2026-01-01'
WHERE status = 'paid'
WHERE created_at > '...' AND status = 'paid'

You must use the columns from the left, without gaps. Skipping the first column makes the index useless — exactly like searching a phone book by first name.

The second rule — ranges stop the index

With WHERE user_id = 42 AND created_at > '2026-01-01' AND status = 'paid':

The index seeks efficiently on user_id (equality) and then on created_at (range). But once a range is used, everything after it can no longer be seeked — the rows for status are scattered across that range. So status is checked by filtering rows after retrieval, not by the index.

The rule: put equality columns first, range columns last. Knowing this is what distinguishes someone who has actually tuned queries.

Covering indexes

If the index contains every column the query needs, the database never touches the table at all — an index-only scan.

-- Index on (user_id, created_at, status)
SELECT status FROM orders WHERE user_id = 42;
-- status is IN the index → no row fetch needed → very fast

SELECT * FROM orders WHERE user_id = 42;
-- needs all columns → must fetch each row from the heap

This can be an order-of-magnitude difference, because you eliminate one random read per matching row. It's also a concrete reason to avoid SELECT *.

The trade-off — how many columns?

More columns: covers more queries, more index-only scans.

Cost: the index grows, so fewer entries per page, so more pages to read and more memory consumed — and every write updates a larger structure.

Verdict: add columns for genuinely hot queries, not speculatively. A wide index that covers nothing important is pure cost.

10

What indexes cost

Indexes are not free. This is the trade-off section.

Cost 1 — writes get slower

Every INSERT, UPDATE, and DELETE must update every affected index.

0 indexes1 write
→
3 indexes4 writes
→
8 indexes9 writes
Insert throughput falls roughly linearly with index count.

Cost 2 — storage

Each index is a full copy of its columns plus pointers. On a heavily-indexed table, indexes often exceed the size of the table itself — and they compete with table data for buffer-pool memory.

Cost 3 — the planner may ignore it anyway

An index on a low-selectivity column is usually useless. Selectivity = how well a value narrows the result.

ColumnDistinct valuesUseful index?
email10,000,000 of 10,000,000Excellent — one row per value
city~500Depends — fine for a rare city, useless for the biggest
is_active2Useless alone — matches half the table
Why a scan can beat an index

Using a secondary index means a random read per matching row. If a query matches 40% of the table, that's millions of random reads — slower than sequentially scanning the whole table, which the disk does very efficiently.

So the planner is often correct to ignore your index. That surprises people, and understanding why is a genuine signal of depth.

Cost 4 — maintenance

Indexes fragment over time. Unused indexes are pure overhead — they slow every write and consume memory for nothing. Auditing and dropping them is real, ongoing work.

The decision rule

Index for the queries you actually run, not the columns you have. Look at what's slow and frequent. Check selectivity. Prefer one well-designed composite index over three single-column ones. Verify with EXPLAIN rather than assuming. And periodically drop what isn't used.

How you find out what the database is actually doing, instead of guessing.

  (cost=0.43..8.45 rows=12 width=64)

What to look for

SignalMeaning
Seq Scan on a large tableRed flag if you expected an index. Missing or unusable index.
Index Scan / Index Only ScanGood. "Only" means covering — no table access at all.
rows=12 vs actual rows=14Close is fine. Wildly different means stale statistics — run ANALYZE. Bad estimates cause bad plans.
Nested Loop over two big tablesRed flag — usually a missing index on the join column
Sort with external merge DiskSorting spilled to disk; working memory too small

Common causes of slow queries

CauseFix
N+1 queries — one query for a list, then one per itemThe classic ORM bug. Batch or join.
Non-sargable predicate — WHERE YEAR(created) = 2026Wrapping the column in a function defeats the index. Rewrite as a range: created >= '2026-01-01' AND created < '2027-01-01'. Same for LIKE '%x'.
SELECT *Fetches unneeded columns and defeats covering indexes
Deep offset pagination — OFFSET 100000Produces and discards 100,000 rows. Use cursor pagination: WHERE id > :last.
Stale statisticsPlanner mis-estimates, picks a bad plan. Run ANALYZE.
Too many connectionsDatabases die from connection exhaustion before CPU. Use a pooler.
The word to know

Sargable — "Search ARGument ABLE": a predicate the engine can satisfy with an index seek. Wrapping the column in a function, doing arithmetic on it, or a leading wildcard all make it non-sargable. The fix is always to move the operation to the other side of the comparison.

12

Transactions & ACID

How the database keeps data correct when things go wrong.

The problem

Transfer ₹500 from A to B — two operations:

UPDATE accounts SET balance = balance - 500 WHERE id = 1;
-- ← power cut here
UPDATE accounts SET balance = balance + 500 WHERE id = 2;

₹500 has vanished. A transaction makes both happen or neither:

BEGIN;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
  UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;   -- both, or ROLLBACK → neither

ACID

LetterGuaranteeHow
AtomicityAll or nothingUndo log — on rollback or crash, changes are reversed
ConsistencyConstraints hold before and afterConstraint checking on every write
IsolationConcurrent transactions don't see each other's half-done workLocking and/or MVCC — see §13–14
DurabilityCommitted data survives a crashWAL flushed to disk before commit returns
Two clarifications

The C is weak. It means "the database's own constraints hold," not "your business logic is right." It's also a completely different thing from the C in CAP.

Durability costs latency. Commit means the WAL was fsync'd to physical storage, and that flush is often the dominant cost of a small transaction. Some systems offer relaxed durability — acknowledge before flushing — trading a tiny crash window for much higher throughput.

The trade-off — transaction size

Long transactions: more work is atomic, but locks are held longer, more contention, and in MVCC systems they prevent cleanup of old row versions, causing table bloat.

Short transactions: better concurrency, but you must handle partial completion yourself.

Rule: keep transactions as short as possible. Never wait for user input or a network call inside one.

13

What goes wrong with concurrency

The specific failures isolation levels exist to prevent. Know the names.

AnomalyWhat happens
Dirty readYou read data another transaction wrote but hasn't committed — and it then rolls back. You acted on data that never existed.
Non-repeatable readYou read a row twice in one transaction and get different values, because someone committed a change in between.
Phantom readYou run the same query twice and get different rows, because someone inserted matching data.
Lost updateTwo transactions read the same row, both modify it, both write. One update silently disappears.
Write skewTwo transactions each read a consistent state and write to different rows, together breaking an invariant. Subtle and nasty.

Lost update, concretely

T1reads balance = 1000
T2reads balance = 1000
T1writes 1000 − 100 = 900
T2writes 1000 − 200 = 800 ← T1's deduction is gone
Two withdrawals, only one applied. The classic race.

Fixes: do it in one statement (SET balance = balance - 100, which the database handles atomically), lock the row (SELECT ... FOR UPDATE), or use optimistic concurrency (§15).

Write skew, concretely

Rule: at least one doctor must be on call. Two are on call; both try to go off duty simultaneously. Each checks "is another doctor on call?" — both see yes — and each removes themselves. Now zero doctors are on call.

Neither wrote the same row, so no lock conflicted. Only Serializable isolation prevents this.

14

Isolation levels

The dial between correctness and concurrency. Know each level by the anomaly it prevents.

LevelPreventsStill allows
Read uncommittedNothingDirty reads. Almost never used.
Read committedDirty readsNon-repeatable and phantom reads. PostgreSQL's default.
Repeatable read+ non-repeatable readsPhantoms in the standard. MySQL InnoDB's default, which also blocks most phantoms.
SerializableEverything, including write skew— but costs concurrency and causes aborts you must retry
The trade-off

Higher isolation: fewer surprises, easier reasoning, correct by default.

Cost: less concurrency, more blocking or more transaction aborts that the application must catch and retry.

What most systems do: run at read committed and handle the specific races explicitly — atomic single statements, row locks, or version columns where a lost update would actually matter. Serializable everywhere is correct but usually too expensive.

MVCC — how readers avoid blocking

Multi-Version Concurrency Control. Instead of locking rows for readers, the database keeps multiple versions of each row. Each transaction sees a consistent snapshot as of when it started.

readersnever block writers
↔
writersnever block readers
The single biggest reason PostgreSQL and Oracle handle mixed workloads well.
The cost of MVCC — vacuum and bloat

Old row versions accumulate and must be cleaned up. In PostgreSQL that's vacuum. A long-running transaction holds back the cleanup horizon — the database can't remove versions that transaction might still need — so dead rows pile up and the table bloats.

This is a very common production problem, and it's why "keep transactions short" is operational advice, not just theory.

Locks & deadlocks

How the database stops two writers corrupting each other — and how that goes wrong.

Lock types

LockBehaviour
Shared (read)Many transactions may hold it simultaneously
Exclusive (write)Only one holder; blocks all others
Row lockFine-grained, best concurrency, more memory
Table lockCoarse; blocks everything. Some engines escalate to this when one transaction holds too many row locks — which can turn a normal query into a system-wide stall.
Gap lockLocks the range between index entries, to prevent phantom inserts

Optimistic vs pessimistic

PessimisticOptimistic
ApproachLock first: SELECT ... FOR UPDATERead, then verify nothing changed at write time
Best whenConflicts are likelyConflicts are rare
Failure modeBlocking, deadlocks, lower throughputWasted work and retries under contention
-- Optimistic: the WHERE clause IS the concurrency check
UPDATE accounts
   SET balance = 900, version = version + 1
 WHERE id = 1 AND version = 7;
-- 0 rows affected → someone else won → re-read and retry

Deadlocks

T1locks row A · now wants row B
T2locks row B · now wants row A
both wait foreverdatabase detects the cycle and aborts one
Each holds what the other needs.
Prevention

Consistent lock ordering — if every transaction acquires resources in the same order (say, ascending by ID), a cycle cannot form. Beyond that: keep transactions short, never wait for user input inside one, and make the application retry on deadlock — in a busy system they're normal, not exceptional.

Note this is the identical principle to lock ordering in concurrent programming. Same problem, different layer.

Normalisation

How to decide what goes in which table.

Normalisation means organising data so each fact lives in exactly one place. The informal rule captures it:

The rule

Every non-key attribute depends on the key, the whole key, and nothing but the key.

FormRequirement
1NFAtomic values — no lists crammed into one column
2NFNo column depends on only part of a composite key
3NFNo column depends on another non-key column

Denormalisation — deliberately breaking the rules

Sometimes you duplicate data on purpose, to avoid a join on a hot read path.

NormalisedDenormalised
Single source of truthData duplicated in several places
Updates touch one rowUpdates must touch every copy
Reads need joinsReads are a single lookup
No inconsistency possibleInconsistency is possible — you now own keeping copies in sync
The guidance

Normalise until it hurts, denormalise until it works. Start normalised — it's correct by construction. Denormalise only where you've measured a read path that needs it, and be explicit that you've created a second place the truth lives, with a mechanism to keep them in step.

The mistake isn't denormalising. It's denormalising accidentally and having no plan for divergence.

Scaling

In order of cost. Most teams reach for step 5 when steps 1–3 would have sufficed.

1 · optimiseindexes, query rewrites, connection pooling — most "we need to shard" ends here
2 · cachea read that never reaches the database is free
3 · vertical scalinga bigger machine. Unfashionable, but a single modern instance goes very far
4 · read replicascopies serving reads — for read-heavy workloads
5 · shardingsplit data across servers. Powerful, and effectively a one-way door
Each step costs more operationally than the one above.

Read replicas

Writes go to a primary; copies stream the WAL and serve reads.

The trade-off — replication lag

Replicas are always slightly behind. The bug this causes: a user updates their profile, is redirected, the read hits a lagging replica, and their change appears to have vanished.

Fixes: read from the primary for a short window after a write, use a token carrying the write position so the replica waits to catch up, or make the UI optimistic. Synchronous replication removes the lag but adds a network round trip to every write.

Sharding

Split rows across servers by a shard key — e.g. all data for tenant 1–1000 on server A, 1001–2000 on server B.

What you gainWhat you lose
Horizontal write scalingCross-shard joins — no longer a single query
Each shard is smaller and fasterCross-shard transactions — atomicity across servers is very hard
Failure is isolated to one shardGlobal uniqueness and auto-increment need rethinking
Resharding is painful — plan for it up front
The shard key is the decision

Choose badly and you get hot shards (one enormous tenant swamping a server) or queries that fan out to every shard, which is slower than not sharding at all. For multi-tenant systems tenant_id is usually right, because most queries are naturally tenant-scoped.

Mitigate resharding pain by creating more logical shards than physical servers up front — growth then becomes a rebalance rather than a rewrite.

SQL vs NoSQL

The final trade-off, and the one most often decided for the wrong reasons.

TypeExamplesFits when
RelationalPostgreSQL, MySQLJoins, multi-row transactions, constraints, ad-hoc queries
Key-valueRedis, DynamoDBAccess is always by primary key. Caching, session state, rate limiting.
DocumentMongoDBVariable shape, hierarchical data read as a unit
Wide-columnCassandraWrite-heavy, time-series, massive horizontal scale
Time-seriesInfluxDB, TimescaleTelemetry — writes dominate, queries are windowed aggregates
GraphNeo4jRelationship traversal is the primary query
The myth

"NoSQL scales, SQL doesn't." False. PostgreSQL handles enormous workloads on a single instance. What NoSQL systems really do is remove features — joins, multi-row transactions, flexible queries — and horizontal scaling becomes easier once those are gone.

So the honest framing is: NoSQL scales more easily because it does less, and if you need what it dropped, you'll rebuild it badly in your application.

The decision rule

Choose by access pattern, not by category. Do you need joins and multi-row transactions? Relational. Is every access a single-key lookup with no joins? Key-value fits naturally — and that's why it scales, not because of the label. Is it append-heavy telemetry queried by time window? Time-series.

Most mature systems use more than one — polyglot persistence — chosen deliberately per workload rather than standardised for its own sake.

CAP, stated correctly

Under a network partition, a distributed system must choose: consistency (refuse to answer rather than return stale data) or availability (answer, possibly staleness). It is not "pick two of three" — partitions are a fact of networks, not an option.

PACELC — the better version

CAP only describes partition behaviour. PACELC extends it: if Partition, choose Availability or Consistency; Else, choose Latency or Consistency. More useful, because it covers normal operation — where the real trade-off is that stronger consistency means more coordination means higher latency.

The ten things to carry away
  1. Data lives in 8 KB pages; performance is about how many pages you touch.
  2. Reading from memory is ~1000× faster than disk — the buffer pool is where tuning happens.
  3. A primary key uniquely identifies a row; a foreign key points at another table's primary key.
  4. Without an index, finding a row means scanning every page.
  5. An index is a sorted structure mapping values to locations — O(log n) instead of O(n).
  6. Composite indexes follow the leftmost-prefix rule, and a range condition stops the index for columns after it.
  7. Indexes slow every write and consume storage — index for queries you run, not columns you have.
  8. Transactions give all-or-nothing; isolation levels trade correctness against concurrency.
  9. Keep transactions short — long ones cause blocking and MVCC bloat.
  10. Scale in order: optimise → cache → bigger machine → replicas → shard. Sharding is a one-way door.
