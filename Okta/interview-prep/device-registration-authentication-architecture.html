Device Registration & Authentication

How JumpCloud devices enroll, prove identity to our servers, and protect data in transit and at rest.

← Interview Prep Hub Registration Authentication Security

Overview

JumpCloud uses multiple identity layers on each endpoint. A managed device typically has: (1) a system identity (agent client certificate) for daemon-to-cloud communication, (2) optional MDM identity (Apple/Microsoft enrollment certs), (3) per-user device-trust certificates for browser mTLS, and (4) hardware-bound keys (Secure Enclave DUK) for JumpCloud Go. All cloud communication uses TLS; agent and device-trust paths add mutual TLS (mTLS).

Registration — How a Device Joins the Org

Registration creates a system record in JumpCloud and establishes cryptographic credentials. There are three primary registration paths.

Path 1 — Agent System Registration (all platforms)

Trigger: Admin installs agent with a connect key (org-scoped enrollment token).

Outcome: Device appears in Admin Console Systems tab with a unique systemKey and agent client certificate.

  • registration/seal_renew.go — generate UUID, CSR, sign cert, register
  • registration/register.go — download config template, call registerNewSystem
  • SI/routes/provision/SignCsr.js — kickstart signs agent CSR with org CA
sequenceDiagram participant Admin participant Agent as jumpcloud-agent participant Kickstart as Kickstart SI participant SI as Systems Inventory Admin->>Agent: Install with connect key Agent->>Agent: Generate UUID and RSA private key Agent->>Agent: Build CSR with certuuid in SAN Agent->>Kickstart: POST SignCSR multipart Kickstart->>Kickstart: Sign with org provisioning CA Kickstart-->>Agent: PEM client certificate Agent->>Agent: Save cert key root CA bundle Agent->>Kickstart: registerNewSystem mTLS Kickstart->>SI: Create system document SI-->>Agent: jcagent.conf with systemKey Agent->>Agent: Persist systemKey locally

Path 2 — Apple MDM Enrollment

Trigger: DEP/ABM auto-enroll or user opens enrollment profile URL.

Outcome: MDM-managed device with identity cert, APNs push token, command queue; linked to JumpCloud system via association.

  • jumpcloud-apple-mdm/business/checkin.go — Authenticate, enqueue profiles
  • jumpcloud-apple-mdm/services/scep.go — SCEP identity certificate
  • jumpcloud-apple-mdm/endpoints/checkin.go — verify Mdm-Signature PKCS7
sequenceDiagram participant Mac as macOS Device participant MDM as jumpcloud-apple-mdm participant SCEP as SCEP endpoint participant Agent as jumpcloud-agent Mac->>SCEP: Enrollment profile plus CSR SCEP-->>Mac: MDM identity certificate Mac->>MDM: CheckIn Authenticate MDM->>MDM: Validate enrollment token and topic MDM->>MDM: Insert device record MDM->>Mac: Install agent ES SSO profiles Mac->>Agent: Agent starts with connect key or MDM link Agent->>MDM: Association token reported

Path 3 — JumpCloud Go DURT Registration (per user)

Trigger: User completes SSO login and registers JumpCloud Go (browser extension or Safari SSO extension).

Outcome: Device User Key (DUK) in Secure Enclave bound to user+system; DURT refresh token stored in keychain.

  • jumpcloud-durt-macos/DurtService/DurtService.swift — register with DUK public key
  • jumpcloud-durt-macos/DurtService/DUK.swift — SecureEnclave P256 key
  • docs/jc_go/ARCHITECTURE.md — Register flow overview
sequenceDiagram participant User participant Go as DURT Client macOS participant DUK as Secure Enclave participant DURT as DURT Service User->>Go: SSO login obtain idToken Go->>DUK: Generate or load DUK P256 key DUK-->>Go: Public key never export private key Go->>Go: Build signed JWT with device key and cert chain Go->>DURT: POST register DURT->>DURT: Validate user system org binding DURT-->>Go: Issue DURT refresh token Go->>Go: Store DURT in keychain

Path 4 — Device-Trust User Certificate (per user, on demand)

Trigger: Admin enables device trust for user; user-agent requests cert on login.

Outcome: X.509 cert in user keychain (jumpcloud-device-trust-keychain-db) with trusted-app ACL for Safari/Chrome.

  • certificates/certificate_handler.go — CSR to agent-server signDeviceIdentificationCSR
  • user-agent/cert/cert_darwin.go — keychain install and browser auto-select

Trust Boundaries

  • Internet boundary: TLS + mTLS; server validates cert chain and maps to org/system/user.
  • Root vs user boundary: Root daemon holds system identity and collects posture; user agent holds browser certs in user keychain (TCC and keychain scoping).
  • Local boundary: Tray and user-agent reach daemon via local gRPC — not exposed to network.
  • Hardware boundary: DUK never leaves Secure Enclave; signing delegated via XPC helper.
