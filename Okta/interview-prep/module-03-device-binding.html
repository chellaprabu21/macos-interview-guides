Device Binding & Device Assertions

Two parallel paths - certificate serial and DURT/DUST - converging on a DeviceAssertion JWT consumed by CAP and OAuth.

← Module 02 Hub Module 04 →

Concept Summary

Device binding proves a specific user is on a specific managed device. JumpCloud mints a DeviceAssertion JWT containing device ID, org, OS, FDE status, EDR signals, and optional app-managed flags. Policy engines (CAP) consume this token at login and app access time - analogous to Okta embedding device context in authentication policies.

JumpCloud Implementation

  • jumpcloud-devices/services/device_identification.go - cert serial → JWT with org/user/device/FDE claims
  • jumpcloud-auth/assertions/device.go - assertion claims: disk_encryption, signals, is_app_managed
  • jumpcloud-auth/docs/adrs/adr-011-device-trust-jc-go.md - cert vs Go assertion paths
  • jumpcloud-auth/proto/jumpcloud/auth/device_trust.proto - Authenticate → Authorize → GetToken
// assertions/device.go - key claims in DeviceAssertion
userIDClaim             = "user"
fullDiskEncryptionClaim = "disk_encryption"
signalsClaim            = "signals"      // CrowdStrike ZTA, SentinelOne, OS
isAppManagedClaim       = "is_app_managed"
bundleIDClaim           = "bundle_id"

DeviceTrust RPC (OAuth-like, not RFC 8628): Authenticate (user creds + system binding → auth JWT) → Authorize (auth JWT → authorization code) → GetToken (code → ID token).

Okta Parallel

When a device enrolls in Okta FastPass / Device Access, it becomes a registered device object in Universal Directory with lifecycle states (active, suspended, deleted). Okta auth policies reference device.state, device.managementStatus, and device.provider.deviceAccess.joined. JumpCloud's DeviceAssertion JWT is the equivalent payload - a signed, consumable device context blob.

Interview Q&A

What happens if a device-trust cert moves to another machine?
The cert serial still maps to the original system record, but the session/device binding breaks when the portal detects mismatch - assertion is removed from session and device trust fails. Binding is intentional: cert is issued per user+device pair via SystemsToUsers lookup.
Why does auth mint Go assertions instead of devices service?
ADR-011: DURT service already attests device existence when minting DUST. Auth can embed live signals without an extra devices-service round trip. Separate session keys keep cert and Go paths independent.
What's in the signals claim?
OS version, CrowdStrike status/version/ZTA score, SentinelOne status/version - collected by signal/collector_darwin.go, embedded at assertion mint time, parsed by CAP PDP for conditions like CROWD_STRIKE_ZTA_SCORE.
How does this map to Okta device lifecycle?
Suspend/delete device in Okta → dbSSO breaks until re-enrollment. JumpCloud equivalent: remove system association or revoke cert → assertion fails CAP checks. Both treat device as first-class identity object, not just a User-Agent string.

Gaps & Honest Limits

  • No RFC 8628 device authorization grant - custom DeviceTrust 3-leg flow instead.
  • Portal prefers cert assertion over Go assertion today (ADR-011); Go preference is future.
  • DeviceTrust authenticate lacks mandatory device private key signature (TODO in auth service).
