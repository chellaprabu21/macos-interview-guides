How JumpCloud's Conditional Access Policy evaluates device posture at authentication time - and how it maps to Okta Identity Engine auth policies.

Concept Summary

CAP is JumpCloud's Policy Decision Point (PDP). At login or OAuth token exchange, auth evaluates rules against user context, network context, and - critically - device context. Outcomes: ALLOW, MFA step-up, or DENY. Device data arrives via three paths with very different freshness characteristics.

JumpCloud Implementation

  • jumpcloud-auth/providers/oauth/state_manager.go - device assertion preferred over User-Agent; signal parsing
  • jumpcloud-auth/services/session_token.go - DUST → DeviceAssertion builder
  • jumpcloud-auth/policies/authn/pdp.go - CAP conditions: FDE, CrowdStrike ZTA, managed device
  • planning/ban-3495/context/CAP-end-to-end-flow.html - technical flows
  • planning/ban-3495/context/CAP-explained-simple.html - plain English

In OAuth state manager: DeviceAssertion > User-Agent > nil. Signals embedded in assertion are parsed for CAP evaluation (ZR-1776): OS, CrowdStrike ZTA score, SentinelOne status, etc.

Interview Q&A

Why is the Mongo portal path a Zero Trust gap?
System report updates on ~2 hour cadence. User could disable FileVault after login and retain access until next sync. Go path fixes this for app access; UDTL (BAN-3495) fixes it platform-wide with delta events and <30s SLA for critical attrs.
How does OAuth state manager use device context?
Prefers DeviceAssertion over User-Agent parsing (ZR-808). Parses signals claim for CAP conditions (ZR-1776). This is the same architectural slot Okta uses for device risk signals in OIE authentication policies.
What's the PEP vs PDP split?
PDP = auth service AuthnPolicyDecisions.Evaluate. PEP = User Portal, JumpCloud Go, future BeyondCorp - enforcement points that call PDP and block/step-up based on verdict. Standard Zero Trust reference architecture.
Example CAP rule you'd explain?
"Require managed device + FileVault enabled + CrowdStrike ZTA score above threshold for admin console access." Maps to Okta rule: Managed + Registered device + custom CrowdStrike claim + phishing-resistant factor for sensitive apps.

Gaps & Honest Limits

  • No unified posture store yet - three siloed paths; UDTL is ZR-2375 platform work.
  • BeyondCorp (BAN-3496) consumer blocked on UDTL consumption API.
