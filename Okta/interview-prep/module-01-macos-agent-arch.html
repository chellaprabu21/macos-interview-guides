macOS Multi-Process Agent Architecture

Privilege separation across root daemon, per-user agent, and Swift extensions - the foundation of JumpCloud endpoint security.

← Hub Next: Keychain →

Concept Summary

Enterprise macOS agents cannot run as a single monolith. macOS enforces strict boundaries: root-only operations (service account keychain, system-wide posture), user-scoped keychains (device-trust certs for browser mTLS), TCC-protected APIs, and signed system extensions. JumpCloud splits responsibilities across three process tiers connected by local gRPC and XPC.

JumpCloud Implementation

  • docs/jc_go/ARCHITECTURE.md - DUK/DURT/DUST terms, client component map
  • agent/agent.go - root daemon wiring (registration, policies, MDM hooks, DURT client)
  • localgrpc/local_grpc_handler.go - Unix socket gRPC API to tray and user-agent
  • user-agent/main.go - per-user agent for cert install and browser integration
  • loginwindow/loginwindow_darwin.go - JCLoginPlugin authorization mechanisms
  • External: jumpcloud-macos-agent-apps - jcagent-tray, ES extension, SSO extension (Swift)

The localGRPCHandler struct exposes OIDC config, signal collection, service account ops, certificate handling, and streaming updates to the tray app - all over a Unix domain socket with transport credentials limiting access to local processes.

// localgrpc/local_grpc_handler.go - key dependencies wired into handler
type localGRPCHandler struct {
    certificateHandler    CertificateHandler
    serviceAccountHandler ServiceAccountHandler
    oidcHandler           OIDCHandler
    signalCollector       signal.Collector
    // ... streaming clients for tray UI
}

Okta Parallel

Okta Verify + Device Access uses a similar split: a privileged service daemon handles crypto and device registration while user-facing UI (Verify app, login window integration) runs in separate signed processes. Platform SSO 2.0 and Device-Bound SSO rely on MDM-deployed extensions and login items - analogous to JumpCloud's MDM-provisioned SSO extension + tray app pattern.

Interview Sound Bite

"We designed for least privilege - privileged crypto and posture collection in the root daemon, user-scoped cert and keychain in the per-user agent, UI and Endpoint Security in signed Swift helpers with XPC. Local gRPC is the IPC contract; cloud services never talk to the tray directly."

Interview Q&A

Why not run everything as root?
User keychains are per-UID - browser mTLS for device trust must run in the user's session. TCC prompts and SSO extensions require user context. Root handles what only root can: service account password rotation, system-wide osquery, and protecting the SA keychain with an ES extension.
How does the tray app talk to the daemon?
Unix domain socket gRPC (localgrpc) implementing the LocalAgent protobuf service. The handler exposes OIDC configuration, signal export, certificate operations, and bidirectional streams for user info and software app configs. Transport credentials restrict callers to local processes.
What's the platform abstraction pattern?
*_darwin.go, *_linux.go, *_windows.go build tags across the agent. Shared interfaces in default files; platform-specific keychain, login window, and signal collection in tagged files. Same pattern Okta uses for cross-platform device clients.
How does this compare to Okta Device Access?
Same principle: privileged daemon for device identity and crypto, user-space Verify/tray for UX, MDM-delivered profiles for extensions and login items. JumpCloud adds a per-user Go agent for cert lifecycle because device-trust mTLS certs live in the user keychain.

Gaps & Honest Limits

  • Production Swift code (tray, ES, SSO) lives in jumpcloud-macos-agent-apps, not jumpcloud-agent - cite as sibling repo you integrate with via gRPC/XPC.
  • Safari JumpCloud Go uses SSO Extension Policy instead of browser NMH - separate flow documented in ARCHITECTURE.md.
