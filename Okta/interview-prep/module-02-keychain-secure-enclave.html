Keychain, Secure Enclave & Cryptographic Device Identity

How JumpCloud binds device identity to hardware: keychain ACLs, device-trust certs, and Secure Enclave DUK.

← Module 01 Hub Module 03 →

Concept Summary

Device identity requires secrets that cannot be exfiltrated. JumpCloud uses two complementary approaches: (1) X.509 device-trust certificates in a per-user keychain with trusted-app ACLs for browser mTLS, and (2) a Secure Enclave–backed P256 signing key (DUK) for JumpCloud Go token refresh. A separate service-account keychain at /opt/jc/ holds privileged credentials protected by an ES extension.

JumpCloud Implementation

  • keychain/keychain_darwin.go - SecKeychain APIs, PKCS#12 import, trusted-app ACL verification
  • user-agent/cert/cert_darwin.go - jumpcloud-device-trust-keychain-db, Chrome/Safari auto-select
  • serviceaccount/serviceaccount_darwin.go - dedicated SA keychain at /opt/jc/
  • certificates/certificate_handler.go - CSR generation, POST to /signDeviceIdentificationCSR
  • External: jumpcloud-durt-macos/DurtService/DUK.swift - SecureEnclave.P256.Signing.PrivateKey

Cert path: Agent generates CSR → agent-server signs → PKCS#12 imported into user keychain with private key ACL limited to Safari, Chrome, WebKit trusted apps → browser presents cert via mTLS → serial number maps to device in devices service.

DUK path: On JumpCloud Go registration, DURT service provisions a refresh token bound to a Secure Enclave key. Each access request signs a challenge with DUK - key never leaves the SE.

Okta Parallel

Device Access certificates (SCEP via MDM) and Device-Bound SSO use similar crypto binding. Okta requires Secure Enclave hardware (macOS 14+) for dbSSO; certs are installed via SCEP and linked to FastPass enrollment. JumpCloud's cert path mirrors SCEP + mTLS; DUK path mirrors hardware-protected session binding.

Key Tradeoff (ADR-011)

Cert-based trust requires a round trip to the devices service (serial → assertion). DURT/DUST path lets auth mint device assertions directly - fewer inter-service calls, same CAP guarantees when signals are embedded. Desktop still uses certs; mobile and Go prefer DURT.

Interview Q&A

Why trusted-app ACLs on the device-trust private key?
Only Safari, Chrome, and WebKit should use the private key for mTLS. Without ACLs, any process in the user's session could export or use the key. We verify trusted apps at install time via trustedapps/ handlers.
Cert-based vs Secure Enclave - when do you pick each?
Certs excel at browser mTLS (standard TLS stack). SE keys excel at programmatic signing without export - ideal for token refresh where the client proves possession without a browser. Okta dbSSO combines both: SCEP cert for device registration + SE for session crypto binding.
What protects the service account keychain?
Dedicated keychain at /opt/jc/, root-only access, plus a Swift Endpoint Security extension that restricts file access to the SA keychain database - defense in depth if malware runs as user.
Known gap in DeviceTrust RPC?
jumpcloud-auth/services/device_trust.go has a TODO to force signature from the system's private key on authenticate requests. Today binding relies on user password + system association, not cryptographic device proof. Closing it would align with Okta-joined device guarantees.

Gaps & Honest Limits

  • DUK Swift code is in jumpcloud-durt-macos, not the agent repo.
  • Device private key signature on DeviceTrust authenticate is not yet enforced.
  • No Apple App Attest - pragmatic cert + SE binding, not full hardware attestation chain.
