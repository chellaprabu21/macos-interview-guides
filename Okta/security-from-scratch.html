00 / Foundation

What is security even trying to do?

Before any math, know the four questions. Every tool in this guide is an answer to one of them.

Forget cryptography for a second. "Security" sounds vague, but in practice it's four very concrete promises a system tries to keep. Hold these in your head — when you meet a new tool later, ask "which of these four is it solving?"

01 / Building block

Hashing — a one-way fingerprint

The simplest cryptographic tool. Start here because signatures and passwords both rely on it.

Why it exists

Sometimes you need to ask "is this exactly the same as before?" or "was this tampered with?" without storing or revealing the whole thing. You need a compact, reliable fingerprint.

Picture it

A human fingerprint. It's tiny compared to a whole person, the same person always leaves the same print, and two different people leave totally different prints. Critically: you cannot rebuild the person from the fingerprint. A hash is a fingerprint for data.

How it works: a hash function takes any input — a word, a file, a 4 GB video — and produces a fixed-size string of characters (the digest). Properties that make it useful:

  • Deterministic — same input always gives the same digest.
  • Fixed size — "hi" and a movie both produce, say, a 64-character SHA-256 digest.
  • One-way — you can't reverse a digest back into the original. That's the whole point.
  • Avalanche — change one character of input and the entire digest changes unrecognizably.
  • Collision-resistant — it's practically impossible to find two different inputs with the same digest.

Any input in, fixed-size fingerprint out, and no path backwards.

Where it's used: verifying a downloaded file wasn't corrupted or swapped (compare digests), storing passwords (a site stores the hash of your password, not the password), and fingerprinting a program so you can recognize it again (you'll use this idea in endpoint security — a binary's hash identifies it).

Say it in interview words

"A cryptographic hash like SHA-256 is a deterministic, one-way function producing a fixed-length digest; it's collision-resistant, so it works for integrity checks and fingerprinting. For passwords you never use a plain hash — you use a salt plus a deliberately slow key-derivation function (bcrypt, scrypt, PBKDF2) so attackers can't precompute or brute-force."

The gotcha

Hashing is not encryption. Encryption is reversible if you have the key; hashing is one-way on purpose and has no key. Mixing these up is a classic tell that someone learned security from headlines.

02 / Building block

Symmetric encryption — one shared lock

The intuitive kind of encryption. It works, but it has one big problem that sets up the next module.

Why it exists

You want to send a message so that only the intended person can read it. Anyone who intercepts it should see gibberish.

Picture it

A lockbox with one key. You lock your message inside and send the box. Your friend has an identical copy of that key and unlocks it. The same key both locks and unlocks — that's why it's called "symmetric."

One secret key, shared by both sides, used to both encrypt and decrypt.

This is fast and great for bulk data. The standard algorithm is AES, usually in a mode called AES-GCM that also detects tampering (encryption + integrity in one).

The problem it can't solve alone

Two problems, actually. (1) Key distribution: how do Alice and Bob both get the same secret key in the first place, without an eavesdropper grabbing it on the way? (2) Identity: the key proves nothing about who you are — anyone holding it can read and write. These two gaps are exactly what the next module fixes.

Say it in interview words

"Symmetric encryption — AES-GCM — is fast and gives confidentiality plus integrity, but it has the key-distribution problem: both parties need the same secret, and sharing it securely is hard. That's why real systems use asymmetric crypto to exchange the symmetric key."

03 / The hinge — read slowly

Public-key (asymmetric) crypto

If you only deeply understand one module, make it this one. Everything from here — signatures, certificates, TLS, Secure Enclave, passkeys — is built on it.

Why it exists

To fix the two gaps from module 02: how to communicate securely with someone you've never met (no pre-shared secret), and how to prove identity.

The core idea: instead of one shared key, every person gets a pair of keys that are mathematically linked:

  • a public key — you hand it to everyone, publish it, put it on a billboard;
  • a private key — you guard it and never, ever share it.

The magic property: whatever one key does, only the other key can undo. This gives you two completely different superpowers depending on which key you start with.

Superpower 1 — privacy (encrypt to someone)

Picture it

A mailbox with a public slot. Anyone can drop mail in (encrypt with your public key), but only the person with the private key can open the box and read it (decrypt with the private key).

Say it in interview words

"Asymmetric crypto uses a public/private key pair. Common algorithms are RSA and elliptic-curve (ECC, e.g. P-256) — ECC gives equivalent strength with much smaller keys, which is why hardware like Apple's Secure Enclave uses it."

04 / Building block

Digital signatures, properly

Superpower 2 in detail — because signed tokens and certificates run the identity world.

Why it exists

You want a way to prove a message (a token, a certificate, a software update) genuinely came from a specific source and wasn't altered by even one byte.

How it actually works — it combines modules 01 and 03:

SignTake the message → hash it (module 01) → encrypt that hash with your private key (module 03). The result is the signature, attached to the message.
VerifyThe receiver hashes the message themselves, decrypts your signature with your public key to reveal the hash you computed, and compares the two. Match → authentic + untampered.
Hashing makes it efficient; the private key makes it unforgeable.

A valid signature gives you three things at once: authentication (it came from the private-key holder), integrity (any change breaks the match), and non-repudiation (they can't later deny signing it).

Say it in interview words

"A digital signature is the hash of the message encrypted with the signer's private key; verification re-hashes and checks against the public key. It delivers integrity, authentication, and non-repudiation. JWTs, X.509 certificates, and WebAuthn assertions are all just signed data — once you see signing, you see them all."

05 / Trust

Certificates & the chain of trust

Public keys prove identity only if you know whose key it is. This module solves "how do I trust a stranger's public key?"

Why it exists

Signatures prove a message came from "whoever owns this private key." But how do you know that key really belongs to bank.com and not an impostor who also has a key pair? You need someone trustworthy to vouch.

Picture it

A passport. You believe a stranger's passport not because you know them, but because a government you trust issued it, stamped it, and is hard to forge. A certificate is a passport for a public key: a trusted authority signs a statement saying "this public key belongs to bank.com."

How it works — the chain: your operating system ships with a small, pre-trusted list of root Certificate Authorities (CAs). A root signs intermediate CAs, and intermediates sign the actual website's leaf certificate. When you visit a site, your device walks the chain upward and checks each signature until it reaches a root it already trusts.

Say it in interview words

"This is PKI — public-key infrastructure. An X.509 certificate binds an identity to a public key, signed by a CA. Trust derives from a chain up to a root in the OS trust store. The same machinery issues device certificates, which is how an endpoint proves its identity to a backend."

Your bridge to the role

This is the foundation of device identity: an enterprise can issue a certificate to a managed device, binding the device's hardware key to a trusted identity. You've worked near this with MDM and device trust — it's PKI applied to machines instead of websites.

06 / It assembles

TLS / HTTPS / mTLS — the padlock

The little padlock in your browser is modules 01–05 working together in under a second.

Why it exists

When you talk to a website, you want to know (a) you're really talking to that site, not an impostor, and (b) nobody in between can read or change the conversation. TLS delivers both.

The handshake, step by step:

1Your browser connects to the server and says "let's set up a secure channel."
2The server sends its certificate (its public key + the CA chain from module 05).
3Your browser verifies the chain — is this really the right site, vouched for by a trusted CA? If not, you get the scary warning page.
4Using asymmetric crypto (module 03), the two sides agree on a fresh symmetric session key.
5They switch to fast symmetric encryption (module 02) for the rest of the conversation.
Authenticate with certificates → exchange a key with asymmetric crypto → encrypt the data with symmetric. All four guarantees from module 00, at once.

Mutual TLS (mTLS): normally only the server proves its identity. In mTLS, the client also presents a certificate, so both sides prove who they are. This is the natural way for a device to authenticate to a backend using a hardware-bound key — a pattern central to this role.

Say it in interview words

"The TLS handshake uses the server's certificate for authentication, asymmetric crypto to establish a shared session key, then symmetric encryption for throughput. mTLS adds a client certificate so the device authenticates too. Certificate pinning hardens an agent against a rogue CA by trusting only a specific cert/key — at the cost of rotation complexity."

07 / Hardware

Secure Enclave — a key that can't be stolen

Your strongest area. Now you'll see exactly why it's the foundation of modern device identity.

Why it exists

All the crypto above assumes your private key stays secret. But if that key sits in a file or in a program's memory, malware — or anyone with root — can copy it and impersonate you forever. We need a place a key can live where nothing, not even the operating system, can read it.

Picture it

A sealed vault with a mail slot but no door. You can pass a document in and the vault stamps it and passes it back out — but you can never reach inside to take the stamp itself. The Secure Enclave is that vault for your private key.

How it works: the Secure Enclave is a separate, isolated chip. It can generate a private key inside itself, and that key's material never leaves the chip. Your app can't read it; the OS can't read it. All you can do is ask the Enclave to perform an operation (sign this, decrypt this) with the key. You can also require that the user prove presence — Face ID, Touch ID, or passcode — before the Enclave will act.

Why this is your edge

A Secure-Enclave key that is non-exportable, user-presence-gated, and origin-bound is, mechanically, exactly what a modern passkey (module 12) and a device-attestation key (module 13) are. You've already built this primitive. The rest of the identity world is just different product wrappers around it.

Say it in interview words

"The Secure Enclave generates and stores a non-exportable private key; the application processor can only request operations, never read the key, and use can be gated on user presence (biometric/passcode). It typically uses ECC (P-256). That hardware binding is what makes a credential phishing-resistant and tied to a specific device."

08 / Storage

Keychain — the system's secret vault

Where the OS keeps passwords, keys, and tokens — and how it differs from the Enclave.

Why it exists

Apps need somewhere safe to store secrets (passwords, tokens, certificates) instead of in plain files. The Keychain is the OS-managed, encrypted, access-controlled store for that.

How it works: items are encrypted at rest, unlocked with the device, and an app can normally only read its own items. You can tune when an item is readable (only while the device is unlocked, only on this device so it never syncs to backups) and require authentication to access it.

The key distinction — interviewers love this

The Keychain protects a secret at rest, but to use it the secret is loaded into the app's memory — where a compromised process could grab it. The Secure Enclave never lets the key out at all. So the strongest design keeps secrets out of memory entirely: store a non-exportable key in the Enclave and only ask it to sign, rather than storing a usable secret in the Keychain.

Say it in interview words

"Keychain Services is the system credential store with per-item accessibility (e.g. WhenUnlocked, ThisDeviceOnly) and access-control gating. Use it for retrievable secrets, but prefer a Secure-Enclave key when the secret should never be exportable or live in process memory."

09 / Pivot to identity

Why passwords are weak

This is the motivation for the entire second half. Once you feel why passwords fail, OAuth, OIDC, and FIDO all make sense.

Passwords are a shared secret: you and the server both know it. That creates four chronic problems:

  • Reuse — people use the same password everywhere, so one breach unlocks many accounts.
  • Guessable — weak passwords fall to dictionaries and brute force.
  • Breachable — if a server is hacked, the secrets can leak.
  • Phishable — and this is the big one: a fake look-alike site can simply ask you to type your password, and you hand it over.
What about MFA?

Multi-factor authentication adds a second proof — something you have (your phone) or something you are (your fingerprint) on top of something you know (the password). It's much better. But many common forms are still phishable: a convincing fake site can ask for your SMS or authenticator code and instantly replay it to the real site before it expires.

The goal we're building toward

A credential with no secret to type, bound to the real site's address, so a fake site literally cannot obtain anything usable. That's phishing-resistant authentication — modules 10–12 — and it's built entirely on the public-key crypto and Secure Enclave you now understand.

10 / Identity protocol

OAuth — letting an app act for you

Okta's core. OAuth is about authorization — what an app may do on your behalf — not about proving who you are.

Why it exists

A photo-printing app wants access to your Google Photos. You should absolutely not give it your Google password — that would let it do anything, forever. You need to grant limited, revocable access without ever sharing your password.

Picture it

A valet key. It lets the valet park your car — but not open the glovebox or drive 200 miles. Limited powers, and you can take it back. OAuth hands apps a "valet key" to specific parts of your account.

How it works: you log in directly with Google (never with the app), Google asks "allow this app to view your photos?", and on your yes, Google gives the app a limited token — not your password. The app uses that token to call the Photos API. You can revoke it anytime.

  • Scopes — exactly what the token may do ("view photos," not "delete account").
Say it in interview words

"OAuth 2.0 is an authorization framework. The authorization-code flow with PKCE is the modern default, even for native apps. PKCE binds the flow to a one-time secret the real client generated, so an intercepted authorization code is useless to an attacker — it closes the code-interception attack for clients that can't keep a secret."

Don't mix it up

OAuth tells an app what it's allowed to do. It does not cleanly tell the app who you are. That gap is filled by the next module — and conflating the two is the mistake interviewers probe for.

11 / Identity protocol

OIDC & JWT — proving who you are

OpenID Connect adds identity on top of OAuth. The token format is the JWT — and it's just signed data (module 04).

Why it exists

OAuth gives an app access but doesn't reliably answer "who is the logged-in user?" OpenID Connect (OIDC) is a thin layer on OAuth that adds exactly that: after login, you also receive an ID token — a signed statement of who you are.

The ID token is a JWT. A JWT has three parts joined by dots: header.payload.signature.

HHeader — which signature algorithm (e.g. ES256, RS256) and which key was used.
PPayload — the claims: who issued it (iss), who it's for (aud), who you are (sub), when it expires (exp). This part is readable by anyone.
SSignature — the issuer signs the header+payload with its private key (module 04), so anyone can verify with the issuer's public key that it's genuine and untampered.
A JWT is signed data. Verification = the signature check you already learned.
Two mistakes interviewers fish for

(1) A JWT is signed, not encrypted — anyone can read the payload, so never put secrets in it. (2) You must verify the token (check signature, issuer, audience, expiry), not merely decode it. Decoding is not validation.

Say it in interview words

"OIDC adds an ID token (a JWT) and a userinfo endpoint to OAuth. To validate a JWT I verify the signature against the issuer's published keys (JWKS) matching the kid, then check iss, aud, exp/nbf, and the nonce for replay protection. The payload is base64url, not encrypted."

12 / The payoff

FIDO / WebAuthn / passkeys

The unphishable login. This is where modules 03, 04, 07, and 09 all come together — and where your Secure Enclave experience becomes identity expertise.

Why it exists

To kill the password and its phishability (module 09) once and for all, using public-key crypto (module 03) and hardware keys (module 07).

The idea: instead of a password, your device holds a private key (typically generated in the Secure Enclave). To register, your device makes a new key pair for that specific website and sends the website the public key. To log in, the website sends a random challenge; your device signs it with the private key after you prove presence (Face/Touch ID); the website verifies the signature with your public key. No secret is ever typed or transmitted.

RegDevice generates a key pair bound to this site's address, stores the private key in the Enclave, and sends the public key to the site, which saves it for your account.
LoginSite sends a random challenge → you confirm with biometric → device signs the challenge with the private key → site verifies with your stored public key. Done.
Registration shares a public key; login is a signed challenge. The private key never leaves the device.
Why it can't be phished

The credential is cryptographically bound to the real site's origin. A fake look-alike domain can't elicit a usable signature — the browser/device simply won't sign for the wrong origin, and there's no secret to capture and replay. This is the property SMS and TOTP codes lack.

Say this in the interview — it's your strongest move

"A platform authenticator is, mechanically, the Secure Enclave work I've shipped: a non-exportable, user-presence-gated, origin-bound key that signs a challenge. WebAuthn standardizes that primitive for user login. I've built the hard part; the protocol is the wrapper." This turns endpoint depth into credible identity fluency — without claiming hands-on FIDO stack work you don't have.

Say it in interview words

"FIDO2 / WebAuthn uses three actors: the relying party (the service), the client/browser, and the authenticator (platform = built-in via Secure Enclave/TPM; roaming = a security key over CTAP). Registration produces an attestation; login produces an assertion. Passkeys are WebAuthn credentials, often synced across a user's devices for convenience and recovery."

13 / Trusting the machine

MDM & device attestation

We can now trust a user (module 12). Can we trust the device they're on? Same crypto, applied to hardware.

Why it exists

A company wants to allow access only from devices it manages and trusts — not from an attacker's laptop or a cloned machine. So it needs to (a) manage company devices and (b) let a device prove it's a genuine, specific, healthy machine.

MDM (Mobile Device Management) is how an organization configures and controls devices: it installs settings, certificates, and rules, and can lock or wipe a lost device. A neat detail: a server can't reach a sleeping device behind a home router, so Apple's push service (APNs) acts as a doorbell — it silently tells the device "wake up and check in," and the device then connects out and pulls its commands.

Device attestation is the device's version of a passkey: using a Secure Enclave key, the device produces hardware-backed proof that it's a real Apple device with a specific identity and a non-exportable key — not a spoof or clone. That proof, bound into a device certificate (module 05), is what lets a backend trust the machine.

You've done MDM attestation and device trust. Frame it as: "I built the device end of the device-identity contract" — the hardware-backed proof that makes a machine a credential the identity platform can rely on. That is precisely this team's mission.

14 / The synthesis

Zero trust & conditional access

Everything so far, assembled into the model Okta sells — and the literal job you're interviewing for.

Why it exists

The old model was "inside the corporate network = trusted." That fails the moment an attacker gets inside or work happens from anywhere. Zero trust flips it: trust nothing by default, and verify every access request.

A conditional access engine decides each request by combining three things you now understand:

SignalHow it's provenModule
WHO (user)Phishing-resistant login — ideally a passkey12
WHAT (device)Managed & attested via MDM + Secure Enclave13
CONTEXT (risk)Location, time, anomaly/risk signals—

Based on all three, the engine decides: allow, deny, or step up (ask for more proof). If it allows, it issues a short-lived signed token (module 11) the app trusts.

Okta FastPass — a real example

FastPass is a passwordless, phishing-resistant, device-bound factor that uses the platform's hardware-backed crypto. It is, in one product, modules 03 + 07 + 12 + 13 working together — the exact intersection of your background and Okta's mission.

Your one-line positioning

"I've spent my career on the device end of zero trust — System Extensions, Endpoint Security, Secure-Enclave-backed credentials, MDM attestation, conditional access. That's exactly the primitive Okta turns into a trusted identity factor, and I want to build the macOS side of it at their scale."

One walk-through & glossary

A single secure login, narrated

1An employee opens a work app. The app redirects to Okta to authenticate (OAuth/OIDC, mod 10–11).
2Okta asks the user to confirm with a passkey: the device signs a challenge with a Secure-Enclave key after Face ID (WebAuthn + Secure Enclave, mod 12, 07, 03–04). Phishing-resistant.
