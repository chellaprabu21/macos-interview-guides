Architectural reconstruction · the products your interviewer personally built

Desktop MFA, from the login window down.

A complete walkthrough of how MFA at the macOS login window is implemented — the authorization plugin, the daemon, the offline problem, and the operational machinery that keeps a fleet from being locked out. This is reconstruction from public platform mechanisms, not inside knowledge, so hold it as "how I would build it" rather than "how Okta did."

01

The problem & constraints

Understand what makes this hard and the architecture becomes inevitable.

What the product does

Require a second factor before a user can log into a Mac — and optionally before unlocking the screensaver. The corporate laptop is the highest-value endpoint an attacker can reach: a stolen device with a weak or phished password gives access to everything the user has, including cached credentials, local secrets, and any session tokens on disk.

Why it's hard

ConstraintConsequence
You don't own the login windowNo API to "add a step to login." You must insert into Apple's authorization machinery.
No user session exists yetNo user keychain, no LaunchAgents, no home directory (it may not be mounted), no normal app environment.
The network may be unavailableWi-Fi often hasn't connected. Your IdP is unreachable at exactly the moment you need it.
FileVault happens firstPre-boot unlock occurs before macOS is running — no plugin, no daemon, no network.
A bug locks people out permanentlyThere is no "uninstall from the login window." This dominates every design decision.
Recovery must work offlineA locked-out user can't open a browser to self-serve.
Multiple OS versions in the fleetBehaviour differs across macOS releases; you support several simultaneously.
The sentence that governs everything

A bug in an authorization mechanism locks every user out of every Mac in the fleet, with no way in from the login window. That single fact drives fail-open defaults, hard timeouts on every network call, a remotely-deliverable kill switch, staged rollout with automatic halt, and a documented local recovery path. If you say one thing about this product, say this — it's what the team actually lives with.

02 / ★

The three environments

Any design must state which of these it operates in. Getting this wrong is the most common misunderstanding of the product.

1 · pre-boot — FileVaultEFI/recoveryOS environment · local password or recovery key only · no macOS, no daemons, no plugins, no network · you cannot run code here
↓
2 · login window — loginwindow + SecurityAgent + authdmacOS is running · your plugin executes as an authorization mechanism · a root daemon can run · network may exist · no user session, no user keychain, no home directory
↓
3 · user sessionfull environment · LaunchAgents, UI, user keychain, reliable network · enrollment and settings live here
Three environments, three capability sets. State which one you're in before proposing anything.

The FileVault complication

With FileVault enabled, the pre-boot unlock authenticates the user against the volume's encryption keys. macOS then commonly passes those credentials through to complete login automatically — so the login window may never appear, and a naive MFA plugin never runs.

How products handle it
  • Disable the pass-through so the login window always appears after FileVault unlock — the user unlocks the disk, then authenticates properly with MFA. Costs an extra step; gains actual enforcement.
  • Also gate the screensaver (system.login.screensaver), so even if initial login is bypassed, the machine is protected on every subsequent unlock.
  • Accept the gap explicitly and document it — FileVault protects data at rest, MFA protects session establishment, and they're different threat models.

Being able to explain this gap is one of the strongest signals you understand the product rather than the marketing.

03

The authorization system — the hook point

The platform mechanism that makes the whole product possible.

The model

  • Rights — named strings for privileged operations: system.login.console (console login), system.login.screensaver (unlock), system.preferences, authenticate.
  • The authorization database — policy stored in /var/db/auth.db, seeded from /System/Library/Security/authorization.plist. Inspect with security authorizationdb read system.login.console.
  • Rules and mechanisms — a right is satisfied by an ordered chain of mechanisms, each a piece of code that runs and votes.
  • authd evaluates rights. SecurityAgent hosts mechanisms that draw UI.
The key realisation

Login is just an authorization right. Because it's a chain, and the chain is data in a database, a vendor can insert their own mechanism into it. That's the entire basis of Desktop MFA, Jamf Connect, and every comparable product.

The chain, with your mechanism inserted

$ security authorizationdb read system.login.console

<key>mechanisms</key>
<array>
  <string>builtin:policy-banner</string>
  <string>loginwindow:login</string>                // collects user + password
  <string>builtin:login-begin</string>
  <string>system.login.fus</string>                 // fast user switching
  <string>builtin:home-directory-mount</string>
  <string>builtin:authenticate,privileged</string>  // local credential check

  <string>OktaMFA:check,privileged</string>         // ← privileged: policy, no UI
  <string>OktaMFA:prompt</string>                   // ← unprivileged: draws UI
  <string>OktaMFA:verify,privileged</string>        // ← privileged: final verdict

  <string>builtin:auth-with-user-record</string>
  <string>loginwindow:success</string>
  <string>builtin:login-end</string>
</array>

The privileged / non-privileged split

Non-privilegedPrivileged (,privileged)
Host processSecurityAgentauthd
Runs asThe _securityagent userroot
Can draw UIYesNo
Used forThe MFA prompt, number entry, statusReading policy, talking to the privileged daemon, the final verdict

They communicate through the authorization context — a key-value store shared along the chain. That's why a real implementation needs at least two mechanisms in the same plugin bundle.

A security note worth making

Earlier mechanisms may have placed the user's password in the context in plaintext. That's precisely why this is such a sensitive place to run code, why the bundle must be signed and manually installed, and why the interface between your mechanisms should carry the minimum necessary — never more of the context than you need.

04 / DESKTOP MFA

Process architecture

Five components, split on trust and session boundaries.

1 · Enrollment app (user session)SwiftUI · enroll factors · generate the Secure Enclave key · register with the IdP · show status
2 · LaunchAgent (per user)menu bar · notifications · keeps the offline verifier fresh while the session is active
3 · Authorization plugin (login window)two or three mechanisms in one bundle · runs inside SecurityAgent and authd · votes allow/deny
4 · LaunchDaemon (root, always running)the brain · policy · network to the IdP · offline verifier store · Secure Enclave operations · telemetry
5 · The IdP (cloud)factor verification · policy source · audit · admin console
The plugin is deliberately thin. The daemon does the work, because the plugin runs in a hostile, short-lived environment.

Why the daemon, and not logic in the plugin

  • Lifetime — the plugin is instantiated per login attempt and torn down. It has nowhere to keep state, connections, or caches.
  • Network — a long-lived daemon can maintain a warm connection, pre-fetch policy, and know the network state before the login window even appears.
  • Crash isolation — a crash inside a login mechanism is catastrophic; a crash in a daemon is a restart.
  • Reuse — the same daemon serves the login window, the screensaver, and the user-session app.
  • Testability — logic in a framework the daemon links can be unit tested. Logic inside an authorization plugin effectively cannot.
The design rule

"The plugin is a thin client. It gathers the username from the context, asks the daemon for a decision over XPC with a hard timeout, presents whatever UI the daemon says to present, and votes. All policy, crypto, network, and state live in the daemon — which is testable, restartable, and shared."

The XPC interface

@objc protocol MFADaemonProtocol {
    // Does this user need MFA at all, and which factors are available?
    func evaluatePolicy(username: String,
                        reply: @escaping (Data?, Error?) -> Void)

    // Start a verification; returns a challenge to display (e.g. a number)
    func beginVerification(username: String, factor: String,
                           reply: @escaping (Data?, Error?) -> Void)

    // Poll or submit; daemon owns all network and crypto
    func completeVerification(sessionID: String, response: Data?,
                              reply: @escaping (Bool, Error?) -> Void)

    // NOT: func runCommand(_ s: String) — never a general lever
}

The daemon validates every connecting peer by audit token against a code-signing requirement — never by pid, since pids recycle and can be raced. The plugin, the agent, and the enrollment app each have their own designated requirement.

Invoke is where you vote. Deactivate is where you clean up if the user backs out.

The mechanism, conceptually

// Real API is C with function-pointer tables; shown here for clarity.

OSStatus MechanismInvoke(AuthorizationMechanismRef inMechanism) {

    // 1. Read what earlier mechanisms gathered
    const AuthorizationValue *user = NULL;
    callbacks->GetContextValue(engine, kAuthorizationEnvironmentUsername,
                               &flags, &user);

    // 2. Ask the daemon — with a HARD timeout
    Decision d = askDaemonWithTimeout(user, /* seconds */ 8);

    // 3. Vote
    switch (d) {
      case DecisionAllow:
        callbacks->SetResult(engine, kAuthorizationResultAllow); break;
      case DecisionDeny:
        callbacks->SetResult(engine, kAuthorizationResultDeny); break;
      case DecisionUserCancelled:
        callbacks->SetResult(engine, kAuthorizationResultUserCanceled); break;
      case DecisionUnavailable:
        // Daemon unreachable, timed out, or internal error.
        // THE MOST IMPORTANT LINE IN THE PRODUCT:
        callbacks->SetResult(engine, failOpenPolicy
                                     ? kAuthorizationResultAllow
                                     : kAuthorizationResultDeny);
        break;
    }
    return errAuthorizationSuccess;
}
Why that last branch is the whole product

Every unexpected condition — daemon crashed, XPC unavailable, timeout exceeded, an internal exception — must land in a deliberate, configurable branch, never in an accidental deny and never in a crash. A crash inside the mechanism is worse than either outcome, because the behaviour then depends on how the OS handles a failed mechanism. So the plugin wraps everything, times out aggressively, and has exactly one place where the fail-open/fail-closed policy is decided.

The four results

ResultEffect
kAuthorizationResultAllowProceed to the next mechanism
kAuthorizationResultDenyFail the right — login refused
kAuthorizationResultUserCanceledUser backed out; chain unwinds cleanly, back to the login window
kAuthorizationResultUndefinedError state — treated as failure

Drawing the UI

The non-privileged mechanism runs inside SecurityAgent and can present an interface, but it's a constrained environment — not a normal app. Practical approach: keep the UI minimal (a number-matching field, a status line, a cancel button), avoid anything requiring a full app lifecycle, and drive all content from the daemon so the plugin holds no logic. Localisation matters here, since this is the first thing a user sees.

06

Enrollment

Happens in the full user session, where you have every capability. This is where the cryptographic foundation is laid.

1user authenticates to the IdP normally (browser or embedded flow, OIDC)
2daemon generates a P-256 key pair inside the Secure Enclave — non-exportable
3public key + device identifiers sent to the IdP, bound to this user and device
4optional device attestation proves it's genuine hardware with a hardware-bound key
5IdP issues a device credential; daemon provisions the offline verifier (section 08)
6recovery codes generated and shown once — the user must store them
Enrollment is the only moment you're guaranteed network, UI, and a user session simultaneously.
// The key that anchors everything
let access = SecAccessControlCreateWithFlags(
    nil,
    kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly,  // daemon needs it pre-login
    [.privateKeyUsage],
    nil)!

let attrs: [String: Any] = [
    kSecAttrKeyType as String:       kSecAttrKeyTypeECSECPrimeRandom,
    kSecAttrKeySizeInBits as String:  256,
    kSecAttrTokenID as String:       kSecAttrTokenIDSecureEnclave,
    kSecPrivateKeyAttrs as String:  [
        kSecAttrIsPermanent as String:   true,
        kSecAttrAccessControl as String: access
    ]
]
let deviceKey = SecKeyCreateRandomKey(attrs as CFDictionary, &error)!
The accessibility choice matters

WhenUnlocked would be wrong here — the daemon must use the key at the login window, before any user has unlocked. AfterFirstUnlock makes the key available once the device has been unlocked at least since boot. ThisDeviceOnly prevents it migrating to another machine via backup. Explaining that choice demonstrates you've actually thought about the pre-login environment.

The framing

"Enrollment is a bootstrapping problem. It's the one moment where I have network, UI, and a user session at once — so everything the constrained environments will need later must be provisioned here: the hardware key, the offline verifier, the cached policy, and the recovery codes. Get enrollment wrong and there's no way to fix it from the login window."

07

Online authentication

The happy path. Network available, IdP reachable.

1user enters username/password at the login window; earlier mechanisms verify the local credential
2privileged mechanism reads the username from the context, asks the daemon over XPC whether MFA is required for this user
3daemon requests a challenge from the IdP, signing the request with the Secure Enclave device key
4IdP dispatches the factor — push to the phone with a number-matching code, or the user provides a TOTP / security key
5unprivileged mechanism displays the number or input field in SecurityAgent
6daemon polls or receives the result; verifies the IdP's signed assertion
7privileged mechanism votes allow; the chain continues and the session starts
Every network hop lives in the daemon. The plugin only asks and displays.

Design details worth naming

  • Number matching — the user must type a number shown on the Mac into the phone. This defeats MFA fatigue, where an attacker spams approvals hoping the user taps to make it stop.
  • The device key signs the request, so the IdP knows the challenge originates from an enrolled machine, not an attacker replaying a username.
  • Hard timeouts at every layer — the mechanism times out on the daemon, the daemon times out on the network. A hung login window is indistinguishable from a broken Mac to the user.
  • Cancellation must work — if the user hits cancel, MechanismDeactivate fires and the chain must unwind cleanly back to the login window, not hang.
  • Push is a doorbell, not a courier — never trust data in the push payload; the phone app fetches the challenge details over its own authenticated channel.
  • Screensaver unlock is a separate right, so decide independently whether to gate it, and whether a grace period applies after a recent successful login.
08 / ★ THE HARD PART

Offline authentication

A laptop on a plane must still unlock. This is where the real engineering is, and where most candidates' answers fall apart.

The requirement

Verify a second factor with no network, in an environment where the attacker may have physical possession of the machine and root access to its disk. You cannot call the IdP. You cannot trust the local clock. And whatever you store must not let an attacker derive valid codes.

The mechanism — a shared-secret OTP, provisioned in advance

at enrollment (online)IdP and device establish a shared secret · the device seals it so only this machine can use it
sealingsecret wrapped by a Secure Enclave key · stored in the system keychain with AfterFirstUnlockThisDeviceOnly · unusable if copied to another machine
offline loginuser opens the authenticator app (which has the same secret) and reads a code · daemon unseals its copy and verifies locally
on reconnectdaemon reports offline uses to the IdP · counters reconcile · secret rotated if policy requires
The secret never exists in usable form on disk — it's sealed to hardware that can't be extracted.

The controls that make it safe

ControlWhy
Bounded offline usesAllow N offline logins before requiring an online check-in. Limits how long a stolen laptop stays usable with a compromised factor.
Freshness windowThe offline verifier expires after X days without contact, forcing reconnection.
Counter / replay protectionFor HOTP-style counters, track and reject reuse. For TOTP, reject a code already accepted in that window.
Clock-skew toleranceTOTP needs a window of accepted steps, but a wide window weakens it — and an attacker with root can change the clock. Prefer counter-based or bind to a monotonic source where possible.
Rate limiting locallyOffline brute force is otherwise unlimited. Escalating delay between attempts, persisted so a reboot doesn't reset it.
Tamper resistanceCounters and attempt state sealed alongside the secret, so editing a file on disk doesn't grant more attempts.
Reconciliation on reconnectReport offline usage so the IdP has an audit trail and can spot anomalies.
The honest trade-off to state

"Offline verification is strictly weaker than online, and I'd say so rather than pretend otherwise. Online you get real-time policy, revocation, risk signals, and full audit. Offline you're verifying against a pre-shared secret with no ability to revoke and no live policy. So the design bounds the exposure — limited uses, a freshness window, and local rate limiting — rather than claiming equivalence. An organisation that can't accept that gap can set the policy to fail closed, and accept that a user with no network can't log in."

Why FIDO2 doesn't simply solve this

A natural question: "why not just use a security key offline?" A hardware authenticator can work offline for the crypto, but the relying party — the IdP that issued the challenge and verifies the assertion — is unreachable. You'd need the local daemon to act as a relying party with a pre-provisioned public key and a locally-generated challenge, which is workable but means local policy, local replay protection, and no live revocation. It's the same trade-off in different clothing, and being able to reason through that rather than hand-wave is a strong answer.

09

Recovery & lockout

Existential for this product. A locked-out user cannot open a browser to self-serve.

The recovery paths, in order of preference

  1. Recovery codes — generated at enrollment, shown once, stored by the user. Single-use, verified against a sealed local hash so they work fully offline. The primary mechanism.
  2. Admin-generated bypass code — an admin issues a time-limited code from the console; the user types it at the login window. Requires the user to reach the helpdesk by another channel, which is realistic.
  3. MDM-delivered kill switch — an administrator remotely puts the agent into passthrough mode. Requires the machine to have network and a working daemon, so it's not universal.
  4. Local escape — a documented recovery procedure (safe mode, or removing the mechanism from the auth database via recovery) for the case where nothing else works. Uncomfortable but necessary.
Lockout is itself an attack surface

If failed MFA attempts lock the account, an attacker with physical access can deliberately lock a user out — a denial of service. So: escalating delays rather than hard permanent locks, local rate limiting sealed against tampering, and a recovery path that doesn't depend on the thing that's failing. At an identity company this trade-off is the conversation.

Failure matrix — have this ready

FailureBehaviour
No networkFall back to the offline verifier, within its use count and freshness window
Offline verifier expiredPolicy decides: deny, or allow with an audit event. Configurable per tenant.
Daemon not runningMechanism times out fast and applies the fail-open/fail-closed policy — never hangs
Daemon crashes mid-flowXPC invalidation handler fires; mechanism treats it as unavailable and applies policy
Plugin itself crashesWorst case — which is why everything is wrapped and timed out. Fleet health telemetry must surface this immediately.
User has no enrolled factorPolicy decides: allow with a grace period and a prompt to enroll, or deny. Grace periods are how you roll this out without an incident.
IdP returns an errorDistinguish "denied" (deny) from "unavailable" (apply the unavailable policy). Conflating these is a real bug.
10 / PASSWORD SYNC

Desktop Password Sync

The second product — and a genuinely harder problem than it sounds.

The problem

A user has a local macOS account password and a separate IdP password. They drift apart, so the user maintains two credentials, forgets one, and files a ticket. Password Sync keeps them the same: change it in one place and the other follows.

Why it's hard

ConstraintWhy it bites
The login keychain is encrypted with the local passwordChanging the local password without going through the proper path breaks the user's keychain — every saved credential becomes inaccessible
FileVault keys are tied to the account passwordChange it wrongly and the user can't unlock the disk at pre-boot — a bricked machine
Secure TokenOn modern macOS, an account needs a Secure Token to unlock FileVault. Changing passwords programmatically must preserve it
Two directions of changeThe user may change it in macOS or in the IdP, and the two can conflict
Policy mismatchmacOS and the IdP may have different complexity rules; a valid IdP password may be rejected locally
Offline changesA password changed while offline must reconcile later
The core danger

You must never change the local password by writing to the account record directly. Doing so leaves the keychain and FileVault key material encrypted under the old password. The change must go through the OS's own password-change path, which re-wraps the keychain and updates the Secure Token — and that path requires the old password. This single fact shapes the entire product.

The two sync directions

IdP → macOS (the common case)

1user changes their password in the IdP (or it expires and is reset)
2agent detects the change — a mismatch at next login attempt, or a signalled event
3at the login window, the user types their new IdP password; the mechanism verifies it against the IdP
4the agent prompts for the old local password — required to re-wrap the keychain
5local password changed via the supported API, keychain re-wrapped, Secure Token preserved; user logs in
Step 4 is the step people forget — and the reason a "silent" sync isn't possible without it.

macOS → IdP

The user changes their password in System Settings. The agent detects it (an authorization mechanism on the password-change right, or a directory notification), verifies the new password meets IdP policy, and pushes the change to the IdP. Simpler, because the OS has already handled the keychain correctly.

Design details

  • Never store either password. Verify and discard. If you must hold one transiently, keep it out of logs, crash reports, and memory dumps, and zero it.
  • Policy pre-check — validate the new password against both policies before attempting the change, so you never get a half-applied state.
  • Idempotency and reconciliation — if the change succeeds locally but the network call fails, the state must converge on next contact rather than diverging silently.
  • Conflict resolution — if both sides changed, decide which wins (usually the IdP) and be explicit.
  • The keychain prompt is unavoidable in some flows — better to explain it clearly to the user than to try to hide it.
  • Testing needs real hardware — Secure Token and FileVault behaviour can't be faked, so this needs an integration matrix across macOS versions.
The line that shows you understand it

"Password Sync sounds like a synchronisation problem but it's really a key-management problem. The local password isn't just a credential — it wraps the login keychain and participates in FileVault key material. So you can't just set it; you have to go through the OS's change path with the old password so everything gets re-wrapped. That's why the product needs the old password, and why a truly silent sync isn't achievable."

Platform SSO — the modern alternative

Apple's supported mechanism, and where this space is heading. Worth knowing as the contrast to plugins.

What it is

An Apple framework letting an identity provider register an SSO extension that integrates with macOS login and authentication — rather than injecting into the authorization database. The IdP can link the local account to the IdP account, participate in login, and keep credentials in step through supported APIs.

Authorization pluginPlatform SSO
MechanismInsert into the auth database chainRegistered SSO extension, supported API
SupportWorks, but you're modifying system policyApple-sanctioned and evolving
RiskHigher — a bug can lock out the fleetLower — the OS mediates
FlexibilityVery high — you control the chainBounded by what Apple exposes
OS supportLong-standing, works on older versionsNewer macOS only
The honest assessment to give

"Platform SSO is clearly the direction — it's supported, it's lower risk, and Apple keeps extending it. But real fleets run several macOS versions, and early Platform SSO had genuine gaps: password verification behaviour at the login window, and the FileVault pre-boot boundary which no framework can change. So a mature product typically supports both — Platform SSO where the OS allows it, the plugin path where it doesn't — and carries the complexity of two code paths until the fleet catches up. That kind of transition is usually the most interesting engineering problem in a product like this."

How this gets onto thousands of machines without anyone clicking a dialog.

Registering the mechanism

# Read the current right, insert the mechanism, write it back.
security authorizationdb read system.login.console > /tmp/console.plist
# ... insert "OktaMFA:check,privileged" etc. at the right position ...
security authorizationdb write system.login.console < /tmp/console.plist
Installer discipline

This is the most dangerous moment in the product's lifecycle. The installer must: back up the original right before modifying it, verify the plugin is present and loadable before registering the mechanism, insert at the correct position in the chain (order matters), be idempotent so re-running doesn't duplicate entries, and provide a clean uninstall that restores the original chain. A partially-applied install is how you brick a fleet.

Configuration via MDM

Everything policy-related arrives as managed preferences: which users require MFA, allowed factors, offline use count and freshness window, fail-open vs fail-closed, screensaver gating, grace period for unenrolled users, and the kill switch. Managed preferences are the right channel because they're pushed centrally, can't be edited by the user, and roll back cleanly.

Grace-period rollout — the product-level version

Before enforcing, ship in audit mode: evaluate the policy, log what would have happened, but always allow. That surfaces the population who'd be locked out — unenrolled users, edge-case configurations, machines with no network — before any of them is actually blocked. Then enforce for enrolled users only, with a grace window for the rest.

Telemetry — what you must emit

Every auth outcome with a reason codeallowed / denied / offline-allowed / failed-open / timed-out. The reason is the whole value.
Fail-open rateThe single most important metric. A spike means something is broken and users are silently unprotected.

The telemetry constraint

Events generated at the login window can't be uploaded immediately — there may be no network and no session. So they're spooled locally in a bounded ring buffer and uploaded by the daemon when connectivity returns, with jitter so the fleet doesn't upload simultaneously after a regional outage.

The kill switch

Requirements
  • Signed, so it can't be forged by an attacker to disable MFA fleet-wide.
  • Delivered over a channel that works even if the plugin is broken — MDM to the daemon, not through the auth path.
  • Puts the plugin into passthrough — always allow, keep logging — rather than uninstalling, because uninstalling is riskier than bypassing.
  • Tested regularly in staging. An untested kill switch is theatre; you find out it doesn't work during the incident.
  • Available per-tenant and globally, so you can contain a customer-specific problem without disabling everyone.
14

Testing this

Notoriously difficult — which makes it a great thing to have a clear answer about.

The layering that makes it testable

Core framework — unit testedpolicy evaluation · offline verifier logic · counters · state machine · reason codes
Daemon — thin shellXPC plumbing and lifecycle only; almost no logic
Plugin — thinner shellread context · call daemon with timeout · vote. Under 200 lines of real logic.
Integration — real hardwarelogin window, FileVault, Secure Token, Secure Enclave. Cannot be faked.
Push logic down into a framework; keep the untestable layers as thin as possible.

What gets unit tested

  • Policy evaluation — every combination of user state, enrollment state, network state, and configuration produces a defined decision. Table-driven tests.
  • Offline verifier — code acceptance, replay rejection, counter increment, expiry at the boundary, exhausted use count. Inject the clock so nothing sleeps.
  • Rate limiting — burst allowed, then blocked, then refilled after time passes. Again with an injected clock.
  • Failure paths — daemon unavailable, IdP error vs IdP denial (these must not be conflated), timeout, malformed response.

What must be integration tested

  • Actual login through the real authorization chain, across every supported macOS version.
  • FileVault enabled and disabled; pass-through behaviour.
  • Secure Token preservation across a password change.
  • Keychain integrity after Password Sync.
  • Secure Enclave operations — you cannot fake the SEP.
  • Network-loss scenarios, including loss mid-authentication.
  • Recovery codes, admin bypass, and the kill switch — each exercised, not assumed.
The answer to "how do you test this?"

"I push everything I can into a framework the daemon links, so policy, the offline verifier, and the state machine are unit tested with an injected clock and a faked IdP client. The daemon and the plugin become thin shells with almost no logic. What's left genuinely requires hardware — the login window, FileVault, Secure Token, the Secure Enclave — so that runs as an integration matrix on a rack of real Macs across supported OS versions, with the recovery paths and the kill switch exercised on every run. You can't unit test the SEP, and pretending you can gives false confidence."

15 / ★

Talking about this in the interview

He built it. Your goal is a peer conversation, not a recital.

Set the frame first

Open with something like: "I haven't built the login-window side myself — my work is the device-agent side, System Extensions and Secure Enclave credentials. But I've thought about how Desktop MFA has to work, and I'd expect the architecture to be roughly this — tell me where I'm wrong."

That does three things: it's honest, it invites him to correct you (which he'll enjoy), and it turns an examination into a discussion. Claiming familiarity you don't have with someone who wrote the code is the one unrecoverable move.

The five points that demonstrate real understanding

  1. The lockout risk governs everything. "A bug in a login mechanism locks the fleet out with no way in — so fail-open defaults, hard timeouts, a kill switch, and staged rollout aren't nice-to-haves, they're the architecture."
  2. The three environments. Pre-boot, login window, session — and the FileVault pass-through gap that means a naive plugin may never run.
  3. The privileged/unprivileged split. SecurityAgent draws UI without root; authd has root without UI; they talk through the authorization context.
  4. Offline is the hard part, and it's strictly weaker than online — bounded uses, freshness window, sealed counters, local rate limiting, reconciliation on reconnect.
  5. Password Sync is key management, not synchronisation — the local password wraps the keychain and participates in FileVault, so the change must go through the OS path with the old password.
