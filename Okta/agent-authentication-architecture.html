1. High-Level Overview

JumpCloud device authentication uses a two-phase trust model: first, a one-time enrollment authorization via a Connect Key proves the device is allowed to join an organization; second, a long-lived mutual TLS (mTLS) client certificate binds the agent to a specific system record for all subsequent communication.

Key insight: The Connect Key authorizes initial enrollment only. After registration, every request is authenticated by the client's X.509 certificate (terminated at the load balancer) plus x-system-id and certificate identity headers — not by the Connect Key.

2. System Components

JumpCloud Agent

Runs on macOS, Windows, and Linux. Generates key pairs, submits CSRs, registers the system, and communicates with the Agent Server over mTLS. Source: jumpcloud-agent/registration/

Kickstart Server (Provision)

Public/private endpoints for pre-registration: sign CSRs, deliver config templates, validate Connect Keys, and confirm certificate access. Source: SI/provision.js, routes under routes/provision/

Agent Server (SI)

Primary API for enrolled agents: policies, commands, user auth, metrics, etc. Validates system identity on every request via middleware. Source: SI/routes/agent/AgentApp.js

jumpcloud-auth

Issues and validates ephemeral Connect Keys for MDM-enrolled devices and user-portal agent installs. Source: jumpcloud-auth/services/connect_keys.go

jumpcloud-devices

gRPC services including Kickstart CheckAccess validation and device management APIs. Source: jumpcloud-devices/services/kickstart.go

Edge / Load Balancer

Terminates TLS, performs client certificate verification against the JumpCloud CA, and injects X-SSL-CLIENT-* headers forwarded to backend services.

3. Connect Keys — Enrollment Authorization

A Connect Key is a short-lived secret that proves a device is authorized to enroll in a specific organization. It is passed in the x-connect-key HTTP header during kickstart/provisioning operations.

Microsoft MDM Device jumpcloud-auth Agent pushed via Intune/SyncML after Windows MDM enrollment Linked to Windows device UUID

Registration Request Payload

The agent sends a system report alongside registration data so the device appears in the Admin Console with hardware metadata:

  • templateId — OS template (Windows=21, macOS=34, Linux=varies)
  • certuuid — matches the CSR CN and pending cert entry
  • connectKey — enrollment authorization
  • report — hostname, serial, arch, OS version, network interfaces, etc.

Server-Side Registration Validation

  1. Connect Key validated (org-user lookup or auth service gRPC call)
  2. Pending certificate must exist in Redis for the org + certuuid pair
  3. certuuid must be globally unique (prevents cloned golden images)
  4. System record created with certificate, MDM linkage (if applicable), and provision metadata
  5. Agent receives systemKey (MongoDB ObjectId) stored in jcagent.conf

5. Certificate Lifecycle

Phase Endpoint Auth Mechanism Result
Initial CSR signing POST /SignCsr (public kickstart) Connect Key only Client cert issued; stored as pending
Access verification GET /CheckAccess (private kickstart) mTLS + Connect Key Confirms cert works before registration
Registration POST /registernewsystem (agent server) mTLS (cert exists; system not yet bound) System record + systemKey issued
Renewal POST /Renew (private kickstart) mTLS + systemKey + existing cert New cert with same certuuid (CN)
Runtime All agent server APIs mTLS + systemKey + certuuid match Ongoing authenticated communication
Certificate identity: The device's unique ID (certuuid) is embedded as the X.509 Subject Common Name (CN). The private key is retained across renewals to preserve the chain of locally encrypted secrets (e.g., FileVault keys).

Local Certificate Storage

  • client.key — RSA private key (0600 permissions)
  • client.crt — Signed client certificate
  • ca.crt — JumpCloud CA trust bundle (server + root CA)
  • jcagent.conf — systemKey, server URLs, certuuid, connect key (bootstrap)

6. Ongoing Agent Authentication

After registration, every Agent Server request passes through verifySystemIdAndCertificateMiddleware. The load balancer terminates mTLS and injects certificate-derived headers; the middleware correlates them with the system record in MongoDB. 

sequenceDiagram
  participant Agent as JumpCloud Agent
  participant LB as Load Balancer
  participant AS as Agent Server
  participant DB as MongoDB

  Agent->>LB: HTTPS request
Client cert + x-system-id header
  LB->>LB: Verify client cert against JumpCloud CA
  LB->>AS: Forward request + injected headers:
X-SSL-CLIENT-DN, X-SSL-CLIENT-CN,
X-SSL-CLIENT-OU, x-system-id

  AS->>AS: Parse CN from X-SSL-CLIENT-DN
  AS->>DB: find({ _id: systemKey, certuuid: CN })
  alt System found & active
    AS->>AS: req.system populated → proceed
    AS-->>Agent: 200 + response
  else System not found / cert mismatch
    AS-->>Agent: 400 / 401
  else System deleted/purged
    AS-->>Agent: Uninstall directive
  end

Middleware Validation Steps

  1. TLS layer: Load balancer requires and verifies client certificate (TLS 1.2+)
  2. System ID: x-system-id header must be a valid MongoDB ObjectId
  3. Certificate DN: X-SSL-CLIENT-DN parsed; CN extracted as certuuid
  4. Binding check: System document must match both _id and certuuid
  5. Lifecycle: Deleted/purged systems receive an uninstall directive instead of data

7. End-User Authentication (Device Trust)

Device authentication (agent ↔ server) is separate from user authentication (user ↔ JumpCloud via agent). When a user logs into a managed device, the agent proxies credential verification to the cloud. 

sequenceDiagram
  participant User as End User
  participant Agent as JumpCloud Agent
  participant AS as Agent Server
  participant Auth as jumpcloud-auth
(Device Trust)

  User->>Agent: Login / unlock (password)
  Agent->>AS: POST /authenticate (mTLS)
userid + password
  AS->>AS: Verify user bound to system
  AS->>Auth: DeviceTrust.Authenticate
(org, system, user, credentials)
  Auth->>Auth: Validate credentials + MFA factors
  Auth-->>AS: JWT authentication token
  AS-->>Agent: authenticationToken
  Agent->>Agent: Grant local session / unlock

Additional user-auth paths:

  • POST /authenticate-factor — MFA factor verification (TOTP, push, etc.)
  • POST /authorizeuserportal — SSO to User Portal via one-time authorization code
  • POST /changepassword — Password change with mTLS-protected channel
Two trust layers: mTLS proves which device is calling. User authentication proves which person is using that device, with an additional check that the user is bound to the system.

8. Data Security in Transit

Application Data (JSON payloads, commands, policies)
TLS 1.2+ — Server certificate verified against CA bundle
Mutual TLS — Client certificate required & verified
TCP/IP (optionally via corporate HTTP proxy)

Security Properties

Property Mechanism Details
Encryption TLS 1.2 minimum Agent HTTP clients set MinVersion: tls.VersionTLS12; all traffic encrypted
Server authenticity Custom CA bundle Agent loads ca.crt (JumpCloud issuer + root) — no insecure skip verify
Client authenticity Mutual TLS (mTLS) Load balancer requires client cert signed by JumpCloud CA; CN = certuuid
Enrollment authorization Ephemeral Connect Keys Single-use/time-limited keys scoped to org + requester; validated via auth gRPC
Identity binding systemKey + certuuid Dual lookup prevents cert replay across different systems
Key protection Filesystem permissions Private keys stored at mode 0600; retained across cert renewals
Pending cert isolation Redis namespacing Signed certs stored per org+certuuid until registration completes
Revocation / decommission System state + uninstall Deleted systems trigger uninstall directives; purged systems cannot re-authenticate
Proxy support HTTP proxy aware Agent respects system proxy settings for TLS connections
