REPORTEDMinimum element in a rotated sorted array

Insight

Binary search on the "broken" property: compare mid to right. If nums[mid] > nums[right], the minimum is right of mid; else it's at mid or left of it. O(log n).

func findMin(_ nums: [Int]) -> Int {
    var lo = 0, hi = nums.count - 1
    while lo < hi {
        let mid = (lo + hi) / 2
        if nums[mid] > nums[hi] { lo = mid + 1 }   // min is to the right
        else { hi = mid }                           // min is mid or left
    }
    return nums[lo]
}

Edge cases to say out loud

Not rotated at all (already sorted), single element, two elements. If they add duplicates, note it degrades to O(n) worst case (hi -= 1 when equal).

REPORTEDsqrt(x) — integer square root, optimal complexity

Binary search for the largest m with m*m ≤ x. O(log x). Mention Newton's method as the alternative if they push for "even better in practice."

func mySqrt(_ x: Int) -> Int {
    if x < 2 { return x }
    var lo = 1, hi = x / 2
    while lo <= hi {
        let mid = lo + (hi - lo) / 2
        if mid <= x / mid, (mid + 1) > x / (mid + 1) { return mid }
        if mid > x / mid { hi = mid - 1 } else { lo = mid + 1 }
    }
    return lo
}

Note the overflow-safe trick: compare mid ≤ x/mid instead of mid*mid ≤ x. Saying that unprompted is a senior signal.

REPORTED3-Sum — all sets of 3 indexes summing to 0

Sort, fix one element, two-pointer the rest. O(n²), O(1) extra. Skip duplicates at all three positions.

func threeSum(_ nums: [Int]) -> [[Int]] {
    let a = nums.sorted(); var res = [[Int]]()
    for i in 0..<a.count {
        if i > 0 && a[i] == a[i-1] { continue }        // skip dup anchors
        var l = i + 1, r = a.count - 1
        while l < r {
            let s = a[i] + a[l] + a[r]
            if s == 0 {
                res.append([a[i], a[l], a[r]])
                repeat { l += 1 } while l < r && a[l] == a[l-1]
                repeat { r -= 1 } while l < r && a[r] == a[r+1]
            } else if s < 0 { l += 1 } else { r -= 1 }
        }
    }
    return res
}
REPORTEDPalindrome escalation → palindrome partitioning (backtracking)

The reported round started easy ("is this a palindrome") and escalated to backtracking. The escalation target: partition a string so every substring is a palindrome; return all partitions.

func partition(_ s: String) -> [[String]] {
    let ch = Array(s); var res = [[String]](), path = [String]()
    func isPal(_ l: Int, _ r: Int) -> Bool {
        var l = l, r = r
        while l < r { if ch[l] != ch[r] { return false }; l += 1; r -= 1 }
        return true
    }
    func backtrack(_ start: Int) {
        if start == ch.count { res.append(path); return }
        for end in start..<ch.count where isPal(start, end) {
            path.append(String(ch[start...end]))   // choose
            backtrack(end + 1)                       // explore
            path.removeLast()                        // un-choose
        }
    }
    backtrack(0)
    return res
}

Name the pattern out loud — "choose, explore, un-choose" — and offer the DP-precompute of the palindrome table as the optimization if asked.

How to win it

  • Handle the dirty cases without being asked: malformed lines (skip + count), missing fields (optionals with defaults), empty input, huge input (stream line-by-line rather than loading everything).

REPORTEDThreading design question

Reported in a US Principal loop. The classic shape: design a thread-safe structure (bounded blocking queue / producer-consumer / a cache with concurrent reads). For a macOS role, answer twice: classic primitives, then Swift-native.

The layered answer

  • Classic: bounded buffer with a mutex + two condition variables (notFull/notEmpty); explain why while not if around the wait (spurious wakeups, recheck after re-acquire).
  • GCD: serial queue confines state; DispatchSemaphore for capacity; concurrent queue + .barrier for a read-heavy cache.
  • Modern Swift: an actor owning the buffer, AsyncStream for the producer-consumer relationship; call out actor reentrancy across await as the trap you'd guard.

Then the Principal move: pick one and justify against requirements (contention level, cancellation, backpressure) instead of listing options forever.

04 / THE RECURRING ASSIGNMENT

The rate limiter — Okta's favorite exercise

Reported as a take-home ("implement a rate limiter endpoint"), as a CodeSignal assessment, and defended in a code-walkthrough round. If any practical exercise comes, odds favor this one. Own it completely.

Why Okta loves this problem

Rate limiting is core to their business: an identity provider is a giant authentication API that must survive credential-stuffing attacks and misbehaving clients while staying fair to legitimate tenants. Your solution gets judged as infrastructure for an auth service, not as a toy.

Know all four algorithms and their trade-offs cold

AlgorithmHowProCon
Fixed windowCounter per window (e.g. 100/min), reset at boundaryTrivial, O(1) memoryBoundary burst: 200 requests straddling the reset
Sliding logStore timestamp of every request; count within windowPerfectly accurateO(requests) memory — unacceptable at scale
Sliding window counterWeighted blend of current + previous window countsAccurate enough, O(1) memoryApproximation (assumes even spread)
Token bucketBucket of capacity B refills at rate R; each request takes a tokenAllows controlled bursts; industry defaultTwo parameters to tune

Default choice: token bucket — say why: legitimate clients are bursty (an app launch fires several calls at once); token bucket permits a burst up to capacity while enforcing the average rate. The lazy-refill trick means you store just two numbers per key and compute refill on access — no timers.

A defensible Swift implementation

struct Bucket { var tokens: Double; var last: Date }

actor RateLimiter {
    private let capacity: Double       // max burst
    private let refillPerSec: Double   // sustained rate
    private var buckets: [String: Bucket] = [:]

    init(capacity: Double, refillPerSec: Double) {
        self.capacity = capacity; self.refillPerSec = refillPerSec
    }

    func allow(key: String, now: Date = Date()) -> Bool {
        var b = buckets[key] ?? Bucket(tokens: capacity, last: now)
        let elapsed = now.timeIntervalSince(b.last)
        b.tokens = min(capacity, b.tokens + elapsed * refillPerSec) // lazy refill
        b.last = now
        let allowed = b.tokens >= 1
        if allowed { b.tokens -= 1 }
        buckets[key] = b
        return allowed
    }
}

Design points to volunteer in the walkthrough — these are what the round is really scoring:

  • Concurrency: the actor serializes access — no data race on the bucket map. (In a server language: mutex per shard, or Redis atomic ops.)
  • Injecting now makes it unit-testable without sleeping — write tests showing burst-then-block and refill-over-time.
  • Memory: unbounded keys → add LRU eviction of idle buckets; state the bound.
  • HTTP contract: respond 429 Too Many Requests with Retry-After and rate-limit headers — clients need to back off intelligently.
  • Distributed version (they will ask): local buckets don't work across N servers. Options: sticky routing per key; a Redis-backed bucket with atomic Lua script (correct, adds a network hop on the hot path); or local buckets with async sync (fast, approximate). State the trade and pick per requirement — auth endpoints usually justify the Redis hop.
  • Fairness & keying: per-user, per-tenant, per-IP, or layered (per-tenant cap + per-user cap under it) — for an identity provider, layered is the real answer.
  • Fail-open or fail-closed if the limiter's store is down? For login endpoints: fail-open with alerting usually beats locking every customer out — but say it's a product decision and name both sides. Very Okta.
Win condition

The walkthrough round is scoring whether you can defend choices under questioning. For every decision above, know the alternative you rejected and why. "Why token bucket over sliding window?" "Why an actor over a lock?" "What breaks at 10K RPS?" — have one-sentence answers ready.

Multi-level parking lot — the reported question, structured

Win condition

LLD is won by process: requirements → entities → relationships → APIs → concurrency → extensibility. Don't jump to classes. Spend 5 minutes on requirements and state assumptions crisply.

  1. Requirements (ask, then fix): vehicle types (bike/car/truck) with different spot sizes; multiple floors; ticket on entry, fee on exit; find-nearest-spot; multiple entry/exit gates (⇒ concurrency).
  2. Core entities: ParkingLot (singleton-ish coordinator), Floor, Spot (size, state), Vehicle hierarchy or enum, Ticket, FeeCalculator (protocol), SpotAssignmentStrategy (protocol).
  3. Pattern choices to name: Strategy for both spot assignment (nearest / cheapest / EV-priority) and pricing (hourly / flat / weekend) — swap without touching the lot; Factory for creating the right spot/fee objects per vehicle type; Observer for the display boards showing free counts per floor.
  4. Concurrency — the Principal differentiator: two gates must not assign the same spot. Own it: spot allocation is a critical section — an actor (or per-floor lock) owns free-spot state; allocation is atomic claim-then-return; explain why per-floor locking beats one global lock (contention) and what invariant the lock protects.
  5. Extensibility close: "adding EV charging spots touches the Spot enum and one strategy — nothing else" — demonstrating open/closed is the mic-drop.

06 / SYSTEM DESIGN — THE BATTLEGROUND

System design ×3 — full worked designs

A Bengaluru Principal loop reported three design rounds. Prepare three distinct designs deeply: the reported one (cross-domain SSO), the team-obvious one (device trust at fleet scale), and the adjacent one (push MFA). One framework, three applications.

Your 5-step frame for every round

  1. Requirements & scale (3–5 min): users/devices, RPS on the hot path, latency budget, availability target, security constraints. For Okta always ask: multi-tenant? What's the blast radius of failure?
  2. API & data model (5 min): the 3–4 core endpoints and entities.
  3. High-level architecture (15 min): draw it; separate the latency-critical decision plane from the high-volume telemetry plane.
  4. Deep dives (15 min): follow the interviewer, but steer to your strengths — the client/agent side, crypto, caching, failure modes.
  5. Failure & operations (10 min): what breaks, staged rollout, kill switch, observability. This step is where Principal is decided.

Design 1 — Cross-domain SSO (REPORTED verbatim)

Problem: a user signs in once and is signed in across app1.com, app2.com, app3.com — different domains, so cookies don't cross. Design it.

  • Core insight to state first: cookies are domain-scoped, so cross-domain SSO requires a central identity domain (the IdP) that each app redirects to. The session lives at the IdP; apps hold their own short sessions derived from it.
  • Flow (OIDC authorization code + PKCE): unauthenticated user at app1 → redirect to idp.com/authorize → IdP has no session → login (ideally phishing-resistant) → IdP sets its own session cookie → redirects back with a one-time code → app1's backend exchanges code for ID/access tokens → app1 establishes its local session. When the user hits app2, same redirect — but the IdP session cookie exists, so it's an instant silent redirect back with a new code. That silent hop is the SSO experience.
  • Token validation at each app: verify JWT signature via the IdP's JWKS, check iss/aud/exp/nonce. Keys cached with rotation via kid.
  • Single logout — raise it before they do: the hard part. Options: front-channel logout (iframe pings to each app — unreliable), back-channel logout (IdP calls each app's logout endpoint — reliable, needs registration), or short app-session TTLs + revocation checks. Recommend back-channel + short TTLs; be honest that SLO is never perfect.
  • Scale & availability: the IdP session store is the crown jewel — replicated in-memory store (Redis) with persistence; the authorize endpoint is read-heavy and cacheable except session checks; multi-region with session affinity or a replicated session layer. IdP down = nobody logs in anywhere: this is where "Always secure. Always on." becomes an engineering requirement — active-active regions, aggressive health-based failover.
  • Security deep-dive ammo: why the code flow beats implicit (tokens never transit the browser URL), PKCE (code interception), state (CSRF), nonce (replay), exact redirect-URI allow-listing (open-redirect/token theft).

Design 2 — Device trust / FastPass-style auth for 10M endpoints (LIKELY — it's the team's product)

  • Enrollment: agent generates a P-256 key in the Secure Enclave (non-exportable); registers the public key with the backend bound to user+device; MDM-based managed device attestation proves genuine hardware — defeats cloned enrollments.
  • Auth hot path (the latency-critical plane): app hits IdP → IdP issues a challenge → agent signs with the SE key (user presence if policy requires) → IdP verifies signature + checks device posture from a hot cache → decision. Budget the path: signature verify is sub-ms; the posture lookup must be a cache read, never a telemetry-store query.
  • Posture/telemetry plane (high volume, not latency-critical): agents report posture on change + heartbeat with jitter (never synchronized); ingestion via queue (Kafka/SQS) absorbing spikes; stream processors update the posture store; decision cache invalidated on material change.
  • Offline & failure: agent caches last-known-good policy with a freshness window; device login (Desktop MFA) must define offline behavior explicitly — a laptop on a plane still needs to unlock. Fail-open vs fail-closed is per-resource policy, not an accident; revocation propagates via short decision TTLs + push-triggered recheck.
  • Fleet safety: staged rollout of agent + policy, kill switch, a bad policy push must never brick a customer fleet — canary tenants first. This paragraph alone can win the round.
Your unfair advantage

You have run this exact architecture at JumpCloud scale — millions of devices. In this round, drop real operational scars: thundering herds after OS updates, cache invalidation pain, agent upgrade rollbacks. Reported experience beats textbook diagrams at Principal level.

Design 3 — Push-notification MFA (Okta Verify style) (LIKELY — adjacent product)

  • Flow: login attempt → challenge created (state machine: created → delivered → approved/denied/expired) → push via APNs/FCM → app fetches challenge details over authenticated channel (never trust push payload — it's a doorbell, not a courier) → user approves with number matching → device signs the approval with its enrolled key → backend verifies.
  • Push unreliability — raise it yourself: APNs is best-effort; provide a pull fallback (app polls for outstanding challenges on open) — this mirrors how Okta's own SDK actually handles it.
  • Security: push-fatigue attacks → number matching + rate-limit challenges per user + risk signals; approval must be a signature from the enrolled device key, not a bare "yes" API call.
  • Scale: challenge store is short-TTL and huge-write — a TTL-native store; per-user challenge rate limiting (Section 04 reappears!); idempotent challenge creation on retries.
07 / DOMAIN — THEIR ACTUAL PRODUCTS

The macOS deep dive — speak to what this team ships

The Device Identity org ships Okta Verify (with FastPass), Okta Device Access (Desktop MFA + Platform SSO), and Device Assurance on macOS. Knowing how these work — and their engineering pain points — makes you sound like a teammate, not a candidate.

Platform SSO — the center of gravity for macOS device identity

Apple's Platform SSO framework lets an identity provider plug into the macOS login itself — linking the Okta account to the device and syncing the local password with the Okta password. Okta engineering has publicly discussed the framework's early limitations, and these make superb interview conversation:

  • Local-first verification gap: early Platform SSO verified the entered password against the local account first and only checked the IdP in the background — meaning an out-of-sync, non-IdP password could still unlock the machine. Understanding why that ordering matters (the IdP must be authoritative or device login isn't really IdP-gated) is exactly the security judgment this team exercises.
  • FileVault boundary: FileVault unlock happens pre-boot, before any IdP is reachable — users unlock disk encryption with the local password first, then authenticate to the IdP. Any design you propose for "Okta at login" must respect that boundary and define offline behavior.
  • Registration & trust: Platform SSO registration binds the device to the IdP — combine with device attestation and only registered users can log in with valid Okta credentials.
Win condition

When asked "how would you extend Okta's presence at the macOS login?", structure by trust boundary: pre-boot (FileVault — local only) → login window (Platform SSO / authorization plugin, network may be absent → cached verifier with freshness window) → post-login (Okta Verify agent, full IdP connectivity). Naming the offline case at each layer unprompted is the Staff/Principal signal.

Desktop MFA — the engineering questions they live with

  • Where does the second factor come from at the login window (no browser)? Push to phone, TOTP, or on-device factors — each with an offline story.
  • Offline access: cached factor verification with a bounded number of offline unlocks — how do you make the cache tamper-resistant? (Answer: seal it to the Secure Enclave / Data Protection keybag.)
  • Failure posture: MFA service unreachable — lock everyone out (secure) or allow with local password (available)? Policy-driven per customer; know both arguments. "Always secure. Always on." is literally this trade-off.

FastPass & Device Assurance — connect them to your work

  • FastPass = device-bound, passwordless, phishing-resistant factor: an enrolled hardware-backed key (Secure Enclave on Mac) signs origin-bound challenges, with posture checked at auth time. Mechanically, this is the primitive you built at JumpCloud — say so.
  • Device Assurance = posture policy (OS version, disk encryption, screen lock, jailbreak/root signals) evaluated as part of the access decision — your conditional-access work, productized.

08 / RAPID-FIRE

The IAM question bank — Okta-flavored answers

Compiled from Okta-specific interview question banks and screening reports. These get asked as warm-ups and in screening rounds; answer in two sentences, offer depth if invited.

REPORTEDWhat is SSO and why do organizations want it?

One authentication grants access to many applications: the user authenticates to a central identity provider, which asserts their identity to each app (SAML or OIDC). Wins: fewer passwords (less reuse/phishing surface), central policy and revocation, and lower helpdesk cost — credentials touch only the IdP, never each app.

REPORTEDSAML vs OIDC — when each?

Same job (federated authentication), different eras. SAML: XML, browser-redirect assertions, entrenched in legacy enterprise apps. OIDC: JSON/JWT on OAuth 2.0 rails, friendlier to native and mobile apps and APIs. New builds → OIDC; enterprise integrations → support both, which is exactly what Okta does.

REPORTEDName MFA factor types; what makes a factor strong?

Knowledge (password/PIN), possession (phone, security key, enrolled device), inherence (biometric). Strength is really about phishability: SMS < TOTP < push-with-number-matching < device-bound FIDO2/FastPass, which is phishing-resistant because the credential is origin-bound hardware crypto with nothing to type or relay.

REPORTEDWhat is adaptive / risk-based authentication?

The auth requirement adapts to context: device trust, location, network, behavior anomalies. Low risk → seamless; elevated risk → step-up or deny. It's how you raise security without taxing every login — the balance Okta explicitly optimizes.

REPORTEDHow do you defend against MFA push-fatigue attacks?

Number matching (the approver must type the number shown at login — breaks blind approve), rate-limiting challenges per user, risk-signal gating on when push is even offered, monitoring for anomalous challenge volume, and migrating high-risk users to phishing-resistant factors (FIDO2/FastPass) where there is no approvable prompt at all.

REPORTEDWhat is lifecycle management / SCIM, and why is JIT provisioning not enough for deprovisioning?

SCIM is the standard API for provisioning/deprovisioning users and groups into apps. JIT creates users at first login — but it's login-driven, so it can never remove access. Deprovisioning must be event-driven from the authoritative source (HR system → IdP → downstream apps), so a terminated employee is disabled within minutes regardless of login activity.

REPORTEDWhat is Zero Trust, in one crisp answer?

No implicit trust from network location: every access request is verified against user identity, device trust, and context, continuously. Identity becomes the perimeter — which is why an identity company and a device-trust team sit at the center of it.

LIKELYOAuth flows in prod vs preview behave differently — how do you debug?

Diff the configs first: redirect URIs, client IDs, issuer/authorization-server URLs, PKCE settings, token lifetimes, scopes, grant types — environment drift explains most of it. Then verify the verifier/challenge handling and consent settings match. Boring, systematic, correct — that's the point of the question.

LIKELYPrinciple of Least Privilege; threat vs vulnerability (reported in an Okta screen)

PoLP: every principal gets the minimum access needed, for the minimum time — the design principle behind scoped tokens, JIT access, and zero standing privileges. A vulnerability is a weakness in a system; a threat is an actor/event that could exploit it; risk is the product of the two.
