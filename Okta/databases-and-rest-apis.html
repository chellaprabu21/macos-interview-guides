01 / DATABASES

The storage model

A quick foundation so the rest has somewhere to attach. Knowing this layer explains why indexes behave as they do.

How a row actually gets read

storagepages from

The planner is where performance is decided — which is why you read the plan rather than guess.
  • Pages (blocks) — the unit of I/O, typically 8 KB. Databases never read one row from disk; they read the page containing it. This is why row size and locality matter.
  • Buffer pool — an in-memory cache of pages. Most tuning is really about keeping the working set in memory; once you're hitting disk on every query, nothing else saves you.
  • Write-ahead log (WAL) — changes are written to a sequential log before the data pages. This is what makes durability possible without a random write per change, and it's what enables crash recovery and replication.
  • Heap vs index-organised — a heap stores rows in no particular order with indexes pointing at them; an index-organised (clustered) table stores rows inside the index structure itself.
Why this matters in an interview

Saying "the buffer pool caches pages, and the WAL gives durability without random writes" shows you understand that a database is a storage engine, not a magic box. With an interviewer who has worked inside one, that framing is worth more than memorised SQL syntax.

02 / ★ THE CORE TOPIC

Indexes

The single most likely database question. Know the structures, the rules, and the costs.

Structures

TypeHow it worksSupports
B-treeBalanced sorted tree; leaves link sidewaysEquality, range scans, ordering, prefix matching. The default for a reason.
HashHash of the key → bucketEquality only. O(1) but no ranges, no ordering.
BitmapA bit vector per distinct valueLow-cardinality columns in analytics. Terrible under concurrent writes.
GIN / invertedTerm → list of rowsFull-text search, JSON containment, array membership.
GiST / R-treeSpatial partitioningGeometric and geographic queries.
LSM-treeBuffered writes flushed and compactedWrite-heavy workloads (Cassandra, RocksDB). Trades read amplification for write throughput.

Clustered vs non-clustered

  • Clustered — determines the physical order of rows. One per table, because the data can only be sorted one way. Range queries on the clustering key are extremely fast because the rows are physically adjacent.
  • Non-clustered (secondary) — a separate structure holding the key plus a pointer to the row. A lookup means traversing the index, then fetching the row — a second I/O per row, which is why the planner sometimes prefers a table scan.

Composite indexes — the leftmost-prefix rule

This is the classic probe. An index on (tenant_id, created_at, status) can serve:

-- ✓ uses the index
WHERE tenant_id = 42
WHERE tenant_id = 42 AND created_at > '2026-01-01'
WHERE tenant_id = 42 AND created_at > '...' AND status = 'active'

-- ✗ cannot use it (no leftmost prefix)
WHERE created_at > '2026-01-01'
WHERE status = 'active'

Why: the index is sorted by the first column, then the second within that, and so on — like a phone book sorted by surname then first name. You can't efficiently find everyone named "James" as a first name.

The follow-on rule

A range condition stops the index being used for columns after it. In (a, b, c) with a = ? AND b > ? AND c = ?, the index helps for a and b, but c is filtered afterwards rather than seeked. So put equality columns first, range columns last. That detail is what distinguishes someone who has actually tuned queries.

Covering indexes

If an index contains every column the query needs — in the key or as included columns — the engine answers from the index and never touches the table. That's an "index-only scan," and it can be an order-of-magnitude win because it eliminates the row fetch.

The costs — always name these

  • Writes slow down — every INSERT/UPDATE/DELETE must update every affected index.
  • Storage — indexes can exceed the size of the table itself.
  • Low selectivity is useless — an index on a boolean or a status with three values usually won't be used; the planner correctly decides a scan is cheaper than millions of random row fetches.
  • Unused indexes are pure cost — they slow writes and consume space for nothing. Auditing and dropping them is real work.
The answer to "how do you decide what to index?"

"I start from the queries, not the schema — index for the actual access patterns, which means looking at what's slow and frequent rather than indexing everything plausible. Then: equality columns before range columns in a composite, aim for a covering index on the hottest query, check selectivity because a low-cardinality index won't get used, and audit for unused indexes because each one taxes every write. And I'd verify with EXPLAIN rather than assuming the planner does what I expect."

03

Transactions & ACID

Know what each letter actually guarantees, and what the database does to provide it.

PropertyGuaranteeMechanism
AtomicityAll or nothing — no partial effectsUndo log / rollback segments
ConsistencyConstraints hold before and afterConstraint checking, triggers, foreign keys
IsolationConcurrent transactions don't see each other's intermediate stateLocking and/or MVCC
DurabilityCommitted data survives a crashWrite-ahead log flushed to stable storage before commit returns
The nuance on Consistency

The C in ACID is the weakest letter — it means "the database's own constraints are satisfied," not "your business rules are correct." It's also a different thing entirely from the C in CAP, which is about all nodes seeing the same data. Interviewers sometimes probe that conflation deliberately.

Durability in practice

Commit means the WAL record has been fsync'd to durable storage. That fsync is often the dominant cost of a small transaction, which is why: group commit batches multiple transactions into one flush; some systems offer relaxed durability (acknowledge before fsync) trading a small crash window for throughput; and battery-backed write caches on controllers exist specifically to make fsync fast.

04

Isolation levels & MVCC

Know the levels by the anomaly each prevents, not by name alone.

The anomalies

AnomalyWhat happens
Dirty readYou read data another transaction wrote but hasn't committed — and it may roll back
Non-repeatable readYou read the same row twice in one transaction and get different values, because someone committed in between
Phantom readYou run the same query twice and get different rows, because someone inserted matching data
Lost updateTwo transactions read, modify, and write the same row; one update silently disappears
Write skewTwo transactions each read a consistent state and write disjoint rows, together violating an invariant. Only Serializable prevents it.

The levels

LevelPreventsStill allows
Read uncommittedNothingDirty reads
Read committedDirty readsNon-repeatable and phantom reads. PostgreSQL's default.
Repeatable read+ non-repeatable readsPhantoms (in the standard). MySQL InnoDB's default, which also blocks most phantoms via gap locks.
SerializableEverything — behaves as if transactions ran one at a time— at the cost of aborts or reduced concurrency

MVCC — the mechanism to name

Multi-Version Concurrency Control. Instead of readers blocking on locks, the database keeps multiple versions of each row. A transaction sees a consistent snapshot as of its start, so readers never block writers and writers never block readers. That's the single biggest reason PostgreSQL and Oracle handle mixed read/write workloads well.

The cost — worth volunteering

Old row versions accumulate and must be cleaned up. In PostgreSQL that's vacuum, and a long-running transaction holds back the cleanup horizon, causing table bloat — a very common production problem. So "we use MVCC" comes with "and we watch for long transactions." Saying that shows operational experience rather than textbook knowledge.

Locking, deadlocks & concurrency control

The practical layer — where real applications go wrong.

Optimistic vs pessimistic

PessimisticOptimistic
ApproachLock first (SELECT ... FOR UPDATE)Read, then check nothing changed at write time (version column)
Best whenContention is high; conflicts are likelyContention is low; conflicts are rare
Failure modeBlocking, deadlocks, reduced throughputWasted work and retries under contention
-- Optimistic: the WHERE clause is the concurrency check
UPDATE accounts
   SET balance = 50, version = version + 1
 WHERE id = 1 AND version = 7;
-- 0 rows affected → someone else won; re-read and retry.

Deadlocks

Two transactions each hold a lock the other needs. Databases detect this and abort one as the victim, returning a deadlock error.

The prevention answer

"Consistent lock ordering — if every transaction acquires resources in the same order, a cycle can't form. Beyond that: keep transactions short so locks are held briefly, avoid user interaction inside a transaction, use the lowest isolation level that's correct, and make the application retry on deadlock, because in a busy system they're normal rather than exceptional. Same principle as lock ordering in concurrent code — it's the identical problem at a different layer."

Lock granularity

Row-level locks give the best concurrency but consume more memory. Some engines escalate to page or table locks when a single transaction holds too many, which can turn a well-behaved query into a system-wide stall. Also know gap locks (MySQL locks the range between index entries to prevent phantoms) and advisory locks (application-level mutual exclusion using the database as the coordinator).

06

Schema design & normalisation

Have a position on the normalise-vs-denormalise trade-off rather than reciting normal forms.

Normal forms, briefly

  • 1NF — atomic values, no repeating groups in a column.
  • 2NF — no partial dependency on part of a composite key.
  • 3NF — no transitive dependency; non-key columns depend only on the key.
  • The informal version: every non-key attribute depends on the key, the whole key, and nothing but the key.
The judgment answer

"Normalise until it hurts, denormalise until it works. Normalisation eliminates update anomalies and keeps a single source of truth, which is what you want for transactional data — user records, policy, entitlements. But it costs joins on read, so for read-heavy paths I'll denormalise deliberately: a materialised view, a counter cache, or duplicated fields — while being explicit that I've now created two places the truth lives, and I need a mechanism to keep them consistent. The mistake isn't denormalising; it's denormalising accidentally and having no plan for divergence."

Practical schema decisions

  • Primary keys: auto-increment integers are compact and index well but are enumerable and awkward across shards. UUIDv4 is unguessable and shard-friendly but random, which causes B-tree page splits and poor locality. UUIDv7 (time-ordered) is the modern compromise — unguessable and sequential.
  • Soft deletes (deleted_at) preserve history and make recovery possible, but every query must filter on it and indexes must account for it — a very common source of leaked data.
  • Timestamps in UTC, always, with timezone conversion at the edges.
  • Multi-tenancy: a tenant_id column with row-level security (simplest, but a missing filter is a cross-tenant leak), separate schemas, or separate databases (strongest isolation, heaviest operations). At an identity company this trade-off is a real conversation.
  • Migrations must be backward compatible in a rolling deployment — add a nullable column, backfill, then start writing, then make it non-null. Never a destructive change in one step.

Query performance

"This query is slow" is a likely prompt. Have a method, not a guess.

The method

1 · measurefind the actual slow queries — slow query log, pg_stat_statements — rather than the one you suspect
2 · EXPLAIN ANALYZEread the plan. Sequential scan where you expected an index? Row estimates wildly off?
3 · diagnosemissing index · wrong index · stale statistics · non-sargable predicate · N+1 · fetching too much
4 · fix and verifyre-run the plan; confirm the improvement under realistic data volume
"I'd read the plan" is the answer. Guessing at indexes is not.

Reading a plan — what to look for

  • Sequential scan on a large table where you expected an index seek.
  • Estimated vs actual rows diverging badly — the planner is working from stale statistics, so it chose a bad plan. Fix with ANALYZE.
  • Join algorithm: nested loop (good when one side is tiny), hash join (good for large unsorted sets), merge join (good when both inputs are already sorted). A nested loop over two large tables is a red flag.
  • Sort or hash spilling to disk — the working memory setting is too low for this query.

Common causes

CauseFix
N+1 queriesOne query for the list then one per item — the classic ORM bug. Batch or join.
Non-sargable predicateWHERE YEAR(created) = 2026 wraps the column in a function so the index can't be used. Rewrite as a range: created >= '2026-01-01' AND created < '2027-01-01'. Same for leading wildcards in LIKE '%x'.
SELECT *Fetches columns you don't need and defeats covering indexes.
Offset pagination deep in a setOFFSET 100000 makes the database produce and discard 100,000 rows. Use keyset/cursor pagination.
Missing statisticsPlanner mis-estimates and picks a bad plan. Run ANALYZE.
Connection exhaustionDatabases die from too many connections long before CPU. Use a pooler (PgBouncer) and bound the app's pool.
The word to know

Sargable — "Search ARGument ABLE," meaning a predicate the engine can satisfy with an index seek. Wrapping a column in a function, applying arithmetic to it, or leading a LIKE with a wildcard all make a predicate non-sargable. Using the term correctly signals real tuning experience.

08

Scaling & replication

The order matters: exhaust the cheap options before reaching for distribution.

The ladder

  1. Optimise first — indexes, queries, connection pooling. Most "we need to shard" conversations end here.
  2. Cache — the cheapest scaling there is. A read that never reaches the database costs nothing.
  3. Vertical scaling — unfashionable but effective; modern hardware is enormous, and a single PostgreSQL instance goes much further than people assume.
  4. Read replicas — for read-heavy workloads.
  5. Sharding — last, because it's a one-way door operationally.

Replication

ModeBehaviourTrade-off
AsynchronousPrimary commits without waiting for replicasFast, but replication lag and possible data loss on failover
SynchronousPrimary waits for replica acknowledgementNo data loss, but write latency now includes the network round trip
Semi-synchronousWait for at least one replicaA middle ground; common in practice
Replication lag — the bug it causes

Read-after-write: a user updates their profile, is redirected, the read hits a lagging replica, and their change appears to have vanished. Fixes: route reads to the primary for a short window after a write, use a session token carrying the write position (replicas wait to catch up), or make the UI optimistic. Naming this failure unprompted shows you've operated replicas rather than just configured them.

Sharding

  • The shard key is the decision. Choose badly and you get hot shards, or every query fanning out to all of them. tenant_id is usually right for multi-tenant systems because most queries are naturally tenant-scoped.
  • Strategies: range (simple, prone to hot spots), hash (even distribution, no range queries), directory (flexible, adds a lookup and a single point of failure).
  • What you lose: cross-shard joins, cross-shard transactions, and global uniqueness — each of which needs a workaround.
  • Resharding is the hard part — plan for it up front with more logical shards than physical nodes, so growth is a rebalance rather than a rewrite. Consistent hashing minimises movement when nodes change.

SQL vs NoSQL & CAP

Have a real position, framed by access pattern.

The families

TypeExamplesFits when
RelationalPostgreSQL, MySQLJoins, multi-row transactions, strong constraints, ad-hoc queries
Key-valueRedis, DynamoDBAccess is always by primary key; caching; session and rate-limit state
DocumentMongoDBVariable shape, hierarchical data read as a unit
Wide-columnCassandra, HBaseWrite-heavy, time-series, massive horizontal scale
Time-seriesInfluxDB, TimescaleTelemetry — writes dominate, queries are windowed aggregates
GraphNeo4jRelationship traversal is the primary query
SearchElasticsearchFull-text and faceted search over documents
The answer

"I choose by access pattern, not by category. Relational when I need joins, multi-row transactions, and constraints — and PostgreSQL scales far further than people assume, so 'we need NoSQL for scale' is usually premature. Key-value when access is always by primary key and there are no joins — a URL shortener or a device-posture store is a perfect fit, and that's why it scales, not because of the label. Time-series for telemetry. In our backend we use PostgreSQL for relational policy data and a document store for telemetry, precisely because the access patterns differ — polyglot persistence, chosen deliberately rather than by default."

CAP — state it precisely

Under a network partition, a distributed system must choose between consistency (refuse to answer rather than return stale data) and availability (answer, possibly with stale data). It is not "pick two of three" — partitions are a fact of networks, not a choice.

PACELC — the better framing

CAP only describes behaviour during a partition. PACELC extends it: if Partition, choose Availability or Consistency; Else, choose Latency or Consistency. That's more useful because it covers normal operation, where the real trade-off is that stronger consistency means more coordination means higher latency. Mentioning PACELC is a small, genuine signal of depth.

Know also BASE (Basically Available, Soft state, Eventually consistent) as the NoSQL counterpoint to ACID, and that "eventually consistent" needs a stated convergence window to be meaningful.

10 / APIs

REST fundamentals

Know the semantics precisely — especially safety and idempotency, which is where the interesting questions live.

The constraints (what makes it REST)

  • Client-server separation · Stateless — every request carries everything needed; no server-side session state, which is what makes horizontal scaling easy.
  • Cacheable — responses declare their cacheability.
  • Uniform interface — resources identified by URI, manipulated through representations, self-descriptive messages.
  • Layered system — proxies and gateways are transparent. HATEOAS — hypermedia links; the constraint almost nobody implements, and it's fine to say so.

Methods — safety and idempotency

MethodSafeIdempotentMeaning
GETYesYesRetrieve. Never mutates. Cacheable.
HEADYesYesGET without a body — metadata only
POSTNoNoCreate, or any non-idempotent action
PUTNoYesFull replace at a known URI
PATCHNoNot necessarilyPartial update
DELETENoYesRemove (repeating it leaves the same state)

Safe = no side effects. Idempotent = doing it N times has the same effect as once.

Why idempotency is the concept to emphasise

"It's not academic — it's what makes retries safe. A client whose request times out doesn't know whether the server processed it. If the operation is idempotent it can simply retry. If it isn't — a payment, a shorten request — you need an idempotency key: the client generates a unique ID, the server records it with the result, and a repeat with the same key returns the original result rather than acting again. That's the bridge between API design and distributed-systems reliability, and it's why at-least-once delivery plus idempotency beats chasing exactly-once."

Status codes

CodeUse
200 / 201 / 202 / 204OK · Created (with Location) · Accepted (async, still processing) · No Content
301 vs 302Permanent is cached by browsers indefinitely — you lose analytics and revocation. Temporary keeps control. The URL-shortener question.
304Not Modified — conditional request, client's cache is valid
400 / 422Malformed syntax · syntactically valid but semantically wrong
401 vs 403Unauthenticated (who are you?) · authenticated but forbidden (you may not). Frequently confused.
404 vs 410Not found · Gone — existed, now permanently removed. Semantically different, and useful for expiry.
409Conflict — version mismatch, duplicate
429Rate limited — always with Retry-After
5xxYour fault. Never leak stack traces in the body.
A security nuance

Sometimes you should return 404 instead of 403 — telling an unauthorised user that a resource exists is itself an information leak. If the mere existence of a record is sensitive, deny by pretending it isn't there.

API design

The concerns that separate an API you can evolve from one you're stuck with.

Resources and URIs

  • Nouns, not verbs: /users/42/sessions, not /getUserSessions. The method is the verb.
  • Plural collections, consistent casing, hierarchy only where the child genuinely belongs to the parent.
  • For genuinely non-CRUD actions, a sub-resource is cleaner than contorting REST: POST /devices/42/revoke.

Versioning

URI path (/v1/) is pragmatic, visible, and easy to route — the common choice. Header or media-type versioning is purer but harder to debug and cache. Pick one and be consistent. The real rule: never break an existing contract. Additive changes are safe; removing or renaming a field is not. Deprecate with a timeline and a Sunset header.

Pagination

// Offset — simple, but degrades and can skip rows
GET /events?limit=50&offset=100000
// The DB produces and discards 100,000 rows. And if a row is
// inserted between pages, the reader silently misses an item.

// Cursor / keyset — stable and fast at any depth
GET /events?limit=50&after=evt_01H9XK...
// WHERE id > :cursor ORDER BY id LIMIT 50  — always an index seek

Cursor pagination is the right answer for large or actively-changing sets. Say why: constant cost regardless of depth, and no skipped or duplicated rows when data shifts underneath.

Other design concerns

  • Filtering and sorting as query parameters, with an allow-list of sortable fields (an arbitrary sort column is both an injection risk and a performance risk).
  • Sparse fieldsets — ?fields=id,name to reduce payload.
  • ETags and conditional requests — If-None-Match for caching, If-Match for optimistic concurrency to prevent lost updates.
  • Consistent error format — a machine-readable code, a human message, and a request ID for correlation. application/problem+json is the standard shape.
  • Rate-limit headers so clients self-regulate rather than discovering limits by being blocked.
  • Long-running work → 202 Accepted with a status URL, rather than holding a connection open.
  • Bulk operations — decide whether a partial failure is all-or-nothing or per-item results, and say which.
Webhooks — worth mentioning

If push-style integration comes up: webhooks must be signed (HMAC over the payload with a shared secret) so the receiver can verify origin, include a timestamp to prevent replay, be delivered at-least-once with retries and backoff — which means receivers must be idempotent — and offer a dead-letter path for permanent failures. That's the same reliability vocabulary as the rest of this document.

12

API security

At an identity company this is the part of the API conversation that matters most.

Authentication vs authorization

The single most important point

They are different checks and both must happen on every request. Authenticating a user and then failing to verify they own the resource is broken object-level authorization — consistently the top vulnerability category in real APIs. It shows up as IDOR: change an ID in the URL, get someone else's data. The fix is authorizing against the acting principal on every access, server-side, not just at the entry point.

Token handling

  • Bearer tokens — whoever holds it can use it, so keep them short-lived and tightly scoped.
  • Refresh tokens — long-lived and powerful; store securely (ideally hardware-backed), rotate on use, and make them revocable server-side. Binding a refresh token to a device key so a stolen token is useless off-device is the hardening move.
  • JWT validation — verify the signature against the issuer's JWKS matching kid, then check iss, aud, exp/nbf, and nonce. Remember a JWT is signed, not encrypted — the payload is readable, so no secrets in it. And decoding is not validating.
  • Scopes bound what a token can do — least privilege applied to credentials.

The checklist

ControlWhy
TLS everywhere, validation never disabledConfidentiality and server authenticity
Server-side input validation, allow-list basedClient validation is UX, not a control
Parameterised queriesInjection
No secrets or PII in URLsURLs land in logs, proxies, referrers, browser history
Rate limiting per user and per IPBrute force, scraping, cost control. Hardest on auth endpoints.
Bound response sizes and query complexityResource-exhaustion DoS
Restrictive CORSA permissive Access-Control-Allow-Origin undermines the same-origin policy
Audit logging of security eventsDetection and forensics — without logging the secrets themselves
Generic error messagesDetailed errors are a reconnaissance gift
The CSRF nuance to volunteer

"Token-based APIs are naturally CSRF-resistant, because the browser doesn't automatically attach an Authorization header — the application must. Cookie-based sessions are vulnerable, because cookies are attached automatically, which is why they need SameSite and anti-CSRF tokens. So the auth mechanism you choose changes which class of attack you have to defend against."

REST vs GraphQL vs gRPC

Have an opinion with reasons, not a preference.

RESTGraphQLgRPC
TransportHTTP + JSONHTTP + JSON (usually one endpoint)HTTP/2 + Protobuf (binary)
ContractOpenAPI (optional)Schema (mandatory, typed).proto (mandatory, typed)
FetchingFixed shapes — over/under-fetchingClient specifies exactly what it needsFixed, but efficient
CachingHTTP caching works nativelyHard — everything is a POST to one URLManual
StreamingNo (SSE/WebSocket separately)SubscriptionsBidirectional, first class
Browser supportNativeNativeNeeds grpc-web proxy

GraphQL's security cost

Letting the client shape the query means letting them shape the cost. Deeply nested or recursive queries can be a denial-of-service vector, so you need query depth and complexity limits, cost analysis, and persisted queries in production. Naming that trade-off is more valuable than praising the flexibility.

The answer

"REST for public and partner APIs — it's cacheable, debuggable, universally understood, and HTTP semantics do a lot of work for you. gRPC for internal service-to-service where I want a typed contract, efficient binary encoding, and streaming. GraphQL when clients genuinely need varied shapes and I'm aggregating several sources — accepting that I now own query-cost control and lose HTTP caching. Most systems end up with more than one, chosen per boundary rather than standardised for its own sake."

14

Interview Q&A

Two or three sentences, then depth if invited.

LIKELYHow do indexes work, and when would you add one?

A B-tree index is a sorted structure giving O(log n) lookup and supporting ranges and ordering, at the cost of slowing every write and consuming space. I add them from the queries, not the schema — find what's slow and frequent, then index for that access pattern. Rules I apply: equality columns before range columns in a composite because a range stops the index being used for anything after it, aim for a covering index on the hottest path so it never touches the table, and check selectivity because a low-cardinality index won't get chosen. Then verify with EXPLAIN rather than assuming.

LIKELYExplain ACID.

Atomicity — all or nothing, via the undo log. Consistency — the database's own constraints hold before and after, which is narrower than "your business rules are right." Isolation — concurrent transactions don't see each other's intermediate state, via locking or MVCC. Durability — committed data survives a crash, because the write-ahead log is fsync'd before commit returns. Worth noting the C in ACID is not the C in CAP; they're different properties.

LIKELYWhat are isolation levels?

They define which concurrency anomalies you tolerate. Read committed prevents dirty reads but allows non-repeatable and phantom reads — it's PostgreSQL's default. Repeatable read also prevents non-repeatable reads. Serializable prevents everything including write skew, but costs concurrency and causes aborts you must retry. Most systems run read committed and handle the specific races explicitly, with optimistic concurrency on the rows where lost updates would matter.

LIKELYSQL or NoSQL — how do you choose?

By access pattern. Relational when I need joins, multi-row transactions, and constraints — and PostgreSQL scales much further than people assume, so reaching for NoSQL "for scale" is usually premature. Key-value when access is always by primary key with no joins, which is exactly why something like a URL shortener or a posture store scales trivially. Time-series for telemetry. We run both: PostgreSQL for relational policy data, a document store for telemetry, because the access patterns genuinely differ.

LIKELYThis query is slow. What do you do?

Measure first — find the actually-slow queries from the slow log or pg_stat_statements rather than the one I suspect. Then EXPLAIN ANALYZE and read the plan: sequential scan where I expected a seek, estimated versus actual rows diverging badly (stale statistics), a nested loop over two large tables, or a sort spilling to disk. Common causes are a missing or wrong index, an N+1 pattern, or a non-sargable predicate like wrapping the column in a function. Fix, re-run the plan, and verify at realistic data volume.

LIKELYHow would you scale a database?

In order of cost. Optimise queries and indexes and pool connections — most "we need to shard" conversations end here. Then cache, because a read that never reaches the database is free. Then vertical scaling, which is unfashionable but a single modern instance goes very far. Then read replicas for read-heavy load, accepting replication lag and handling read-after-write. Sharding last, because the shard key choice is effectively irreversible and you lose cross-shard joins and transactions.

LIKELYWhat's the difference between PUT and POST?

PUT is idempotent and replaces a resource at a URI the client already knows — sending it five times leaves the same state. POST is not idempotent and typically creates a resource whose URI the server assigns. Practically it matters for retries: a client whose request times out can safely retry a PUT, but retrying a POST might create duplicates. That's why non-idempotent endpoints should accept an idempotency key, so the server can recognise a repeat and return the original result.

LIKELYHow do you secure a REST API?

Authentication and authorization are separate checks and both happen on every request — authenticating then failing to verify resource ownership is broken object-level authorization, the top real-world API vulnerability. TLS everywhere with validation never disabled. Server-side allow-list input validation and parameterised queries. No secrets or PII in URLs, since they land in logs and proxies. Short-lived scoped tokens with a revocation path, rate limiting per user and IP with the auth endpoints limited hardest, restrictive CORS, and audit logging that doesn't log the secrets.

POSSIBLEHow would you paginate a large result set?

Cursor-based, not offset. Offset pagination makes the database produce and discard everything before the offset, so it degrades linearly with depth, and it silently skips or duplicates rows if data changes between pages. A cursor is an opaque encoding of the last seen sort key, so the query is always WHERE id > :cursor ORDER BY id LIMIT n — a constant-cost index seek regardless of depth, and stable under concurrent inserts. The trade-off is you can't jump to page 50, which is almost never a real requirement.

POSSIBLEExplain CAP.

Under a network partition a distributed system must choose between consistency — refusing to answer rather than returning stale data — and availability, answering with possibly stale data. It isn't "pick two of three," because partitions are a fact of networks rather than a design choice. PACELC is the more useful framing: during a partition choose availability or consistency, and else, in normal operation, choose latency or consistency — because stronger consistency means more coordination and therefore higher latency.
