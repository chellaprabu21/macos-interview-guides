Attacks · application security · secure design · threat modelling

Cybersecurity, from mechanism to defence.

Every named attack explained by how it actually works, not just what it's called — because an interviewer at a security company can tell the difference immediately. Each section ends with the defence and the trade-off, and section 11 covers the design principles that tie it all together.

01 / FOUNDATION

The mental model

Frame everything with these and individual attacks become instances rather than facts to memorise.

CIA triad

PropertyViolated by
Confidentiality — only authorised parties can readData breach, eavesdropping, MITM
Integrity — data isn't altered without detectionTampering, injection, MITM modification
Availability — the system works when neededDDoS, ransomware, lockout abuse

Add authentication (who are you), authorization (what may you do), and non-repudiation (you can't deny it) and you have the full vocabulary.

Vulnerability, threat, risk — use these precisely

  • Vulnerability — a weakness in the system (an unpatched library).
  • Threat — an actor or event that could exploit it (a ransomware crew).
  • Exploit — the technique that turns the vulnerability into a compromise.
  • Risk — likelihood × impact. This is what you actually prioritise on; a critical vulnerability in an unreachable component may be lower risk than a moderate one on your login path.

Defence in depth means breaking the chain at multiple links — you don't have to catch stage one.
Why this framing helps

"I think in terms of the kill chain rather than individual attacks. Phishing is initial access; malware is execution and persistence; a MITM might be either recon or exfiltration. The value of that framing is that you don't need to stop stage one — you need multiple opportunities to detect and break the chain. It's also how endpoint detection actually works: individual events are noise, and the sequence is the signal."

Malware

Know the taxonomy, but spend your words on detection and containment — that's your actual expertise.

Taxonomy

TypeDefining behaviour
VirusAttaches to a host file; needs the user to run it
WormSelf-propagating across a network without user action
TrojanDisguised as legitimate software; the user installs it willingly
RansomwareEncrypts data and extorts. Modern variants also exfiltrate first — "double extortion" — so backups alone aren't sufficient
Spyware / keyloggerCovert monitoring and credential theft
RootkitHides at a privileged layer (kernel or firmware) to evade detection
RATRemote access — interactive control by an operator
CryptominerSteals compute. Low harm, high prevalence, often the first sign of a broader compromise
FilelessLives in memory, abuses legitimate tools (living off the land) — leaves no file to scan

Detection approaches — the trade-offs

ApproachStrengthWeakness
Signature / hashPrecise, no false positivesUseless against anything new or repacked
Heuristic / static analysisCatches variantsFalse positives; defeated by packing and obfuscation
BehaviouralCatches novel and fileless malwareNeeds correlation and tuning; noisier
Reputation / cloudFleet-wide intelligenceNeeds connectivity; latency on the decision path
Your ground — say this

"This is what our agent does. The Endpoint Security framework gives me process-execution events carrying the binary's code-signing identity and CDHash, so I can enforce deny-listing at exec time, and file events let me spot ransomware behaviour — a process rapidly rewriting many files across directories. The detection value is in correlation, not individual events: an Office app spawning a shell that spawns curl to a rare domain, then writing an executable to a user directory, is an incident. Each of those events alone is noise. So I maintain a process tree from fork/exec/exit and evaluate chains, not points."

Defences worth naming

  • Code signing and notarization — on macOS, unsigned or un-notarized code doesn't launch by default. That's a platform-level control, not something each app implements.
  • Least privilege — a compromised unprivileged process is a much smaller problem than a compromised root one.
  • Application allow-listing — strong but operationally heavy.
  • Network egress control — even if execution succeeds, command-and-control and exfiltration need the network.
  • Rapid patching — most successful compromises use known vulnerabilities, not zero-days.
  • Isolation and response — the ability to remotely cut a machine off while keeping your own management channel alive.
03 / NAMED

Phishing

Directly Okta's problem space. The defence answer here matters more than the taxonomy.

Variants

  • Phishing — mass, generic. Spear phishing — targeted with personal detail. Whaling — executives.
  • Smishing / vishing — SMS and voice, increasingly with synthetic audio.
  • Business email compromise — no malware at all, just a convincing instruction to transfer money. Often the most costly.
  • Adversary-in-the-middle (AiTM) — the critical modern variant: a reverse-proxy phishing site relays credentials and the MFA code to the real site in real time, then steals the resulting session cookie. This defeats most MFA.
  • Consent phishing — no credentials stolen at all; the user is tricked into granting an OAuth app persistent access.
The point that matters most

Most MFA is still phishable. SMS and TOTP are just typed secrets a real-time relay can forward. Push-approve is vulnerable to MFA fatigue — spam prompts until the user taps to make it stop. The step change is origin-bound hardware crypto: with FIDO2/WebAuthn the credential is cryptographically scoped to the legitimate origin, so a look-alike domain cannot elicit a usable assertion and there is nothing to relay. That's why the industry is converging on passkeys and device-bound factors.

The layered defence

LayerControl
Prevent deliverySPF, DKIM, DMARC; attachment sandboxing; external-sender banners
Prevent the clickDNS filtering, newly-registered-domain blocking, URL rewriting
Prevent the harmPhishing-resistant MFA (FIDO2), device trust, conditional access
Limit the blast radiusLeast privilege, short session lifetimes, token binding, re-auth for sensitive actions
Detect after the factImpossible-travel and anomaly detection, session-token anomaly monitoring
The framing to use

"User training helps at the margins but doesn't scale — a sufficiently good pretext beats anyone on a bad day. So I treat phishing as a design problem, not a training problem: make the credential unphishable, and the attack stops working regardless of how convincing the pretext is. Then add device trust so a stolen session from an unmanaged device still fails the access check."

04 / NAMED

Brute force & credential attacks

Distinguish the variants — they need different defences, and most people conflate them.

AttackMechanismWhy standard defences miss it
Brute forceTry every combinationRate limiting handles it
DictionaryTry likely passwordsRate limiting handles it
Credential stuffingReplay username/password pairs from other breachesEach attempt may be a valid credential — no per-account failure spike. By far the most common in practice.
Password sprayingOne common password against thousands of accountsPer-account lockout never triggers — each account sees one or two failures. You must monitor across accounts.
Offline crackingAttack a stolen hash databaseNo online defence applies at all — only slow KDFs help

Defences, matched to the attack

  • Slow password hashing (Argon2id/bcrypt) — the only defence against offline cracking.
  • Rate limiting per account and per IP — token bucket with exponential backoff.
  • Lockout with escalating duration — but see the warning below.
  • MFA — makes a correct password insufficient, which is the actual answer to credential stuffing.
  • Breached-password checks at registration and reset.
  • Cross-account failure monitoring — the only way to see spraying.
  • Device and behavioural signals — a login from a never-seen device in a new country should step up, not just pass.
The insight that will land at an identity company

Lockout is itself a denial-of-service vector. If I can lock any account by failing five times, I can deny service to your entire user base — and at an enterprise IdP that's an outage. Mitigations: key on IP + account rather than account alone, prefer progressive delays over hard locks, and require a CAPTCHA before locking. And responses must be identical for wrong-password and unknown-user, including timing — otherwise your lockout behaviour becomes a user-enumeration oracle.

The distributed caveat

Per-process counters mean an attacker who lands on different servers gets N times the allowed attempts. A real guarantee needs shared state — Redis with atomic operations — which puts a network hop on the auth path. That's a genuine trade-off worth naming.

05 / NAMED

DDoS

Know the three layers — the defences differ completely.

LayerMechanismExamples
VolumetricSaturate bandwidthUDP flood; DNS/NTP/memcached amplification — a small spoofed request produces a huge response aimed at the victim
ProtocolExhaust connection stateSYN flood (half-open connections), Slowloris (holding connections open with partial requests)
ApplicationExpensive requestsHTTP flood on a search endpoint, GraphQL query complexity abuse. Hardest — traffic looks legitimate

Defences

  • Absorb — CDN and scrubbing providers with capacity far beyond yours; anycast to distribute load geographically.
  • Filter — rate limiting, connection limits, SYN cookies (no state until the handshake completes), geo/ASN blocking as a blunt instrument.
  • Cache — every request served from cache is one that never reaches origin. Often the highest-leverage control.
  • Scale — autoscaling with a cost ceiling, because "scale infinitely" is also a way to lose (economic denial of service).
  • Degrade gracefully — shed non-essential features to keep the core alive. Decide in advance what's essential.
  • Prioritise — authenticated known-good traffic over anonymous during an attack.
Your angle — the self-inflicted version

"There's also the DDoS you do to yourself. Millions of agents that all wake at the same moment after an OS update are a thundering herd against your own backend — which is why every timer in our fleet carries jitter, why ingestion sits behind a queue that absorbs spikes rather than passing them to the database, and why retries use exponential backoff with randomisation. A synchronised retry storm after a brief outage will re-create the outage; that's a real operational scar."

06 / NAMED

Man in the middle

An attacker between two parties, reading or modifying traffic.

How they get in position

  • Rogue Wi-Fi — an evil-twin access point, or an open network the attacker controls.
  • ARP spoofing — claiming another host's IP on a local network.
  • DNS poisoning / hijack — sending the victim to the wrong address entirely.
  • BGP hijack — rerouting traffic at internet scale.
  • Compromised or rogue CA — issuing a certificate for a domain the attacker doesn't own.
  • SSL stripping — downgrading an HTTPS link to HTTP before the user notices.
  • Malicious proxy on the device — malware installing its own trusted root.

Defences

ControlWhat it stops
TLS with proper validationThe baseline. Chain to a trusted root, valid dates, hostname matches SAN. Never disable validation to make something work.
Certificate pinningA rogue or compromised CA. Cost: rotation must be planned, and it breaks under corporate TLS inspection.
HSTSSSL stripping and protocol downgrade
Certificate TransparencyDetects mis-issued certificates after the fact
mTLSBoth sides authenticate — the natural fit for a device with a hardware-bound key
Forward secrecy (ECDHE)Recorded traffic stays safe even if the long-term key later leaks
The nuance to volunteer

"Enterprise TLS inspection is a sanctioned MITM — the organisation installs its own CA on managed devices so a proxy can decrypt and inspect traffic. It's legitimate and common, but it means pinned clients break, which is why some security agents must be explicitly exempted from inspection. It's a good illustration that 'MITM' describes a position, not necessarily malice — and that a control which helps one team can break another's product."

07 / NAMED

SQL injection

The mechanism in one sentence: user input becomes code instead of data.

// ✗ Vulnerable — the input is concatenated into the query text
let sql = "SELECT * FROM users WHERE email = '\(email)'"

// Attacker supplies:  x' OR '1'='1
// Resulting query:    SELECT * FROM users WHERE email = 'x' OR '1'='1'
//                     → returns every row

// Or worse:           x'; DROP TABLE users; --
// ✓ Parameterised — the input can never be interpreted as SQL
let sql = "SELECT * FROM users WHERE email = ?"
statement.bind(1, email)

// The database parses the query structure FIRST, then binds
// values into placeholders. Structure and data are separated.
Why parameterisation is the answer and escaping isn't

"Parameterised queries work because the database parses the query structure before the data is supplied — so the input can never change the meaning of the statement. Manual escaping tries to sanitise data into a form that looks safe inside a string, which is fragile: character-set edge cases, nested quoting, and second-order injection all defeat it. The structural fix beats the filtering fix."

Variants and depth

  • Blind SQLi — no error output, so the attacker infers data one bit at a time from boolean differences in the response, or from timing (SLEEP()). Slow but completely effective.
  • Second-order — the payload is stored safely, then used unsafely later by a different code path. Input validation at entry doesn't catch it.
  • NoSQL injection — the same class in a different syntax. Passing an unvalidated object where a scalar is expected can produce {$ne: null} style operator injection.
  • ORM escape hatches — ORMs protect you until someone uses a raw fragment, which reintroduces the risk in a codebase everyone assumes is safe.

Defence in depth

  • Parameterised queries everywhere — non-negotiable.
  • Least-privilege database accounts — the application does not need DROP or GRANT. This turns a catastrophic injection into a limited one.
  • Input validation as an additional layer, allow-list based.
  • Never expose raw database errors — they hand the attacker a schema map.
  • Static analysis in CI to catch string concatenation into query builders.
08 / NAMED

Cross-site scripting

Same root cause as SQLi — data interpreted as code — but the interpreter is the browser.

The mechanism

Attacker-controlled input is rendered into a page, and the browser executes it as script in the victim's origin. That means it runs with the victim's session: it can read cookies (unless HttpOnly), read the DOM, make authenticated requests, keylog the page, or rewrite what the user sees.

TypeWhere the payload livesImpact
StoredPersisted server-side — a comment, a profile fieldHighest — served to every viewer, no delivery needed
ReflectedIn the request, echoed into the responseNeeds a crafted link, so it's a delivery problem
DOM-basedClient-side JS writes untrusted data into the DOMServer never sees the payload — server-side filtering can't help

Defences

  • Context-aware output encoding — the crucial nuance. HTML body, HTML attribute, JavaScript, CSS, and URL contexts each need different escaping. Encoding for one context inside another is still vulnerable. Use the framework's context-aware escaping; don't hand-roll.
  • Content Security Policy — restrict which origins scripts may load from, and disallow inline script. Strong defence in depth, though it takes effort to deploy on an existing app.
  • HttpOnly cookies so JavaScript cannot read the session token; Secure so it's HTTPS-only.
  • Avoid dangerous sinks — innerHTML, document.write, eval. Prefer text-setting APIs. Use a vetted sanitiser (DOMPurify) if you genuinely must render user HTML.
  • Framework auto-escaping — React, Vue and similar escape by default; the vulnerabilities come from the deliberate escape hatches like dangerouslySetInnerHTML.
The Apple-platform angle — worth raising

"XSS isn't only a web problem. A WKWebView inside a native app has the same exposure, and it's more dangerous because of the native bridge: if I inject unvalidated data into JavaScript, or expose a broad message handler, an XSS becomes a path into native code and whatever entitlements my app holds. So I'd keep the bridge surface minimal and strongly typed, validate everything crossing it in both directions, avoid evaluateJavaScript with interpolated input, and disable JavaScript entirely if the view doesn't need it."

09 / NAMED

Cross-site request forgery

The subtlest of the three. The attacker never reads anything — they borrow authority.

The mechanism

1victim is logged into bank.com — the browser holds a session cookie
2victim visits evil.com, which contains a form or image auto-submitting to bank.com
3the browser automatically attaches the bank.com cookie — because that's what browsers do
4bank.com sees a properly authenticated request and performs the action
The attacker never sees the response. They don't need to — the side effect is the goal.

Defences

  • SameSite cookies — Lax (the modern browser default) blocks cookies on cross-site POSTs; Strict blocks them on all cross-site requests. This is now the primary defence.
  • Anti-CSRF token — an unpredictable per-session value required on state-changing requests. The attacker can't read it because of the same-origin policy. Still the belt-and-braces control.
  • Never use GET for state changes — a GET can be triggered by an <img> tag with no user interaction at all.
  • Verify Origin/Referer headers as a secondary check.
  • Re-authenticate for sensitive actions — password change, payment, adding an MFA factor.
The distinction to draw — this is the good answer

"XSS and CSRF are often confused but they're different problems. XSS is a code-execution problem — the attacker runs script in your origin and can therefore read anything. CSRF is an authority problem — the attacker can't read anything, they just cause the browser to send a request that carries the user's ambient credentials. That's why the defences differ: XSS is fixed by output encoding, CSRF by ensuring requests can't be forged blind.

Worth adding: token-based auth in an Authorization header is naturally CSRF-resistant, because the browser doesn't attach it automatically — the application has to. So a pure-API architecture with bearer tokens largely sidesteps CSRF, while cookie-based sessions need explicit protection. Note that XSS defeats everything — if an attacker can run script in your origin, they can read the CSRF token too."

OWASP & the wider vulnerability landscape

Beyond the named three. Know the categories that dominate real findings.

CategoryWhat it means
Broken access controlConsistently the top category. Authenticating a user then failing to check they own the resource — IDOR, where changing an ID in a URL returns someone else's data. Fix: authorize every access, server-side, against the acting principal.
Cryptographic failuresData unencrypted in transit or at rest, weak algorithms, hardcoded keys, secrets in logs.
InjectionSQL, NoSQL, command, LDAP, XPath — all the same root cause.
Insecure designA flaw in the design itself, not the implementation — no amount of clean code fixes a missing control. This is what threat modelling addresses.
Security misconfigurationDefault credentials, verbose errors, unnecessary features, open storage buckets, permissive CORS.
Vulnerable componentsOutdated dependencies with known CVEs. Needs an SBOM and automated scanning.
Auth failuresWeak passwords permitted, no MFA, session fixation, tokens that don't expire or can't be revoked.
Software & data integritySupply chain — compromised dependencies, unsigned updates, poisoned CI. Increasingly the dominant threat.
Logging & monitoring failuresYou can't respond to what you can't see. Also: don't log secrets or PII while fixing this.
SSRFThe server fetches a URL the attacker controls, reaching internal services or cloud metadata endpoints. Fix: allow-list destinations, block internal ranges, no redirects.

Mobile and macOS-specific

  • Insecure local storage — secrets in UserDefaults or plist files instead of the Keychain.
  • Improper platform usage — disabling certificate validation, over-broad entitlements, exported interfaces that shouldn't be.
  • Reverse engineering and tampering — a shipped binary is in the attacker's hands. Never rely on client-side checks for security; enforce server-side.
  • IPC exposure — an XPC interface that takes an arbitrary path or command is a privilege-escalation API. Validate the peer by audit token, never by pid.
  • Supply chain — every dependency ships under your signature with your entitlements.
Your credibility line

"In a security agent the supply-chain angle is sharpest: every dependency I take ships signed by me, with my entitlements, onto machines I don't own. A compromised upstream package becomes a root-privileged compromise on a customer fleet. So I pin versions, commit the resolved file, review update diffs rather than floating, and I'm especially wary of build-time plugins — that's arbitrary code executing where the signing identity lives."

Secure design & shift left

Explicitly on your focus list. This is where you demonstrate judgment rather than knowledge.

What shift left actually means

Security work moves earlier — into requirements, design, and development — rather than a penetration test the week before release, where every finding is expensive and half get deferred. The economics drive it: a design flaw caught in a whiteboard session costs an hour; the same flaw found in production costs an incident.

Threat modelling — STRIDE

ThreatProperty violatedMitigated by
SpoofingAuthenticationStrong auth, mTLS, code-signature verification of peers
TamperingIntegritySignatures, MACs, checksums, immutable logs

The method: draw the data flow, mark the trust boundaries, and walk STRIDE at each boundary. Trust boundaries are where the interesting threats live — that's where data crosses from a less-trusted to a more-trusted context.

The design principles

PrincipleIn practice
Least privilegeEvery process, token, and account gets the minimum for the minimum time
Defence in depthMultiple independent controls — assume any one will fail
Fail securelyAn error path denies. Default deny, and be deliberate about any fail-open
Complete mediationCheck authorization on every access, not just the first — this is what broken access control violates
Separation of privilegeSplit a system so compromising one part isn't enough
Minimise attack surfaceFewer entry points, narrower interfaces, features off by default
Secure defaultsThe out-of-the-box configuration is the safe one; insecurity requires deliberate action
No security through obscurityAssume the attacker has your source. Kerckhoffs's principle
Economy of mechanismSimple designs are auditable; complex ones hide flaws
The worked example that proves you live this

"Our agent architecture is these principles made concrete. The UI process is large and parses untrusted input, so it gets no privilege. The daemon has root, so it stays small and boring with a narrow XPC interface — the client requests, the daemon decides, and no method ever takes an arbitrary path or command. Every XPC connection is validated by audit token against a code-signing requirement, not by pid, because pids recycle and can be raced. That's separation of privilege and minimised attack surface as a design choice — the architecture limits what a compromise can reach, rather than relying on the code being bug-free."

Secure coding practices

  • Never trust input — validate at the trust boundary, allow-list based, server-side. Client-side validation is UX, not a control.
  • Parameterise, don't concatenate — SQL, shell commands, everything.
  • Context-aware output encoding.
  • Constant-time comparison for secrets and tokens.
  • Don't roll your own crypto; use vetted libraries and safe modes.
  • No secrets in source, logs, or URLs — URLs land in proxies, browser history, and referrer headers.
  • Bounds and integer-overflow discipline, especially at C boundaries — directly relevant when working against the Endpoint Security C API.
  • Fail closed on error paths, and make error handling explicit rather than incidental.
  • Dependency hygiene — pin, scan, audit, and treat every dependency as code you sign.

Security in the pipeline

  • SAST — static analysis on every PR. DAST — running-app scanning. SCA — dependency/CVE scanning with an SBOM.
  • Secrets scanning to stop credentials being committed.
  • Sanitizers in CI — Thread Sanitizer and Address Sanitizer on scheduled runs eliminate whole classes of memory and concurrency bugs.
  • Security review as part of code review rather than a separate gate — the gate is where velocity dies and findings get deferred.
  • Fuzzing for parsers and anything handling untrusted input.
The closing framing

"I work on the enforcement side of this — the agent that detects and blocks — so I think about attacks from both directions: what an attacker does, and what telemetry would reveal it. Threat modelling is the same exercise done before the code exists rather than after the incident, and it's cheaper in exactly the same way that writing a test before the bug is cheaper than debugging in production."

Interview Q&A

Two or three sentences each, then depth if invited.

CERTAINExplain SQL injection and how you prevent it.

User input gets concatenated into a query, so the input is interpreted as SQL rather than data — an attacker can then change what the query means, returning all rows or executing other statements. The fix is parameterised queries: the database parses the query structure first and binds values into placeholders, so input can never alter the statement. Manual escaping is fragile and gets bypassed. Defence in depth: least-privilege database accounts so the app can't DROP, allow-list input validation, and never returning raw database errors.

CERTAINWhat's XSS and how does it differ from CSRF?

XSS is when attacker input gets rendered into a page and the browser executes it as script in the victim's origin — so it can read cookies, the DOM, and act as the user. CSRF is different in kind: the attacker can't read anything, they just cause the victim's browser to send a request that automatically carries the session cookie. XSS is a code-execution problem fixed by context-aware output encoding and CSP; CSRF is an authority problem fixed by SameSite cookies and anti-CSRF tokens. And note XSS defeats CSRF protection entirely — script in your origin can read the token.

CERTAINHow would you defend against brute-force attacks?

Depends which variant. Classic brute force yields to rate limiting and lockout. Credential stuffing needs MFA and breached-password checks, since each attempt may be a valid credential. Password spraying evades per-account lockout entirely — you only see it by monitoring failures across accounts. And offline cracking of a stolen database is unaffected by any online control; only a slow memory-hard KDF like Argon2id helps there. The caveat I'd raise: lockout is itself a DoS vector, so I'd key on IP-plus-account and prefer progressive delays over hard locks.

LIKELYWhat is a man-in-the-middle attack and how do you prevent it?

An attacker positioned between two parties, reading or modifying traffic — via rogue Wi-Fi, ARP or DNS spoofing, BGP hijack, or a compromised CA. TLS with proper certificate validation is the baseline: chain to a trusted root, valid dates, hostname matching the SAN. For a controlled client like an agent I'd add certificate pinning to defeat a rogue CA, while planning rotation carefully and knowing it breaks under corporate TLS inspection. HSTS prevents downgrade, forward secrecy protects recorded traffic, and mTLS authenticates the client too.

LIKELYHow do you protect against phishing?

Treat it as a design problem, not a training problem. Training helps at the margins but a good pretext beats anyone eventually. The structural fix is phishing-resistant credentials: FIDO2/WebAuthn binds the credential to the legitimate origin, so a look-alike domain can't elicit a usable assertion and there's nothing to relay. That matters because most MFA is still phishable — SMS and TOTP are typed secrets an adversary-in-the-middle proxy forwards in real time, and push-approve falls to MFA fatigue. Then layer device trust and conditional access so a stolen session from an unmanaged device still fails.

LIKELYWhat does "shift left" mean?

Moving security work earlier in the lifecycle — into requirements, design, and development — instead of a penetration test before release where findings are expensive and often deferred. In practice: threat modelling at design time using STRIDE across trust boundaries, security requirements written alongside functional ones, security as part of ordinary code review rather than a separate gate, and automated SAST, dependency scanning, and secrets scanning in CI. The driver is economics — a design flaw caught on a whiteboard costs an hour; the same flaw in production costs an incident.

LIKELYWhat are the most important secure design principles?

Least privilege, defence in depth, fail securely, and complete mediation — checking authorization on every access, not just the first, which is exactly what broken access control violates. I'd add minimising attack surface and secure defaults. The concrete example I'd give is our agent: an unprivileged UI process talking over a narrow XPC interface to a small root daemon, with every connection validated by audit token against a code-signing requirement. The design limits what a compromise can reach, rather than depending on the code being bug-free.

LIKELYHow would you secure an API?

Authentication and authorization are separate checks and both happen on every request — authenticating the user then failing to verify they own the resource is broken object-level authorization, consistently the top vulnerability category. TLS everywhere with proper validation. Validate and bound every input server-side. Rate limit by user and IP, hardest on auth endpoints. Never put secrets or PII in URLs, because they land in logs and proxies. Short-lived tokens with a revocation path, and audit logging of security-relevant events without logging the secrets themselves.

POSSIBLEWalk me through how you'd threat model a feature.

Draw the data flow — components, data stores, and the paths between them — then mark the trust boundaries, because that's where the interesting threats live. Walk STRIDE at each boundary: can an attacker spoof this identity, tamper with this data, deny this action happened, read what they shouldn't, deny service, or escalate privilege? Then rank by risk — likelihood times impact — and decide for each: mitigate, accept, transfer, or eliminate. Write the accepted risks down explicitly, because an undocumented accepted risk is indistinguishable from an oversight.

POSSIBLEHow do you handle a dependency with a known CVE?

First establish real exposure — is the vulnerable code path actually reachable from our usage? A critical CVE in an unused function is lower risk than a moderate one on our auth path. Then patch if an update exists; if not, assess whether we can pin to a safe version, vendor and fix, or mitigate at another layer. Ship it through the normal release process unless it's actively exploited, in which case it's an incident. And structurally: SBOM plus automated scanning so we learn about these from a pipeline rather than from a customer.

POSSIBLEWhat's the biggest security risk in a macOS agent?

Privilege escalation through the IPC surface. The agent runs a root daemon by necessity, and the UI process — which parses untrusted input and is the realistic compromise target — talks to it. So every XPC method is a potential escalation path. Mitigations: the narrowest possible interface where the client requests and the daemon decides, never a method taking an arbitrary path or command, peer validation by audit token against a code-signing requirement rather than pid, and treating every parameter as hostile. Second biggest is supply chain, because everything I ship carries my signature and entitlements.

The posture

You work on the defensive side of this daily, so speak from that: what an attacker does and what telemetry reveals it. Where you hit your limit — exploit development, cryptanalysis, red-team tradecraft — say so cleanly and pivot to reasoning. At a security company, honest boundaries plus sound judgment reads far better than a confident approximation, and an interviewer with a security background will spot the difference immediately.
