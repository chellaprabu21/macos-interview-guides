Every primitive, every named algorithm, and the Apple platform layer

Cryptography, properly — from primitives to production.

Built for an interview at an identity company, where crypto isn't trivia — it's the product. Each section gives the concept, the algorithms, what breaks it, and the exact words to say. Section 10 connects everything to the Secure Enclave work you already do.

01 / FOUNDATION

The four goals

Every primitive exists to serve one of these. When you meet a new tool, ask which.

GoalPlain questionServed by
ConfidentialityCan a stranger read this?Encryption — symmetric and asymmetric
IntegrityWas this changed in transit?Hashes, MACs, signatures
AuthenticationAre you really who you claim?Signatures, certificates, MACs
Non-repudiationCan you later deny you sent it?Digital signatures only — not MACs
The distinction interviewers probe

A MAC gives integrity and authentication but not non-repudiation, because both parties share the key — either could have produced it. A signature gives all three, because only the private-key holder could have signed. That single sentence separates people who've studied crypto from people who've read a blog post.

02

Hashing

One-way fingerprints. The building block under signatures, passwords, and integrity checks.

Properties

  • Deterministic — same input, same digest, always.
  • Fixed output size — "hi" and a 4 GB file both produce a 256-bit SHA-256 digest.
  • One-way (preimage resistance) — given a digest, you can't find an input producing it.
  • Second preimage resistance — given input A, you can't find a different B with the same digest.
  • Collision resistance — you can't find any two inputs sharing a digest. This is the weakest property and the first to fall.
  • Avalanche effect — one bit of input change alters roughly half the output bits.

The algorithms

AlgorithmOutputStatus
MD5128-bitBroken. Practical collisions since 2004. Never for security.
SHA-1160-bitBroken. SHAttered (2017) produced a real collision. Deprecated everywhere.
SHA-256 / SHA-512256 / 512-bitSHA-2 family. Current workhorse, no practical attacks.
SHA-3 (Keccak)variableDifferent internal construction (sponge). A hedge against a SHA-2 break, not a replacement.
BLAKE2 / BLAKE3variableFaster than SHA-2, secure. Common in non-standardised contexts.
Nuance worth knowing

MD5 and SHA-1 are broken for collision resistance, not preimage resistance. So MD5 as a non-security checksum for accidental corruption is still technically fine — but say you'd use SHA-256 anyway, because a reviewer shouldn't have to reason about which property you were relying on.

Where hashing is misused

Never hash passwords with a plain hash. SHA-256 is designed to be fast — modern GPUs compute billions per second, so a stolen database falls quickly. Passwords need a deliberately slow, salted KDF (section 09). This is the single most common crypto mistake in real applications.

One key, both directions. Fast — but how do both parties get it?

The algorithms

AlgorithmKey / blockStatus
AES128/192/256-bit key, 128-bit blockThe standard. No practical break. AES-128 is fine; AES-256 for long-term or regulatory reasons.
3DES168-bit effective, 64-bit blockDeprecated. DES applied three times to extend the 56-bit key. Slow, and the 64-bit block enables birthday attacks (Sweet32) after ~32 GB under one key.

Modes of operation — this is where implementations fail

A block cipher encrypts one fixed-size block. A mode defines how you handle a message longer than one block, and the choice matters enormously.

ModeBehaviourVerdict
ECBEach block encrypted independentlyNever use. Identical plaintext blocks give identical ciphertext, so structure leaks. The famous "encrypted penguin" image is still recognisable.
CBCEach block XORed with the previous ciphertext; needs an IVAcceptable but fragile — padding-oracle attacks, and it provides no integrity on its own.
CTRTurns a block cipher into a stream cipherFine, but no integrity, and nonce reuse is catastrophic.
GCMCTR plus an authentication tagThe default choice. AEAD — confidentiality and integrity together.
The answer to "how would you encrypt data?"

"AES-256-GCM. GCM is authenticated encryption, so I get confidentiality and integrity in one primitive rather than bolting on a separate MAC and risking getting the composition order wrong. A unique nonce per message — never reused under the same key, because with GCM nonce reuse leaks the authentication key and lets an attacker forge messages. And I'd use the platform's implementation, not my own."

AEAD — know the term

Authenticated Encryption with Associated Data. It encrypts the payload and authenticates additional unencrypted context (headers, a message ID) that must not be tampered with. AES-GCM and ChaCha20-Poly1305 are the two you'd name.

The structural problem

Two things symmetric encryption cannot solve alone: key distribution (how do both parties get the same secret without an eavesdropper capturing it?) and identity (the key proves nothing about who you are — anyone holding it can read and write). Those gaps are what asymmetric crypto exists for.

04

Asymmetric encryption

A mathematically linked key pair. The hinge that everything modern depends on.

The core idea

Each party has a public key (published freely) and a private key (guarded absolutely). Whatever one key does, only the other can undo — which gives two completely different capabilities:

confidentialityencrypt with the recipient's PUBLIC key → only their PRIVATE key decrypts
authenticitysign with YOUR PRIVATE key → anyone verifies with your PUBLIC key
Two directions, two different guarantees. Getting these the right way round is the test.

The algorithms

AlgorithmHard problemNotes
RSAFactoring large semiprimesSigning and key transport. 2048-bit minimum, 3072/4096 for longer term. Padding is mandatory — OAEP for encryption, PSS for signatures. Textbook RSA without padding is broken.
ECC / ECDSAElliptic curve discrete logEquivalent security with far smaller keys — a 256-bit ECC key ≈ a 3072-bit RSA key. Faster, less memory. P-256 is what the Secure Enclave uses.
Ed25519Edwards-curve discrete logModern signature scheme. Fast, deterministic, resistant to the nonce-reuse failure that has broken ECDSA implementations.
Diffie-HellmanDiscrete logarithmKey agreement, not encryption. See section 05.
Why ECC won on constrained hardware

A 256-bit ECC key gives roughly the security of a 3072-bit RSA key. Smaller keys mean less storage, less bandwidth, and much less computation — which is why the Secure Enclave, smart cards, and IoT devices all use elliptic curves. It's also why the SEP supports P-256 and not RSA: the hardware is deliberately constrained.

The practical limitation

Asymmetric crypto is orders of magnitude slower than symmetric and size-limited (RSA can only encrypt data smaller than its key). So it's never used for bulk data. Real systems use it briefly — to authenticate and agree on a symmetric session key — then switch to AES. That handoff is exactly what TLS does, and saying so shows you understand why both exist.

Post-quantum — worth one sentence

Shor's algorithm on a sufficiently large quantum computer would break RSA and ECC (both rely on problems quantum computers solve efficiently). Symmetric crypto and hashes are far less affected — roughly, you double the key size. NIST has standardised post-quantum algorithms (ML-KEM/Kyber for key encapsulation, ML-DSA/Dilithium for signatures), and the current practice is hybrid — classical plus post-quantum together — because of "harvest now, decrypt later." Mentioning this shows currency without overclaiming.

05

Key exchange & Diffie-Hellman

Named explicitly in your brief. It solves a problem that looks impossible.

The problem it solves

Two parties who have never met, communicating over a channel an attacker is fully monitoring, need to end up sharing a secret. Every byte they exchange is visible. How?

The intuition — the paint analogy

  1. Both agree publicly on a common colour (yellow). The attacker sees it.
  2. Each privately picks a secret colour and mixes it with the yellow.
  3. They exchange the mixtures publicly. The attacker sees both mixtures — but separating a mixture back into its components is prohibitively hard.
  4. Each adds their own secret colour to the other's mixture. Both arrive at the same final colour, which the attacker cannot produce.

Mathematically, the "mixing that's hard to reverse" is modular exponentiation, and the hard problem is the discrete logarithm.

Alicesecret a
sends g^a
⇄public channel
Bobsecret b
sends g^b
both compute g^(ab) — the shared secret. The attacker saw g^a and g^b but cannot derive g^(ab).
The secret is never transmitted. It's independently derived by both sides.

The variants to name

VariantMeaning
DHClassic finite-field Diffie-Hellman
ECDHElliptic-curve version — smaller, faster, what's used today
DHE / ECDHEEphemeral — a fresh key pair per session, discarded afterwards. This gives forward secrecy.
Forward secrecy — the point to make

"With ephemeral key exchange, the session key is derived from key pairs that exist only for that session and are then thrown away. So if an attacker records encrypted traffic today and steals the server's long-term private key a year later, they still can't decrypt the recorded sessions — the keys that protected them no longer exist anywhere. That's forward secrecy, and it's why TLS 1.3 mandates ephemeral key exchange and removed static RSA key transport entirely."

The critical weakness

Raw Diffie-Hellman is completely vulnerable to man-in-the-middle. It establishes a shared secret with someone, but proves nothing about who. An attacker can run DH with each party separately and relay. That's precisely why DH is always combined with authentication — a certificate signature proving the server's identity. Volunteering this shows you understand what key exchange does and doesn't provide.

06

Digital signatures & MACs

How you prove a message came from a specific source and wasn't altered.

Signatures — how they actually work

signhash the message → encrypt the hash with the PRIVATE key → attach as signature
verifyhash the message yourself → decrypt the signature with the PUBLIC key → compare
Hashing makes it efficient; the private key makes it unforgeable.

Why hash first? Asymmetric operations are slow and size-limited, so you sign a fixed-size digest rather than the whole message. A match proves authentication (only the private-key holder could produce it), integrity (any change breaks the comparison), and non-repudiation (they can't credibly deny it).

MACs

A Message Authentication Code uses a shared secret key rather than a key pair. HMAC-SHA256 is the standard construction — a specific way of combining a hash with a key that resists length-extension attacks.

SignatureMAC
KeyAsymmetric pairShared secret
Who can verifyAnyone with the public keyOnly holders of the secret
Non-repudiationYesNo — either party could have made it
SpeedSlowVery fast
UseCertificates, JWTs (RS256/ES256), code signingAPI request signing, session tokens, JWTs (HS256)
Encrypt-then-MAC

If you're composing encryption and authentication manually, the correct order is encrypt, then MAC the ciphertext. MAC-then-encrypt and encrypt-and-MAC both have known weaknesses. Better still: use AEAD (AES-GCM) and avoid the question entirely — which is the real answer to give.

Certificates & PKI

Public keys prove identity only if you know whose key it is. This solves that.

The problem

A signature proves the message came from "whoever holds this private key." But how do you know that key belongs to your bank rather than an impostor who also generated a key pair? You need a trusted third party to vouch.

Trust flows down from a root your device already trusts. Roots stay offline; intermediates do the daily signing.

X.509 fields worth knowing

  • Subject — who it identifies. Issuer — who signed it.
  • Subject Alternative Name (SAN) — the hostnames it's valid for. Modern validation uses SAN, not the legacy Common Name.
  • Validity period — notBefore/notAfter. Expiry is the most common production TLS outage.
  • Public key and signature from the issuer.
  • Key usage / extended key usage — what the key may be used for (server auth, client auth, code signing).

Validation — what a client actually checks

  1. Signature chain verifies up to a trusted root.
  2. Certificate is within its validity period.
  3. Hostname matches a SAN entry.
  4. Not revoked — via CRL (a list, poorly scaling) or OCSP (a live query, with privacy and availability issues). OCSP stapling fixes both by having the server present a recent signed status.
  5. Key usage permits this purpose.
Certificate pinning — say the trade-off

"Pinning means trusting a specific certificate or public key rather than any valid chain — it defeats a rogue or compromised CA, which matters for an agent talking to a known backend. The cost is operational: rotation must be planned well in advance or you brick clients, and pinning breaks under corporate TLS inspection, which is why some enterprise agents must be explicitly exempted from inspection. I'd pin the intermediate or a backup key rather than the leaf, to leave room to rotate."

Your angle — device certificates

PKI isn't only for websites. An enterprise issues device certificates binding a machine's hardware-backed key to an identity — that's how a device authenticates to a backend with mTLS, and it's the foundation of device trust. Say: "the same X.509 machinery that authenticates a web server authenticates a managed device, except the key lives in the Secure Enclave and the CA is the enterprise's own."

08

TLS in detail

Everything above, assembled. Be able to walk the handshake.

The handshake, conceptually

1 · helloclient offers TLS version, cipher suites, and its ephemeral key share
2 · server responsepicks the cipher suite, sends its certificate chain and its key share
3 · authenticateclient validates the chain, expiry, hostname, revocation
4 · deriveboth sides compute the same session key via ECDHE — never transmitted
5 · switchall further traffic encrypted with AES-GCM using that session key
Asymmetric to authenticate and agree; symmetric for throughput.

TLS 1.3 — what changed and why

  • One round trip instead of two (and 0-RTT resumption, with a replay caveat).
  • Removed static RSA key transport — all key exchange is now ephemeral, so forward secrecy is mandatory.
  • Removed weak primitives — RC4, 3DES, CBC modes, MD5/SHA-1 signatures, compression (which enabled CRIME).
  • Encrypts more of the handshake, including the certificate.
  • Cipher suites are shorter because only AEAD modes remain.

mTLS

Normally only the server proves identity. In mutual TLS, the client also presents a certificate — so both sides authenticate. This is the natural mechanism for a device with a hardware-bound key to authenticate to a backend, and for service-to-service auth inside a zero-trust network.

Attacks to name

Downgrade (forcing an older protocol — mitigated by HSTS and version pinning in the handshake), BEAST/CRIME/POODLE (older protocol and compression flaws, resolved by TLS 1.2+/1.3), Heartbleed (an OpenSSL implementation bug, not a protocol flaw — a good example of why implementation matters as much as design), and rogue CA (mitigated by pinning and Certificate Transparency).

09

Password storage & key derivation

The most commonly botched area in real applications — and directly relevant at an identity company.

Why a plain hash is wrong

SHA-256 is designed to be fast — that's a virtue for integrity and a catastrophe for passwords. A modern GPU rig computes billions of SHA-256 hashes per second, so a stolen database of hashed passwords falls in hours. Passwords need functions that are deliberately slow and resource-hungry.

Salt, pepper, and work factor

  • Salt — a unique random value per password, stored alongside the hash. Defeats rainbow tables and ensures two users with the same password have different hashes. Not secret; uniqueness is the point.
  • Pepper — a single application-wide secret kept outside the database (in an HSM or secrets manager). If only the database leaks, the hashes are still uncrackable. Optional but a nice detail.
  • Work factor / cost — a tunable parameter making the function slower. You raise it as hardware improves.

The functions

FunctionResistanceVerdict
Argon2idCPU + memory + parallelism tunableCurrent recommendation. Winner of the Password Hashing Competition.
scryptCPU + memoryStrong. Memory-hardness resists GPU and ASIC attacks.
bcryptCPUStill fine and widely deployed. Note the 72-byte input limit.
PBKDF2CPU onlyAcceptable where required by standards, but not memory-hard, so GPUs parallelise it well. Needs a high iteration count.
Memory-hardness — the key concept

"The reason Argon2 and scrypt are preferred is memory-hardness. An attacker's advantage comes from massive parallelism on GPUs or custom ASICs — but those have limited memory per core. Forcing each hash computation to consume significant memory removes that advantage, because you can't run thousands of instances in parallel. PBKDF2 only burns CPU, which is exactly what specialised hardware is good at."

Two more points

Constant-time comparison when checking a hash or token — a normal comparison returns early on the first mismatch, leaking information through timing. KDFs vs password hashing: HKDF is for deriving multiple keys from an already-strong secret (a TLS session key), while Argon2/bcrypt are for stretching a weak human-chosen secret. Different jobs; don't swap them.

Apple platform cryptography

Where the theory meets what you actually ship. This is your strongest section — lead with it whenever crypto comes up.

The Secure Enclave

A separate, isolated coprocessor with its own boot ROM and encrypted memory. The property that matters: a key generated inside the SEP never leaves it. Not to your app, not to the OS, not to root. You can only ask the SEP to perform operations with it.

// P-256 key, non-exportable, gated on biometric or passcode
let access = SecAccessControlCreateWithFlags(
    nil,
    kSecAttrAccessibleWhenUnlockedThisDeviceOnly,   // no backup, no migration
    [.privateKeyUsage, .userPresence],              // require user presence
    nil)!

let attrs: [String: Any] = [
    kSecAttrKeyType as String:      kSecAttrKeyTypeECSECPrimeRandom,
    kSecAttrKeySizeInBits as String: 256,
    kSecAttrTokenID as String:      kSecAttrTokenIDSecureEnclave,   // ← in the SEP
    kSecPrivateKeyAttrs as String: [
        kSecAttrIsPermanent as String:   true,
        kSecAttrAccessControl as String: access
    ]
]

var err: Unmanaged<CFError>?
let privateKey = SecKeyCreateRandomKey(attrs as CFDictionary, &err)!
// Only signatures leave the device — never the key itself.
The sentence to lead with

"The property I care about most in practice is non-exportability. A key in the Keychain is protected at rest, but to use it you load it into process memory — where a compromised process can exfiltrate it. A Secure Enclave key never enters the application processor's memory at all. Even root can't extract it; it can only request operations while policy allows. That's what makes a credential genuinely device-bound, and it's the same primitive underneath FIDO2 platform authenticators and MDM device attestation."

Keychain vs Secure Enclave

Keychain accessibility classes worth naming: WhenUnlocked, AfterFirstUnlock (for daemons that must work before a user logs in), and the ThisDeviceOnly suffix which prevents the item syncing or restoring to another device.

CryptoKit — the modern Swift API

import CryptoKit

// Hashing
let digest = SHA256.hash(data: data)

// Symmetric AEAD
let key = SymmetricKey(size: .bits256)
let sealed = try AES.GCM.seal(plaintext, using: key)
let opened = try AES.GCM.open(sealed, using: key)

// Signing
let signingKey = P256.Signing.PrivateKey()
let signature = try signingKey.signature(for: data)
let valid = signingKey.publicKey.isValidSignature(signature, for: data)

// Key agreement (ECDH) + HKDF derivation
let priv = P256.KeyAgreement.PrivateKey()
let shared = try priv.sharedSecretFromKeyAgreement(with: theirPublicKey)
let sessionKey = shared.hkdfDerivedSymmetricKey(
    using: SHA256.self, salt: salt, sharedInfo: Data(), outputByteCount: 32)

// MAC
let mac = HMAC<SHA256>.authenticationCode(for: data, using: key)

Note CryptoKit deliberately doesn't expose ECB or unauthenticated modes — the API design steers you toward safe choices. Worth saying: "I prefer CryptoKit over CommonCrypto precisely because the unsafe options aren't reachable."

Device attestation — the synthesis

Where all of this converges in your work: a device generates a Secure Enclave key at enrollment, proves via hardware attestation that it's a genuine device with a non-exportable key, receives a device certificate binding that key to an identity, and then authenticates via mTLS or signed challenges. That's PKI plus hardware-backed keys plus challenge-response — the entire document in one flow.

12

Interview Q&A

Answer in two or three sentences, then offer depth if invited.

CERTAINSymmetric vs asymmetric — explain the difference.

Symmetric uses one shared key for both encryption and decryption — fast and suitable for bulk data, but it has the key-distribution problem: both parties need the same secret and getting it to them securely is the hard part. Asymmetric uses a mathematically linked key pair: encrypt with the public key so only the private-key holder reads it, or sign with the private key so anyone can verify authorship. It solves distribution and identity but is far slower and size-limited. Real systems combine them — asymmetric to authenticate and agree a session key, symmetric for the payload. That's exactly TLS.

CERTAINHashing vs encryption vs encoding?

Encoding (base64) is a reversible format change with no key and no security — purely for transport. Hashing is one-way with no key, used for integrity and fingerprinting. Encryption is reversible with a key, used for confidentiality. Mixing these up is the classic tell, and "we base64 the password" is the classic incident.

LIKELYHow would you encrypt sensitive data at rest?

AES-256-GCM, with a unique nonce per message and never reused under the same key. GCM is AEAD, so I get integrity along with confidentiality rather than composing them by hand. The real question is key management, not the cipher: I'd derive or wrap the data key with a key held in hardware — on Apple platforms, a Secure Enclave key, so the wrapping key is non-exportable. Rotation strategy matters too: wrap the data key so rotating means re-wrapping rather than re-encrypting everything.

LIKELYHow does TLS work?

The client and server negotiate a version and cipher suite, the server presents its certificate chain, and the client validates it — signature chain to a trusted root, validity period, hostname against the SAN, revocation. Then both sides derive a shared session key via ephemeral ECDH, which is never transmitted, and switch to symmetric AES-GCM for the actual data. TLS 1.3 made ephemeral key exchange mandatory, which means forward secrecy by default, and dropped the weak primitives that enabled the older downgrade attacks.

LIKELYWhat is forward secrecy and why does it matter?

Session keys are derived from ephemeral key pairs that are discarded after the session. So an attacker who records encrypted traffic today and later compromises the server's long-term private key still can't decrypt those recordings — the keys that protected them no longer exist. It's why TLS 1.3 removed static RSA key transport and mandates ECDHE, and it's the direct defence against "harvest now, decrypt later."

LIKELYHow do you store passwords?

Argon2id, or bcrypt/scrypt if that's what the platform provides, with a unique per-password salt and a tuned work factor. Never a plain hash — SHA-256 is fast by design, so a stolen database falls to GPUs quickly. Memory-hardness is the key property: it removes the attacker's parallelism advantage on GPUs and ASICs. Optionally a pepper held outside the database. And constant-time comparison on verification. Better still, move to passwordless — a phishing-resistant credential means there's no password database to steal.

LIKELYExplain Diffie-Hellman.

It lets two parties derive a shared secret over a fully public channel without ever transmitting it, based on the discrete logarithm problem — the exchanged values are easy to compute forward and infeasible to reverse. ECDH is the elliptic-curve version used today, and the ephemeral variant gives forward secrecy. The crucial caveat: raw DH is completely vulnerable to man-in-the-middle, because it establishes a secret with someone but proves nothing about who — which is why it's always paired with certificate-based authentication.

LIKELYSignature vs MAC?

Both give integrity and authentication. A MAC uses a shared secret, so it's fast but offers no non-repudiation — either party could have produced it. A signature uses a private key, so only the holder could have made it and they can't credibly deny it, at the cost of being much slower. Certificates and code signing need signatures; internal API request signing is usually fine with HMAC.

LIKELYWhat does the Secure Enclave give you that the Keychain doesn't?

Non-exportability. Keychain protects a secret at rest, but using it means loading it into process memory, where a compromised process can exfiltrate it. A Secure Enclave key never enters the application processor's memory at all — you can only request signing or decryption, optionally gated on biometric user presence. The trade-off is that SE keys are limited to supported algorithms like P-256 and can't be backed up or migrated, which is precisely the point for a device-bound credential.

POSSIBLEWhy is 3DES deprecated?

Two reasons. Its 64-bit block size makes it vulnerable to birthday-bound collision attacks — Sweet32 — after roughly 32 GB under a single key, which is reachable on a long-lived connection. And it's slow, being DES applied three times. AES has a 128-bit block, is faster, and has hardware acceleration. 3DES only appears now in legacy systems that can't be changed.

POSSIBLEWhat about quantum computing?

Shor's algorithm on a sufficiently large quantum computer breaks RSA and ECC, since both rest on problems quantum computers solve efficiently. Symmetric crypto and hashes are much less affected — Grover's algorithm roughly halves the effective key length, so you double key sizes. NIST has standardised post-quantum algorithms like ML-KEM and ML-DSA, and current practice is hybrid deployment — classical plus post-quantum together — because of harvest-now-decrypt-later. It's not urgent for session data with short lifetimes, but it matters for anything that must stay confidential for a decade.

POSSIBLEHow would you design credential storage for a device agent?

Generate a P-256 key inside the Secure Enclave at enrollment, non-exportable and optionally user-presence gated. Send only the public key to the backend, which issues a device certificate binding it to an identity. Authenticate via mTLS or signed challenges. The result is that there's no bearer secret to steal — even root on the machine can't exfiltrate the private key, only request signatures while policy allows. Rotation means minting a new SE key and re-binding. That's the design I'd defend, and it's what I've shipped.

The closing posture

If pushed past your depth — internals of a cipher, lattice-based constructions, side-channel countermeasures — say so cleanly and pivot: "I haven't worked at that level; my depth is in applied crypto and key management on Apple platforms. Here's how I'd reason about it…" At an identity company, judgment about key management matters far more than reciting algorithm internals, and that's where your real experience sits.
