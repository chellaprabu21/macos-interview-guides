The answer that shows depth

"My default is struct for data, class for services. The reason isn't style — it's that a struct copy is trivially thread-safe, so an immutable policy snapshot as a struct means my readers never need a lock. I only reach for a class when I need identity or a shared lifecycle: a cache, a list node, something with a deinit. And the subtlety is that a let on a class reference doesn't make the object immutable, only the pointer — which is exactly the bug people write when they think let means constant."

§8

Optionals & error handling — the API design question in disguise

The three-way split (memorise this — it's §14's rubric in code)

// 1. "Not found" is a NORMAL outcome → Optional. Not an error.
func get(_ key: Key) -> Value?          // 404 is not a crash

// 2. "You gave me bad input" → throw. Recoverable, caller's fault.
func add(_ rule: Rule) throws           // 400

// 3. "You violated the contract" → precondition. Programmer error.
init(capacity: Int) {
    precondition(capacity > 0, "capacity must be positive")  // this is a BUG
}

// 4. Optional bonus: Result when you need to defer handling
func evaluate(_ e: Event) -> Result<Verdict, PolicyError>
"I split failures three ways. Not-found is an Optional, because it's a normal outcome and forcing the caller into a do/catch for a cache miss is hostile. Bad input throws — that's a 400, the caller can fix it. And violating the contract, like a zero capacity, is a precondition, because that's a bug in the calling code and crashing loudly in a test beats limping in production. Getting that split wrong is how you end up with APIs where every call site has an empty catch block."

Optional handling — the four forms

guard let v = map[k] else { return nil }   // early exit — DEFAULT. flat.
if let v = map[k] { ... }                     // nested — fine for one level
let v = map[k] ?? .allow                     // default value
let n = map[k]?.count                        // optional chain → Int?
let v = map[k]!                              // ← justify or don't use it

The force-unwrap question: "When is ! acceptable?" — "When the invariant guarantees it and the alternative is noise. In my LRU, map[key]! right after I inserted it is safe by construction. But I'd rather write it so the compiler knows, and I'd never force-unwrap anything that crossed an API boundary or came from parsing — a force-unwrap on untrusted input is a remote crash, and in a system extension a crash is a fleet incident."

Error types
enum PolicyError: Error, Equatable {   // Equatable ⇒ testable with ==
    case duplicateID(RuleID)
    case notFound(RuleID)
    case invalidRule(reason: String)
}
// Associated values carry context. `case error` with no payload is useless
// at 3am. This is the same argument as "don't return bare 500".

Protocols & generics

// The protocol IS the API. This is what "API skeleton" means in Swift.
protocol RuleStore {
    associatedtype R: Identifiable
    func add(_ r: R) throws
    func remove(_ id: R.ID) throws
    func all() -> [R]
}

// Protocol with a default implementation — free behaviour for conformers
extension RuleStore {
    func count() -> Int { all().count }
}

// Generic constraint — the everyday form
final class LRUCache<Key: Hashable, Value> { ... }

// The dependency-injection form. THE testability move.
protocol Clock { var now: TimeInterval { get } }
final class SystemClock: Clock { var now: TimeInterval { Date().timeIntervalSince1970 } }
final class FakeClock: Clock {
    private(set) var now: TimeInterval
    init(_ t: TimeInterval = 0) { now = t }
    func advance(_ d: TimeInterval) { now += d }
}
He asksYou say
Protocol vs class inheritance?"Protocols compose; inheritance doesn't. A type can conform to five protocols but have one superclass. And protocols let me inject a fake — a Clock protocol is why my TTL test runs in a microsecond instead of sleeping eleven seconds."
some vs any?"some P is an opaque type — one concrete type, resolved at compile time, no boxing, fast. any P is an existential — a box, dynamic dispatch, slower, but it lets me put heterogeneous conformers in an array. On a hot path I want some or a generic; in a plugin registry I want any."
Why final class?"Static dispatch. Without final, every method call goes through a vtable in case someone subclasses. On an ES callback path that's real. It also documents intent: this isn't a base class."
Associated type vs generic?"Same idea, different placement. A generic parameter is chosen by the caller; an associated type is chosen by the conformer. Associated types make the protocol non-existential though — you can't have [any RuleStore] without a type eraser, which is the classic Swift papercut."
§10

ARC, retain cycles, closures

Guaranteed to come up if you write a linked list. Which you will, if it's an LRU.

final class Node {
    var next: Node?          // strong  ─┐
    var prev: Node?          // strong  ─┴─► CYCLE. Neither ever deallocs.
}

// Fix: one direction must be non-owning.
final class Node {
    var next: Node?          // strong — the list owns forward
    weak var prev: Node?     // weak — becomes nil automatically
}
// or `unowned` if you can guarantee prev outlives next (faster: no
// side table, no optionality — but a dangling unowned is a CRASH).
weakunowned
TypeAlways OptionalNon-optional
On deallocAuto-nilsDangles → crash on access
CostSide table lookupFree
UseDelegates, anything that can outlive youWhen the referent provably outlives you (child → parent)
Closure capture — the other half of the same question
// Closures capture STRONGLY by default. self holds the closure,
// the closure holds self. Cycle.
timer = Timer.scheduledTimer(...) { _ in self.tick() }        // ✗ leak
timer = Timer.scheduledTimer(...) { [weak self] _ in self?.tick() }  // ✓

// Escaping vs non-escaping — the distinction he'll ask about
func sync(_ f: () -> Void)           { f() }        // non-escaping (default)
func async(_ f: @escaping () -> Void) { queue.async(execute: f) }
// @escaping = "I'm storing this and calling it later", so the compiler
// forces you to think about lifetime — hence the [weak self] requirement.

// Capture by VALUE at creation time:
var x = 1
let f = { [x] in print(x) }   // captures 1
x = 2; f()                       // prints 1, not 2
"If I write a doubly-linked list for the LRU I'm going to make one direction weak or unowned, because two strong references means the whole list leaks even after you drop the cache — and it's invisible until you look at a memory graph. The production version I'd actually reach for is an array-backed node pool with integer indices: no ARC traffic at all, better cache locality, and the cycle can't exist by construction. But for 75 minutes I'll write the linked list and just be honest about the trade."

That answer does three things at once: shows you know ARC, shows you know what you'd do differently in production, and pre-empts the follow-up. It's the single best 20 seconds available in an LRU problem.

The two answers to have loaded

"Make it thread-safe."

"One lock, narrow scope, no callbacks or I/O inside it. Measure. If contention shows up, shard the map by hash into N stripes with N locks — most of lock-free's benefit for a fraction of the risk. And I'd keep the lock outside the data structure: a thread-safe container still can't do 'get, then put if absent' atomically, so baking the lock in gives you false confidence. Lock the operation, not the container."

"Reader-writer lock on the LRU?"

"There's no reader. get promotes the entry to most-recent, so it's a write. A reader-writer lock on an LRU is pure cost. If I needed genuinely lock-free reads I'd change the eviction policy — a clock/second-chance algorithm only sets a bit on read, which can be atomic." Genuine differentiator

§13

Rapid-fire Swift

struct vs class — one sentence?

Struct copies, class shares. Struct for data, class for identity and shared lifecycle. The practical consequence is thread safety: a struct copy is trivially isolated, a class isn't.

What does mutating do?

Marks a struct method that changes self. Under the hood self is inout. You can't call it on a let, which is the compiler enforcing value semantics for you.

weak vs unowned?

Both non-owning. weak is optional and auto-nils on dealloc; unowned is non-optional and dangles into a crash. unowned is faster (no side table) and correct when the referent provably outlives you — a child pointing at its parent. When in doubt, weak.

What's @escaping?

The closure outlives the function call — you're storing it or dispatching it. It's the compiler making lifetime explicit, which is why escaping closures are where [weak self] matters and non-escaping ones don't.

Why is Dictionary unordered, and when does it bite?

Hash order, and Swift seeds the hasher per process so it's not even stable across launches. It bites when correctness leaks onto iteration order — e.g. a policy engine that breaks ties by "first match found" is non-deterministic across machines, so the same event gets different verdicts on two laptops. Break ties on an explicit field.

lazy var?

Computed once on first access, then stored. Not thread-safe — two threads can both initialise it. Fine for a struct that's confined to one thread; a landmine in a shared service class.

Enum with associated values — why care?

Sum types. Verdict.deny(reason: String) carries context the caller needs, and the compiler forces you to handle every case in a switch. It's how you make illegal states unrepresentable, which is worth more than any test.

@discardableResult?

Suppresses the "result unused" warning. Correct on something like @discardableResult func push(_:) -> Bool where most callers don't care whether it was dropped but some do. It's a small API-design signal.

Access control levels?

private (this scope) · fileprivate · internal (default, the module) · public · open (public + subclassable). And private(set) — publicly readable, privately writable — which is exactly right for a stats counter.

How does Swift call C? (he built ES sensors — fair game)

Direct import; C structs become Swift structs, pointers become UnsafePointer<T>, C string tokens need copying into a Swift String before the underlying memory dies. The genre of bug is lifetime: capture an es_message_t pointer in an escaping closure without retaining it and you get a use-after-free that only fires under load. I wrap those in a small RAII-style Swift type at the boundary so ARC owns the lifetime and the mistake is impossible.

struct Rule: Equatable {              // struct: it's data
    let id: RuleID
    let pathPrefix: String?           // nil = matches any path
    let appID: String?                // nil = matches any app
    let priority: Int                 // higher wins
    let verdict: Verdict
}

enum Verdict: Equatable { case allow, deny, readOnly }

enum PolicyError: Error, Equatable {
    case duplicateID(RuleID)
    case invalidRule(reason: String)
}

protocol PolicyService {
    /// - Throws: `.duplicateID` if id exists; `.invalidRule` if malformed.
    /// - Complexity: O(1).
    /// - NOT idempotent by design: a silent overwrite of a policy rule
    ///   destroys the audit trail. Use `update` to change one.
    func add(_ rule: Rule) throws

    /// - Returns: the removed rule, or nil if absent.
    /// - IDEMPOTENT: removing a missing id is a no-op, not an error.
    /// - Complexity: O(1).
    @discardableResult func remove(_ id: RuleID) -> Rule?

    /// - Complexity: O(1). Returns nil if absent — a normal outcome.
    func rule(_ id: RuleID) -> Rule?

    /// - Returns: rules in a STABLE order (by id). Never hash order.
    func all() -> [Rule]

    /// - Complexity: O(1) on cache hit, O(matching rules) on miss.
    /// - Deterministic: same input + same rule set ⇒ same verdict, always.
    /// - Default when nothing matches: .allow  ← a product decision
    func evaluate(_ event: Event) -> Verdict

    func stats() -> Stats
}


// ═══ 2. THE IMPLEMENTATION ══════════════════════════════════

final class InMemoryPolicyService: PolicyService {

    private var byID: [RuleID: Rule] = [:]
    private var cache: LRUCache<EventKey, Verdict>
    private var epoch: UInt64 = 0          // O(1) cache invalidation
    private(set) var hits = 0, misses = 0, evaluations = 0

    init(cacheCapacity: Int = 10_000) {
        precondition(cacheCapacity > 0)
        cache = LRUCache(capacity: cacheCapacity)
    }

    func add(_ rule: Rule) throws {
        try validate(rule)
        guard byID[rule.id] == nil else { throw PolicyError.duplicateID(rule.id) }
        byID[rule.id] = rule
        invalidate()
    }

    @discardableResult
    func remove(_ id: RuleID) -> Rule? {
        guard let r = byID.removeValue(forKey: id) else { return nil }
        invalidate()
        return r
    }

    func rule(_ id: RuleID) -> Rule? { byID[id] }

    func all() -> [Rule] {
        // Sorted, NOT hash order. Iteration order of a Dictionary is not
        // stable across launches — leaking it into the API makes the
        // service non-deterministic.
        byID.values.sorted { $0.id < $1.id }
    }

    func evaluate(_ event: Event) -> Verdict {
        evaluations += 1
        let key = EventKey(event, epoch: epoch)

        if let v = cache.get(key) { hits += 1; return v }
        misses += 1

        let v = byID.values
            .filter { matches($0, event) }
            .max { a, b in
                // DETERMINISTIC tie-break. Priority, then id. Never
                // "whichever the dictionary handed me first."
                (a.priority, a.id) < (b.priority, b.id)
            }?.verdict ?? .allow     // ← default allow. Say why.

        cache.put(key, v)
        return v
    }

    func stats() -> Stats {
        Stats(rules: byID.count, evaluations: evaluations,
              hits: hits, misses: misses,
              hitRate: evaluations == 0 ? 0 : Double(hits)/Double(evaluations),
              evictions: cache.evictions)
    }

    // ── private ─────────────────────────────────────────────
    private func validate(_ r: Rule) throws {
        if r.id.isEmpty { throw PolicyError.invalidRule(reason: "empty id") }
        if let p = r.pathPrefix, !p.hasPrefix("/") {
            throw PolicyError.invalidRule(reason: "path must be absolute: \(p)")
        }
        if r.pathPrefix == nil && r.appID == nil {
            // A rule matching everything is almost always a mistake.
            throw PolicyError.invalidRule(reason: "rule must constrain something")
        }
    }

    private func matches(_ r: Rule, _ e: Event) -> Bool {
        if let p = r.pathPrefix, !e.path.hasPrefix(p) { return false }
        if let a = r.appID, a != e.appID { return false }
        return true
    }

    private func invalidate() {
        epoch &+= 1     // every cached key is now unreachable. O(1).
    }                  // walking the cache would be O(n) under a lock.
}

The five things to say while writing it

  1. Default allow. "No rule matched → allow. On an endpoint, default-deny means a broken policy set bricks every Mac in the fleet. That's a product decision, not a technical one — I'd make it configurable but ship allow."
  2. Deterministic tie-break. "Two rules, same priority, both match — if the answer depends on dictionary iteration order, the same event gets different verdicts on two machines. Compliance needs 'why was this blocked' to have exactly one answer."
  3. Epoch invalidation. "Rule set changed → bump an integer → every cached key is stale by construction. O(1). Walking the cache to invalidate is O(n) while holding a lock on the hot path."
  4. Idempotency, asymmetric. "remove is idempotent, add isn't. That's deliberate — removing something that's already gone converges on the state you wanted, but silently overwriting a rule loses the audit trail."
  5. Ordered all(). "Sorted, not hash order. The moment iteration order leaks out of the API someone will depend on it and it isn't stable across launches."

The follow-up he'll ask "This filter over every rule is O(n) per evaluate — what if there are 10,000 rules?" Have the answer ready: "Right — I'd index by the most selective dimension. A path trie narrows thousands of rules to a handful in O(depth), then I linear-scan the survivors. I started with the linear scan deliberately: it's correct, it's testable, and the index is a drop-in optimisation once I have the tests to prove it didn't change behaviour. If you want, I'll add the trie now." That answer is better than having written the trie, because it shows judgement about when to optimise — which is what a four-year engineer coming from cloud is actively learning and will recognise.

The event batcher — his home turf

/// Batches events and flushes on size OR time, whichever first.
/// Bounded — drops with a counter rather than growing without limit.
/// This is a Kafka producer's linger.ms + batch.size + buffer.memory,
/// scaled down to one endpoint. Say that out loud.
final class EventBatcher {

    enum DropPolicy { case dropOldest, dropNewest }

    private var buffer: [Event] = []
    private let maxBatch: Int          // batch.size
    private let maxWait: TimeInterval  // linger.ms
    private let maxBuffer: Int         // buffer.memory
    private let policy: DropPolicy
    private let clock: Clock
    private let sink: ([Event]) -> Bool   // false = upload failed → retry
    private var lastFlush: TimeInterval

    private(set) var accepted = 0, flushed = 0, dropped = 0, retries = 0

    init(maxBatch: Int = 100, maxWait: TimeInterval = 5,
         maxBuffer: Int = 10_000, policy: DropPolicy = .dropOldest,
         clock: Clock, sink: @escaping ([Event]) -> Bool) {
        precondition(maxBatch > 0 && maxBuffer >= maxBatch,
                     "buffer must hold at least one batch")
        self.maxBatch = maxBatch; self.maxWait = maxWait
        self.maxBuffer = maxBuffer; self.policy = policy
        self.clock = clock; self.sink = sink
        lastFlush = clock.now
        buffer.reserveCapacity(maxBatch)
    }

    /// - Returns: false if the event was dropped due to backpressure.
    /// - Complexity: O(1) amortised; O(batch) when a flush triggers.
    @discardableResult
    func ingest(_ e: Event) -> Bool {
        if buffer.count >= maxBuffer {
            dropped += 1
            switch policy {
            case .dropNewest: return false              // reject the new one
            case .dropOldest: buffer.removeFirst()      // O(n) — see note
            }
        }
        buffer.append(e)
        accepted += 1
        if buffer.count >= maxBatch { flush() }        // size trigger
        return true
    }

    /// Call from a timer. Idempotent — flushing an empty buffer is a no-op.
    func tick() {
        if !buffer.isEmpty && clock.now - lastFlush >= maxWait { flush() }
    }

    /// - IDEMPOTENT: no-op on an empty buffer.
    func flush() {
        guard !buffer.isEmpty else { lastFlush = clock.now; return }
        let batch = buffer
        if sink(batch) {
            flushed += batch.count
            buffer.removeAll(keepingCapacity: true)
        } else {
            // Sink failed. KEEP the batch — at-least-once beats at-most-once
            // for audit data. The backend dedups on (device, seq).
            retries += 1
        }
        lastFlush = clock.now
    }
}

The four things to say — each one is aimed at him

  1. Name the analogy. "This is batch.size, linger.ms and buffer.memory from a Kafka producer, scaled to one endpoint. Same three knobs, same three failure modes." He will visibly relax
  2. At-least-once, not at-most-once. "On a flush failure I keep the batch rather than dropping it, and the backend dedups on (device, sequence). Exactly-once on a laptop that sleeps mid-upload is a fantasy — at-least-once plus an idempotent consumer is the real answer." That's his language, verbatim.
  3. Two queues, two policies. "Drop-oldest is right for telemetry, where recent data is more valuable. It's wrong for audit records — those are a compliance obligation and you may not lose them. So a real agent has two buffers with different drop policies. Asking which one this is matters more than the implementation."
  4. The dropped counter. "A security product that silently discards events is lying to its customer about coverage. Every drop is counted and exported."

Catch your own bug buffer.removeFirst() on an Array is O(n) — it shifts everything. Under drop-oldest at a full buffer, that's O(n) per ingest, and your hot path just became quadratic. Say this out loud when you notice it: "Actually — removeFirst on an Array is O(n), so at a full buffer I'm shifting 10,000 elements per event. I want a ring buffer or a deque here. Let me note that and either fix it or flag it depending on our clock." Finding your own performance bug, mid-flow, unprompted, is the single most valuable thirty seconds available in this entire round. It's the closest he'll get to watching you actually work.

var _pass = 0, _fail = 0

func expect(_ c: @autoclosure () -> Bool, _ what: String,
            _ f: String = #file, _ l: Int = #line) {
    if c() { _pass += 1 }
    else { _fail += 1
           print("✗ \(what)  [\((f as NSString).lastPathComponent):\(l)]") }
}

func expectEqual<T: Equatable>(_ a: T, _ b: T, _ what: String,
                              _ f: String = #file, _ l: Int = #line) {
    expect(a == b, "\(what) — expected \(b), got \(a)", f, l)
}

func expectThrows<E: Error & Equatable>(_ expected: E, _ what: String,
                                       _ body: () throws -> Void) {
    do { try body(); expect(false, "\(what) — expected throw, got success") }
    catch let e as E { expectEqual(e, expected, what) }
    catch { expect(false, "\(what) — wrong error type: \(error)") }
}

func suite(_ n: String, _ b: () -> Void) { print("\n── \(n) ──"); b() }
func report() -> Int { print("\n\(_pass) passed, \(_fail) failed"); return _fail == 0 ? 0 : 1 }

The three tests that separate you from every other candidate

1 · Cache coherence. Add a rule, evaluate (caches), remove the rule, evaluate again. If your epoch logic is wrong you'll return the stale deny — and this is the actual bug the design exists to prevent. Testing your own hardest bug is the flex.

2 · Determinism under repetition. Run the same tie-break 100 times. Swift randomises the hash seed per process, so if you leaked iteration order into your verdict, it'll pass locally and fail in CI three weeks later. He's from a QA background; flaky tests are his personal nemesis.

3 · The invariant under random ops. 10,000 random operations, assert the structural invariant after each. It's a property test in three lines and it finds things example-based tests never will.

"I'd rather write six tests that each pin down one behaviour of the contract than twenty that walk the happy path. And the two I care most about are the coherence test — because a stale cache after a policy change is the actual bug this design exists to prevent — and the determinism loop, because Swift randomises the hash seed per process, so an order-dependent tie-break passes on my machine and fails in CI a month later. Flaky tests are worse than no tests; they train people to hit re-run."

§19

What he'll ask

"Why this data structure?"

Give two options and a reason. "Map plus a doubly-linked list. Map for O(1) find, list for O(1) reorder — the map stores node references, not values, which is the whole trick. The alternative is an array with a timestamp and a linear scan for the victim, which is O(n) per eviction. On a hot path where I'm doing this per file open, that's not viable." Never just name the structure.

"What's the complexity?"

Per method, and say amortised or average where it's true. "get and put are O(1) average — the hash map is O(n) worst case on adversarial keys, but that's not a threat model that applies to an inode key. The eviction is O(1) because I hold the tail pointer."

"How would you make this thread-safe?"

§12. And the killer addition: "I'd put the lock outside the container, not inside. A 'thread-safe' collection still can't do 'get, then put if absent' atomically, so baking the lock in gives callers false confidence. Lock the operation."

"What if there were 10 million entries?"

Memory first: "the node overhead dominates — an ARC-managed class per entry is 16 bytes of header plus the pointers before you've stored anything. At 10M I'd move to an array-backed node pool with Int32 indices: no ARC, better locality, and a fixed allocation. Then I'd question whether it belongs in memory at all — that's a mmap'd file or an on-disk store with an in-memory hot tier."

"How would you test this?"

Don't list test names — give categories: contract (each documented behaviour has a test), boundaries (capacity 1, exactly full, one over), errors (expectThrows for each case), idempotency, determinism under repetition, the structural invariant under random ops, and time via an injected clock. Then say: "and I'd keep the lock out of the data structure so I can test the logic deterministically without threads at all."

"What would you change for production?"

"Metrics — hit rate, eviction rate, drop count. And I'd argue eviction rate is a security metric, not a perf metric: on an endpoint, an eviction is a cache miss is a verdict I can't compute in time is a fail-open. So it belongs on the same dashboard as coverage. Then: a memory cap rather than an entry count, because entry sizes vary. And the index I skipped."
