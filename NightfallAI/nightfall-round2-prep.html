§05 · The core round

Endpoint Security framework

Assume 30–40% of Round 2 lives here. He built ES event sources at FireEye and a sensor at CrowdStrike. Precision matters more than breadth.

The shape of it

es_new_client(&client, ^(es_client_t *c, const es_message_t *msg) { ... })
  → ES_NEW_CLIENT_RESULT_ERR_NOT_PERMITTED   // missing TCC Full Disk Access
  → ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED    // missing com.apple.developer.endpoint-security.client
  → ES_NEW_CLIENT_RESULT_ERR_NOT_PRIVILEGED  // not root

es_subscribe(client, events, count);
// AUTH events  → must call es_respond_auth_result() / es_respond_flags_result()
//                BEFORE msg->deadline, or the OS kills your client.
// NOTIFY events → informational, no response, still counts against your budget.

Facts to have cold

  • Entitlement com.apple.developer.endpoint-security.client requires Apple approval; plus Full Disk Access (TCC) and root. Three separate failure modes, three distinct error codes — knowing which is which is the tell of someone who's actually shipped.
  • es_respond_auth_result for most AUTH events; es_respond_flags_result specifically for ES_EVENT_TYPE_AUTH_OPEN — you return the allowed fcntl flags, so you can permit read and deny write on the same open. This is the single most useful DLP primitive in ES and most candidates don't know it.
  • The message is only valid for the callback's lifetime — es_retain_message / es_release_message if you go async (and you must go async for anything non-trivial).
  • es_message_t.deadline is a Mach absolute time, not a fixed constant, and it varies by event type. Never assume "I have 20ms." Read it, and budget against it.
  • Muting: es_mute_process (audit token), es_mute_path with ES_MUTE_PATH_TYPE_LITERAL / PREFIX / TARGET_LITERAL / TARGET_PREFIX, and inverted muting (es_invert_muting) to flip an allowlist into a watchlist — huge for a DLP agent that only cares about a few thousand sensitive paths.
  • es_process_t gives you: audit_token, ppid, original_ppid, signing_id, team_id, cdhash, codesigning_flags (check CS_VALID, CS_PLATFORM_BINARY), is_platform_binary, is_es_client. Identity for policy comes from cdhash / team_id / signing_id, never from the path or the process name.
  • Multiple ES clients coexist (you, CrowdStrike, Jamf, MDM). All must respond to an AUTH event; the slowest one sets user-visible latency and any DENY wins. On a customer's Mac you are never alone — design for it and say so.

The DLP-specific insight to lead with

NOTIFY_WRITE fires per write and will drown you. The right trigger for content classification is ES_EVENT_TYPE_NOTIFY_CLOSE with modified == true — one event per completed mutation, at the moment the file is coherent enough to scan. Pair it with AUTH_OPEN (flags-result) for the enforcement decision and AUTH_RENAME / AUTH_COPYFILE / AUTH_CLONE for the movement decision. Naming that trio unprompted tells him you've done this.

"Walk me through how you'd block a file copy to an unauthorised destination using ES."

Commit: AUTH on the movement events, not on write. Subscribe to AUTH_OPEN, AUTH_CREATE, AUTH_RENAME, AUTH_COPYFILE, AUTH_CLONE, AUTH_TRUNCATE, AUTH_UNLINK.

  1. On the event, extract the actor: audit token → cdhash / team_id / signing_id, plus the parent chain and whether it's a platform binary.
  2. Extract the target: es_file_t → path and stat. Use st_dev to know which volume — that's how you cheaply know "this is the USB volume" without string-matching /Volumes/.
  3. Look up the verdict in an in-memory policy cache keyed by (actor identity, destination class, sensitivity label of the source inode). No IPC, no disk, no network on this path.
  4. Respond: es_respond_auth_result(ES_AUTH_RESULT_DENY), or for OPEN, es_respond_flags_result stripping the write bits so read still works — much lower blast radius than a hard deny.
  5. Emit the audit event asynchronously on a separate queue after responding. Never before.

Caveat, stated second: content classification cannot happen inside the auth path. So the label has to already exist — you pre-classify on NOTIFY_CLOSE(modified) and cache the label by (dev, inode, mtime/generation). If the label is unknown at auth time, you have a policy choice: fail-open and log, or block-and-scan with a hard timeout. In a DLP product on a laptop, I'd fail-open by default and let the customer opt into strict mode, because a false block on /usr/bin/ld is an outage and a missed copy is an alert.

"Your ES client misses a deadline. What happens, and how do you make sure it never does?"

Commit: the kernel kills your client. Not a warning — the process is terminated, and if it's a system extension you get a restart loop and, on repeat, a very unhappy fleet. It's the number one way to take down every Mac in a customer's org simultaneously.

Prevention, in order of value:

  • Never do unbounded work in the auth path. No locks that another queue can hold, no XPC round trip, no disk read, no allocation storm, no regex over content.
  • Aggressive muting up front so the event never reaches you: mute your own audit token (else your scanner reading a file generates the AUTH_OPEN that makes it scan the file — a self-deadlock), mute platform binaries you'll never police, mute noisy build/cache paths (~/Library/Caches, DerivedData), and use target-path muting for the write-heavy trees. Inverted muting if the watchlist is small.
  • A watchdog timer per message set to a fraction of msg->deadline — say 50% — that fires a default response if the decision path hasn't answered. You choose your own timeout so the OS never chooses for you.
  • Bounded queues with backpressure and a global drop/fail-open switch. Under overload, degrade to notify-only rather than dying.
  • Measure it in production: histogram of (respond_time / deadline) per event type, exported as a metric. If p99 crosses a threshold you self-demote to monitor mode and alert. That's the answer that sounds like someone who ran an agent at scale.

The scar to attach: pick a real one from JumpCloud — a hang, a queue starvation, a lock contention, a stall you found with Instruments — and tell it in 40 seconds with the fix.

"How do you avoid recursive events from your own agent?"

Mute your own audit token via es_mute_process at startup — audit token, not pid, because pids get reused and the token is the only identity that's actually stable. Same for your helper tools and any scanner subprocess you spawn. Then be careful about the second-order case: your log writes and your database writes generate file events too, so mute your own container/support paths by prefix. If you have multiple XPC-connected components, each one needs muting or you get an event storm between them. At FireEye's OAS this exact problem is why suppression modules exist — call that out to him.

"What can't ES do?"

Good question to answer confidently, it shows the edges of real experience:

  • No content. ES tells you an open happened, not what's in the file. You read it yourself — and that read is subject to TCC and to your own muting.
  • No network. Sockets are Network Extension territory. ES's process/file view stops at the syscall boundary.
  • No clipboard, no UI, no keystrokes. Pasteboard is completely invisible to ES (§08).
  • No pipes contents. Relevant for MCP stdio (§13) — you see the exec and the fds, not the bytes.
  • Not a full syscall audit. The event set is what Apple ships, versioned per macOS release; you must handle msg->version and guard newer fields with availability, or you crash on older OSes.
  • You're not first. Your DENY can't override another client's ALLOW, and vice versa — ES is AND-of-denies, so you can't guarantee you saw the operation before someone else's client did something with it.

System Extensions — lifecycle & deployment

This is where fleet experience differentiates you from an app developer. It's your home turf. Use it.

  • Anatomy: a container app in /Applications (must be there — SysExes won't activate from arbitrary paths) → OSSystemExtensionRequest.activationRequest → user approval prompt in System Settings → extension runs as root, out of your app's lifecycle. The container app can be closed; the extension persists.
  • Fleet reality: nobody clicks approve at scale. You ship an MDM configuration profile: com.apple.system-extension.install (allowed team IDs / bundle IDs) to pre-approve, plus a PPPC profile for Full Disk Access, plus com.apple.webcontent-filter if you also load a network extension. Without MDM, your agent is a support ticket. Say this — it's the practical knowledge Nightfall needs because their customers deploy via Jamf/Kandji/Intune.
  • Upgrades: replace the container app → request activation again → the system handles the swap, and the old extension is torn down. Version pinning matters: the extension's CFBundleVersion must be strictly greater or the request is ignored. Downgrades are effectively impossible without deactivation — which is why a remote kill switch inside the extension matters more than the ability to roll back the binary.
  • Debugging: systemextensionsctl list, systemextensionsctl developer on (SIP-disabled dev box only), log stream with --predicate 'subsystem == "com.yourco.agent"', and attaching LLDB to a root extension requires sudo + the right entitlement combination. Crash logs land in /Library/Logs/DiagnosticReports, not the user's.
  • The trap: a crash-looping system extension with an ES client is the worst failure in this domain. On macOS the system may throttle relaunch, and every relaunch re-subscribes and re-floods. You need a local circuit breaker: on N crashes in M minutes, boot into monitor-only mode with policy disabled, and phone home. Fail-open, always, on an endpoint agent that can wedge a machine.
"The thing I've learned running an agent at fleet scale is that the interesting bugs aren't in the code path, they're in the deployment path. Version skew between the container app and the extension, MDM profile ordering, TCC grants that didn't land, users on an OS you didn't test. Ninety percent of my production incidents came from there, not from the ES logic."
§07

XPC & IPC trust

Aehjaj's profile says "XPC-based architectures" explicitly. Expect at least one question. The security question here is the one people fail.

The architecture

Typical macOS DLP agent has three or four processes: a privileged daemon / system extension (root, ES client, policy engine), a LaunchAgent in the GUI session (user notifications, pasteboard access, screen capture — none of which work from a daemon), a network extension, and maybe a menu-bar app. They talk over XPC / NSXPCConnection, or Mach services registered in the launchd plist.

The question that separates people

"How do you know the process connecting to your privileged XPC service is really your agent and not malware?"

Wrong answers: check the pid, check the process name, check the path. All spoofable or racy — the classic pid-reuse attack: the caller exits between your check and your action, another process takes the pid, you authorise the wrong one.

Right answer: validate the peer's code signature, not its identity-by-position. Get the peer's audit_token from the connection (NSXPCConnection.auditToken, or xpc_connection_get_audit_token on the C API) and pass it to SecCodeCopyGuestWithAttributes with the kSecGuestAttributeAudit key, then SecCodeCheckValidity against a requirement string pinning your team ID and identifier, plus a minimum signing time so an old vulnerable signed build of yours can't be used against you. Audit token, never pid — that's the whole point, and it's why Apple deprecated the pid-based API. Also set NSXPCConnection.setCodeSigningRequirement() on macOS 13+, which does this for you and is the modern answer.

  • Keep the privileged surface tiny: the daemon exposes verbs ("evaluate this event", "fetch policy version"), not primitives ("read this path", "run this command"). A confused-deputy in a DLP agent running as root is a privilege escalation for every Mac in the fleet.
  • Bound everything: message size caps, rate limits per peer, timeouts on every reply block, and never block the ES queue on an XPC reply.
  • Whitelist your interface classes explicitly (setClasses:forSelector:argumentIndex:ofReply:) — an unrestricted NSXPCInterface with NSSecureCoding off is a deserialisation hole.

Clipboard DLP on macOS

You already answered this in Round 1 at a design level. He will re-ask it at an implementation level, because it's genuinely hard on macOS and it's a core Nightfall feature.

The truth to lead with macOS gives you no clipboard event API. No ES event, no notification, no callback. Anyone who says otherwise hasn't built it. Say this first — it's the commit — then show how you'd work around it.

Detection: change-count polling

// From a LaunchAgent in the GUI session — NOT from a root daemon.
// NSPasteboard is per-session; a daemon sees nothing.
let pb = NSPasteboard.general
var last = pb.changeCount
timer = Timer(timeInterval: 0.25) { _ in
    guard pb.changeCount != last else { return }   // cheap; no read, no TCC prompt
    last = pb.changeCount
    // now: who owns it, what types, how big
}
  • changeCount is monotonic and free to read — poll it, don't read the contents. 200–500ms is the sane range; that's your CPU/latency trade-off and he'll ask for the number.
  • Inspect pb.types before pb.string(forType:) — a copied 50MB image shouldn't be pulled into memory. Cap the inspection size; classify a prefix.
  • Who copied it: there's no clean owner API. In practice you correlate with NSWorkspace.shared.frontmostApplication at the instant of the change count bump, plus NSWorkspace.didActivateApplicationNotification to keep a running foreground history. It's inference, not ground truth — say so, it's the honest engineering answer.
  • Privacy landmine (know this): recent macOS releases surface a user-facing prompt/notification when an app programmatically reads pasteboard contents it didn't put there. A DLP agent that reads the clipboard on every change is a UX incident. Mitigations: NSPasteboard.detectPatterns/type detection to check what kind of data is there without a full read, only read when the type and the destination make it policy-relevant, and get the behaviour blessed via MDM where possible. Bringing this up unprompted is a strong signal you've shipped against modern macOS, not macOS 11.

USB & removable media

Aehjaj shipped USB exfil monitoring + blocking at Nightfall in 4 weeks. High chance he asks. Match his level.

Three enforcement points, from blunt to surgical

  1. Block the mount: ES_EVENT_TYPE_AUTH_MOUNT — you get the statfs, deny and the volume never appears. Also DiskArbitration: DARegisterDiskMountApprovalCallback, and DADiskUnmount to eject after the fact. Blunt: kills legitimate read-only use, and the user just sees "USB doesn't work on my Mac."
  2. Force read-only: allow the mount, then remount with MNT_RDONLY, or via DA approval callbacks. Good middle ground for "read your files, never write ours."
  3. Policy per write (the real DLP answer): allow the mount, capture the volume's f_mntonname and, crucially, its st_dev. Then on AUTH_CREATE / AUTH_OPEN / AUTH_RENAME / AUTH_COPYFILE / AUTH_CLONE, compare the target's st_dev against your removable-volume set. Match the source file's sensitivity label; deny only sensitive→removable. Everything else flows.

Why st_dev and not the path: because /Volumes/Untitled is a string an attacker controls, symlinks and firmlinks exist, and /Volumes prefix matching is a bypass waiting to happen. A device number is a kernel fact. That distinction is exactly the kind of thing an ex-CrowdStrike engineer will notice you making.

Device identity (allowlisting a corporate USB key)

IOKit: walk the IORegistry from the BSD name (IOBSDNameMatching) up the parent chain to the USB device node and read idVendor, idProduct, kUSBSerialNumberString. Vendor+product alone is not identity — the serial is, and even that is forgeable by a determined attacker with a programmable device. So allowlist on serial, but treat it as a convenience control, not a security boundary, and say that out loud.

The cases that catch people

  • Not everything is USB. SD cards, Thunderbolt enclosures, network shares (SMB/AFP), disk images (.dmg mounted from a download), and iCloud/Dropbox sync folders all move data off the machine. A DMG on a removable volume is a nested filesystem with a different st_dev. Ask which classes are in scope.
  • APFS clones. copyfile with COPYFILE_CLONE and clonefile() aren't reads-then-writes — if you only watch OPEN/WRITE you miss them entirely. Hence AUTH_CLONE and AUTH_COPYFILE.
  • Finder is not the actor. A drag-copy in Finder means the writing process is Finder, not the user's app. Attribution by process alone lies; you need the source inode's label, not the actor's intent.
"The version I'd build first isn't mount-blocking, it's device-scoped write policy keyed on st_dev, with the sensitivity label carried on the source inode. Mount-blocking is a one-day feature that generates support tickets forever; the st_dev model is the one you can actually tune per-customer."
§11 · He built this too

Screen capture & ScreenCaptureKit

  • SCShareableContent to enumerate displays/windows/apps; SCContentFilter to scope; SCStream + SCStreamOutput for frames; SCScreenshotManager (macOS 14+) for one-shots. Frames arrive as CMSampleBuffer — you get IOSurface-backed pixel data, so you can go straight to VideoToolbox for H.264 without a CPU copy.
  • Must run in the GUI session (LaunchAgent), needs Screen Recording TCC. A root daemon cannot capture. PPPC profile can pre-grant it via MDM, which is the only way this ships to a fleet.
  • macOS 15 added a recurring user prompt for screen recording (monthly-ish, and per-app), which is a real product problem for a forensics feature. The mitigation is MDM pre-approval; know that this exists because it burned every vendor in this space, including, probably, him.
  • DLP-relevant design: don't record continuously — that's a privacy nightmare and a disk/CPU disaster. Trigger on policy events (sensitive file open, blocked paste, exfil attempt), capture a bounded ring buffer of the seconds around it, redact aggressively, upload with the audit event. What you can actually build (be concrete, this is a design he'll grade)

  3. Capability, not just presence. The risk of an MCP server is what it can reach. A filesystem server rooted at ~, a Postgres server with prod creds in env, a browser-automation server — that's the risk model. You derive it from argv + env + subsequent behaviour (what does that child open? what does it connect to?). This is where an endpoint agent beats an inventory tool: you see the actual file opens and flows of the server process, not the declared scope.

  5. Honesty The stdio bytes themselves: you cannot read another process's pipe without something like a task port (blocked by SIP/hardened runtime) or an injected shim (which breaks the hardened runtime and is a support nightmare). So the honest position is: inventory + capability + behavioural attribution at the process level, not content interception on the pipe. §15

Performance, concurrency, and the auth path

Queue discipline

  • Dedicated serial queue for the ES client, high QoS (.userInteractive) — you're on a syscall path a human is waiting on.
  • AUTH and NOTIFY on separate queues; never let notify volume starve auth latency.
  • es_retain_message + hop off the callback queue for anything that isn't a cache lookup.
  • Zero locks in the auth path that any other queue can acquire. Prefer immutable snapshots of policy, swapped atomically on update.

Overload behaviour

  • Bounded queues, explicit drop policy, and a metric for drops. Silent drops in a security agent are a compliance lie.
  • Self-demotion: p99 latency or queue depth over threshold → notify-only mode → alert.
  • Watchdog per message at a fraction of the deadline.
  • Budget for the fact that a Mac in a build loop generates tens of thousands of file events per second. Xcode is your worst adversary, not malware.

Tooling to name: Instruments (Time Profiler, System Trace, Points of Interest with os_signpost around the auth path), log stream/log collect with a subsystem predicate, fs_usage, spindump for hangs, sample, LLDB against a root extension, and Malloc/Zombies for the ARC-meets-C-API lifetime bugs you get wrapping es_message_t in Swift.

"The Swift-over-ES lifetime bugs are their own genre: es_message_t is a C struct with a manual retain/release, and the moment you capture it in a Swift closure that outlives the callback without es_retain_message, you get a use-after-free that only reproduces under load. I've learned to wrap it in a small RAII-style Swift type at the boundary so ownership is unmissable."

  • Full Disk Access is required for ES, and is required to read the files you're policing. Without it your ES client won't even instantiate (ES_NEW_CLIENT_RESULT_ERR_NOT_PERMITTED). At fleet scale it's a PPPC profile over MDM; on an unmanaged Mac it's a support call.

Rapid-fire bank

Kext vs system extension — why did Apple move?

Kexts run in the kernel: a bug is a panic, a vuln is ring-0, and every kext is an attack surface Apple can't patch. System extensions run in userspace with an entitlement, so a crash kills your process, not the machine, and Apple controls the API surface and can version it. Kexts are deprecated and require reduced security on Apple Silicon — which for a security vendor is a non-starter, because you'd be asking customers to weaken the machine to run your security product.

How do you identify a process for policy?

cdhash for exact binary identity, team ID + signing ID for "any build from this vendor", and codesigning_flags to check CS_VALID and platform-binary status. Never the path, never the process name, never the pid — all three are attacker-controlled or racy. For scripts and interpreters the identity problem is genuinely unsolved: node is node, so you fall back to the argv + parent chain + the script file's own hash.

What's the difference between AUTH_OPEN and NOTIFY_OPEN for DLP?

AUTH_OPEN is synchronous, on the caller's syscall path, deadline-bound, and lets you return a flags result so you can strip write access without failing the open. NOTIFY_OPEN is after the fact — you can't stop anything, but there's no deadline and no risk of wedging the machine. Real agents use AUTH sparingly on a narrow, muted-down path and NOTIFY for everything else.

Why can't your root daemon read the clipboard or capture the screen?

Both are per-GUI-session, window-server-mediated resources. A root LaunchDaemon has no session context and no TCC identity tied to a logged-in user. You need a LaunchAgent running in the user's session, which then talks to the daemon over XPC. This split — daemon for kernel-adjacent, agent for session-adjacent — is the fundamental shape of every macOS endpoint agent.

A customer says your agent makes their Mac slow. Walk me through it.

First, data: pull the agent's own metrics — ES event rate by type, respond-time p99 vs deadline, queue depth, drop count, CPU by subprocess. Nine times out of ten it's event volume from a build or a sync client, not the policy logic. Then Instruments System Trace and fs_usage on the box to find the generator. Fix order: mute the source (path/process/target muting), then reduce subscription set, then optimise the path. Ship a per-customer mute config so it's a support action, not a release. And the real fix is that the agent should have self-demoted before the customer noticed — if a human told you first, your telemetry failed.

How do you handle a new macOS release?

Run the beta from day one on a dedicated ring; the ES event enum and es_message_t version grow every release, so you guard new fields with version checks and compile with the new SDK but keep the deployment target. The recurring breaks: TCC prompts changing (Sequoia's screen-recording nag), new privacy gates (pasteboard), SysEx approval flow changes, and event semantics quietly shifting. Budget for one fire-drill per major release, because there will be one.
