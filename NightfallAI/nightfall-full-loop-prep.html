The whole loop,
round by round

Sabin's mail gives you the exact shape: 75 min build-a-class-and-test-it, 60 min macOS system design, 45 min deep dive + HM behavioural. That's an unusual amount of information. Most candidates get "a technical round." You get the rubric.

Round 1 is the one people underestimate. It isn't LeetCode — it's "can you build a clean, testable component under time pressure," which is a different skill and much closer to the job. It's also the round where your decade of shipping actually shows, if you let it.

The thread through all three

Commit first, caveat second. In Round 1 that's "I'll use a hash map plus a doubly-linked list — here's why, and here's what it costs." In Round 2 it's "here's my design — and here's the part I'd expect to break." In Round 3 it's "here's what I decided and here's what I got wrong." The pattern that has cost you rounds before is committing to nothing and covering everything. Three rounds, one fix.

What "console application, not a web service" tells you

This constraint is doing a lot of work. It means:

  • No frameworks, no DI containers, no HTTP. Pure data structures and logic.
  • Your "API" is a class interface, not an endpoint. They want to see how you design a contract.
  • Tests will be hand-rolled — they're not going to make you set up XCTest or GoogleTest in a shared editor. Write your own 10-line assert harness. §5.
  • "Driver code" = a main() that exercises scenarios and prints. They want to see it run.
  • The DS hint (stacks, queues, maps, hash tables) is not decoration. Someone chose those four words. Expect a problem whose correct answer is a composition of two of them — which is exactly what an LRU cache, a dedup engine, or a path trie is.

§1

Decoding "API skeleton service class"

They hand you something like this and you fill it in.

// They give you this. Or dictate it. Or paste it in a doc.
protocol PolicyService {
    func addRule(_ rule: Rule) throws -> RuleID
    func removeRule(_ id: RuleID) throws
    func evaluate(_ event: Event) -> Verdict
    func stats() -> Stats
}
// "Implement this. Write unit tests. Write driver code. 75 minutes. Go."

Why this format, and what it rewards

It's a proxy for the actual job. At Nightfall you'll be handed "we need USB exfil blocking" and you'll produce a class that other people call. Nobody will give you a LeetCode problem. What they want to know is:

  • Do you ask about the contract before coding? (What happens on a duplicate rule? Is evaluate thread-safe? What's the expected call rate?)
  • Do you pick a data structure for a stated reason, or the first one that comes to mind?
  • Do you handle the degenerate inputs — empty, nil, duplicate, huge, concurrent — without being asked?
  • Does your code run? A working 80% beats a beautiful 100% that doesn't compile.
  • Do your tests test behaviour or just repeat the implementation back?

§2

The 75-minute clock

Have this in your head before you start. Announce it. It makes you look like you've run projects, because you have.

0–7 min
Clarify & contract. Ask 4–6 sharp questions. Restate the requirements in your own words. Write the API contract as comments above each method: preconditions, postconditions, complexity, thread-safety. This is not wasted time — it's the deliverable they said they're scoring ("solution ideation").
7–12 min
Pick the DS out loud. Two options, why you chose one, what it costs. Sketch the invariant. "The invariant is: the map and the list always contain exactly the same keys."
12–45 min
Implement. Core happy path first, compiling as you go. Talk while you type — silence is the enemy in this format.
45–60 min
Tests. This is where most candidates run out of clock and it's explicitly in the brief. Budget it. Do not let implementation eat it.
60–70 min
Driver code + run it. Show the output. There is nothing more persuasive in this round than a terminal printing the right answers.
70–75 min
Extensions out loud. "If this were production I'd add X, Y, Z. Here's what I'd do about thread safety. Here's the O(1) I traded away." Never end on silence.

The failure mode Minute 60, still implementing, no tests, no driver, and the interviewer writes "did not complete the stated task." At minute 45 you stop implementing, no matter what state you're in. A partially implemented class with real tests and a working driver scores higher than a complete class with nothing to prove it. The brief literally lists three deliverables — deliver three partial things, not one whole thing.

"Before I start — I'm going to spend about five minutes on the contract, thirty on the implementation, fifteen on tests and ten on the driver, and leave five to talk about what I'd do differently in production. If you'd rather I weight it differently, tell me now."

That sentence alone puts you in the top decile of this round. It says: I've done this, I know the clock is the enemy, and I plan.

§3

The method — same eight steps every time

1 · Clarify (the six questions that always apply)

  1. Scale. "How many entries? Calls per second?" — decides map vs sorted array vs trie. On an endpoint the answer is usually "millions of events, thousands of rules" and that immediately kills anything O(n) per event.
  2. Concurrency. "Is this called from multiple threads? Is there a single writer?" — decides lock vs lock-free vs "document as not thread-safe." Never silently assume single-threaded. Ask, then state your assumption.
  3. Lifetime & bounds. "Is memory bounded? What's the eviction policy?" — a cache without a bound is a bug, and in an endpoint agent it's an OOM in a process that must never die.
  4. Error semantics. "Duplicate insert — overwrite, throw, or ignore? Unknown key — nil or throw?" — this is API design, which is what they're actually testing.
  5. Time. "Is there a clock? Can I inject it?" — if anything involves TTL, windows, or rates, inject the clock or you cannot test it. Doing this unprompted is a strong signal.
  6. Ordering. "Do results need to be ordered? Stable?" — cheap to ask, expensive to retrofit.

2 · Write the contract before the code

/// Thread-safe. Safe to call from any queue.
/// - Complexity: O(1) amortised.
/// - Precondition: capacity > 0.
/// - If `key` exists, the value is replaced and the entry becomes most-recent.
/// - If at capacity, evicts exactly one least-recently-used entry.
func put(_ key: Key, _ value: Value)

Four comment lines. They take ninety seconds. They answer half the follow-up questions before they're asked, and they demonstrate that you think about contracts — which is the entire named subject of the round.

3 · State the invariant

Every composite data structure has one sentence that must always be true. Say it out loud, write it as a comment, and — this is the move — write a test that asserts it.

  • LRU: "map.count == list.count, and every list node's key is in the map."
  • Trie: "a node is terminal iff a rule ends here."
  • Ring buffer: "count ≤ capacity, and head/tail are always in range."
  • Dedup: "no two records with the same key inside the window."
// This test is worth three normal tests. Nobody writes it. Write it.
func testInvariantHoldsUnderRandomOps() {
    let c = LRUCache<Int,Int>(capacity: 8)
    for i in 0..<10_000 {
        if Int.random(in: 0...2) == 0 { _ = c.get(Int.random(in: 0..<20)) }
        else { c.put(Int.random(in: 0..<20), i) }
        expect(c.checkInvariant(), "invariant broken at op \(i)")
    }
}

4 · Implement the happy path, compiling as you go

Do not write 200 lines then compile. Write 20, compile, run. In a shared editor with no compiler, say "let me trace through this with a small example" and do it. Tracing an example out loud catches more bugs than staring does, and it fills the silence with signal.

5 · Edge cases, before they ask

Empty. One element. Capacity 1. Capacity 0 (throw? clamp? document it). Duplicate key. Missing key. Update-in-place. Eviction of the thing you just added. Overflow of your counter. Clock going backwards (it does — NTP). Same key from two threads.

6 · Tests that test behaviour, not implementation

Bad: expect(cache.map.count == 1). That tests your internals and breaks when you refactor. Good: expect(cache.get(1) == nil, "evicted key must be gone"). Test through the public API only. If a behaviour is important enough to test, it's important enough to be public — and if it's not public, don't test it.

7 · Driver code that tells a story

Not a dump of every method. A scenario: "here's a rule set, here are five events, here's the verdict for each, here are the stats." Print it in a table. It takes ten minutes and it's the thing they'll remember.

8 · Close with the production delta

"In production I'd add: metrics on hit rate and eviction rate, because eviction rate is a security metric not a perf metric when you're caching verdicts. A bounded memory cap rather than an entry count, because entry sizes vary. And I'd inject the clock, which I've done here, so the TTL logic is testable without sleeping."

§4

Swift or C++?

They said either. It's a real choice with real consequences.

Pick this Swift
  • It's your language. Ten years of it. Under a 75-minute clock, fluency beats everything.
  • The role is a macOS agent role. Nightfall's agent is Swift + XPC + ES (per Aehjaj's own profile). Swift is the job.
  • Less ceremony: no headers, no build config, value semantics, Dictionary is right there.
  • Risk: your interviewer is a deep C++ person. He may read Swift more slowly, so narrate more.
Only if pushed C++
  • Speaks the interviewer's native language (C++11/14/20, boost, cmake, conan on his profile).
  • Exposes you to: iterator invalidation, unordered_map reference stability, move semantics, RAII, lifetime — a much bigger surface to slip on under time pressure.
  • If he asks "could you do it in C++?" — say yes and mean it, then talk through the shape (§8 has the C++ LRU). Don't switch unless he asks.
"I'll write it in Swift — it's what I've been shipping in the macOS agent for the last three years and it's what your agent is written in. I'm comfortable talking about the C++ shape of the same design if that's more useful for the discussion; the trade-offs are mostly in the memory model, not the algorithm."

The C++ facts to have ready if he probes

He asksYou say
Why std::list + unordered_map for LRU?std::list gives O(1) splice and — critically — iterators and references stay valid across insert/erase of other elements. So the map can store list::iterator safely. A vector or deque would invalidate. That reference-stability point is the whole answer.
unordered_map vs map?O(1) average vs O(log n) guaranteed. unordered_map invalidates iterators on rehash but not references to elements. map is stable and ordered but slower and cache-hostile. On an endpoint hot path: unordered_map, with reserve() up front to avoid rehash stalls.
Custom key type?Specialise std::hash<Key> and provide operator==. Combine field hashes properly (boost's hash_combine shape) — don't XOR raw hashes, you'll collide on permutations.
Thread safety?std::shared_mutex for read-heavy (C++17), std::mutex otherwise. But an LRU has no read-only path — a get mutates recency — so a reader-writer lock buys you nothing. That observation is the real answer and it's a lovely thing to volunteer.
Move semantics?emplace over insert, std::move into the container, and mark your move ctor noexcept or vector will copy instead of move on reallocation.
§5

The test harness (write this from memory)

No XCTest, no GoogleTest. Console app. So you bring your own. Ten lines. Memorise them.

Swift
// ── Micro test harness ───────────────────────────────────────
var _passed = 0, _failed = 0

func expect(_ cond: @autoclosure () -> Bool, _ what: String,
            _ f: String = #file, _ l: Int = #line) {
    if cond() { _passed += 1 }
    else { _failed += 1; print("✗ FAIL: \(what)  [\((f as NSString).lastPathComponent):\(l)]") }
}

func expectEqual<T: Equatable>(_ a: T, _ b: T, _ what: String,
                              _ f: String = #file, _ l: Int = #line) {
    expect(a == b, "\(what) — expected \(b), got \(a)", f, l)
}

func suite(_ name: String, _ body: () -> Void) {
    print("\n── \(name) ──"); body()
}

func report() -> Int {
    print("\n\(_passed) passed, \(_failed) failed")
    return _failed == 0 ? 0 : 1
}

The move that separates you

Write the harness first, before the implementation — it takes two minutes — and say: "I'll write a tiny assert harness up front so I'm not doing this at minute 60 when the clock's against me." That is exactly what a senior engineer does and exactly what a junior doesn't. It also means that when you're at minute 47 and behind, testing costs you nothing but the tests themselves.

The seven tests to write for literally any class

  1. Empty state. Fresh object, query it, don't crash, return sensible nothing.
  2. Single element. Add one, get it back.
  3. The core behaviour. The one thing the class exists to do.
  4. The boundary. Capacity exactly reached, then exceeded by one.
  5. Update semantics. Same key twice. Does it replace? Does it change recency/order?
  6. Removal. Remove present, remove absent, remove twice.
  7. The invariant, under random ops. §3, step 3. This one is worth three of the others.

Then, if you have clock left: concurrency (N threads hammering, assert no crash and count is sane) and time (inject a fake clock, jump it forward, assert expiry).

The three compositions that answer almost every question in this round

map + doubly-linked list

= LRU cache. Map gives O(1) find; list gives O(1) reorder. Map stores node references. Invariant: same keys in both, always.

map + heap

= TTL store / scheduler. Map for lookup; min-heap on expiry for "what dies next" in O(log n). Lazy deletion: leave stale entries in the heap and skip them on pop.

map + deque

= sliding-window rate limiter / dedup. Map keys → deque of timestamps. Pop from the front while older than the window.

trie + terminal flags

= path/domain matcher. Longest-prefix wins. O(depth), not O(rules). This is literally how ES path muting works.

§8 · Problem bank A

LRU cache & TTL store

The single most likely problem. Know it so well you can talk while writing it.

Swift — LRU with an intrusive doubly-linked list
final class LRUCache<Key: Hashable, Value> {

    private final class Node {
        let key: Key
        var value: Value
        var prev: Node?
        unowned var next: Node?      // see note on cycles below
        init(_ k: Key, _ v: Value) { key = k; value = v }
    }

    private var map: [Key: Node] = [:]
    private var head: Node?          // most recently used
    private var tail: Node?          // least recently used — the eviction victim
    private let capacity: Int
    private(set) var hits = 0, misses = 0, evictions = 0

    /// - Precondition: capacity > 0
    init(capacity: Int) {
        precondition(capacity > 0, "capacity must be positive")
        self.capacity = capacity
        map.reserveCapacity(capacity)     // no rehash on the hot path
    }

    /// O(1). Promotes the entry to most-recently-used.
    func get(_ key: Key) -> Value? {
        guard let n = map[key] else { misses += 1; return nil }
        hits += 1
        moveToFront(n)
        return n.value
    }

    /// O(1). Replaces an existing value and promotes it.
    /// Evicts exactly one LRU entry if at capacity.
    func put(_ key: Key, _ value: Value) {
        if let n = map[key] { n.value = value; moveToFront(n); return }

        let n = Node(key, value)
        map[key] = n
        addToFront(n)

        if map.count > capacity, let victim = tail {
            remove(victim)
            map[victim.key] = nil
            evictions += 1
        }
    }

    @discardableResult
    func remove(_ key: Key) -> Value? {
        guard let n = map.removeValue(forKey: key) else { return nil }
        remove(n)
        return n.value
    }

    var count: Int { map.count }

    // ── list plumbing ────────────────────────────────────────
    private func addToFront(_ n: Node) {
        n.prev = nil; n.next = head
        head?.prev = n
        head = n
        if tail == nil { tail = n }
    }

    private func remove(_ n: Node) {
        if let p = n.prev { p.next = n.next } else { head = n.next }
        if let nx = n.next { nx.prev = n.prev } else { tail = n.prev }
        n.prev = nil; n.next = nil
    }

    private func moveToFront(_ n: Node) {
        guard head !== n else { return }
        remove(n); addToFront(n)
    }

    // ── the test that's worth three tests ────────────────────
    func checkInvariant() -> Bool {
        var seen = 0, node = head
        while let n = node { guard map[n.key] === n else { return false }
                            seen += 1; node = n.next }
        return seen == map.count && map.count <= capacity
    }
}

The Swift detail to volunteer A doubly-linked list with two strong references creates a retain cycle — the classic Swift memory bug. You break it with unowned or weak on one direction. Say this out loud as you write it: "I'm making next unowned to break the cycle; with strong both ways the whole list leaks even after you drop the cache." That single sentence is worth more than the rest of the implementation, because it says you've debugged real Swift memory problems rather than read about them. (If you'd rather not reason about it under pressure, the safe alternative is an array-backed node pool with integer indices — no ARC, no cycles, better cache locality. That's also a great thing to mention as the production version.)

C++ — the same thing, 20 lines
template <typename K, typename V>
class LRUCache {
    using Entry = std::pair<K, V>;
    std::list<Entry> order_;                                 // front = MRU
    std::unordered_map<K, typename std::list<Entry>::iterator> map_;
    size_t cap_;
public:
    explicit LRUCache(size_t cap) : cap_(cap) {
        if (cap == 0) throw std::invalid_argument("capacity must be > 0");
        map_.reserve(cap);
    }

    std::optional<V> get(const K& k) {
        auto it = map_.find(k);
        if (it == map_.end()) return std::nullopt;
        order_.splice(order_.begin(), order_, it->second);   // O(1), no realloc
        return it->second->second;
    }

    void put(const K& k, V v) {
        auto it = map_.find(k);
        if (it != map_.end()) {
            it->second->second = std::move(v);
            order_.splice(order_.begin(), order_, it->second);
            return;
        }
        order_.emplace_front(k, std::move(v));
        map_[k] = order_.begin();
        if (map_.size() > cap_) {
            map_.erase(order_.back().first);
            order_.pop_back();
        }
    }
};

// OTHER elements. That reference stability is why the map can hold iterators
// at all. With a vector or deque this design is simply invalid.

Variant: TTL / expiring store (map + min-heap)

protocol Clock { var now: TimeInterval { get } }
final class FakeClock: Clock {          // ← INJECT THIS. Do not use Date().
    private(set) var now: TimeInterval
    init(now: TimeInterval) { self.now = now }
    func advance(_ d: TimeInterval) { now += d }
}

final class TTLStore<K: Hashable, V> {
    private struct Box { let value: V; let expires: TimeInterval }
    private var map: [K: Box] = [:]
    private var heap = MinHeap<(TimeInterval, K)>()   // lazy deletion
    private let clock: Clock, ttl: TimeInterval

    func put(_ k: K, _ v: V) {
        let e = clock.now + ttl
        map[k] = Box(value: v, expires: e)
        heap.push((e, k))                // old heap entries left behind on purpose
    }

    func get(_ k: K) -> V? {
        guard let b = map[k] else { return nil }
        if b.expires <= clock.now { map[k] = nil; return nil }   // lazy expire on read
        return b.value
    }

    /// Amortised bulk reclaim. Call on a timer, not on the hot path.
    func sweep() {
        while let (e, k) = heap.peek(), e <= clock.now {
            heap.pop()
            // The heap entry may be stale — the key may have been re-put
            // with a later expiry. Check before deleting. THIS is the bug
            // they're looking for.
            if let b = map[k], b.expires <= clock.now { map[k] = nil }
        }
    }
}
Two things to say here, both high-value

1. Inject the clock. "I'm taking a Clock protocol rather than calling Date(), because otherwise the only way to test expiry is sleep(11) and my test suite takes a minute. With an injectable clock the test is instant and deterministic." Interviewers love this because it's the difference between someone who writes tests and someone who has maintained tests.

2. Lazy deletion in the heap. A heap can't delete an arbitrary element in O(1), so when a key is re-put with a new expiry the old heap entry is stale. You leave it and validate on pop. Volunteer the trade: the heap can grow larger than the map under a re-put-heavy workload, so if that's a concern you either cap it or switch to an indexed heap. Naming the leak before they find it is the whole game.

Rate limiter

Two canonical answers. Know both and know when each is right.

Token bucket — O(1) memory per key, allows bursts
final class TokenBucket {
    private var tokens: Double
    private var lastRefill: TimeInterval
    private let capacity: Double      // max burst
    private let refillRate: Double    // tokens per second = steady-state rate
    private let clock: Clock

    init(capacity: Double, refillRate: Double, clock: Clock) {
        self.capacity = capacity; self.refillRate = refillRate
        self.clock = clock; tokens = capacity; lastRefill = clock.now
    }

    /// O(1) time, O(1) memory. No history stored — that's the whole point.
    func allow(_ cost: Double = 1) -> Bool {
        refill()
        guard tokens >= cost else { return false }
        tokens -= cost
        return true
    }

    private func refill() {
        let now = clock.now
        let elapsed = max(0, now - lastRefill)   // max(0,·) — NTP can move time BACK
        tokens = min(capacity, tokens + elapsed * refillRate)
        lastRefill = now
    }
}
Sliding window log — exact, but O(n) memory per key
final class SlidingWindow {
    private var hits: [String: Deque<TimeInterval>] = [:]
    private let limit: Int, window: TimeInterval, clock: Clock

    func allow(_ key: String) -> Bool {
        let now = clock.now
        var q = hits[key] ?? Deque()
        while let f = q.first, f <= now - window { q.removeFirst() }   // evict old
        guard q.count < limit else { hits[key] = q; return false }
        q.append(now)
        hits[key] = q
        return true
    }
}

The follow-ups, guaranteed

  • "Millions of keys?" — the buckets themselves are now the leak. Wrap it in an LRU (§8) or a TTL sweep on idle buckets. Now you're composing two problems, which is exactly what they hoped you'd do.
  • "Thread safety?" — one lock per bucket, not one global lock. Or shard the map by hash(key) % N with N locks. Global lock on a rate limiter serialises the entire hot path.
  • "Clock goes backwards?" — it does. NTP steps, sleep/wake on a laptop (very relevant here!). Use a monotonic clock (mach_absolute_time / CLOCK_MONOTONIC), and clamp with max(0, elapsed) anyway. On macOS specifically: does your monotonic clock advance during sleep? mach_absolute_time historically does not; mach_continuous_time does. Naming that pair is a genuine macOS-internals flex and it belongs in this round even though it looks like a DS round.

Path trie — the endpoint-security classic

If they ask a domain-flavoured question, it's probably this. It's literally how ES path muting works.

/// Longest-prefix path matcher.
/// Cost: O(depth of the query path). INDEPENDENT of the number of rules —
/// that's the whole reason we're not using an array of prefixes.
final class PathTrie<Value> {

    private final class Node {
        var children: [String: Node] = [:]
        var value: Value?          // non-nil ⇒ a rule terminates here
        var isExact = false       // literal match only, not a prefix rule
    }
    private let root = Node()

    // "/Users/chella/Docs" → ["Users","chella","Docs"]  — components, not chars.
    // Component-keying is the right call for paths: fewer nodes, and it makes
    // "/Users/chellaprabu" NOT match a "/Users/chella" prefix rule — which a
    // naive string hasPrefix() gets WRONG. That bug is a real DLP bypass.
    private func split(_ p: String) -> [String] {
        p.split(separator: "/").map(String.init)
    }

    func insert(prefix path: String, value: Value, exact: Bool = false) {
        var n = root
        for c in split(path) {
            if n.children[c] == nil { n.children[c] = Node() }
            n = n.children[c]!
        }
        n.value = value
        n.isExact = exact
    }

    /// Longest match wins — the most specific rule for this path.
    func match(_ path: String) -> Value? {
        let comps = split(path)
        var n = root
        var best: Value? = nil

        if let v = root.value, !root.isExact { best = v }   // "/" catch-all rule

        for (i, c) in comps.enumerated() {
            guard let next = n.children[c] else { break }
            n = next
            if let v = n.value {
                let atEnd = (i == comps.count - 1)
                if !n.isExact || atEnd { best = v }   // exact rules only fire at the leaf
            }
        }
        return best
    }

    func remove(prefix path: String) {
        // Clear the value; prune childless nodes on the way back up.
        // Use an explicit STACK of the visited nodes — this is where they
        // wanted "stacks" to show up.
        var stack: [(Node, String)] = []
        var n = root
        for c in split(path) {
            guard let next = n.children[c] else { return }
            stack.append((n, c)); n = next
        }
        n.value = nil; n.isExact = false
        var child = n
        while let (parent, key) = stack.popLast() {
            guard child.children.isEmpty, child.value == nil else { break }
            parent.children[key] = nil
            child = parent
        }
    }
}
The three things to say while writing this

1. Why not just an array of prefixes and hasPrefix()? Because it's O(rules) per event and you're doing this on the AUTH path a hundred thousand times a second. The trie is O(depth) — about 6 — regardless of whether you have 10 rules or 10,000. That's the argument, and it's the only argument you need.

2. Why components, not characters? Because "/Users/chellaprabu" .hasPrefix("/Users/chella") is true, and that's a real, shipped-in-production DLP bypass class. Component-splitting makes it structurally impossible. This is the best single observation you can make in this problem.

3. What about symlinks, firmlinks, .., case-insensitivity, and Unicode normalisation? APFS is case-insensitive by default but case-preserving; macOS normalises Unicode differently in different places; /tmp is a symlink to /private/tmp; /Users crosses a firmlink. So you canonicalise before you match — and on a real agent you'd key on (dev, inode) where you can rather than trusting any string at all. Saying this turns a data-structures answer into a macOS-security answer, in a round that's nominally about data structures. It will be remembered.

Event deduplication / suppression

Your interviewer built the suppression module for AV at FireEye. If this comes up, it's personal.

/// Suppresses duplicate events within a time window, and reports how many
/// were suppressed so a rollup can be emitted. Never silently drops —
/// silent drops in a security product are a compliance lie.
final class Suppressor<Key: Hashable> {

    struct Decision {
        let emit: Bool
        let suppressedSinceLast: Int      // attach to the rollup
    }

    private struct Record { var lastEmitted: TimeInterval; var suppressed: Int }

    private var records: LRUCache<Key, Record>   // ← bounded. Composition.
    private let window: TimeInterval
    private let clock: Clock
    private(set) var emitted = 0, suppressed = 0

    init(window: TimeInterval, maxKeys: Int, clock: Clock) {
        records = LRUCache(capacity: maxKeys)
        self.window = window; self.clock = clock
    }

    func shouldEmit(_ key: Key) -> Decision {
        let now = clock.now

        guard var r = records.get(key) else {
            records.put(key, Record(lastEmitted: now, suppressed: 0))
            emitted += 1
            return Decision(emit: true, suppressedSinceLast: 0)   // first sighting
        }

        if now - r.lastEmitted >= window {
            let n = r.suppressed
            r.lastEmitted = now; r.suppressed = 0
            records.put(key, r)
            emitted += 1
            return Decision(emit: true, suppressedSinceLast: n)  // window rolled → emit + rollup
        }

        r.suppressed += 1
        records.put(key, r)
        suppressed += 1
        return Decision(emit: false, suppressedSinceLast: 0)
    }
}

The design conversation this problem is really about

  • What's the key? This is the whole question and it's a domain question, not a code question. For file events: (actor cdhash, target dev+inode, event type). Not the path — paths change, inodes don't. Not the pid — pids get reused. Choosing the key correctly is 80% of the grade here.
  • Bounded? Yes — LRU-wrapped, because the key space is unbounded on a real machine. An unbounded dedup map on a build machine is an OOM. Compose, don't reinvent.
  • First-emit or last-emit? Emit the first immediately (low latency for the alert), suppress the rest, then emit a rollup at the window boundary with the count. Never just drop — the count is the signal that something is looping.
  • What about a burst that stops? If 5,000 events arrive then silence, the rollup never fires because nothing triggers the check. Need a timer to flush. Volunteer this hole. It's the bug in the naive version and finding your own bug is the best thing you can do in this round.
"The interesting part isn't the algorithm, it's the key. If you key on path you'll suppress two different files that got renamed into the same name, and you'll fail to suppress the same file being hammered under two paths through a symlink. So I'd key on dev+inode plus the actor's cdhash plus the event type. And I'd bound it with an LRU, because on a machine doing an Xcode build the key space is effectively infinite."

Policy rule engine

The most "API service class"-shaped problem in the bank. If the brief mentions add/remove/evaluate, it's this.

// ── The contract, written FIRST ──────────────────────────────
struct Rule {
    let id: RuleID
    let pathPrefix: String?      // nil = any
    let actorTeamID: String?     // nil = any
    let eventType: EventType?    // nil = any
    let priority: Int            // higher wins ties
    let verdict: Verdict         // .allow / .deny / .readOnly
}

final class PolicyEngine {

    private var byID: [RuleID: Rule] = [:]              // O(1) remove
    private var pathIndex = PathTrie<[RuleID]>()        // O(depth) narrowing
    private var wildcards: [RuleID] = []                // rules with no path
    private var cache = LRUCache<EventKey, Verdict>(capacity: 10_000)
    private var epoch: UInt64 = 0                       // O(1) invalidation

    /// - Throws: `.duplicateID` if `rule.id` already exists.
    /// - Complexity: O(path depth).
    /// - Invalidates all cached verdicts.
    func add(_ rule: Rule) throws {
        guard byID[rule.id] == nil else { throw PolicyError.duplicateID(rule.id) }
        byID[rule.id] = rule
        if let p = rule.pathPrefix {
            var ids = pathIndex.match(p) ?? []
            ids.append(rule.id)
            pathIndex.insert(prefix: p, value: ids)
        } else {
            wildcards.append(rule.id)
        }
        bumpEpoch()
    }

    func remove(_ id: RuleID) throws {
        guard let r = byID.removeValue(forKey: id) else {
            throw PolicyError.notFound(id)
        }
        // … unindex …
        bumpEpoch()
    }

    /// - Complexity: O(1) on cache hit; O(depth + matching rules) on miss.
    /// - Thread-safe for concurrent reads. See note on the snapshot below.
    func evaluate(_ e: Event) -> Verdict {
        let key = EventKey(e, epoch: epoch)
        if let v = cache.get(key) { return v }

        let candidates = (pathIndex.match(e.path) ?? []) + wildcards
        let v = candidates
            .compactMap { byID[$0] }
            .filter { matches($0, e) }
            .max(by: { ($0.priority, $0.id) < ($1.priority, $1.id) })?   // tie-break on id
            .verdict ?? .allow                                           // DEFAULT: ALLOW

        cache.put(key, v)
        return v
    }

    private func bumpEpoch() {
        epoch &+= 1        // every cached key is now unreachable. O(1). No map walk.
    }
}

The five design points, each worth saying out loud

  1. Default allow. "No rule matched → allow. On an endpoint agent, default-deny means an unhealthy policy set bricks every Mac in the fleet. The default is a business decision, not a technical one — I'd make it configurable but ship allow." This connects the DS round to the product and it's the single best thing you can say in it.
  2. Deterministic tie-breaking. Two rules, same priority, both match. If the answer depends on map iteration order, your policy engine is non-deterministic and the same event gets different verdicts on two machines. Break ties on rule ID. Compliance requires that "why was this blocked?" has one answer.
  3. Epoch invalidation. Policy changed → bump an integer → every cached key is stale by construction. O(1). Walking the cache to invalidate is O(n) and you'd be doing it while holding a lock on the hot path.
  4. Index, don't scan. Trie narrows thousands of rules to a handful in O(depth). Then linear-scan the handful. Volunteering "I index by the most selective dimension, then linear-scan the survivors" is exactly how a real rule engine works.
  5. Immutable snapshot for concurrency. Don't lock the evaluate path. Build a new immutable rule set on write, swap the reference atomically. Readers never block, writers are rare. "Copy-on-write with an atomic swap" is the right answer for a policy engine and it's how you'd actually ship it.

Bounded queue & ring buffer

final class RingBuffer<T> {
    private var storage: [T?]
    private var head = 0, tail = 0
    private(set) var count = 0        // keep a count — do NOT play the
    private let capacity: Int          // "waste one slot" game under pressure
    private(set) var dropped = 0      // ← THE FIELD THAT MATTERS

    enum Policy { case rejectNew, overwriteOldest }
    private let policy: Policy

    init(capacity: Int, policy: Policy = .overwriteOldest) {
        precondition(capacity > 0)
        self.capacity = capacity; self.policy = policy
        storage = Array(repeating: nil, count: capacity)
    }

    @discardableResult
    func push(_ x: T) -> Bool {
        if count == capacity {
            switch policy {
            case .rejectNew:
                dropped += 1
                return false
            case .overwriteOldest:
                head = (head + 1) % capacity     // evict the oldest
                count -= 1
                dropped += 1
            }
        }
        storage[tail] = x
        tail = (tail + 1) % capacity
        count += 1
        return true
    }

    func pop() -> T? {
        guard count > 0 else { return nil }
        let x = storage[head]
        storage[head] = nil        // release the reference — otherwise you leak
        head = (head + 1) % capacity
        count -= 1
        return x
    }
}

The question inside the question "Overwrite oldest or reject new?" is not a coding decision, it's a product decision, and the right move is to ask rather than guess. Telemetry: overwrite oldest (recent data is more valuable). Audit log: reject new and alarm loudly (you may not lose records — that's a compliance obligation). Work queue: reject new and apply backpressure upstream. Asking this question is worth more than the implementation.

And the field they're looking for is dropped. A security product that silently discards events is lying to its customer about coverage. Every drop is counted and exported. If you add nothing else to this class, add the counter and say why.

Process tree

Domain-native, uses map + tree + stack, and it's exactly what an endpoint agent maintains. Very plausible ask.

final class ProcessTree {
    struct Proc {
        let pid: Int32
        let startTime: TimeInterval   // (pid, startTime) = the real identity.
        var ppid: Int32              // pid ALONE is reused. Always.
        let cdhash: String
        let argv: [String]
        var children: Set<Int32> = []
        var exited = false
    }

    private var procs: [Int32: Proc] = [:]

    func onFork(pid: Int32, ppid: Int32, at t: TimeInterval) { ... }
    func onExec(pid: Int32, cdhash: String, argv: [String]) { ... }

    func onExit(pid: Int32) {
        guard var p = procs[pid] else { return }
        p.exited = true
        // DON'T delete immediately: a late-arriving event may still
        // reference it, and you need the record to attribute it.
        // Tombstone + sweep. This is the bug in the naive version.
        procs[pid] = p
        tombstones.append((pid, clock.now))
    }

    /// Walk to root. ITERATIVE with an explicit stack — a fork bomb or a
    /// cycle from a corrupt event stream will blow a recursive version.
    func ancestors(of pid: Int32) -> [Proc] {
        var out: [Proc] = []
        var seen = Set<Int32>()          // cycle guard — events CAN be malformed
        var cur = pid
        while let p = procs[cur], !seen.contains(cur) {
            seen.insert(cur)
            out.append(p)
            if p.ppid == 0 || p.ppid == 1 { break }   // kernel_task / launchd
            cur = p.ppid
        }
        return out
    }

    /// Everything under this pid. DFS with an explicit stack.
    func subtree(of pid: Int32) -> [Proc] {
        var out: [Proc] = []
        var stack = [pid]
        var seen = Set<Int32>()
        while let cur = stack.popLast() {
            guard !seen.contains(cur), let p = procs[cur] else { continue }
            seen.insert(cur)
            out.append(p)
            stack.append(contentsOf: p.children)
        }
        return out
    }
}

The three things that make this a senior answer

  • pid is not identity. pids wrap and get reused within minutes on a busy Mac. The identity is (pid, start_time) — or, on the real thing, the audit token. Say this immediately; it's the domain knowledge the problem is fishing for.
  • Don't delete on exit. Events arrive after the process is gone, and you need the record to attribute them. Tombstone with a timestamp and sweep on a timer. Deleting on exit is the naive answer and it loses you the attribution for the last thing the process did — which, for an exfil event, is the only thing you cared about.
  • Iterative, with a cycle guard. They gave you "stacks" in the hint. Use an explicit stack, and guard against cycles — because your input is an event stream that can drop, reorder, or lie, and a recursive walk on a corrupt tree takes down the extension.

§23

Design bank — six problems, worked

1 · "Design a macOS agent that prevents sensitive data going to AI applications." ← most likely

Scope: managed fleet, monitor-first with enforcement built in, fail-open, offline-capable.

Channels → sensors (say this table out loud, it's the spine): web AI app → browser extension + NE filter · native app → NE filter for host, transparent proxy for content · CLI/IDE agent → ES exec + file reads + NE flow · local MCP → ES exec + config watch · removable/other → ES file events.

The core mechanism: classify async on NOTIFY_CLOSE(modified) → label cache keyed on (dev, inode, gen) → AUTH path is an O(1) lookup with a watchdog at half the deadline → fail open and count.

The join: NE's sourceAppAuditToken is the same identity ES gives you. That join produces lineage — "read the customer list 4s ago, now opening TLS to an unsanctioned model host" — and it's the thing a network-only or file-only vendor structurally cannot do.

Trace an event: paste of a Salesforce export into claude.ai in Chrome → browser ext sees paste into a known AI origin → agent classifies (PII, high confidence, 100+ records) → policy: unsanctioned-AI + restricted → block + coach → audit event with policy version and redacted snippet → backend correlates to the earlier ES read of the export in ~/Downloads = lineage.

Name your own blind spot: "If they use the Claude desktop app instead of Chrome, my browser extension is blind and I'm down to the transparent proxy or the provider API. And if the app pins, the proxy doesn't work either. So my honest coverage claim for native apps is host-level, not content-level, unless we MITM — and I'd rather use the provider's compliance API for the sanctioned centre and accept the gap on the pinned tail."

Ops: rings, kill switch honoured at startup and on heartbeat, local circuit breaker, shadow mode before enforce, health telemetry as a first-class feature.

2 · "Design MCP server observability across a 10,000-Mac fleet."

Open with why it's hard — stdio pipes never touch a socket, DNS, or a proxy. No gateway on earth can see it. The endpoint isn't a place to observe this, it's the only place. That framing is the design.

Sources: (1) config inventory — watch claude_desktop_config.json, ~/.claude.json, .cursor/mcp.json, per-repo .mcp.json; diff over time = config drift. (2) runtime inventory — ES AUTH_EXEC, argv, parent/responsible = AI runtime. (3) capability — the scope in argv (a filesystem server rooted at ~ vs at one repo), secrets in env (count, never log values). (4) behaviour — what that subtree actually opened and connected to. (5) remote MCP over HTTP/SSE → NE filter.

The finding is the disagreement: a server that runs but isn't declared, or a declared scope that's narrower than the observed reads. Design the inventory as a reconciliation, not a list.

The boundary, stated before asked: you cannot read the stdio pipe. Task ports are blocked by SIP + hardened runtime; injection breaks the runtime and is unsupportable. So it's inventory + capability + behaviour, not content interception.

Backend: per-device inventory upserts, dedup by (device, server identity), risk scoring, drift timeline. Scale is trivial here — 10k devices × a handful of servers is a small table. The hard part is entirely on the endpoint.

3 · "Design USB exfiltration prevention."

Three enforcement points, blunt → surgical: block the mount (ES AUTH_MOUNT / DiskArbitration approval — kills legit read use, generates tickets forever) · force read-only (remount MNT_RDONLY) · per-write policy on st_dev — allow the mount, capture the volume's device number, then on AUTH_CREATE/OPEN/RENAME/COPYFILE/CLONE compare the target's st_dev against the removable set and match the source's sensitivity label. Deny only sensitive→removable.

Why st_dev not the path: /Volumes/Untitled is an attacker-controlled string; symlinks and firmlinks exist; prefix-matching /Volumes is a bypass. A device number is a kernel fact.

Device identity: IOKit, walk from the BSD name to the USB node for vendor/product/serial. Allowlist on serial — but say plainly that a serial is forgeable with programmable hardware, so it's a convenience control, not a security boundary.

The cases that catch people: SD cards, Thunderbolt enclosures, network shares, mounted DMGs (nested filesystem, different st_dev), iCloud/Dropbox sync folders. APFS clonefile copies with zero reads. Finder is the actor on a drag-copy, not the user's app — so attribution by process alone lies.

4 · "Design policy distribution to 10,000 endpoints."

Shape: backend publishes an immutable, signed, versioned bundle. Agent polls (or long-polls) with its current version, gets a delta or a full bundle, verifies the signature against a pinned key, writes atomically (temp + rename), loads into an immutable snapshot, swaps the reference atomically. Readers never block.

Why signed: the policy is a root-privileged control input. If someone can forge a policy they can turn your agent into a rootkit that reads any file. Signature verification isn't a nice-to-have.

Why versioned: every audit event records the policy version that produced it. "Why was this blocked six months ago?" must have an answer. This is the difference between a tool and a compliance product.

Offline: the cached bundle keeps working. A laptop on a plane still enforces. Add a staleness bound — after N days, warn; you'd probably still enforce rather than fail open, because a stale policy is better than none. Say the trade.

Rollout: rings (canary → 1% → 10% → fleet), server-side kill switch, and a bundle that's rejected by the agent (bad signature, unparseable, version too new) must leave the previous one running rather than leave the agent with no policy.

Cache invalidation: bump the epoch on load — O(1), no map walk. And es_clear_cache is global and rate-limited by the kernel, so a policy that updates every 30 seconds is a design mistake.

5 · "Design the telemetry pipeline from agent to backend."

On device: bounded ring buffer → batch → compress → local SQLite (WAL) with a hard disk cap → upload with backoff. The agent must never fill a user's disk. Drop policy is explicit and counted; a silent drop is a lie about coverage.

Ordering & dedup: monotonic sequence per device; backend dedups on (device, seq). At-least-once delivery + idempotent writes is the right trade — exactly-once on a laptop that sleeps mid-upload is a fantasy.

Privacy: classify locally, ship labels and metadata, not content. Redact before upload. Snippets only with explicit policy, capped and masked. This is a GDPR/DPDP question as much as an engineering one, and Nightfall sells into EU orgs.

Backpressure: if the backend is down, the local store fills, and then what? Drop oldest telemetry, but never drop audit/incident records — those are a compliance obligation. Two queues with different policies. That distinction is the answer they're fishing for.

Scale: 10k devices × even 10 events/sec = 100k/sec — that's a real ingestion problem. Kafka-shaped ingest, but the interesting engineering is entirely on the device side, so don't spend your 60 minutes drawing the backend unless they push you there.

6 · "Design agent self-update."

The nightmare scenario is the design driver: you ship a bad build and 10,000 Macs are now running an ES client that crash-loops. Everything below exists to make that survivable.

Mechanism: download signed package → verify signature + notarisation ticket → replace the container app in /Applications → re-request system extension activation (CFBundleVersion must strictly increase) → OS handles the swap and tears down the old extension.

Why you can't just roll back: version must increase, so a "rollback" is really a forward release with a higher version. Which means your kill switch matters more than your rollback — the extension must be able to disable itself from a server flag at startup and on heartbeat, without a new binary. Draw that.

Local circuit breaker: N crashes in M minutes → boot to monitor-only, disable policy, phone home. The agent protects the machine from the agent.

Rings + bake time: internal → canary (100 devices, 24h) → 1% → 10% → fleet, with automatic halt on crash-rate regression. And someone runs the macOS beta from day one, because every WWDC is a potential fleet-wide break.
