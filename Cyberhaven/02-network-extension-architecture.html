01The provider zoo — picking the right one

NetworkExtension is six frameworks in a trenchcoat. Choosing the wrong provider type is the most consequential early decision in an endpoint network component, so know the trade-offs.

ProviderYou receiveTypical product
NEFilterDataProviderSocket flows + optional inbound/outbound byte stream, with app attributionDLP / EDR content filter. The Cyberhaven-shaped choice.
NEFilterPacketProviderRaw packets (macOS 11+)Firewalling by IP/port at line rate; no app-layer context.
NETransparentProxyProviderTCP/UDP flows redirected to you, which you re-originateZTNA / SASE agents. Enables local TLS termination.
NEAppProxyProviderFlows from managed apps onlyPer-app VPN on managed devices.
NEPacketTunnelProviderIP packets via a virtual interfaceFull-tunnel VPN. What most legacy ZTNA agents used.
NEDNSProxyProviderAll DNS queries on the systemDomain policy, C2 detection, DNS-tunnelling detection.
The decision rule: if you need to see application data, you need a content filter or a transparent proxy. If you only need to allow or deny by destination, a packet filter or DNS proxy is far cheaper. Filters observe; proxies re-originate — and only re-origination gives you plaintext.

02Content filter: the two-process split

The most commonly misunderstood part of NE. Apple splits the filter into two providers with deliberately asymmetric powers, and the split dictates your whole design.

┌─────────────────────────────────────────────────────────────────┐
│  NEFilterDataProvider          — in the SYSTEM EXTENSION        │
│  ‣ sees every flow, sees the bytes                              │
│  ‣ returns verdicts, synchronously, in the connection path      │
│  ‣ HARD SANDBOX: no network of its own, no arbitrary disk I/O,  │
│    tight memory ceiling, no user interaction                    │
│  ‣ must be fast and self-contained. Rules are DATA it is given. │
└───────────────────────────┬─────────────────────────────────────┘
                            │ NEFilterControlVerdict / IPC
┌───────────────────────────▼─────────────────────────────────────┐
│  NEFilterControlProvider       — in the CONTAINING APP process  │
│  ‣ allowed to be slow, allowed to do network calls              │
│  ‣ resolves unknown destinations, fetches policy, prompts user  │
│  ‣ pushes updated rules DOWN into the data provider             │
└─────────────────────────────────────────────────────────────────┘
  • The data provider is where correctness and latency live. The control provider is where anything expensive lives.
  • A data provider returning .needRules() escalates to the control provider, which does the slow lookup and then updates rules. Later flows to the same destination are decided locally.
  • Everything the data provider needs must be pushed to it in advance. Same architectural principle as the ESF AUTH fast path: no synchronous dependency on anything outside your address space.
Pattern recognition worth naming: ESF's AUTH path and NEFilterDataProvider's verdict path are the same architecture under two APIs — a latency-critical, sandboxed decision point that must be fed pre-compiled policy by a privileged component that is allowed to be slow. If you say that in a design round, you're describing the product rather than reciting APIs.

03Flow lifecycle and verdicts

class FilterDataProvider: NEFilterDataProvider {

  // 1. New connection. You must return a verdict — fast.
  override func handleNewFlow(_ flow: NEFilterFlow) -> NEFilterNewFlowVerdict {
      guard let socketFlow = flow as? NEFilterSocketFlow else { return .allow() }

      // App attribution — the join key back to the ESF world.
      let token   = socketFlow.sourceAppAuditToken
      let signing = socketFlow.sourceAppSigningIdentifier   // e.g. "com.google.Chrome"
      let remote  = socketFlow.remoteEndpoint

      switch policy.verdict(for: signing, remote) {
      case .allowSilently:  return .allow()          // stop seeing this flow entirely
      case .block:          return .drop()
      case .unknown:        return .needRules()      // escalate to control provider
      case .inspect:
          // Ask for outbound bytes. peekOutboundBytes is a BUDGET, not a wish —
          // every byte you peek is copied and costs latency.
          return .filterDataVerdict(withFilterInbound: false, peekInboundBytes: 0,
                                     filterOutbound: true,  peekOutboundBytes: 8192)
      }
  }

  // 2. Streamed outbound content, if you asked for it.
  override func handleOutboundData(from flow: NEFilterFlow,
                                    readBytesStartOffset offset: Int,
                                    readBytes: Data) -> NEFilterDataVerdict {
      inspector.feed(flow: flow, bytes: readBytes, at: offset)
      if inspector.matchedSensitiveContent(flow) { return .drop() }
      return .allowDataVerdict()      // or request more with another peek window
  }

  // 3. Stream finished.
  override func handleOutboundDataComplete(for flow: NEFilterFlow) -> NEFilterDataVerdict {
      return inspector.finalize(flow)
  }
}

Verdict semantics you must get right

VerdictMeaning
.allow()Permanent pass for this flow. You stop receiving callbacks — cheap, and the right answer for the overwhelming majority of flows.
.drop()Connection killed. The app sees a network error, not a policy message — hence the user agent's job to explain what happened.
.needRules()Defer to the control provider. Costs a round trip; use for cache misses, not as a default.
.filterDataVerdict(...)Stream inspection. The expensive path. Reserve it for flows that policy says matter.
.pause()macOS 11+. Hold the flow while you decide asynchronously, then resumeFlow(with:). Bounded — a flow paused too long stalls the app's connection and users perceive it as the network being broken.
Latency reality: your handleNewFlow verdict sits directly in TCP connection establishment. A 20 ms verdict on a page load with 80 subresource connections is a visibly slower browser. The target is microseconds via an in-memory match, with .allow() as the fast exit.

04Transparent proxy and TLS interception

This is the ZTNA/SASE architecture — Zscaler, Netskope, Check Point's agent, and the world you interviewed into at Zscaler.

class ProxyProvider: NETransparentProxyProvider {

  override func startProxy(options: [String:Any]?,
                            completionHandler: @escaping (Error?) -> Void) {
      let settings = NETransparentProxyNetworkSettings(tunnelRemoteAddress: "127.0.0.1")
      let rule = NENetworkRule(remoteNetwork: nil, remotePrefix: 0,
                               localNetwork: nil, localPrefix: 0,
                               protocol: .TCP, direction: .outbound)
      settings.includedNetworkRules = [rule]        // claim all outbound TCP
      setTunnelNetworkSettings(settings, completionHandler: completionHandler)
  }

  // Return true to CLAIM the flow; false to let it route normally.
  override func handleNewFlow(_ flow: NEAppProxyFlow) -> Bool {
      guard let tcp = flow as? NEAppProxyTCPFlow else { return false }
      let app = flow.metaData.sourceAppSigningIdentifier
      let tok = flow.metaData.sourceAppAuditToken       // ← join key again
      relay.handle(tcp, attributedTo: app, token: tok)
      return true
  }
}

Why a proxy, when a filter is simpler

A content filter observes the flow. A transparent proxy terminates it and opens its own connection onward. That difference is what makes TLS inspection possible:

app ──TLS──▶ [ your proxy: terminate with a locally-trusted CA cert ]
                        │  plaintext visible here
                        └──TLS──▶ real server (you validate the real chain)
  • Requires installing a root CA in the System keychain and marking it trusted — an MDM operation on managed fleets, and a hard blocker on unmanaged ones.
  • Certificate pinning defeats it. Many apps — and increasingly OS components — pin, so a bypass list is mandatory or you break Slack, Teams, Dropbox and software updates on day one.
  • Adds a full TLS handshake of latency and a real CPU cost per connection.
  • You become a cryptographic single point of failure holding a CA key trusted by every managed Mac. Attack surface, plus a governance conversation with the customer's security team.
A strong opinion to hold: "Full TLS interception is a heavy hammer with real breakage and a serious key-custody problem. For a data-lineage product I'd rather get plaintext where it's cheap — a browser extension inside the TLS boundary, and OS-level file and clipboard events — and use the network layer for attribution and destination policy rather than as the primary content inspection point." That is, essentially, Cyberhaven's actual architecture. Arriving at it independently is the strongest possible signal in a design round.

05Process attribution — the join key

This is the hinge of the entire two-document architecture. Everything else is plumbing around it.

FrameworkAttribution field
ESFes_process_t.audit_token

NEFilterSocketFlowsourceAppAuditToken

NEAppProxyFlowmetaData.sourceAppAuditToken

The whole trick: both frameworks hand you an audit_token_t. Decompose it to (pid, pidversion) and you have a stable key into the process cache that ESF built at exec time. That is how "Chrome opened a socket to drive.google.com" becomes "the Chrome instance that, four seconds ago, read Q3-forecast.xlsx from the Finance share."
ESF  NOTIFY_EXEC   ──▶  ProcessCache[(pid,pidver)] = { Chrome, TeamID, cdhash, … }
ESF  NOTIFY_OPEN   ──▶  edge:  Q3-forecast.xlsx ──read──▶ (pid,pidver)
NE   handleNewFlow ──▶  edge:  (pid,pidver) ──connect──▶ drive.google.com
                        └─ same key ⇒ the graph closes ⇒ lineage exists
Two traps. (1) PID reuse — key on (pid, pidversion), never pid alone, or you attribute one app's egress to another's identity. (2) Helper processes — a browser network process is not the browser. Resolve through responsible_audit_token before applying app-level policy, or every rule written against "Chrome" silently fails to match.

06The TLS problem, honestly

Be able to state this cleanly. Candidates who claim the network layer solves content inspection reveal they haven't built one.

What you get at the socketReality
Destination IP, port, SNI hostnameAvailable. SNI is plaintext today, but Encrypted Client Hello is eroding even that.
Byte volume, timing, directionAvailable. Enough for "Chrome uploaded 40 MB to an unmanaged Google account" — genuinely useful.
The actual file contentsNot available. It is ciphertext unless you terminate TLS.
Which web app, which actionNot available. Personal Gmail and corporate Gmail are the same TLS session to the same host.

The three ways products get past this, in ascending order of preference for a lineage product:

  • TLS interception via transparent proxy + local CA. Complete, invasive, breaks pinned apps, heavy key custody burden.
  • Browser extension — sits inside the TLS boundary in the renderer. Sees the actual upload, the target web app, the tenant, the pasted text, the AI prompt. Limited to browsers, but that is where the majority of modern data egress happens.
  • Endpoint-side inference — ESF told you which file the process read before the flow started, so you can attribute the upload to a file without ever reading the wire. Cheap, robust, and immune to encryption.
Why this matters for your specific interview: Cyberhaven runs a macOS endpoint team, a Linux endpoint team, and a browser-extension team. That organisational shape is the answer to this section. Being able to explain why the browser extension has to exist demonstrates you understand their product's architecture from the outside — which is exactly the kind of preparation a hiring manager notices.

07DNS proxy and packet tunnel — the supporting cast

NEDNSProxyProvider

  • Handles every DNS query on the system as NEAppProxyUDPFlow / TCP flows, with app attribution attached.
  • Cheap domain-level policy, and the natural place to detect DNS tunnelling and algorithmically generated C2 domains.
  • Degrading fast: DoH and DoT bypass the system resolver entirely, so a growing share of name resolution never reaches you. Know this limitation.

NEPacketTunnelProvider

  • Virtual interface, raw IP packets in and out. You implement the tunnel protocol yourself.
  • Maximum control, maximum cost — you are now responsible for MTU discovery, fragmentation, and per-packet throughput on the main data path.
  • Directly relevant to you: your Citrix work on runtime MTU discovery and UDP throughput tuning is the same class of problem. Worth mentioning if packet-level work comes up.
  • Modern ZTNA increasingly prefers transparent proxy over packet tunnel, because flow-level app attribution is free and packet-level attribution is not.

08Performance constraints specific to NE

ConstraintConsequence
Verdict latency is in the connection pathBudget microseconds. Every flow decision must be an in-memory lookup with no IPC.
Data provider memory ceilingYou cannot buffer a 2 GB upload to inspect it. Streaming inspection over a bounded window, or hand off the decision.
Data provider sandboxNo sockets, no arbitrary file writes, no user prompts. Anything else happens elsewhere.

The verdict cache

value  : { verdict, ttl, policyGeneration }

         are a slow memory leak with extra steps.

The five design invariants

  • Latency-critical components hold no dependencies. Both sysexts decide from resident memory. Policy arrives as pre-compiled data.
  • Exactly one component talks to the network. The daemon. One place to harden against untrusted backend input.
  • The audit token is the universal join key. Every subsystem records it; the correlator does nothing else.
  • Fail-open in the data path, fail-loud in telemetry. Never hang a user's save or connection; always report that you degraded.
  • The user agent exists because root has no session. Pasteboard, prompts and notifications are inherently per-GUI-session.

11The lineage graph, worked end to end

Follow one file through the system. This is the story to tell if asked "how would data lineage actually work?"

t0   ESF NOTIFY_EXEC        Excel starts.  cache[(431,7)] = Microsoft Excel, TeamID UBF8T346G9
t1   ESF NOTIFY_OPEN        (431,7) reads /Volumes/Finance/Q3-forecast.xlsx
                            ⇒ node: FILE:Q3-forecast.xlsx  { origin = corporate share }
                            ⇒ edge: FILE ──read──▶ PROC(431,7)
t2   ESF NOTIFY_CLOSE       (431,7) closes ~/Desktop/summary.xlsx  modified = true
     (modified)             ⇒ node: FILE:summary.xlsx
                            ⇒ edge: PROC(431,7) ──wrote──▶ FILE:summary.xlsx
                            ⇒ INHERITED CLASSIFICATION: derivative of a corporate-share file
t3   ESF NOTIFY_CLONE       Finder clones summary.xlsx → ~/Personal/summary.xlsx
                            ⇒ edge preserves lineage across an APFS clone
                              (an open/write-only sensor loses the file HERE)
t4   ESF NOTIFY_EXEC        Chrome starts.  cache[(902,3)] = Google Chrome
t5   ESF NOTIFY_OPEN        (902,3) reads ~/Personal/summary.xlsx
                            ⇒ edge: FILE ──read──▶ PROC(902,3)
t6   NE  handleNewFlow      sourceAppAuditToken → (902,3) → Chrome
                            remote = drive.google.com : 443
                            ⇒ edge: PROC(902,3) ──egress──▶ DEST:drive.google.com
t7   BROWSER EXTENSION      upload to account personal@gmail.com, not the corp tenant
                            ⇒ DEST resolves to UNSANCTIONED

VERDICT  A file whose origin is the Finance share reached an unsanctioned
         personal cloud account, via two derivations and one clone.
         No content inspection was required at any point.
Why this example is the right one to tell: it shows lineage beating classification. A content-matching DLP would have to recognise summary.xlsx as sensitive on its own merits, and it probably wouldn't — the numbers were retyped. Provenance carries the sensitivity through derivations that content matching cannot follow. That is Cyberhaven's actual thesis, arrived at from first principles.

Graph engineering notes

  • Nodes: files (by inode + volume UUID, not path — paths change), processes (by pid+pidversion), destinations, users, devices.
  • Edges: read, wrote, cloned, renamed, egressed, pasted — each timestamped and each carrying the responsible process.
  • Locally bounded: the endpoint holds a recent window with an eviction policy; the backend holds the durable cross-machine graph. The endpoint must be useful offline, which is why the local store exists at all.
  • Propagation is the hard part: deciding when a derivative inherits classification, and when the chain is too diluted to matter, is a product judgement, not an algorithm. Saying so is a mark of maturity.

12Coverage gaps and how products fill them

Neither framework covers these. Knowing the full egress surface is what makes someone a DLP engineer rather than an ESF engineer.

ChannelMechanism
ClipboardNo notification API. A per-session LaunchAgent polls NSPasteboard.general.changeCount. On newer macOS, reading the pasteboard triggers a user-visible privacy notice — a real product constraint, not a footnote.
Drag and dropAlso pasteboard-backed (drag pasteboard), plus the resulting file events at the destination.
ScreenshotsFile creation on Desktop, TCC screen-recording grants, NOTIFY_TCC_MODIFY. Genuinely hard to cover well; be honest about that.
AirDropsharingd process activity plus file events in its staging directories.
USB / removable mediaIOKit matching notifications + DiskArbitration for volume appearance, joined with ESF NOTIFY_MOUNT and file events under /Volumes/. AUTH_OPEN flag downgrade gives read-only enforcement without hard denials.
PrintingCUPS spool directory monitoring; the spooled job is a file, and files are ESF's home turf.
Cloud sync clientsFile events inside the sync folder plus the sync daemon's own flows. The daemon is the process to attribute, and the file that entered the folder is the lineage edge.
SSH / scp / rsyncESF exec with argv, plus NE flow attribution to the same process. Trivially covered, and often forgotten.
AI assistants and agentsBrowser extension for web chat UIs; NE flow attribution for native clients and API calls; ESF for local model file access. This is Cyberhaven's current strategic frontier and your JumpCloud team's charter.

13NE-specific failure modes

  • Data provider crash. Decide and document whether the system fails open (traffic flows, you're blind) or closed (machine loses network). Failing closed on a laptop fleet is a company-wide outage; almost everyone fails open and detects instead.
  • Slow verdicts. Users don't report "the DLP agent is slow" — they report "the internet is slow." You will be blamed for the network. Ship per-flow verdict latency telemetry from day one so you can prove it isn't you.
  • Pinned apps versus TLS interception. Slack, Teams, Dropbox, software updaters. A bypass list is mandatory and is permanent maintenance.
  • Filter coexistence. A second vendor's content filter can prevent yours from installing.
  • QUIC and HTTP/3. UDP-based, and easy to accidentally miss if your rules only claim TCP. Some products deliberately block QUIC to force TCP fallback into their inspection path — a defensible choice you should be able to argue.
  • Encrypted DNS. Apps using DoH bypass your DNS proxy entirely.
  • VPN interaction. A corporate VPN plus your transparent proxy plus a personal VPN is a real customer configuration and a real support nightmare.

14Whiteboard summary

If you have thirty seconds and a marker, this is the whole thing:

  • ESF = what happened on disk, and which process did it. Userspace C API, AUTH events block a syscall under a deadline, and every design decision follows from that.
  • NE = which process sent what, where. Content filter for observation and policy; transparent proxy when you must have plaintext.
  • The join = audit_token → (pid, pidversion) → a process cache built at exec time, resolved through the responsible process.
  • The shared pattern = both hot paths are sandboxed, latency-critical, dependency-free deciders, fed pre-compiled policy by a privileged daemon that is permitted to be slow.
  • The gap = TLS. Filled by a browser extension inside the crypto boundary, or by endpoint-side inference from file reads that preceded the flow.
  • The output = a provenance graph where sensitivity propagates through derivations, which is what content classification alone can never do.
