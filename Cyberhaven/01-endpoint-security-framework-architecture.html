01What ESF is, and what it replaced

Context matters here because Aristide lived through the transition — he joined Cyberhaven in 2016, when this was all kernel extensions.

The old world (pre-Catalina)

  • KAuth — kernel authorisation KPI. Scope-based callbacks on file operations. No process-exec authorisation, coarse, and kext-only.
  • MAC framework (TrustedBSD) — private, unsupported, but what most serious EDRs actually used via kexts because KAuth was insufficient.
  • OpenBSM audit — /dev/auditpipe, userspace-readable audit trail. Notification only, never blocking, and Apple has been deprecating it.
  • Network kexts — socket filters, IP filters, NKEs.

A kext ran in the kernel: a bug was a panic, and a vulnerability was ring-0. Apple deprecated kexts in 10.15 and on Apple Silicon they require reduced security mode and a reboot — commercially dead.

The new world

EndpointSecurity.framework (macOS 10.15+) is a userspace C API. Your client runs as a normal (root, entitled) process; the kernel does the interception and delivers messages over a mach-based transport. A crash in your logic terminates your process, not the machine.

The trade: you are now on the far side of a context switch from the syscall you are gating, and the kernel enforces a deadline on your answer. Every hard problem in ESF engineering descends from that one fact.

Interview line: "ESF moved the interception boundary out of the kernel, which fixed the stability and security story and created a latency story. The entire sensor design is a response to being a userspace process sitting synchronously in a syscall path."

02The API contract

Small surface, brutal semantics. Roughly a dozen functions matter.

Client lifecycle

// Create. Must be root + entitled + TCC-approved for Full Disk Access.
es_client_t *client = NULL;
es_new_client_result_t res = es_new_client(&client, ^(es_client_t *c, const es_message_t *msg) {
    handle_message(c, msg);          // runs on an ES-owned queue — DO NOT BLOCK
});

// Failure modes you must handle distinctly — they mean different things:
//   ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED   → missing endpoint-security.client entitlement
//   ES_NEW_CLIENT_RESULT_ERR_NOT_PERMITTED  → TCC / Full Disk Access not granted  ← most common in the field
//   ES_NEW_CLIENT_RESULT_ERR_NOT_PRIVILEGED → not running as root
//   ES_NEW_CLIENT_RESULT_ERR_TOO_MANY_CLIENTS → system-wide ES client limit hit

es_event_type_t events[] = { ES_EVENT_TYPE_NOTIFY_EXEC,
                             ES_EVENT_TYPE_NOTIFY_CLOSE,
                             ES_EVENT_TYPE_AUTH_OPEN };
es_subscribe(client, events, sizeof(events)/sizeof(*events));

// teardown
es_unsubscribe_all(client);
es_delete_client(client);
Field detail worth knowing: ERR_TOO_MANY_CLIENTS is real. macOS caps concurrent ES clients (historically single-digit). On a machine already running CrowdStrike, Jamf Protect and a corporate DLP agent, your client can simply fail to start. Any production sensor needs a clear diagnostic for this, not a generic "failed to initialise".

The message struct and versioning

struct es_message_t {
    uint32_t              version;        // ← check before touching newer fields
    struct timespec       time;
    uint64_t              mach_time;
    uint64_t              deadline;       // mach_absolute_time deadline for AUTH
    es_process_t         *process;        // the actor
    uint64_t              seq_num;        // per-event-type sequence → detect drops
    es_action_type_t      action_type;    // AUTH | NOTIFY
    es_action_t           action;         // the response handle for AUTH
    es_event_type_t       event_type;
    es_events_t           event;          // union — read per event_type
    uint64_t              global_seq_num; // across all events → detect drops
    ...
};
  • version is not optional. The struct has grown every macOS release. responsible_audit_token arrived at v4, thread info at v5, and so on. Reading a field your runtime OS doesn't populate is undefined behaviour. Production code has a version gate on every non-v1 field.
  • seq_num / global_seq_num are your drop detector. Gaps mean the kernel dropped events for you — telemetry that must be reported, because a silent blind spot in an EDR is a security incident, not a perf issue.
  • es_string_token_t is not a C string. It carries { length, data } and is not guaranteed NUL-terminated. Copy by length. This is a classic source of over-read bugs in sensors — and exactly the kind of thing an ex-pen-tester interviewer enjoys.
  • Message lifetime. The message is valid only inside the handler block. To process asynchronously you must es_retain_message() (10.15 had es_copy_message(), deprecated) and later es_release_message(). Leaking retains is how sensors OOM under load.

03AUTH vs NOTIFY — the deadline contract

If you retain one thing from this document, retain this section. It is the axis every ESF design question rotates around.

PropertyAUTHNOTIFY
Originating threadBlocked in kernel until you answerContinues immediately
You must respondYes, before deadlineNo
Can you deny the operationYesNo
Miss the deadlineKernel kills your clientN/A
Can you drop under loadNeverYes, with a counter
Cost modelAdds directly to user-visible syscall latencyCost is yours alone

Responding

// Most AUTH events: binary verdict.
es_respond_auth_result(client, msg, ES_AUTH_RESULT_ALLOW, true /* cache */);

// AUTH_OPEN is special: you return the *permitted flags*, not a boolean.
// This is the single most useful primitive in DLP — allow read, strip write:
uint32_t allowed = msg->event.open.fflag & ~(FWRITE | O_APPEND);
es_respond_flags_result(client, msg, allowed, false);
Why es_respond_flags_result matters for DLP: it lets you downgrade an operation instead of blocking it. A user opening a classified document on a removable volume can be given read-only access rather than a hard denial. Hard denials generate helpdesk tickets; downgrades generate compliance. Naming this distinction signals you have thought about DLP as a product, not just as a hook.

Deadline management — the pattern every sensor implements

// The deadline is generous on paper (seconds) but you are competing with
// the user's perception. Budget in microseconds and enforce your own timer.

void handle_auth(es_client_t *c, const es_message_t *msg) {
    uint64_t budget = (msg->deadline - mach_absolute_time()) / 2;   // 50% safety margin

    es_retain_message(msg);
    __block atomic_bool answered = false;

    // Watchdog: if the decision path stalls for ANY reason, fail open.
    dispatch_after(budget, watchdog_q, ^{
        if (!atomic_exchange(&answered, true)) {
            es_respond_auth_result(c, msg, ES_AUTH_RESULT_ALLOW, false);
            metrics_inc("auth.watchdog_fallback");   // alarm on this in the fleet
            es_release_message(msg);
        }
    });

    dispatch_async(decision_q, ^{
        es_auth_result_t verdict = policy_evaluate(msg);
        if (!atomic_exchange(&answered, true)) {
            es_respond_auth_result(c, msg, verdict, cacheable(msg));
            es_release_message(msg);
        }
    });
}
The deadlock that kills real products: making a synchronous XPC call from inside an AUTH handler to your daemon — for a policy lookup, say. If the daemon is blocked on anything (a network call, a lock, its own file I/O which generates ES events you are handling), you blow the deadline, get killed, and the machine loses its sensor. Rule: no synchronous IPC, no disk I/O, no network, no unbounded locks in an AUTH path. Everything the fast path needs must already be in memory.
Say this in the interview: "The first architectural constraint I'd state is that the AUTH path is a real-time path. Everything it needs — policy, process metadata, verdict cache — has to be resident in memory and lock-light, because the alternative is a watchdog fail-open or a dead client."

04Event catalogue, grouped by product need

There are 100+ event types. What separates someone who has shipped from someone who has read the header is knowing which handful you actually subscribe to, and why.

Core process telemetry — every EDR subscribes to these

EventWhy
NOTIFY_EXECThe backbone. Gives you the new process, its argv/env, signing identity, and the parent chain. Every provenance graph starts here.
NOTIFY_FORKTrack pid creation between fork and exec — needed or you attribute a forked child's file writes to the wrong image.
NOTIFY_EXITEvict from the process cache (with a grace period — in-flight events for a dead pid still arrive).
AUTH_EXECOnly if you block execution (malware prevention, app allow-listing). Very cacheable, so cheaper than it sounds.

Tamper and injection — the EDR self-defence set

EventWhy
AUTH_GET_TASK
AUTH_GET_TASK_READ		Acquiring another process's task port is the macOS code-injection and memory-scraping primitive. Deny anyone taking a task port on your own agent. This is your anti-tamper cornerstone.
AUTH_SIGNALDeny SIGKILL/SIGSTOP aimed at your own components.
NOTIFY_REMOTE_THREAD_CREATEThread created in another process — near-unambiguous injection signal.
NOTIFY_PROC_CHECKproc_info calls — process enumeration and reconnaissance.
AUTH_UNLINK / AUTH_RENAMEGuard your own binaries, config and databases from deletion or replacement.

File and data movement — the DLP set

EventWhy
NOTIFY_CLOSEThe most important DLP event. Carries a modified flag. "File X was written and closed by process Y" is the single edge your lineage graph needs, and it fires once per file rather than once per write.
AUTH_OPENGate on read/write with flag downgrade. Extremely high volume — subscribe only with aggressive muting, or not at all.
NOTIFY_CREATENew file appears; where destination-side lineage nodes are born.
NOTIFY_RENAMECritical. A rename is how a file's identity changes without its content changing. Miss these and your lineage graph fragments.
NOTIFY_CLONE
NOTIFY_COPYFILE		APFS clonefile and copyfile — copies that never appear as read+write pairs. A lineage engine that only watches open/close silently misses every Finder copy.
NOTIFY_LINK / AUTH_LINKHard links create a second path to the same inode — an easy lineage evasion if unhandled.
AUTH_MOUNT / NOTIFY_MOUNTRemovable media. Combine with a /Volumes/ path prefix rule to gate exfiltration to USB.
NOTIFY_SETEXTATTR
NOTIFY_DELETEEXTATTR		Extended attributes carry com.apple.quarantine and, in many DLP products, the classification label itself. Watch for someone stripping the label.
The design point behind that table: a naive DLP watches OPEN and WRITE. A correct one watches CLOSE(modified), RENAME, CLONE, COPYFILE, LINK and EXCHANGEDATA, because those are the ways a byte-range moves between paths on APFS without a read/write pair. Saying that out loud demonstrates you've thought about evasion, which is the whole job.

Newer high-value events (macOS 13+)

EventWhy
NOTIFY_BTM_LAUNCH_ITEM_ADDBackground Task Management — a launch agent/daemon/login item was registered. Persistence detection, essentially free.
NOTIFY_LOGIN_LOGIN / LOGOUT
NOTIFY_LW_SESSION_LOCK / UNLOCK		Session context. A DLP policy usually differs for an unattended machine.
NOTIFY_SUDO / NOTIFY_SUPrivilege escalation attempts, including failures.
NOTIFY_XP_MALWARE_DETECTEDXProtect verdicts surfaced to you — free signal from Apple's own scanner.
NOTIFY_TCC_MODIFY (14+)Privacy grants changing — screen recording or accessibility being granted to something is a strong exfil precursor.

05Muting, caching, inversion — the three performance levers

You cannot optimise your way out of event volume in userspace. You have to not receive the events. These three APIs are where the real perf work lives.

1 · Muting — stop delivery at the kernel boundary

// Coarse (10.15+): mute an entire path or process for ALL subscribed events.
es_mute_path(client, "/System/Library", ES_MUTE_PATH_TYPE_PREFIX);
es_mute_process(client, &my_own_audit_token);        // ← ALWAYS. See below.

// Fine-grained (macOS 12+): mute specific events for a path. Much better.
es_event_type_t noisy[] = { ES_EVENT_TYPE_NOTIFY_OPEN, ES_EVENT_TYPE_NOTIFY_CLOSE };
es_mute_path_events(client, "/private/var/folders", ES_MUTE_PATH_TYPE_PREFIX,
                    noisy, 2);
Mute yourself, first line of code. Your sensor writes logs, spool files and a local database. Those writes generate file events, which you handle, which produces log writes. Unmuted, this is an unbounded feedback loop that saturates a core within seconds. Every engineer who has actually built one of these has hit it — which is exactly why mentioning it is credible.

2 · Result caching — make the kernel answer for you

The cache parameter on es_respond_auth_result tells the kernel to remember the verdict for that executable and stop asking. For AUTH_EXEC this is transformative: the second launch of the same binary costs you nothing.

  • Cache is keyed on the executable and invalidated when it is modified — safe by construction for exec.
  • es_clear_cache(client) when policy changes. Cheap, and forgetting it means stale verdicts survive a policy push, which is a compliance bug.
  • Do not cache verdicts that depend on runtime context (user, time, network posture) rather than the binary itself.

3 · Mute inversion — turn the mute list into an allow-list (macOS 13+)

es_invert_muting(client, ES_MUTE_INVERSION_TYPE_PROCESS);
// Now es_mute_process() means "ONLY deliver events from this process".
// For targeted DLP — watch Chrome, Slack, Mail, Finder and nothing else —
// this cuts event volume by orders of magnitude.
Strong architectural answer: "For a DLP sensor I'd default to inverted process muting over an allow-list of data-handling applications, and fall back to broad subscription only for the detection use cases that genuinely need whole-system visibility. Most of the event firehose on a developer's Mac is a compiler, and no lineage policy cares about object files."

Volume reality check

WorkloadRough ESF event rate
Idle desktoptens/sec
Normal office usehundreds to low thousands/sec
Xcode build, npm install, Spotlight reindextens of thousands/sec, sustained

Budget: a shipping agent targets low single-digit percent CPU steady-state and a hard memory ceiling (typically 100–250 MB). The build-machine case is what breaks naive sensors, and it is the first scenario a serious interviewer will raise.

06Process identity and the provenance cache

Attribution is the product. If you cannot say which application touched the data, you have telemetry, not security.

Never key on PID alone

// audit_token_t carries pid AND pidversion. PIDs are reused; pidversion is not.
pid_t    pid  = audit_token_to_pid(proc->audit_token);
uint32_t pidv = audit_token_to_pidversion(proc->audit_token);
ProcKey  key  = { pid, pidv };          // ← the only safe identity
Why this is a security bug, not a hygiene issue: a process exits, a PID is recycled, and your cache now attributes the new process's actions to the old one's identity and policy. An attacker who can win that race gets another application's DLP exemption. The same reasoning applies to XPC peer validation — validate by audit token, never by PID.

What es_process_t gives you

FieldUse
signing_id, team_idIdentity that survives the binary being moved or renamed. Policy should be written against these, not paths.
cdhashExact binary identity. Pin sensitive allow-list entries to it.
codesigning_flagsCheck CS_VALID, CS_HARD, CS_KILL, and notably CS_GET_TASK_ALLOW — a debuggable process is an injection target.
is_platform_binaryShipped by Apple. Useful, but not a trust decision on its own — living-off-the-land attacks use curl, osascript and zip, all platform binaries.
is_es_clientAnother security agent. Don't fight it; don't block it.
ppid, original_ppidParent chain. ppid reparents to launchd on parent exit; original_ppid preserves the truth.
responsible_audit_tokenThe attribution field that matters. See below.

Responsible process — the field most people miss

When Chrome spawns a renderer, or an app's XPC service is started by launchd on its behalf, the immediate parent is often launchd. The responsible process is the one macOS holds accountable — the app itself. TCC uses it for privacy prompts, and you should use it for attribution.

Concrete DLP consequence: without responsible-process resolution, an upload performed by a browser helper process attributes to a nameless helper rather than to Chrome, and your policy — written against Chrome — never fires. This is exactly the kind of specific, been-there detail that separates candidates.

The cache itself

ProcessCache:
  key    : (pid, pidversion)
  value  : { signing_id, team_id, cdhash, path, argv_digest,
             ppid_key, responsible_key, start_time, first_seen,
             policy_tags }          // pre-resolved policy match, so the
                                    // AUTH fast path does zero string work

  populate : on NOTIFY_EXEC / NOTIFY_FORK
  evict    : on NOTIFY_EXIT + grace period (in-flight events outlive the process)
  bootstrap: enumerate existing processes at startup via libproc —
             your sensor starts after the machine does

Pre-resolving policy_tags at exec time is the key move: the AUTH hot path then does a hash lookup and a bitmask test, with no path comparison, no code-signing call, and no allocation.

Why the layer boundaries fall where they do

  • L1/L2 are inside the extension because the deadline forbids a hop. Any decision requiring IPC has already lost.
  • Policy is compiled in the daemon, evaluated in the extension. The extension never parses policy JSON; it receives a pre-built matcher structure. Parsing untrusted backend data in the component that sits in the syscall path would be both a perf and a security mistake.
  • Network lives only in the daemon. Sysexts are sandboxed and the ES extension has no business holding sockets. This also means one component to harden for untrusted backend input.
  • The user agent exists because the extension has no session. The pasteboard is per-GUI-session, and so are notifications and prompts. Root daemons cannot see either.

08Threading and backpressure

Queue topology

QueueConcurrencyRule
ES handler queue (ES-owned)serialNever block. Enqueue or respond, then return.
AUTH decision queueconcurrent, QoS userInteractivePure in-memory work. No locks held across any call you don't own.
Watchdog queueserial, high priorityTimers only. Must never be starved.
NOTIFY worker poolconcurrent, QoS utilityNormalisation, correlation, graph updates.
Transport queueserial, QoS backgroundSpool and upload. Deliberately lowest priority.

Backpressure policy — the honest answer

NOTIFY queue depth
  < 60%   normal
  60–85%  shed low-value event classes first (metadata changes,
          reads of non-sensitive paths); keep exec + file-write
  85–98%  aggregate: collapse N writes to one path into a single
          "modified" record with a count
  > 98%   drop, increment counter, emit a gap record to the backend

AUTH  →  NEVER queue-drop. If saturated: watchdog fires, fail open,
         and emit a HIGH-SEVERITY telemetry event, because a fleet-wide
         spike in watchdog fallbacks is a silent policy outage.
The framing that lands: "Dropping is a product decision, not an engineering failure — so it has to be explicit, ordered by information value, and reported. A sensor that silently loses events gives the SOC false confidence, which is worse than a sensor that reports it went partially blind for four seconds."

  • System extensions must live inside an app bundle in /Applications and are activated by the containing app via OSSystemExtensionRequest. They cannot be installed standalone by a package script.
  • All XPC endpoints validate their peer by audit token → SecCodeCopyGuestWithAttributes with kSecGuestAttributeAudit → SecCodeCheckValidity against a requirement string pinning Team ID and signing ID. Without this, any local process talks to your privileged daemon.
  • Hardened runtime, notarization, and no get-task-allow in release builds — otherwise you ship a debuggable root daemon.

11Tamper resistance

An EDR/DLP sensor is an adversarial target by definition. Aristide is a CTF finalist; this is the section he will enjoy.

AttackDefence
Kill the extensionAUTH_SIGNAL — deny signals targeting your own components. System extensions also cannot be unloaded without approval; MDM can forbid removal entirely.
Inject into the agentAUTH_GET_TASK / AUTH_GET_TASK_READ — deny task-port acquisition on yourself. Ship with hardened runtime and without get-task-allow.
Delete or replace binaries and policyAUTH_UNLINK, AUTH_RENAME, AUTH_TRUNCATE guarded on your own install paths; sign and verify policy blobs.
Talk to the daemon directlyXPC peer validation by audit token + code requirement. Never by PID.
Starve the sensor to force fail-openWatchdog fallbacks are telemetry, not just a local recovery. A machine emitting a burst of them is itself a detection.
Race the DLP check on a filePrefer AUTH at the operation boundary over "scan then allow"; TOCTOU is the classic DLP bypass.
Evade lineage via clone/hardlink/renameSubscribe to the full APFS movement set (§04), not just open/write.
The one sentence to volunteer: "If I were attacking this agent I'd start at the XPC boundary between the extension and the privileged daemon, because that's where an unprivileged local process can reach root-owned logic — which is why peer validation there is by audit token and code requirement rather than PID."

12Failure modes worth naming out loud

  • Deadline overrun → client killed. Sysextd restarts you, but in-flight state is gone and the machine was unprotected for the gap. Detect, report, and treat as a sev.
  • Synchronous XPC in an AUTH handler → deadlock → mass kill. The single most common architectural mistake.
  • Self-monitoring feedback loop. Unmuted agent writes saturate a core.
  • Retain leak on messages. Under a build storm, unreleased messages OOM the extension within minutes.
  • PID-keyed cache. Misattribution and a real privilege-confusion bug.
  • Version-blind field access. Works on your Mac, crashes on an older or newer OS in the fleet.
  • New macOS major release. Event semantics and struct versions shift; sysext approval and entitlements need revalidation. Testing against betas from the first developer seed is not optional at this layer.
  • ES client limit reached because the customer already runs two other security agents.
