01What this round actually is

A prediction, not inside knowledge — but the format constrains the possibilities tightly.

What 90 minutes with two panelists rules out

  • Not a puzzle round. Nobody books 90 minutes and two senior engineers to watch you reverse a linked list. The duration exists so the problem can grow.
  • Not a whiteboard-only round. That length implies real code that runs — expect a shared editor, possibly your own Xcode with screen share.
  • Not pure DSA. There will be a data structure in it, but wrapped in a plausible sensor scenario. Their daily problem is event streams under load, and interview problems drift toward what the team argues about at work.

The two shapes it will take

ShapeWhat it looks like
A · Build and extend
most likely		One problem, 3–4 escalating stages. "Implement X." → "Now make it thread-safe." → "Now bound it and handle overflow." → "Now how would you test it?" Each stage is the real question; the first is just setup.
B · Split roundTwo 40-minute halves, one per panelist. Typically one implementation problem and one debugging/code-review problem, or one algorithmic and one API-design.

In both shapes the extension stages carry the signal. Finishing stage one quickly and cleanly buys you time in the stages that actually differentiate a senior candidate.

The domain tell: every problem in §07–§13 is a real component of the architecture in your two previous documents — a bounded NOTIFY queue, a mute-path trie, a process cache keyed by (pid, pidversion), a write coalescer, a telemetry rate limiter, a C-struct parser. That is not a coincidence. Teams generate interview problems by shrinking their own codebase.

02How to run the 90 minutes

Process is graded as heavily as code at this level. Two panelists means one is often watching how you work rather than what you type.

MinutesDo this
0–5Clarify before typing. Single or multi producer? Bounded? What's the failure policy on overflow? Is this in the latency-critical path? Ask three sharp questions, then stop asking. Endless clarification reads as stalling.
5–10State the approach and the complexity out loud, then get agreement. "I'll do a fixed-capacity ring buffer with a lock, O(1) enqueue and dequeue, dropping oldest on overflow with a counter. Sound right?" This one sentence prevents 40 wasted minutes.
10–40Write the type signature and the public API first, then fill in bodies. Panelists can course-correct you from a signature. They cannot from a half-written function.
40–50Test it yourself before they ask. Even three assertions. Volunteering the empty case, the full case and the wraparound case is a senior signal that costs two minutes.
50–85The extensions. This is the round. Thread safety, bounding, metrics, cancellation, testability.
85–90Ask them something real about their sensor's actual implementation of what you just built.
The habit that most separates senior from mid: naming the trade-off before they find it. "I'm using a lock here rather than a lock-free ring because the contention profile is one writer and one reader, and a correct lock-free implementation is harder to review than it's worth — if profiling showed lock contention I'd revisit." That sentence is worth more than a flawless implementation delivered silently.
Your known failure mode applies here too. Under pressure you hedge. In a coding round hedging sounds like uncertainty about your own code. Commit to a design, say why, and change it if challenged — but commit first.

03Swift semantics they will probe

Ten years of Swift means you know most of this. Skim for the ones you'd fumble if asked to justify out loud.

Value vs reference — the one they always ask

Pick struct whenPick class when
Data with no identity; you want copies; you want thread-safety by isolation; you want it in an array without a pointer chase.You need identity, shared mutable state, deinit, inheritance, or ObjC interop.

The sensor-flavoured answer: events are structs, caches are classes. An event is a value that gets handed between queues — copying it removes an entire class of data race. A cache has identity and lifetime, so it's a final class with a lock.

Copy-on-write, precisely

struct EventBatch {
    private var storage: ContiguousArray<Event>

    mutating func append(_ e: Event) {
        // Array already does CoW. If you implement CoW over a class buffer:
        if !isKnownUniquelyReferenced(&buffer) { buffer = buffer.copy() }
        ...
    }
}

isKnownUniquelyReferenced is the whole mechanism. Being able to name it is the difference between "structs are copied" and understanding why passing a large array is cheap until you mutate it.

ARC pitfalls that show up in sensor code

  • Escaping closure capturing self inside a class that owns the queue → retain cycle. [weak self] in every stored/escaping closure; [unowned self] only when the lifetime is genuinely guaranteed.
  • weak costs. Weak references go through side tables and are meaningfully slower than unowned. In hot paths this matters.
  • ARC traffic in tight loops. Retain/release on every element of a loop over class instances is real overhead. final classes, value types, and occasionally Unmanaged are the escapes.
  • lazy var is not thread-safe. Two threads can both run the initialiser. Global let and static let are thread-safe (swift_once). This exact contrast is a favourite senior question.

Dispatch and generics

ConstructDispatchNote
final class methodstaticMark classes final by default; it's free performance.
non-final class methodvtableDevirtualised by WMO when the compiler can prove no override.
protocol via generic <T: P>static after specialisationPreferred in hot paths.
any P (existential)witness table + possible heap boxFlexible, slower. Fine at module boundaries, bad in a per-event loop.
@objc / dynamicobjc_msgSendSlowest. Avoid entirely in the sensor path.

some P is an opaque type — one concrete type, resolved at compile time, no box. any P is an existential — heterogeneous, boxed. If you're asked "some vs any", that sentence is the answer.

Memory and layout

MemoryLayout<T>.stride    // bytes per element in an array (size + padding)
MemoryLayout<T>.alignment // required alignment
// Allocating a buffer? Always use stride, never size. Classic bug source.

04Concurrency: GCD vs structured concurrency

Have an opinion here. On a sensor team it is the most consequential API choice in the codebase, and a strong opinion with reasons is the single highest-signal thing you can bring.

The modern toolkit

// Actor: isolated mutable state, compiler-enforced.
actor LineageGraph {
    private var edges: [Edge] = []
    func add(_ e: Edge) { edges.append(e) }      // implicitly serialised
    func snapshot() -> [Edge] { edges }
}

// Structured concurrency with cancellation.
try await withThrowingTaskGroup(of: Result.self) { group in
    for chunk in chunks { group.addTask { try await process(chunk) } }
    for try await r in group { collect(r) }
}   // group cannot outlive this scope; cancellation propagates in

// AsyncStream — the correct bridge from a C callback into async Swift,
// and note the buffering policy: this IS backpressure, expressed declaratively.
let (stream, continuation) = AsyncStream<Event>.makeStream(
    bufferingPolicy: .bufferingNewest(4096))

continuation.onTermination = { _ in teardownESClient() }

// from the C callback thread:
switch continuation.yield(event) {
case .enqueued:        break
case .dropped:         metrics.droppedEvents += 1      // account for it!
case .terminated:      break
@unknown default:      break
}

Sendable and the concurrency checker

  • Sendable = safe to cross an isolation boundary. Value types of Sendable members conform automatically; classes only if final and immutable, or manually synchronised.
  • @unchecked Sendable = "I have synchronised this myself, trust me." Legitimate for a lock-protected final class. Be ready to justify every use — an interviewer will ask, and "I added it to silence the warning" is a failing answer.
  • Actor reentrancy is the trap. An actor method suspends at every await, and other calls can interleave during the suspension. Invariants must hold across suspension points, not just at method boundaries. Being able to state this unprompted is a strong senior marker.

The opinion to hold

Say something like this: "I'd use structured concurrency for everything above the ingest boundary — correlation, transport, policy refresh — because the cancellation and isolation guarantees are worth a lot in a long-lived daemon. But I would not put an actor in the ESF AUTH path. An actor hop is a suspension with unbounded queuing latency, and that path has a hard deadline enforced by the kernel. That layer stays synchronous with an unfair lock and preallocated storage. Right tool, right layer."

That answer demonstrates you know modern Swift and know when not to use it, which is exactly the judgement a systems team is screening for. Candidates who reach for actors everywhere and candidates who've never used them both lose here.

LayerToolWhy
ESF / NE callbackPlain function + lockHard deadline; no suspension allowed.
Ingest queueLock-protected ring, or AsyncStream with a bounded policyExplicit, measurable backpressure.
Correlation / graphActor or serial queueIsolated mutable state, latency-tolerant.
TransportTask + async/awaitRetry, backoff, cancellation on shutdown.

The os_unfair_lock trap — a genuinely great answer if it comes up. Storing var lock = os_unfair_lock() as a property and calling os_unfair_lock_lock(&lock) is undefined behaviour: Swift's exclusivity rules mean &lock may hand you a temporary copy, so different threads can lock different memory. It usually appears to work, which makes it worse. The lock must live at a stable address.
final class UnfairLock: @unchecked Sendable {
    private let _lock: UnsafeMutablePointer<os_unfair_lock>

    init() {
        _lock = .allocate(capacity: 1)        // stable address — the whole point
        _lock.initialize(to: os_unfair_lock())
    }
    deinit { _lock.deinitialize(count: 1); _lock.deallocate() }

    @inline(__always)
    func withLock<T>(_ body: () throws -> T) rethrows -> T {
        os_unfair_lock_lock(_lock)
        defer { os_unfair_lock_unlock(_lock) }
        return try body()
    }
}

Every solution below uses this type. Introducing it unprompted, with the one-line reason, is a strong opening move.

06C interop — their real world

EndpointSecurity is a C API. Every Swift engineer on that team writes bridging code weekly. This is the most under-prepared area in most candidates and the most likely place to stand out.

The es_string_token_t conversion — a real bug factory

// es_string_token_t = { size_t length; const char *data }
// It is NOT guaranteed NUL-terminated. String(cString:) can over-read.

extension es_string_token_t {
    var stringValue: String {
        guard let data, length > 0 else { return "" }
        return String(decoding: UnsafeRawBufferPointer(start: data, count: length),
                      as: UTF8.self)          // length-bounded, never over-reads
    }
}
Why this scores: it's a bounded-read fix to an unbounded-read bug in a security product's parser, written for a manager who used to do penetration testing. If you get any opening to show this, take it.

Making audit_token_t usable as a key

// audit_token_t imports into Swift as a tuple of 8 UInt32 — not Hashable.
struct ProcessKey: Hashable, Sendable {
    let pid: pid_t
    let pidversion: Int32

    init(_ token: audit_token_t) {
        var t = token
        pid        = audit_token_to_pid(t)
        pidversion = audit_token_to_pidversion(t)   // PID reuse guard
    }
}

Keying on pid alone is the misattribution bug from document 1. Bringing it up here connects your coding round to your architecture answer, which is exactly the coherence panels talk about afterwards.

Pointer lifetime rules to state correctly

  • withUnsafeBytes { } — the pointer is only valid inside the closure. Escaping it is undefined behaviour, even though it compiles. Interviewers love asking this.
  • Copy out of C memory into Swift value types at the boundary. Never hold a C pointer past the callback — with ESF specifically, the message is freed when the handler returns unless you es_retain_message.
  • withMemoryRebound(to:capacity:) for type punning; raw pointers plus loadUnaligned(fromByteOffset:as:) for wire formats, because load(as:) traps on misalignment.
  • C callbacks that take a context pointer: Unmanaged.passUnretained(self).toOpaque() going in, Unmanaged<T>.fromOpaque(ctx).takeUnretainedValue() coming back. Know who owns the lifetime.

07Problem 1 · Bounded event queue with backpressure

The single most likely problem on this list. It is literally their NOTIFY ingest path.

Prompt as they'd give it"Events arrive from a kernel callback faster than we can process them. Build a queue that never blocks the producer and never grows without bound."
struct QueueStats: Sendable {
    var enqueued: UInt64 = 0
    var dropped:  UInt64 = 0
    var highWaterMark: Int = 0
}

final class BoundedEventQueue<Element>: @unchecked Sendable {

    enum OverflowPolicy { case dropNewest, dropOldest }

    private var storage: ContiguousArray<Element?>
    private var head = 0            // read index
    private var tail = 0            // write index
    private var count = 0
    private var stats = QueueStats()

    private let capacity: Int
    private let policy: OverflowPolicy
    private let lock = UnfairLock()

    init(capacity: Int, policy: OverflowPolicy = .dropOldest) {
        precondition(capacity > 0)
        self.capacity = capacity
        self.policy = policy
        // Preallocate. No allocation on the hot path, ever.
        self.storage = ContiguousArray(repeating: nil, count: capacity)
    }

    /// Called from the kernel callback thread. Never blocks, never allocates.
    @discardableResult
    func enqueue(_ element: Element) -> Bool {
        lock.withLock {
            if count == capacity {
                switch policy {
                case .dropNewest:
                    stats.dropped &+= 1
                    return false
                case .dropOldest:
                    storage[head] = nil
                    head = (head &+ 1) % capacity
                    count &-= 1
                    stats.dropped &+= 1
                }
            }
            storage[tail] = element
            tail = (tail &+ 1) % capacity
            count &+= 1
            stats.enqueued &+= 1
            stats.highWaterMark = max(stats.highWaterMark, count)
            return true
        }
    }

    /// Drain in bulk — one lock acquisition per batch, not per element.
    func drain(max limit: Int) -> [Element] {
        lock.withLock {
            let n = min(limit, count)
            guard n > 0 else { return [] }
            var out = [Element]()
            out.reserveCapacity(n)
            for _ in 0..<n {
                out.append(storage[head]!)
                storage[head] = nil          // release the reference
                head = (head &+ 1) % capacity
            }
            count &-= n
            return out
        }
    }

    var statistics: QueueStats { lock.withLock { stats } }
}

The points to make while writing it

  • Preallocated ContiguousArray. No allocation in enqueue. Say this — it's the reason the structure exists.
  • storage[head] = nil on drain. Without it you hold references to drained elements until the slot is overwritten — a slow leak that only shows up under a quiet fleet, which is the worst kind.
  • Drop policy is a parameter, not a decision. For file events you want oldest-dropped; for alerts you want newest-dropped. Making it a policy shows product thinking.
  • Dropping is counted and exposed. Silent loss in a security sensor is a correctness bug, not a perf trade.
  • Bulk drain. One lock per batch. If you drain element-by-element you've built a contention machine.
  • &+ wrapping arithmetic on counters that will run for months.

Extensions they will ask for

AskAnswer
"Make the consumer wait when empty."Add a DispatchSemaphore signalled per enqueue — but flag that the consumer must then never be a Swift-concurrency thread. Or expose an AsyncStream instead.
"Multiple consumers?"Already safe — the lock covers it. Ordering across consumers is no longer guaranteed; say so.
"Can you make it lock-free?"Single-producer/single-consumer, yes: atomic head and tail with acquire/release ordering. Then push back — a reviewable lock beats an unreviewable lock-free ring unless profiling proved contention. That pushback is the answer they want.
"Prioritise some events?"Two rings, drain high-priority first with a starvation guard (e.g. every Nth batch takes from low). Naming starvation unprompted scores.

08Problem 2 · Path-rule trie

Their mute-path and policy matcher. Tests string handling, tree structure, and hot-path thinking in one problem.

Prompt"We have thousands of path rules — some exact, some prefix. Given a file path, find the matching rule fast."
struct Rule: Sendable { let id: Int; let eventMask: UInt64 }

final class PathRuleTrie {

    private final class Node {
        var children: [String: Node] = [:]
        var exactRule:  Rule?     // matches only this full path
        var prefixRule: Rule?     // matches this path and everything below it
    }

    private let root = Node()

    enum Kind { case exact, prefix }

    func insert(_ path: String, kind: Kind, rule: Rule) {
        var node = root
        for component in path.split(separator: "/", omittingEmptySubsequences: true) {
            let key = String(component)
            if let next = node.children[key] {
                node = next
            } else {
                let fresh = Node()
                node.children[key] = fresh
                node = fresh
            }
        }
        switch kind {
        case .exact:  node.exactRule = rule
        case .prefix: node.prefixRule = rule
        }
    }

    /// Longest-prefix-wins, with exact match taking precedence at the leaf.
    func match(_ path: String) -> Rule? {
        var node = root
        var best = root.prefixRule
        for component in path.split(separator: "/", omittingEmptySubsequences: true) {
            guard let next = node.children[String(component)] else { return best }
            node = next
            if let p = next.prefixRule { best = p }   // deeper prefix wins
        }
        return node.exactRule ?? best
    }
}

Complexity

Insert and match are both O(d) in path depth, independent of the number of rules — which is the entire point versus scanning a rule list. State that explicitly: "matching cost is independent of rule count, so policy can grow without touching the hot path."

The optimisation conversation (this is where seniority shows)

  • String(component) allocates on every lookup. Spot it yourself. Fixes: intern components into Int IDs at policy-compile time and key children by Int; or key by a precomputed hash of the UTF-8 bytes; or match over path.utf8 without materialising components at all.
  • Swift String is grapheme-aware and expensive. For byte-oriented filesystem paths, work over String.UTF8View or raw [UInt8].
  • Case sensitivity. APFS is case-insensitive by default but case-preserving, and HFS+ volumes vary. Ask which semantics they want — this is a genuine correctness question, not pedantry, and it's an evasion vector in a DLP product.
  • Normalisation. /a/./b, /a//b, /a/../a/b and symlinks all reach the same file. Rules must be matched against a canonicalised path or they're trivially bypassed. In ESF you use the resolved path from the event rather than canonicalising yourself.
  • Unicode normalisation. HFS+ uses decomposed UTF-8; two visually identical paths can differ byte-wise. A real evasion in a security product.
Raising the normalisation and case-sensitivity points unprompted is probably the highest-value thirty seconds available in this entire problem. It reframes you from "can implement a trie" to "thinks about how someone bypasses the rule."

09Problem 3 · LRU process cache with TTL

Classic structure, domain wrapper. If they open with a plain LRU, this is the version to write.

Prompt"Cache process metadata. O(1) lookup, bounded size, and entries expire."
struct ProcessInfo: Sendable {
    let signingID: String
    let teamID: String?
    let executablePath: String
    let isPlatformBinary: Bool
    let policyTags: UInt64        // pre-resolved, so the hot path does no string work
}

final class ProcessCache: @unchecked Sendable {

    private final class Node {
        let key: ProcessKey
        var value: ProcessInfo
        var expiresAt: UInt64
        weak var prev: Node?        // weak backward → no retain cycle
        var next: Node?             // strong forward → list stays alive
        init(key: ProcessKey, value: ProcessInfo, expiresAt: UInt64) {
            self.key = key; self.value = value; self.expiresAt = expiresAt
        }
    }

    private var map: [ProcessKey: Node] = [:]
    private var head: Node?          // most recently used
    private var tail: Node?          // least recently used → evict here
    private let capacity: Int
    private let ttlNanos: UInt64
    private let lock = UnfairLock()

    init(capacity: Int, ttlSeconds: Double) {
        self.capacity = capacity
        self.ttlNanos = UInt64(ttlSeconds * 1_000_000_000)
        map.reserveCapacity(capacity)
    }

    // MONOTONIC clock. Never Date() — wall clock jumps on NTP sync and sleep/wake.
    @inline(__always) private func now() -> UInt64 {
        clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW)
    }

    func get(_ key: ProcessKey) -> ProcessInfo? {
        lock.withLock {
            guard let node = map[key] else { return nil }
            if node.expiresAt <= now() { removeLocked(node); return nil }
            moveToFrontLocked(node)
            return node.value
        }
    }

    func put(_ key: ProcessKey, _ value: ProcessInfo) {
        lock.withLock {
            if let existing = map[key] {
                existing.value = value
                existing.expiresAt = now() &+ ttlNanos
                moveToFrontLocked(existing)
                return
            }
            let node = Node(key: key, value: value, expiresAt: now() &+ ttlNanos)
            map[key] = node
            insertAtFrontLocked(node)
            if map.count > capacity, let lru = tail { removeLocked(lru) }
        }
    }

    // MARK: - list ops, all called with the lock held

    private func insertAtFrontLocked(_ node: Node) {
        node.prev = nil
        node.next = head
        head?.prev = node
        head = node
        if tail == nil { tail = node }
    }

    private func unlinkLocked(_ node: Node) {
        let p = node.prev, n = node.next
        p?.next = n
        n?.prev = p
        if head === node { head = n }
        if tail === node { tail = p }
        node.prev = nil; node.next = nil
    }

    private func moveToFrontLocked(_ node: Node) {
        guard head !== node else { return }
        unlinkLocked(node)
        insertAtFrontLocked(node)
    }

    private func removeLocked(_ node: Node) {
        unlinkLocked(node)
        map.removeValue(forKey: node.key)
    }
}

What to say out loud

  • Why weak prev, strong next: two strong links between adjacent nodes is a retain cycle and the whole list leaks. Explaining this pre-empts the question they were about to ask.
  • Monotonic clock. Date() moves backwards on NTP correction and jumps across sleep/wake — on a laptop fleet that's not theoretical. CLOCK_MONOTONIC_RAW is the right call.
  • Lazy expiry on read, not a sweeper thread. Mention that a bounded periodic sweep is worth adding if dead entries pin memory.
  • Naming convention ...Locked for functions requiring the lock. Cheap, and it's how real concurrent codebases stay reviewable.
  • The eviction subtlety: in a real sensor you evict on NOTIFY_EXIT, but with a grace period, because in-flight events for a dead PID still arrive. Drop that in and you've connected the data structure to the domain.

10Problem 4 · Event coalescer

Underrated and very likely. Tests stateful design, timers, and the reentrancy instinct.

Prompt"A process writes the same file 10,000 times a second. Collapse that into one record per file per time window."
struct CoalescedWrite: Sendable {
    let path: String
    var count: Int
    let firstSeen: UInt64
    var lastSeen: UInt64
    var processes: Set<ProcessKey>
}

final class WriteCoalescer: @unchecked Sendable {

    private var pending: [String: CoalescedWrite] = [:]
    private var flushScheduled = false
    private let lock = UnfairLock()
    private let window: DispatchTimeInterval
    private let maxPending: Int
    private let timerQueue: DispatchQueue
    private let sink: ([CoalescedWrite]) -> Void

    init(windowMillis: Int, maxPending: Int = 4096,
         timerQueue: DispatchQueue, sink: @escaping ([CoalescedWrite]) -> Void) {
        self.window = .milliseconds(windowMillis)
        self.maxPending = maxPending
        self.timerQueue = timerQueue
        self.sink = sink
    }

    func record(path: String, process: ProcessKey, at t: UInt64) {
        var shouldSchedule = false
        var immediateFlush: [CoalescedWrite]? = nil

        lock.withLock {
            if var existing = pending[path] {
                existing.count &+= 1
                existing.lastSeen = t
                existing.processes.insert(process)
                pending[path] = existing
            } else {
                pending[path] = CoalescedWrite(path: path, count: 1,
                                               firstSeen: t, lastSeen: t,
                                               processes: [process])
            }

            // Bound the map: a fan-out across many distinct paths must not
            // grow unbounded just because the window hasn't elapsed.
            if pending.count >= maxPending {
                immediateFlush = Array(pending.values)
                pending.removeAll(keepingCapacity: true)
                flushScheduled = false
            } else if !flushScheduled {
                flushScheduled = true
                shouldSchedule = true
            }
        }

        // CRITICAL: call out only AFTER releasing the lock.
        if let batch = immediateFlush { sink(batch) }
        if shouldSchedule {
            timerQueue.asyncAfter(deadline: .now() + window) { [weak self] in
                self?.flush()
            }
        }
    }

    func flush() {
        let batch: [CoalescedWrite] = lock.withLock {
            flushScheduled = false
            guard !pending.isEmpty else { return [] }
            let out = Array(pending.values)
            pending.removeAll(keepingCapacity: true)   // keep the buckets
            return out
        }
        guard !batch.isEmpty else { return }
        sink(batch)                       // outside the lock
    }
}

The three things being tested

  • Never call a closure you don't own while holding a lock. The sink may enqueue, log, or re-enter your API. Holding the lock across it is how real deadlocks ship. Swap the state out under the lock, call out after. This is the point of this problem.
  • Bound the pending map. Time-based flushing alone is unbounded if the workload fans out across many distinct paths — a build touching 200,000 files. Size-based flush plus time-based flush.
  • removeAll(keepingCapacity: true) — avoid rehashing on every window. Small, and it's the kind of detail that reads as having done this before.
Likely follow-up: "What if the sink is slow?" Correct answer: the flush becomes backpressure on the timer queue, so either the sink must be non-blocking (hand to the bounded queue from Problem 1) or the coalescer needs its own drop policy. Connecting two components of the interview into one system is exactly the senior move.

11Problem 5 · Token-bucket rate limiter

Short, common, and easy to get subtly wrong. Good warm-up problem.

Prompt"Cap telemetry at N events/second with a burst allowance."
final class TokenBucket: @unchecked Sendable {
    private let capacity: Double        // burst size
    private let refillPerSecond: Double
    private var tokens: Double
    private var lastRefill: UInt64
    private let lock = UnfairLock()

    init(ratePerSecond: Double, burst: Double) {
        capacity = burst
        refillPerSecond = ratePerSecond
        tokens = burst
        lastRefill = clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW)
    }

    func allow(_ cost: Double = 1) -> Bool {
        lock.withLock {
            let now = clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW)
            let elapsed = Double(now &- lastRefill) / 1_000_000_000
            lastRefill = now
            tokens = min(capacity, tokens + elapsed * refillPerSecond)
            guard tokens >= cost else { return false }
            tokens -= cost
            return true
        }
    }
}
  • Lazy refill on access — no timer, no background thread. Say this; the timer-based version is the naive answer.
  • Monotonic clock again. Wall-clock time going backwards makes elapsed negative and the maths nonsense.
  • Clamp at capacity or an idle period grants an unbounded burst.
  • Follow-up: per-key limiting. A dictionary of buckets keyed by process or destination — which then needs bounding and eviction, i.e. Problem 3. Notice out loud when problems compose; panels like candidates who see the system.

12Problem 6 · Parse a C event safely

Lower probability as a standalone problem, high probability as a follow-up. Nearly free marks if it comes up, because most candidates have never done it.

Prompt"Here's a C struct from the kernel. Turn it into a Swift value type safely."
struct FileEvent: Sendable {
    let path: String
    let process: ProcessKey
    let wasModified: Bool
    let timestamp: UInt64
}

func parse(_ msg: UnsafePointer<es_message_t>) -> FileEvent? {
    let m = msg.pointee

    // 1. VERSION GATE — the struct grew across macOS releases.
    //    Reading a field the running OS doesn't populate is UB.
    guard m.version >= 4 else { return nil }
    guard m.event_type == ES_EVENT_TYPE_NOTIFY_CLOSE else { return nil }

    let close = m.event.close

    // 2. Length-bounded string decode. Never String(cString:) on a token.
    guard let file = close.target?.pointee else { return nil }
    let path = file.path.stringValue
    guard !path.isEmpty else { return nil }

    // 3. Prefer the responsible process for attribution, fall back to the actor.
    guard let proc = m.process?.pointee else { return nil }
    let token = m.version >= 4 ? proc.responsible_audit_token : proc.audit_token

    // 4. COPY everything out. The message dies when the handler returns
    //    unless retained — no Swift value here may point into C memory.
    return FileEvent(path: path,
                     process: ProcessKey(token),
                     wasModified: close.modified,
                     timestamp: m.mach_time)
}

Four numbered defensive steps, each with a one-line reason. If you can produce this shape under pressure you will look like someone who has shipped against this API, because the mistakes it avoids are the ones people only learn by making.

13Problem 7 · Find the race

A likely second-panelist segment: code review rather than authorship. Practise reading concurrent Swift for bugs.

Given code — find every bug"This has been crashing in production. What's wrong?"
final class MetricsCollector {
    private var counts: [String: Int] = [:]
    private var observers: [() -> Void] = []
    private let queue = DispatchQueue(label: "metrics", attributes: .concurrent)

    func increment(_ key: String) {
        queue.async { self.counts[key, default: 0] += 1 }
    }

    func snapshot() -> [String: Int] {
        queue.sync { self.counts }
    }

    func addObserver(_ o: @escaping () -> Void) {
        observers.append(o)
        o()
    }
}

The bugs, in the order you should call them

#BugFix
1Concurrent writes to a Dictionary. .concurrent + async mutation = multiple writers at once. Dictionary is not thread-safe; this corrupts the hash table and crashes non-deterministically. This is the headline bug.queue.async(flags: .barrier) for writes, or a serial queue, or a lock.
2Reads racing writes. sync on a concurrent queue runs alongside in-flight non-barrier writes.Fixed by the same barrier change.
3observers has no synchronisation at all. Mutated from any caller's thread.Same protection as counts.
4Unbounded async growth. Under an event storm, increment enqueues faster than the queue drains — memory grows without limit and the metrics path becomes the outage.Atomic counters, or a lock with an O(1) critical section. Metrics must never queue.
5self captured strongly in an escaping closure; the collector cannot deinit while work is pending.[weak self], or accept it deliberately and say so.
6addObserver invokes the callback synchronously while conceptually holding class state — a reentrancy hazard if the observer calls back in.Invoke outside any lock, and document the threading contract.
7String keys on a hot metrics path — hashing and possible allocation per increment.Enum or integer keys with a fixed-size array of counters.

Corrected version

final class MetricsCollector: @unchecked Sendable {
    enum Counter: Int, CaseIterable { case eventsIn, eventsDropped, authFallback }

    private var counts = [Int64](repeating: 0, count: Counter.allCases.count)
    private let lock = UnfairLock()

    @inline(__always)
    func increment(_ c: Counter, by n: Int64 = 1) {
        lock.withLock { counts[c.rawValue] &+= n }    // O(1), no alloc, no hashing
    }

    func snapshot() -> [Counter: Int64] {
        let copy = lock.withLock { counts }
        return Dictionary(uniqueKeysWithValues:
            Counter.allCases.map { ($0, copy[$0.rawValue]) })
    }
}
Close with this: "And I'd run the test suite under Thread Sanitizer in CI — most of these are exactly what TSan catches, and a concurrency bug that only appears on a customer's 16-core machine under load is not one you find by reading." That's the answer that ends the segment well.

14Performance in Swift — the hot-path rules

  • Preallocate. reserveCapacity, fixed-size ContiguousArray. Allocation in a per-event path is the first thing to remove.
  • final everything that isn't designed for subclassing. Static dispatch for free.
  • Generics over existentials in hot paths. any Protocol boxes and dispatches through a witness table.
  • Avoid String in per-event work. Grapheme-aware, heap-allocated, expensive to hash. Intern paths to integer IDs at policy-compile time; work over UTF8View when you must touch bytes.
  • Watch ARC traffic. Retain/release per element in a loop over class instances is measurable. Value types avoid it entirely.
  • @inline(__always) on tiny hot accessors; @inlinable only for cross-module inlining, and be aware it locks the implementation into your ABI.
  • autoreleasepool around tight loops that touch ObjC bridging — otherwise autoreleased objects accumulate until the runloop turn, which on a daemon may be never.
  • Measure, don't guess. Instruments Time Profiler, Allocations, and os_signpost intervals around the event path so you get p50/p99 rather than an average. Averages hide the tail, and the tail is what the deadline cares about.
The framing to use: "I'd instrument first with signposts and get percentile latency per stage, then optimise the stage that owns the p99. On a sensor the mean is nearly meaningless — the deadline is a tail-latency contract."

15Testing concurrent code

Almost certainly one of the extension questions. Have a real answer, not "I'd write unit tests."

  • Inject the clock. A Clock protocol with a real and a fake implementation makes TTL and rate-limiter behaviour deterministic. Tests that call sleep() are flaky by construction — say this explicitly.
  • Inject the scheduler. Same reasoning for the coalescer's timer: a manual scheduler you tick by hand.
  • Stress tests for invariants, not outcomes. N producers, M consumers, then assert conservation: enqueued == drained + dropped. You can't assert exact interleavings; you can assert nothing was lost or duplicated.
  • Thread Sanitizer in CI on the concurrency suite. Address Sanitizer on the C-interop suite.
  • Property-based testing over random operation sequences against a simple reference model — very effective for LRU and ring-buffer semantics.
  • Benchmark as a test. A CI gate on throughput and p99 latency, so a perf regression fails the build rather than the fleet.
protocol Clock: Sendable { func nowNanos() -> UInt64 }

struct MonotonicClock: Clock {
    func nowNanos() -> UInt64 { clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW) }
}

final class FakeClock: Clock, @unchecked Sendable {
    private var t: UInt64 = 0
    private let lock = UnfairLock()
    func nowNanos() -> UInt64 { lock.withLock { t } }
    func advance(seconds: Double) { lock.withLock { t &+= UInt64(seconds * 1e9) } }
}
Volunteering dependency injection for time before they ask is one of the clearest senior signals available in a coding round. It shows you write code you intend to test, rather than code you'll test afterwards.

16Rapid-fire question bank

One-line answers. Cover the mouth-feel of these so nothing catches you cold.

QuestionAnswer
struct vs class?Value semantics, no identity, thread-safe by copying vs identity, shared mutable state, deinit, inheritance.
How does CoW work?Shared buffer until mutation; isKnownUniquelyReferenced decides whether to copy.
weak vs unowned?weak is optional and zeroes on dealloc, costs a side-table lookup; unowned is non-optional, faster, crashes if accessed after dealloc.
Is lazy var thread-safe?No. Global and static let are (swift_once).
some vs any?Opaque single concrete type resolved at compile time vs boxed existential with dynamic dispatch.
What makes a type Sendable?Safe to cross isolation boundaries: value types of Sendable members, immutable final classes, or manually synchronised with @unchecked.
Actor reentrancy?Other calls can interleave at every await. Invariants must hold across suspension points.
Why not an actor in the ESF callback?Suspension with unbounded queuing latency against a hard kernel deadline.
escaping vs non-escaping?Escaping outlives the call, requires explicit capture of self, can create cycles.
size vs stride?Bytes used vs bytes per array element including padding. Allocate with stride.
Lifetime of withUnsafeBytes pointer?Valid only inside the closure. Escaping it is UB.
Deadlock with DispatchQueue.sync?Calling sync on the queue you're already on. Classic on serial queues.
Semaphore in async code?Don't. Blocking a cooperative-pool thread can deadlock the whole runtime.
Array vs ContiguousArray?Array may bridge to NSArray for ObjC-compatible elements; ContiguousArray never does.
How do you find a data race?Thread Sanitizer, plus invariant stress tests. Not by reading.
Optional memory cost?Often free via spare bit patterns (e.g. pointer nil), not always for arbitrary types.
throws vs Result vs Optional?throws for recoverable errors in synchronous flow, Result to store or pass a completion, Optional when absence needs no explanation.
defer ordering?Reverse order of declaration, runs on every exit path including throws.

17Your prep plan

Highest leverage, in order

  • 1 · Type out Problems 1, 3 and 4 from scratch in Xcode, twice. Not read — typed, compiling, with three tests each. Muscle memory on the ring buffer and the LRU is worth more than any amount of reading, and those two cover most of the plausible space.
  • 2 · Write the UnfairLock wrapper from memory until it's automatic. It's the opening move in four of the seven problems.
  • 3 · Rehearse the GCD-vs-actors opinion out loud. Thirty seconds, spoken, twice. It's the highest-signal thirty seconds in the round and it must not come out hedged.
  • 4 · Do the Problem 7 bug hunt cold — cover the answers, find all seven, time yourself.
  • 5 · One evening on C interop: the string-token decode, the audit-token key, pointer lifetime rules. Low probability, near-zero competition.
  • 6 · Skim §16 the morning of. Not the night before — the morning of, so it's warm.

What not to spend time on

  • LeetCode grinding. If a graph or DP problem appears it will be light, and your time is better spent where the round actually is.
  • SwiftUI, Combine, UIKit. Zero relevance to a sysext role.
  • Memorising ESF event-type names. They know you can read a header. They're testing whether you can build the thing behind it.
One last thing. Every problem here is a component from your architecture documents.
