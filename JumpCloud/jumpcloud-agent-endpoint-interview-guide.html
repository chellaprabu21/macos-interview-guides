1. What Is the JumpCloud Agent?

The JumpCloud Agent is a cross-platform Go service that runs as a system daemon on every managed endpoint (macOS, Windows, Linux). It is the bridge between the JumpCloud cloud directory and the local operating system.

Your 60-second interview answer: "The JumpCloud Agent is a privileged system service written in Go that runs on every managed device. On first install it enrolls using a one-time Connect Key, receives an mTLS client certificate, and registers a system record in the cloud. After that, its core runtime is a long-poll loop to the Agent Server — the server returns directives like update configuration, sync users, apply policies, or upgrade the agent. MQTT is used only as a wake signal to poll sooner. Locally, the agent manages OS users, applies policies, runs osquery for inventory, and exposes a gRPC API to tray apps and login window components. Security has two layers: mTLS proves which device is calling the cloud, and user authentication (proxied to jumpcloud-auth) proves which person is using the device."

What the Agent Is Responsible For

User & Identity on Device

Create local OS accounts for JumpCloud users, deactivate deleted users (never remove), sync passwords, manage UID/GID, configure SSH/MFA settings via AuthConf from the cloud.

Policy & Software Enforcement

Apply JumpCloud policy templates, install software from App Catalog or Private Repo, manage trusted apps. Anything not handled by native MDM (Apple/Microsoft) goes through the agent.

Visibility & Reporting

System Insights via osquery (inventory snapshots every 5 min – 2 hr), diagnostics on startup and every 2 hours, event monitoring (logins, file changes, session events), metrics to Datadog.

Remote Administration

Execute admin workflows (arbitrary command sequences), self-upgrade when server detects outdated version, Windows KB patch installation, Remote Assist coordination, FDE recovery key management.

User Experience Components

Local gRPC IPC with tray app (notifications, password change), login window plugin, Windows credential providers, JumpCloud Go SSO, Endpoint Security extension on macOS.

Device Trust & Login

Proxy end-user login credentials to cloud for MFA and Conditional Access Policy evaluation. Device authentication (mTLS) is separate from user authentication.

What the Agent Is NOT

  • It is not an MDM server — Apple MDM and Microsoft MDM are separate services. The agent complements MDM for user management and non-MDM policies.
  • It does not maintain a persistent WebSocket — it uses HTTP long-poll with optional MQTT wake.
  • It does not store user passwords locally — login validation is proxied to the cloud.
  • Tray/login apps do not talk to the cloud directly — they use local gRPC to the agent.

  • report — hostname, serial number, architecture, OS version, network interfaces, FDE status, TPM version

Server-Side Validation (what the cloud checks)

  1. Connect Key is valid and scoped to the correct org (via jumpcloud-auth gRPC or org-user lookup)
  2. Pending certificate exists in Redis for org + certuuid pair
  3. certuuid is globally unique — prevents cloned disk images from re-registering
  4. System record created with certificate, MDM linkage (if applicable), hardware metadata
  5. Agent receives systemKey stored permanently in jcagent.conf

Core Components Explained

Dispatcher (dispatch/dispatcher.go)

The heart of the agent. Runs an infinite loop that:

  1. Sends GET /poll/{directiveID} with mTLS and checksum headers
  2. Receives: heartbeat (nothing to do), directive (action required), or error
  3. Routes directive to registered listener function by name (e.g., update_config → agent.updateAgentConf)
  4. Waits PollDelaySeconds (heartbeat) or PollContinueSeconds (after directive), unless MQTT triggers immediate poll
  5. On error: Fibonacci backoff starting at 55s, 89s, capped at MaxRetryDelayTime
  6. Adds random jitter (up to 10s) to prevent thundering herd across thousands of agents

jchttp Client (http/client.go)

  • TLS 1.2 minimum — no insecure skip verify
  • Loads client cert from client.key + client.crt
  • Verifies server against custom ca.crt bundle (JumpCloud CA only)
  • SSRF-safe redirect policy — won't follow redirects to private/internal IPs
  • HTTP proxy support for corporate environments
  • Rate limiting and configurable retry with backoff
  • Custom headers on every request: x-system-id, agent version, checksums

SQLite — agent.db (db/file_database.go)

  • WAL (Write-Ahead Logging) mode for concurrent readers
  • SetMaxOpenConns(1) — single writer to avoid corruption
  • Stores: config key/values, event bookmarks (resume position), metrics send queue
  • Goose migrations for schema versioning
  • Known admin path — support engineers know where to look

User Management (um/)

Driven by AuthConf received from cloud. Contains:

  • Monitors watch OS for events (file changes, login/logout, session events on Windows Event ID 4624/4634)
  • MUX routes typed agent events to registered handlers by event type
  • Handlers perform one action each (update metrics, enforce policy, log for audit)
  • Bookmarks persisted in SQLite so monitors resume after agent restart

How the Backend Decides What to Send

The jumpcloud-devices agent-api Poll handler (services/systems_poll.go) does this on every poll:

  1. Look up system record in MongoDB by systemKey + validate certuuid from mTLS headers
  2. Compare agent checksums against server-side state
  3. Check flags: AgentConfUpdatePending, pending directives in agentDirQueue
  4. If flag set or checksum mismatch → build directive with full config JSON
  5. If nothing pending → return heartbeat (agent waits and polls again)
  6. Update lastContact timestamp → may produce Kafka device_active event

Poll Loop Internals (from dispatch/dispatcher.go)

The dispatcher runs a select loop with three triggers:

  1. Timer expiry — normal interval poll (PollDelaySeconds for heartbeat, PollContinueSeconds after directive)
  2. MQTT immediate poll channel — wake signal received, poll now
  3. Shutdown channel — graceful stop

After each poll, jitter (0–10s random) is added to the next interval to prevent all agents in an org from polling simultaneously (thundering herd prevention).

Critical interview point: MQTT carries no configuration data. It is purely a wake signal. The agent must still poll to receive the actual directive and config. This design avoids the complexity of guaranteed push delivery, offline message queues, and config versioning over MQTT. If MQTT is down, the agent still syncs on its normal poll interval — degraded latency, not degraded correctness.

Directive ID Tracking

Every directive has an associated directiveID. The agent sends the last processed ID on every poll:

  • On startup, agent uses 0 until server assigns a real ID
  • Queued directives (workflows) create a new MongoDB document in agentDirQueue → new ID generated
  • Ad-hoc directives (config update flags) reuse the last directive ID
  • Server uses directiveID to track what the agent has already processed

7. Security Model — Complete Deep Dive

JumpCloud uses a two-phase trust model: Connect Key for enrollment authorization, then mTLS client certificates for all ongoing communication. User authentication is a separate layer on top.

Phase 1: Enrollment Security (Connect Key)

The Connect Key is a short-lived secret that proves a device is authorized to join a specific organization. It is passed in the x-connect-key HTTP header during kickstart operations only.

Two Trust Layers: Device vs User

Layer 1 — Device authentication (agent ↔ cloud):

mTLS proves which physical device is making the API call. The load balancer verifies the client certificate; the server binds certuuid + systemKey to a MongoDB system record.

Layer 2 — User authentication (person ↔ cloud via agent):

When a user logs in at the login window or credential provider, the agent proxies POST /authenticate to the Agent Server. The server verifies the user is bound to that system, then calls jumpcloud-auth Device Trust to validate credentials and MFA/CAP policies. A JWT authentication token is returned; the agent grants the local OS session.

These are intentionally separate. A valid device cert does not grant access to any user account. A valid user password does not help without a registered device.

8. Step-by-Step Data Flows

Walk through these flows verbally in an interview to demonstrate end-to-end understanding.

Flow 1: Admin Changes a Setting → Agent Applies It

sequenceDiagram
  participant Admin as Admin Console
  participant Internal as devices internal-api
  participant Mongo as MongoDB
  participant Worker as devices worker
  participant MQTT as AWS IoT
  participant Agent as Agent

  Admin->>Internal: Enable feature flag for org
  Internal->>Mongo: Set AgentConfUpdatePending = true on all systems
  Internal->>Worker: Enqueue MQTT wakeup batch
  Worker->>MQTT: Publish to systems/{id}/state
  MQTT-->>Agent: Wake signal
  Agent->>Agent: Immediate poll triggered
  Agent->>Internal: GET /poll/{directiveID}
  Internal->>Mongo: Build agentConf JSON, clear pending flag
  Internal-->>Agent: Directive: update_config + JSON
  Agent->>Agent: Atomic write jcagent.conf
  Agent->>Agent: Reload config, restart affected subsystems

Latency: Without MQTT, agent discovers change on next poll (minutes). With MQTT wake, typically seconds.

Flow 2: User Added to System → Local Account Created

sequenceDiagram

  participant Dir as Directory API
  participant Devices as devices Sync
  participant Mongo as MongoDB
  participant Agent as Agent

  Admin->>Dir: Bind user to system
  Dir->>Devices: Dispatch sync event
  Devices->>Devices: Rebuild SystemToUser, AuthConf

Flow 3: Agent Self-Upgrade

  1. Agent sends current version on every poll request
  2. Server compares against release stream (real-time, dogfood, or delayed rollout)
  3. If outdated, server returns update_agent directive with install script
  4. Agent downloads new binary from S3
  5. Platform-specific install: macOS installer, Windows MSI, Linux deb/rpm
  6. Agent stops, installs, restarts with new version
  7. Windows MSI also downloads component bundles (tray, CEF) from CDN if versions mismatch

Flow 4: System Insights Upload

  1. Agent receives SI config with table names and collection intervals (5 min – 2 hr)
  2. osquery runs scheduled queries locally
  3. Results batched and uploaded via POST /systeminsights/snapshots/:table
  4. Data flows to SI backend for admin visibility, compliance, and (future) device trust
  5. Limitation: Polling-based SI is too slow for real-time device trust — BAN-3495 plans event-driven telemetry

9. Failure Modes & Recovery

Interviewers often ask "what happens when X fails?" — here are the real behaviors.

Failure ScenarioAgent BehaviorRecovery
Network unreachable Poll fails → Fibonacci backoff (55s, 89s, ...). Logs error once, suppresses repeats unless message changes. Auto-retries with increasing delay. Continues local operations (user mgmt already applied). Queues metrics in SQLite.
MQTT broker down Agent logs disconnect, reports X-MQTT-Connection-Status: disconnected on polls. Falls back to normal poll interval. Auto-reconnect with 1–4 min retry. Degraded latency only — config still syncs via poll.
Client cert expired Poll returns 401. Agent should receive renew_certs directive or attempt renewal via systemKey. Renewal via Kickstart POST /Renew. If systemKey valid, new cert issued with same certuuid.
System deleted in admin Server returns uninstall_agent directive on next authenticated poll. Agent removes itself from device. By design — decommissioned devices cannot continue.
Duplicate agent instance Second instance fails lockfile check and exits immediately. Only one agent per device by design.
Panic in goroutine StackDumpOnPanic catches panic, dumps stack trace to log, exits gracefully. OS service manager restarts agent (Windows Service, launchd, systemd).
Server write failure during config update Agent writes jcagent.conf atomically (write to temp, rename). If write fails, old config preserved. Server keeps AgentConfUpdatePending true — will retry on next poll.
Proxy misconfiguration jchttp respects system proxy settings. Connection fails with timeout. Same Fibonacci backoff. Agent logs proxy-related errors at debug level.
Real production incident (June 2026): A MongoDB write storm from systemsToUsers sync loop caused cascading agent poll failures. Lesson: sync operations need idempotency checks, write batching, and circuit breakers for hot tenants. JumpCloud uses org-level diversion FIFO queues to isolate overloaded tenants.

10. Interview Q&A — With Follow-Up Answers

Practice answering these out loud. Each answer includes a likely follow-up question and how to handle it — interviewers often dig deeper on security and scale.

Q1: Walk me through how the JumpCloud agent works.
The agent is a Go binary running as a system service on macOS, Windows, or Linux. On first install it enrolls using a Connect Key — generates an RSA key pair, gets a CSR signed by Kickstart, registers a system record, and receives an mTLS client certificate plus a systemKey. After enrollment, the core runtime is a poll loop: the agent sends GET /poll/{directiveID} with mTLS and config checksums. The server returns either a heartbeat (nothing to do) or a directive (update config, sync users, apply policies, upgrade, etc.). The agent applies changes locally and polls again. MQTT accelerates polling when backend state changes but never carries data. Locally, the agent manages OS users via AuthConf, applies policies, runs osquery for inventory, and exposes local gRPC to tray/login apps.
Likely follow-up: "Why poll instead of WebSocket?" → Poll works through corporate firewalls and HTTP proxies without maintaining stateful connections. MQTT was added later as wake-only optimization. Simpler failure modes with Fibonacci backoff. Agent already uses HTTP for everything else.
Q2: How is the agent secured?
Two-phase model. Enrollment: ephemeral Connect Key authorizes joining an org — validated by jumpcloud-auth, scoped to org and enrollment type. Runtime: every request uses mTLS with a client certificate signed by JumpCloud CA. The load balancer verifies the cert and injects X-SSL-CLIENT-CN (= certuuid). Server middleware binds certuuid + x-system-id to a MongoDB system record — dual lookup prevents cert replay. TLS 1.2 minimum, custom CA bundle, no skip verify. Private key at filesystem 0600, never rotated on cert renewal. User login is a separate layer: agent proxies credentials to jumpcloud-auth Device Trust over the already-authenticated mTLS channel.
Likely follow-up: "What if someone steals the private key?" → They could impersonate that specific device until cert is revoked. Mitigations: 0600 permissions, privileged service context, cert renewal allows server-side revocation, deleted systems get uninstall directive. User login still requires valid credentials + MFA separately.
Q3: How does the agent discover and apply configuration changes?
Checksum-based sync. Agent sends hashes of current policy, software, SI, and trusted app configs on every poll. Server compares against its state. When admin changes something, server sets a flag (e.g., AgentConfUpdatePending) on the system document and publishes MQTT wake. Agent polls, server detects flag or checksum mismatch, returns a directive with full config JSON or a fetch directive. Agent atomically writes config and reloads. Directory graph changes (user bound to system) trigger sync service → rebuild AuthConf → MQTT wake → update_auth_conf directive.
Likely follow-up: "What if the agent misses an MQTT wake?" → It still syncs on the next regular poll interval (minutes). MQTT is optimization, not correctness requirement. Server also keeps pending flags until agent confirms with matching checksum.
Q4: Explain the difference between device auth and user auth.
Device auth (mTLS) proves which physical machine is calling the API. Established at enrollment, validated on every request via client certificate CN + systemKey. User auth proves which person is using the device. When a user logs in, the login window sends credentials to the agent via local gRPC. Agent proxies POST /authenticate to the cloud over mTLS. Server checks user is bound to that system, then jumpcloud-auth validates password and evaluates MFA/CAP. Returns JWT. Agent grants local OS session. A stolen device cert doesn't grant user access. Valid user credentials without a registered device don't work either.
Q5: How would you design the agent communication protocol from scratch?
I'd use a similar pull-based model: devices behind NAT/firewalls need outbound-initiated communication. mTLS for device identity is industry standard (same as IoT). I'd separate enrollment (one-time bootstrap key) from runtime (long-lived cert). Use checksums to avoid sending full configs when unchanged. Add push-notification wake for latency without push-data complexity. Directive pattern decouples server intent from client implementation. I'd also separate privileged system service from per-user UI components via local IPC.
Likely follow-up: "What would you do differently?" → Consider gRPC for agent-server instead of REST (JumpCloud uses gRPC internally via devices-agent-api but HTTP at the edge for proxy compatibility). Event-driven telemetry instead of osquery polling for real-time device trust. Structured agent log streaming instead of local files only.
Q6: How does the agent handle scale — millions of devices polling?
Jitter (0–10s random) on poll intervals prevents thundering herd. Dedicated si-internal-api-devices cluster isolates poll traffic. Server uses checksums to return lightweight heartbeats when nothing changed. MQTT wake reduces unnecessary polling. MongoDB for hot agent state, with org-level diversion FIFO queues for overloaded tenants. Fibonacci backoff on agent side prevents retry storms during outages. Agent sends compact headers, not full state, on every poll.
Q7: What happens during agent enrollment step by step?
Admin provides Connect Key (or MDM/user portal issues one). Agent generates certuuid and RSA key pair. POST /GetRegistrationConf with Connect Key → receives jcagent.conf template. POST /SignCsr → Kickstart signs with JumpCloud CA, stores pending cert in Redis. GET /CheckAccess via mTLS to verify cert works. POST /registernewsystem with system report (hostname, serial, OS, network) → server validates Connect Key, fetches pending cert, creates MongoDB system record, returns systemKey. Connect Key never used again.
Q8: How does the agent manage local users?
Via AuthConf — a JSON document from the cloud listing users and SSH/MFA settings. When agent receives update_auth_conf directive, it fetches AuthConf and for each user: creates OS account if missing, sets password, configures UID/GID, home directory. If user removed from AuthConf, agent deactivates (never deletes) the local account. Also manages sshd_config (AllowPassword, AllowPublicKeys, AllowRootLogin, MFA for SSH). AuthConf is rebuilt by devices Sync service when Directory graph changes (user bound/unbound from system).
Q9: What is the role of SQLite on the agent?
agent.db stores durable local state: config key/values, event monitor bookmarks (resume position after restart), and metrics send queue. WAL mode with single writer (SetMaxOpenConns(1)). Known admin path for troubleshooting. Not used for the primary server-delivered config (that's jcagent.conf). SQLite chosen because admins already know the path, it supports migrations, and concurrent readers work with WAL.
Q10: How does the tray app interact with the agent?
Tray app is a separate per-user process (SwiftUI on macOS, .NET on Windows). It does NOT talk to the cloud. It connects to the agent via local gRPC (unix socket on macOS, named pipes on Windows). Agent polls cloud for UserInformation every 5 seconds, tray flow controllers check for scheduled notifications (password expiry, MDM enrollment, software updates). This privilege separation keeps the tray out of LocalSystem while still enabling user-facing flows.
Q11: How do you prevent golden image clones from enrolling twice?
certuuid is generated fresh on each enrollment and embedded as the X.509 CN. Kickstart verifies global uniqueness before signing CSR. Pending cert stored in Redis per org+certuuid. Registration requires matching pending cert. A cloned image with the same certuuid fails uniqueness check. A clone generating new certuuid still needs a new Connect Key. Both barriers must be passed.
Q12: What are the agent's known limitations?
System Insights polling (5 min – 2 hr) too slow for real-time device trust. Large agentConf JSON increases poll response size. Windows agent runs as LocalSystem (large privilege surface). Logs are local files, not auto-streamed to cloud. Single SQLite writer can bottleneck high-frequency events. Linux agent has fewer UI components than macOS/Windows. No persistent connection means worst-case config latency equals poll interval without MQTT.
Q13: Explain MQTT's role — why not just use MQTT for everything?
MQTT is wake-only (ADR-003). Backend publishes empty payload to systems/{systemId}/state. Agent receives it, sends signal on immediatePoll channel, polls HTTP immediately. Config still delivered via poll response. Why not MQTT for data: would need guaranteed delivery, offline queuing, config versioning, and larger payloads over a protocol designed for small messages. HTTP poll already works reliably. MQTT adds latency improvement without changing the correctness path. If MQTT is down, agent falls back to regular poll interval.
Q14: How does certificate renewal work without breaking local secrets?
Private key is never rotated. Renewal via POST /Renew on Kickstart with mTLS + systemKey. New certificate issued with same certuuid as CN. This preserves the chain of locally encrypted data (FileVault recovery keys encrypted with key derived from cert identity). Server can also send renew_certs directive proactively before expiry. If cert already expired, systemKey alone can authenticate the renewal request.
Q15: How would you debug an agent that's not syncing?
Check local logs: /var/log/jcagent.log (macOS/Linux) or \Windows\Temp\jcagent.log. Verify jcagent.conf has valid systemKey and server URLs. Check client.crt expiry. Test mTLS connectivity to agent.jumpcloud.com. Look for poll errors and backoff messages. Check X-MQTT-Connection-Status in logs. Verify agent.db exists and is writable. On server side: check system record in MongoDB, verify AgentConfUpdatePending flag, check lastContact timestamp. Compare agent checksums vs server state.
