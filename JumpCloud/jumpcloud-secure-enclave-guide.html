Secure Enclave & Hardware Security in JumpCloud

A complete, plain-language guide to what Secure Enclave and TPM are, where JumpCloud actually uses them, and where it does not.

1. What Is a Secure Enclave? (Layman's Terms)

Your Mac or phone has a main processor (CPU) that runs apps, and often a separate secure chip designed only for cryptography. That secure area is what people mean by Secure Enclave (Apple) or TPM (Windows/Linux).

Think of it like this

Your computer is an office building. Normal software runs in open cubicles — including malware with admin access, which can read files on disk. A Secure Enclave / TPM is like a vault inside the building with its own lock. You can ask the vault to sign documents (prove identity), but you cannot photocopy the vault key and take it home. The private key never leaves the chip.

🍎

Apple Secure Enclave

Isolated coprocessor on iPhone, iPad, and Mac (T2 chip or M-series). Used for Touch ID, Face ID, and hardware-backed keys. Keys marked kSecAttrTokenSecureEnclave cannot be exported.

🪟

Windows TPM

Trusted Platform Module chip. Windows uses it for BitLocker, Windows Hello, and "Platform Crypto Provider" (PCP) keys. JumpCloud Go stores DUK keys via pcpcrypto — non-exportable.

🐧

Linux TPM 2.0

Hardware chip on many enterprise laptops. JumpCloud Go creates ECDSA signing keys inside the TPM; private material never exists as a plain file.

3. Agent mTLS — Why It Does NOT Use Secure Enclave

The JumpCloud agent's main identity certificate (client.crt + client.key) used for poll, config sync, and all cloud API calls is software-generated and file-stored.

How the agent key is created (from code)

1

rsa.GenerateKey(rand.Reader, 2048)

In registration/certificate_utils.go, the agent generates a 2048-bit RSA key in software — not inside Secure Enclave or TPM.

2

Written to client.key with mode 0600

Only root/admin can read the file. Still a file on disk — not hardware-isolated.

3

Never rotated on certificate renewal

registration/seal_renew.go explicitly keeps the same private key forever so locally encrypted secrets (FileVault recovery keys) remain decryptable.

Why JumpCloud made this choice

  • Cross-platform consistency — same enrollment flow on macOS, Windows, Linux since early agent versions
  • FileVault / FDE continuity — recovery key encryption chain depends on stable key material
  • Simplicity — TPM/Secure Enclave APIs differ wildly per OS; agent predates JumpCloud Go's hardware model
  • Operational familiarity — admins know where client.key lives for troubleshooting
Security still applied: Private key never sent over network; mTLS challenge-response; dual lookup (certuuid + systemKey); 0600 permissions; privileged service context. Hardware backing would be a hardening improvement, not the current design.

4. JumpCloud Go — Where Hardware Security IS Used

JumpCloud Go is passwordless SSO to work apps (Slack, Google, etc.). It is separate from the agent's mTLS certificate. Go uses a per-user DUK (Device User Key) that is explicitly tied to TPM or Secure Enclave.

Two different badges

Agent mTLS cert = the building's device badge ("this laptop is a managed JumpCloud device").
JumpCloud Go DUK = your personal signing key for SSO ("this human on this device is requesting app access").

The device badge is a file on disk. Your personal signing key lives in the vault (Secure Enclave / TPM).

Hardware requirement: If keyStore.IsSupported() returns false (no TPM on Windows, no TPM on Linux, no Secure Enclave path on Mac), JumpCloud Go registration fails with "No TPM found. JumpCloud Go not supported." (~92% of typical fleet has hardware support per internal estimates.)

5. Implementation Per Platform (From Code)

Windows — TPM via Platform Crypto Provider (PCP)

Source: jumpcloud-durt-client/security/keystore_windows.go

  • Calls goncrypt.OpenProvider(MsPlatformKeyStorageProvider) to detect TPM
  • Creates DUK with pcpcrypto.GenerateECDSAKey(..., nonExportable=true) — key name jumpcloud-duk-{userUID}
  • Signing via pcpcrypto.FindKey() — TPM performs sign operation internally
  • Agent mTLS key still loaded from file: LoadKeyFromFile(config.DefaultConfig.ClientKey)
  • DURT stored in registry HKLM\SOFTWARE\JumpCloud\DeviceIdentity\DURT with DPAPI encryption

Linux — TPM 2.0

Source: jumpcloud-durt-client/security/keystore_linux.go

  • Opens TPM via transport.OpenTPM()
  • Creates ECDSA P-256 key inside TPM with FixedTPM: true (cannot be moved off chip)
  • TPM private/public blobs saved via agent gRPC SaveDUK / LoadDUK (encrypted blobs, not raw private key)
  • Signing via tpmSigner.Sign() — digest sent to TPM, signature returned
  • DURT stored in user's Linux keyring via user-agent

macOS — Secure Enclave

Source: docs/jc_go/ARCHITECTURE.md, jumpcloud-durt-macos repository

  • macOS JumpCloud Go client lives in separate repo: github.com/TheJumpCloud/jumpcloud-durt-macos (Swift)
  • DUK described as "key tied to hardware through TPM or Secure Enclave" in official architecture docs
  • On Mac with T2 or Apple Silicon, ECDSA keys can be created with kSecAttrTokenSecureEnclave — private key non-exportable
  • Safari SSO uses App SSO Extension (jcagent-tray-ssoe) instead of browser extension
  • Agent mTLS client.key remains file-based (same as other platforms)
The agent repo vendors Windows and Linux keystore code. macOS Secure Enclave logic is in jumpcloud-durt-macos — not in the main Go agent binary, but bundled at install time.

6. Device Trust — Certificates vs JumpCloud Go

JumpCloud has two paths to prove "this login is from a trusted device" for Conditional Access Policies:

Hardware chip? macOS Keychain is encrypted; not the same as Secure Enclave-backed DUK Yes — DUK in Secure Enclave / TPM

ADR-011: When user authenticates via JumpCloud Go, Auth adds a device assertion to the session from the DUST — no call to devices service needed. Desktop certificate flow still exists in parallel. User Portal prefers certificate assertion today; Go assertion preferred once more tested.

7. JumpCloud Protect & WebAuthn MFA

JumpCloud Protect (mobile push MFA)

Source: jumpcloud-auth/docs/PROTECT_ARCHITECTURE.md, ADR-008

  • Uses WebAuthn protocol adapted for mobile (ADR-008)
  • During enrollment, phone creates a credential with a private key on the device
  • On iPhone: private key typically in Secure Enclave (non-exportable)
  • Push approve/deny: request signed with device private key (Authorization Signature header, ADR-009)
  • Ephemeral ceremony state in Redis on server (10 min sessions)

Browser WebAuthn MFA (Touch ID / Windows Hello)

When a user registers a passkey or platform authenticator for MFA:

  • Browser asks OS to create key — on Mac often Secure Enclave, on Windows TPM via Windows Hello
  • Public key stored in jumpcloud-auth Postgres (ADR-004 hybrid: credentials in Auth DB, pointer on systemuser in Mongo)
  • Each login: browser/OS signs challenge inside hardware; server verifies signature
Same pattern everywhere

Whether it's JumpCloud Go DUK, Protect on your phone, or Touch ID WebAuthn — the pattern is identical: private key in hardware, public key at JumpCloud, sign challenges to prove presence. Only the agent's main mTLS cert breaks this pattern (file on disk).

9. Interview Answers

"Does JumpCloud use Secure Enclave?"

"Yes, but not for the main agent mTLS certificate. JumpCloud Go stores the per-user DUK (Device User Key) in TPM on Windows and Linux, and Secure Enclave on macOS via the jumpcloud-durt-macos component. JumpCloud Protect and WebAuthn MFA also use hardware-backed keys on phones and platform authenticators. The agent's poll/config mTLS key is software-generated RSA in a file with 0600 permissions — a deliberate cross-platform choice for FileVault key continuity."

"Why doesn't the agent mTLS key use Secure Enclave?"

"Historical and practical reasons: cross-platform consistency since early agent versions, FileVault recovery key encryption depends on stable key material across cert renewals, and TPM/Secure Enclave APIs differ per OS. Security is still enforced via mTLS, dual lookup, and filesystem permissions. JumpCloud Go added hardware-backed keys later for a higher-assurance user SSO use case."

"What's the difference between mTLS cert and DUK?"

"mTLS cert identifies the device to the cloud (one per machine, file-based). DUK identifies the user on that device for JumpCloud Go SSO (per-user, hardware-backed). Different keys, different purposes, different storage."

One paragraph summary: Secure Enclave and TPM are hardware vaults that hold private keys so they cannot be stolen from disk. JumpCloud uses them for JumpCloud Go (per-user SSO signing), JumpCloud Protect (mobile MFA), and browser WebAuthn (Touch ID / Windows Hello). The main agent mTLS certificate does not use them — it is a software RSA key in client.key for device-to-cloud authentication. Knowing which feature uses which storage model is essential for security discussions and interviews.
