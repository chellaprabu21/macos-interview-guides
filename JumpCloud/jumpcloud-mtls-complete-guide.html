Start Here: The Problem We're Solving

Your laptop runs the JumpCloud agent — a small program that talks to JumpCloud's cloud servers all day long. It fetches policies, syncs users, reports inventory, and more.

Every time the agent calls the cloud, JumpCloud must answer one question:

"Is this really one of our customer's devices — or is an attacker pretending?"

Passwords don't work here — the agent can't type a password on every poll (every few minutes, forever). Instead, JumpCloud uses digital certificates and mutual TLS (mTLS) so the device proves its identity automatically, cryptographically, with no human involved.

Three ideas you need first

1. HTTPS — the locked tunnel
When you visit a bank website, you see a padlock. Data travels inside an encrypted tunnel so nobody on the Wi-Fi can read it. The website shows its certificate so your browser knows it's really the bank, not a fake site. This is one-way trust: you check the server, but the server doesn't check you (unless you log in separately).
2. Digital certificate — a computer's ID card
A certificate is like a government ID card for a device. It says: "This is device ABC123, issued by JumpCloud, valid until next year." It comes in two parts: a public certificate (the ID card you can show anyone) and a private key (a secret PIN that never leaves the device).
3. mTLS — both sides show ID
Mutual TLS means both the server and the client show certificates before talking. JumpCloud proves it's really JumpCloud. The agent proves it's really a registered device. No certificate? No connection.
Everyday analogy

Regular HTTPS is like calling a company and hearing their hold music prove you're on the right number — but they don't know who you are.

mTLS is like entering a secure building where you show your employee badge and the guard shows their official credentials. Both sides verify each other before anyone speaks.

What Exactly Is mTLS? (Client vs Server)

In every connection, there are two parties:

  • Client = the JumpCloud agent on your device (it initiates the connection)
  • Server = JumpCloud's cloud (agent.jumpcloud.com, kickstart.jumpcloud.com)

Normal HTTPS (websites)

Server shows certificate ✓
Client stays anonymous ✗

You prove identity later by logging in with username/password.

mTLS (JumpCloud agent)

Server shows certificate ✓
Client shows certificate ✓

Identity proven before any data is sent. No separate login for the device itself.

What happens in mTLS — in plain English

  1. Agent says: "I want to talk to agent.jumpcloud.com"
  2. Server says: "Here's my certificate — I'm really JumpCloud" (signed by JumpCloud CA)
  3. Agent checks that certificate against its ca.crt trust file — "Yes, this is really JumpCloud"
  4. Server says: "Now show me your certificate"
  5. Agent sends client.crt (the public ID card)
  6. Server sends a random challenge: "Prove you own the matching private key"
  7. Agent signs the challenge with client.key (the secret) — without sending the key itself
  8. Server verifies the signature — if valid, the encrypted tunnel opens and API data flows inside it
Key point: The private key (client.key) is never sent over the network. Only a mathematical signature proving you own it travels over the wire. This is the same principle as proving you know your PIN without telling anyone the PIN.

How the Certificate Is Born (Step by Step)

This happens once, during first install, when an admin (or MDM) provides a Connect Key.

Files created on your device

/opt/jc/  (macOS/Linux) or C:\Program Files\JumpCloud\  (Windows)
├── client.key   ← PRIVATE KEY (secret, never sent to cloud)
├── client.crt   ← CERTIFICATE (public ID card)
├── ca.crt       ← TRUST BUNDLE (how to verify JumpCloud servers)
└── jcagent.conf    ← CONFIG (systemKey, server URLs, poll settings)

Phase 1 — On the device (agent does this alone)

1

Generate a unique device ID (certuuid)

The agent creates a random UUID, e.g. a3f8b2c1d4e5f678... (32 hex characters). This becomes the device's permanent name. It is embedded in the certificate as the Common Name (CN) and never changes — even when the certificate is renewed years later.

2

Generate the private key — entirely on the device

The agent uses RSA 2048-bit cryptography (registration/certificate_utils.go) to create a key pair. The private key is written to client.key with file permissions 0600 (only root/admin can read). JumpCloud never sees this key. It never leaves the machine.

3

Create a Certificate Signing Request (CSR)

The agent builds a "please issue me an ID card" request. The CSR says: "Issue a certificate for device ID a3f8b2c1..., organization JumpCloud." It mathematically proves the requester owns the private key — but the private key itself is not included in the CSR.

Phase 2 — Agent talks to Kickstart (still enrolling)

4

Download config template — POST /GetRegistrationConf

Agent sends the Connect Key in the x-connect-key header. Server validates the key and returns an initial jcagent.conf with server URLs. Connection is HTTPS but not yet mTLS — the device doesn't have a certificate yet.

5

Submit CSR — POST /SignCsr

Agent uploads the CSR + certuuid + Connect Key to Kickstart. JumpCloud's CA signs it and returns client.crt. Server stores the signed cert temporarily in Redis (pending until registration finishes) and verifies certuuid isn't already used by another device.

6

Download trust bundle — GET /GetCACerts

Agent downloads JumpCloud's CA certificates into ca.crt. From now on, the agent can verify it's talking to real JumpCloud servers — not an impostor.

7

Test mTLS — GET /CheckAccess

Agent makes its first mTLS connection using the new client.crt + client.key. This confirms the certificate works before proceeding.

Phase 3 — Register with Agent Server

8

Register system — POST /registernewsystem (mTLS)

Agent sends: Connect Key, certuuid, and a system report (hostname, serial number, OS version, network interfaces). Server validates Connect Key via jumpcloud-auth, fetches pending cert from Redis, creates a system record in MongoDB, and returns the systemKey (a MongoDB ObjectId like 507f1f77bcf86cd799439011). This is saved in jcagent.conf.

Enrollment complete. The Connect Key's job is done forever. From this moment on, every API call uses only: client.crt + client.key (mTLS) + x-system-id (systemKey).

How Is the Device Bound to Your Organization?

This is one of the most important parts to understand. There are three layers of org binding:

Layer 1: Connect Key (enrollment gate)

Before any certificate exists, the Connect Key proves: "This device is allowed to join Organization X." The key is issued by:

  • Admin Console (for manual installs) — admin must have "Manage Devices" permission for that org
  • jumpcloud-auth (for MDM or User Portal installs) — key is scoped to org + device/user

Kickstart and Agent Server validate the Connect Key with jumpcloud-auth before signing the CSR or creating the system record. No valid Connect Key = no certificate = no registration.

Layer 2: Pending cert in Redis (temporary lock)

When Kickstart signs the CSR, it stores the signed certificate in Redis keyed by orgId + certuuid. During registration, the server checks: "Does a pending cert exist for this org and this certuuid?" This prevents someone from using a CSR signed for Org A to register in Org B.

Layer 3: System record in MongoDB (permanent binding)

When registration succeeds, MongoDB stores a system document containing:

FieldWhat it stores
_id (systemKey)Unique account number for this device — agent sends this as x-system-id on every request
certuuidMust match the CN on the client certificate
organizationIdWhich JumpCloud customer org owns this device
Hardware metadataHostname, serial, OS — shown in Admin Console
Think of it like…

Connect Key = invitation to join the company (one-time).
certuuid = your employee badge number (permanent).
systemKey = your employee record ID in HR database.
organizationId = which company you work for (stored in HR, not printed on the badge).

Every day at the gate (mTLS), you show your badge (cert). Security looks up badge number + employee ID in the database and confirms you still work for the right company.

The mTLS Handshake — What Happens on Every Connection

Before any poll, config fetch, or login proxy happens, the TLS handshake runs. This is invisible to users — it takes milliseconds.

1

Agent opens connection to agent.jumpcloud.com

The jchttp client loads client.crt, client.key, and ca.crt into the TLS stack (minimum TLS 1.2).

2

Server proves itself

JumpCloud sends its server certificate. Agent checks it against ca.crt — "Is this really JumpCloud, or a fake server?" If the CA doesn't match, connection aborts. This prevents man-in-the-middle attacks.

3

Server asks for the device's certificate

Because this is mTLS, the server says: "Now show me your ID card." Regular websites skip this step.

4

Agent sends client.crt

The public certificate travels over the wire. The private key does not.

5

Server sends a random challenge

"Prove you own the private key that matches this certificate right now." Showing the certificate alone isn't enough — anyone could copy the public file.

6

Agent signs the challenge with client.key

The agent uses the private key to create a cryptographic signature and sends only the signature back. This is like entering your PIN without revealing the PIN.

7

Server verifies → tunnel opens

If the signature matches the certificate, the encrypted tunnel is established. If not → connection rejected (401).

After TLS — the second check (application layer)

mTLS gets you through the front door. The application does one more check:

  1. Load balancer extracts certuuid from the certificate CN → forwards as X-SSL-CLIENT-CN header
  2. Agent also sends x-system-id header (= systemKey from jcagent.conf)
  3. Agent Server queries MongoDB: find({ _id: systemKey, certuuid: CN })
  4. Match found and system active → request proceeds
  5. No match → 401 Unauthorized
  6. System deleted → agent receives uninstall_agent directive
Two locks on the door

Lock 1 (mTLS): Cryptography proves you physically hold the private key matching a valid JumpCloud-issued certificate.

Lock 2 (database): The systemKey and certuuid must match the same active row in MongoDB — proving this cert belongs to this registered device in this org.

An attacker needs to steal the private key file and know the systemKey, and the device must still be registered.

Secure Enclave & Hardware Security — The Honest Answer

Common misconception: "The JumpCloud agent stores its mTLS private key in the Secure Enclave / TPM."

Reality for the main agent mTLS certificate: The private key is generated in software (rsa.GenerateKey in Go) and stored as a file on disk (client.key with 0600 permissions). It is not stored in Apple Secure Enclave, Windows TPM, or a hardware security module for the standard agent enrollment flow.

What is a Secure Enclave / TPM?

Modern devices have a separate secure chip designed to protect cryptographic keys:

  • Apple Secure Enclave (iPhone, Mac with T2/M-series) — isolated processor; keys never leave the chip
  • Windows TPM (Trusted Platform Module) — hardware chip storing keys; used by BitLocker, Windows Hello
  • Linux TPM 2.0 — similar hardware root of trust on many enterprise laptops

If a key lives inside these chips, even an attacker with admin access or malware cannot easily extract the raw private key — the chip performs signing operations internally without revealing the key material.

What JumpCloud agent actually does today

Where JumpCloud DOES use hardware security (different products)

The agent's mTLS cert is separate from these — but it's worth knowing for interviews:

ProductHardware security
JumpCloud Go (mobile/desktop SSO) Uses device TPM on Windows (requires TPM present); WebAuthn keys may use platform authenticators (Secure Enclave on Mac, TPM on Windows)
JumpCloud Protect (push MFA) Mobile app stores signing keys in device secure storage; WebAuthn-derived protocol (ADR-008)
Device Trust certs (user-agent, macOS) Separate certificates with OU field for device trust — may use macOS Keychain, not the agent's client.key
Agent mTLS (this guide) File-based client.key — software-generated, disk-stored
Interview honesty: If asked "Does the agent use Secure Enclave?" — answer: "The standard agent mTLS client certificate uses a software-generated RSA key stored on disk with restricted permissions. JumpCloud Go and Protect use TPM/WebAuthn/platform authenticators for user/device trust flows, which is a separate key hierarchy. Hardware-backed agent keys would be a security hardening improvement but aren't the current implementation."

What would hardware-backed keys improve?

  • Private key could not be extracted even by root/admin malware — signing happens inside TPM/Secure Enclave
  • Stolen disk images wouldn't contain extractable key material (if key never left hardware)
  • Tradeoff: key recovery on hardware failure is harder; renewal flows more complex; cross-platform consistency challenging

Certificate Renewal — Same Identity, New Expiry Date

Certificates expire (typically after ~1 year). The agent renews automatically — you don't notice.

What changes vs what stays the same

ItemOn renewal
client.key (private key)UNCHANGED — same file, same key material
certuuid (CN)UNCHANGED — same device identity
systemKeyUNCHANGED — same database record
client.crt (certificate)REPLACED — new expiry date

Why keep the same private key? The agent uses it to protect locally encrypted secrets (e.g., FileVault recovery keys). Changing the key would break access to those secrets. Source: registration/seal_renew.go explicitly avoids generating a new key on renewal.

Renewal steps

  1. Agent detects cert approaching expiry (~31 days before, with probabilistic spreading to avoid renewal storms)
  2. Creates new CSR with same private key and same certuuid
  3. Connects to private Kickstart (private-kickstart.jumpcloud.com) using existing mTLS cert
  4. POST /Renew with systemKey in x-system-id header
  5. Receives new client.crt, replaces old file
  6. Or: server sends renew_certs directive on poll to trigger renewal proactively

  Note over A: Cert nearing expiry

  A->>K: POST /Renew (mTLS + systemKey)
  K->>K: Verify existing cert + systemKey
  K-->>A: New client.crt (new expiry)
  A->>A: Replace client.crt on disk
  Note over A: client.key unchanged

FAQ — Common Questions & Misconceptions

Does the server give the agent its private key?

No. The agent generates the private key locally. The server only signs the CSR and returns the public certificate (client.crt). The server never possesses the private key.

Is mTLS the same as a username/password?

No. mTLS is cryptographic identity based on certificates. There's no password to type, steal via phishing, or brute-force. The "proof" is a mathematical signature using the private key.

Can someone copy my certificate file and impersonate my device?

They'd also need the matching client.key (private key) to pass the mTLS challenge, and know the systemKey to send in the x-system-id header. Copying only client.crt is not enough.

Where is my company name stored?

In the MongoDB system record (organizationId), not on the certificate. The certificate only has certuuid + "JumpCloud" as Organization. Org binding happened during enrollment via Connect Key.

What if I clone a disk image to another machine?

The clone would have the same certuuid + systemKey + private key. JumpCloud detects duplicate certuuid on new enrollment. For the clone to work as a separate device, it needs a fresh install with a new Connect Key generating a new certuuid. Running the same cloned agent would authenticate as the original system.

What's the difference between device auth and user login?

Device auth (mTLS): Proves which machine is calling. Automatic on every request.
User login (POST /authenticate): Proves which person is using the machine. Requires password + MFA. Proxied through agent to jumpcloud-auth. Completely separate from mTLS.

Summary — the complete picture in one paragraph

On first install, an admin provides a Connect Key that authorizes the device to join their organization. The agent generates a unique certuuid and RSA private key locally (never sent to cloud), creates a CSR, and sends it to Kickstart which signs it with JumpCloud's CA. After a successful mTLS test, the agent registers a system record in MongoDB (binding certuuid + systemKey + organizationId). Forever after, every API call uses mTLS: the agent presents client.crt, signs a challenge with client.key, and sends x-system-id. The load balancer verifies the cert; the server matches certuuid + systemKey in the database. The Connect Key is never used again. The private key lives on disk (not Secure Enclave) with restricted permissions and is never rotated. User login is a separate layer on top for proving who is using the device.
