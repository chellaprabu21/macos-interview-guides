Agent → Backend Data Flow & Scale

How every managed device sends data to JumpCloud, how the backend ingests millions of devices without melting down, and what is actually sent vs what stays on the device.

1. The Big Picture

Common misconception: "Each device sends everything to the backend all the time." That would be impossible at fleet scale. JumpCloud uses a pull + push hybrid: small frequent polls for control, batched uploads for telemetry, deduplication on the agent, and async workers on the server for heavy writes.
Think of it like a warehouse

The poll loop is a driver checking in every ~50 seconds: "Any new instructions for me?" The server answers with a tiny note (heartbeat or one directive).

Telemetry uploads are scheduled deliveries: audit events every 15 seconds (batched), System Insights tables every 5 minutes to 1 week (only if changed), metrics every 30 seconds.

The backend is not one giant database write per device — it routes hot paths to Redis/Mongo, heavy work to SQS FIFO workers, and analytics to Kafka.

Only the main agent talks to the cloud. Tray apps, user-agent, and credential providers use local gRPC on the device; the main agent forwards selected data upstream (e.g. software usage events).

4. Agent-Side: Batching, Limits & Anti-Flood

Before data leaves the device, the agent deliberately shapes traffic so one compromised or misconfigured device cannot overwhelm the cloud.

5/sHTTP upload rate limit (burst 5)
5 MBMax request body size
4500Max events per batch
15sEvent batch window
30sMetrics batch tick
10sMax poll jitter (anti-herd)

Event batching (event/handlers/audit_manager.go)

  • Aggregates events in 15-second buckets
  • Deduplicates repeated events (same type/username/IP) with repeatCount
  • Caps at 4500 events per POST (~5 MB server limit)
  • Overflow spills to jc_failed_audit_event.log (100 MB, rotated)

Metrics batching (metrics/dbqueue.go)

  • SQLite-backed queue on device
  • Sends every 30 seconds, up to 800 metrics per tick, 100 per HTTP batch
  • On failure: exponential backoff up to 5 minutes
  • Explicit anti-flood: limits max rows per interval to prevent DB flooding attacks

System Insights deduplication (system/insights/system_insights.go)

  • Checks tables every 5 minutes; uploads only when due per table interval (default 1 hour, min 5 min, max 1 week)
  • MD5 hash cache on disk — skips POST if table data unchanged
  • Random boot delay up to query interval to spread fleet upgrade load

Software usage (multi-hop)

  1. User-agent collects usage → local gRPC to main agent (max 5000 pending)
  2. Main agent persists to SQLite, forwards in chunks of 50 via gRPC

Log streaming (optional)

  • Batch size: 4 KB – 4 MB; interval: 30s – 1 hour
  • gRPC AgentLog.Snapshot with batched log lines
Poll is NOT rate-limited on the agent — it uses jcclient with Fibonacci backoff on errors (up to 377s). Uploads use jchttp.Client with the 5 req/s limiter.

Poll is the most important recurring request. It is small but hits every device constantly — so both sides optimize it heavily.

What the agent sends on each poll (headers)

  • Config checksums: policies, software apps, trusted apps, System Insights
  • Agent version, Remote Assist version
  • MQTT connection status

What the server returns (first match wins)

Directive chain in jumpcloud-devices/services/systems_poll.go: uninstall, system update, cert renew, upgrade, directive service, FDE, System Insights conf, policies, software apps, trusted apps, auth conf, agent conf, MDM enroll, legacy command queue — or default heartbeat.

MQTT push wake (ADR-003)

When backend state changes, server publishes {} to systems/{systemId}/state via AWS IoT. Agent subscribes and triggers immediate poll. MQTT carries no config — only a "poll now" hint. Batched up to 100 systems per SQS worker message.

6. Upload Paths — Data Plane Detail

System Insights (largest recurring payload)

Osquery runs on-device; agent POSTs JSON snapshots per table:

1

Config from cloud

GET /systeminsightsconf — which tables, intervals, enhanced mode

2

Query locally

Osquery executes SQL against device state (processes, disk encryption, apps, etc.)

3

Upload if changed

POST /systeminsights/snapshots/{tableName} with { "data": [ rows ] } — skipped if MD5 matches cache

Audit events → DI

POST /eventbatch → SI/devices → jcevents.EventLogger → Device Insights event server. Batch timestamp validated (±5 min skew).

Command results (size-aware)

gRPC CommandResults.UpdateCommandResult:

  • ≤ ~256 KiB → enqueue SQS devices-worker-command-results
  • Larger → inline write to Mongo DocDB (bypasses SQS size limit)

Agent logs

gRPC AgentLog.Snapshot → S3 snapshot → devices-worker-logs processes asynchronously.

8. Scaling to Millions of Devices

The math problem

1 million devices × poll every 50s ≈ 20,000 polls/second globally. Plus event batches, SI uploads, metrics. The solution is not "bigger Mongo" alone — it is shaping traffic at the edge (agent jitter, dedup, batching) and specialized async workers on the server.

What happens during a traffic spike?

  1. Poll stays lightweight — checksum compare, one directive, Redis touch
  2. Uploads queue on device (SQLite metrics, event overflow file) if cloud is slow
  3. Workers scale horizontally; FIFO preserves per-org ordering
  4. Offline devices miss MQTT wakes; catch up on next periodic poll (eventual consistency)
Design principle: The poll loop is the control plane (small, frequent, checksum-driven). Telemetry is the data plane (batched, deduped, async on server). Never mix heavy payloads into poll responses — ADR-002 and ADR-003 explicitly keep MQTT and poll bodies small.

10. Future: Near-Real-Time Telemetry (BAN-3495 / UDTL)

Today's System Insights model has 5 minutes to 2 hours latency — fine for inventory, too slow for Conditional Access when encryption is turned off right now.

BAN-3495 (in planning): Agent becomes a stateless delta emitter — detects posture changes via OS events, pushes normalized attribute deltas (≤50 events/envelope) to the Shared Device Trust Layer (ZR-2375 ingestion API). System Insights and poll paths remain; UDTL is additive.

11. Interview Answers

"How does the agent send data to the backend?"

"The main agent is the only cloud-facing process. It uses mTLS to haproxy, which routes to devices-agent-api (gRPC) and SI (legacy HTTP). The poll loop runs every ~50 seconds with jitter — it's the control plane for directives and config checksums. Telemetry goes on separate paths: batched audit events every 15s, System Insights snapshots when tables change, metrics every 30s. On-device components like user-agent talk to the main agent over local gRPC, not directly to cloud."

"How do you handle millions of devices sending data?"

"Multi-layer shaping: agents batch and deduplicate before send, add poll jitter to prevent thundering herd, rate-limit uploads to 5/sec per device. Server-side: poll is a thin hot path to Redis + Mongo; heavy work goes to SQS FIFO workers scaled horizontally per workload type. Directory sync uses per-org FIFO ordering with dynamic partitioning for hot tenants. Policy results use Postgres time partitioning. Kafka decouples device active/inactive analytics from the poll path. MQTT provides wake hints without pushing config over the wire."

"Does every device send all its data constantly?"

"No. Poll is small and frequent. System Insights only uploads tables that are due and only if the MD5 hash changed. Events are batched and deduplicated. Command results over 256 KiB bypass the queue inline. The design explicitly separates control plane (poll) from data plane (batched uploads)."

"What if the backend is down?"

"Poll uses Fibonacci backoff up to 377 seconds. Uploads retry (10× for HTTP client, up to 1440 for jcclient). Events spill to a local overflow file. Metrics queue in SQLite on device with backoff to 5 minutes. Devices keep working locally; they catch up when cloud returns."
