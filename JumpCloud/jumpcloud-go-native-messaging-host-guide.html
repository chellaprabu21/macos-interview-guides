JumpCloud Go & the Native Messaging Host

How the browser talks to the JumpCloud agent through a safe local bridge — explained for humans — and how that enables Zero Trust access to work apps.

1 What is JumpCloud Go?

JumpCloud Go is passwordless SSO from your browser into work apps (Slack, Google Workspace, GitHub, etc.).

Instead of typing a password every time, JumpCloud Go proves two things together:

  • You are the right person (on this managed machine)
  • This is the right device (hardware-backed key + live device signals)
Plain English

JumpCloud Go is like a smart door opener for work apps. The browser asks a tiny local JumpCloud helper: “Can this person on this laptop open Slack right now?” The helper checks with the vault chip and JumpCloud cloud, then hands the browser a short ticket to let you in.

2 The problem: browsers are sandboxed

A browser extension lives in a sandbox. For good reasons, it cannot:

  • Open the TPM / Secure Enclave and ask it to sign things
  • Talk directly to the JumpCloud agent service (named pipe / Unix socket)
  • Read private keys or device signals sitting on the OS
So JumpCloud needs a trusted local bridge between the web world and the agent world. That bridge is the Native Messaging Host (NMH).

4 What is a Native Messaging Host?

Native Messaging is a browser feature, not a JumpCloud invention. Chrome (and Edge / Firefox) can launch a known local program and talk to it using short JSON messages over the program’s standard input/output — like passing notes through a mail slot.

Manifest
A tiny JSON file that tells the browser: “If someone asks for host com.jumpcloud.jumpcloudgo, run this exact executable.”
Message format
Length (4 bytes) + JSON body. Strict and small. No open network port to the web.
1

Extension asks browser for the host

chrome.runtime.connectNative("com.jumpcloud.jumpcloudgo")

2

Browser looks up the manifest

Registry (Windows) or file paths under /etc/.../native-messaging-hosts/ (Linux).

3

Browser starts the NMH executable

Example: JumpCloudGo-Chrome.exe (Windows) or jumpcloudgo-chrome (Linux).

4

They exchange JSON messages

Extension sends “register” or “get access session.” NMH replies with success/error + session.

Important: The NMH is not where the cryptographically hard work lives. It is a short-lived messenger. The agent (DURT service) does signing, signal collect, and cloud calls.

5 Two hops — why communication is split

Hop 1 — Extension ↔ NMH
Browser Native Messaging: stdin/stdout JSON. The web page never gets a local network socket. Only the extension + a JumpCloud-signed host can talk this way.
Hop 2 — NMH ↔ Agent
Local gRPC over a named pipe (Windows: \\.\pipe\jumpcloud-durt) or Unix socket (Linux: /tmp/jumpcloud-durt). Agent checks: “Is the caller a JumpCloud-signed NMH?” and “Is the OS user the right person?”
Analogy

The extension is a receptionist in the lobby (browser).
NMH is a trusted courier who runs upstairs.
The agent is the vault office — only people with the right JumpCloud badge (signed process) get in.

What the agent verifies before doing anything

  1. Process check — caller is the JumpCloud NMH (Authenticode on Windows, GPG-signed binary on Linux).
  2. User check — the OS user owning the connection matches the JumpCloud username being asked about.

If either fails → request rejected. A random malware process cannot simply call “RegisterUser.”

6 How NMH gets installed

When the JumpCloud agent installs, it also lays down Go pieces:

  • NMH executable (downloaded as part of agent packaging from jumpcloud-durt-client)
  • Native Messaging manifest JSON for Chrome / Edge / Firefox
  • Registry keys (Windows) or system paths (Linux)
PlatformWhere browser finds NMH
Windows HKLM\SOFTWARE\Google\Chrome\NativeMessagingHosts\com.jumpcloud.jumpcloudgo (and Edge / Firefox equivalents)
Linux /etc/opt/chrome/native-messaging-hosts/, Chromium + Firefox paths; binary under /opt/jc_user_ro/bin/
macOS Manifest under Chrome NativeMessagingHosts from installer; Mac Go core is often via jumpcloud-durt-macos / Safari SSO (see later)
On Windows, the agent can self-repair broken NMH registry keys at startup (ensureNativeMessagingHostKeys()) so Chrome keeps finding the host after someone messes with the registry.

DUK
Hardware vault stamp. Signs every access request.
DURT
Long refresh token. Rotated on every successful access.
DUST / session
Short ticket for this SSO. Extension uses it; cloud/auth use it for trust.

Extra gate: periodic step-up

Roughly every 12 hours (or when required), Windows Hello / Touch ID / PIN may be asked again before access continues. That refreshes “this human is still at the keyboard.”

9 How this is used for Zero Trust

Zero Trust idea: never trust “just because they know a password.” Continuously check who, which device, and device health before allowing access.

JumpCloud Go helps Zero Trust in three concrete ways:

A. Device-bound user proof (hardware)

Access requests are signed by the DUK in TPM / Secure Enclave. Stealing a password (or even a DURT file) is not enough without that physical device’s chip.

B. Live device signals at SSO time

When the extension asks for a session, the agent attaches fresh signals (OS, CrowdStrike, SentinelOne, and similar) into the signed access request.

  • Collected by the agent (~30 second cache)
  • Sent only on JumpCloud Go access — not on every normal browser page load
  • Cloud Conditional Access Policies can require EDR healthy / OS rules before issuing session

C. Device assertion for Conditional Access (ADR-011)

After Go succeeds, auth can mint a device assertion from the DUST — without calling devices service again. CAP evaluates that assertion alongside user policies.

Zero Trust in one sentence: JumpCloud Go uses NMH so the browser can safely ask the managed agent to hardware-sign “allow this user on this healthy device into this app,” then Conditional Access decides allow / step-up / deny.
Without NMH, the extension could not reach the agent. Without the agent, it could not reach the vault chip or live signals. NMH is the missing link that makes browser SSO zero-trust capable.

10 Safari / macOS is a special case

Safari does not use the Chrome-style Native Messaging Host for JumpCloud Go. Apple’s path uses an App SSO Extension in the JumpCloud tray app (jcagent-tray-ssoe) plus the macOS Go client (jumpcloud-durt-macos).

Same products goals (register, DUK in Secure Enclave, access session, Zero Trust). Different plumbing: Apple SSO Extension / XPC instead of Chrome Native Messaging.

On macOS, the Go agent’s DURT listener may be a no-op stub in the Go agent binary — the Swift client owns the vault work.

11 Security controls (why this is safe design)

ControlWhat it stops
Browser sandbox + NMH only Websites cannot talk to the agent socket directly
JumpCloud-signed NMH binary Fake host pretending to be JumpCloud Go
Agent process/user authorization Wrong process or wrong OS user requesting another user’s session
DUK non-exportable in TPM/SE Copying the private key to another machine
DURT rotation + remote revoke Reuse after logout / password change / device transfer
12h step-up + PKCE Long-lived silent abuse; OAuth request binding
CAP on live signals Unmanaged / unhealthy devices getting SSO even with user credentials
Do not confuse channels:
• Agent ↔ SI/devices poll uses mTLS with client.key.
• JumpCloud Go register/access uses HTTPS + signed JWTs (device cert on register envelope; DUK on access).
• Extension ↔ agent uses NMH + local gRPC, not mTLS.

Interview one-liner: “JumpCloud Go uses a Native Messaging Host as a sandboxed bridge from the browser extension to the local agent. The agent hardware-signs access requests and attaches live device signals; the cloud and Conditional Access enforce Zero Trust before issuing a short SSO session.”
