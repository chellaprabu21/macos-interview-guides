1 First: what is a “key”?

Forget computers for a second. Imagine you have a wax seal stamp and a matching seal reader that can check if a seal came from your stamp.

Private key
Your wax stamp. Keep it secret. Whoever has it can stamp documents “as you.”
Public key
The seal reader. You can give it to anyone. It only checks seals — it cannot stamp.
Remember this

Private key = secret stamp.
Public key = stamp checker.
You create them as a pair. They always match.

2 What does “signing” mean?

Signing does not mean encrypting your whole laptop. It means: “stamp this short message so JumpCloud can prove it came from your device/key.”

A

JumpCloud sends a challenge

Like: “Prove you still have the stamp. Sign this random number: 918273.”

B

Your device stamps that number

Using the private key, it creates a signature (math proof).

C

JumpCloud checks with the public key

If it matches → “Yes, this device/user really has the private key.”

The private key never needs to travel over the internet for this to work. Only the signature (the stamp on the paper) is sent.

3 Soft key vs hardware key

There are two places you can keep the private key (your stamp).

Software key (soft)Hardware key (hard)
Where it lives A file on the hard drive (like client.key) Inside a special security chip
Can someone copy it? Yes — if malware gets admin access and reads the file No — the chip refuses to export the raw stamp
How signing works App loads the key into memory and stamps App asks the chip: “please stamp this”; chip stamps and returns only the signature
Everyday analogy Stamp sitting in an unlocked desk drawer Stamp locked inside a bank vault that only stamps papers slipped through a slot
Pause and absorb: Secure Enclave and TPM are just fancy names for that bank vault chip. Same idea on different brands of computers.

4 What are Secure Enclave and TPM?

Your computer has a main brain (CPU) and often a tiny separate security chip. That chip is purposefully dumb and strict: it can create keys, store them, and sign — but it will not hand you the private key.

Secure Enclave (Apple)
Apple’s name for the vault chip on iPhone, iPad, and modern Macs (T2 or Apple Silicon). Same family of tech that powers Touch ID / Face ID keys.
TPM (Windows & Linux)
Trusted Platform Module — the vault chip on most business PCs. Windows Hello and BitLocker also use it. JumpCloud Go uses it for the user signing key.

So when people say “hardware-backed key,” they mean: the private key was born inside the chip and cannot come out.

5 The most important JumpCloud fact

JumpCloud does NOT put the main agent certificate key in Secure Enclave / TPM.

The agent’s daily cloud identity (client.key) is a software key file on disk. That key is used for mTLS (proving “this is managed device X”) when polling and syncing.
JumpCloud DOES put JumpCloud Go’s DUK in Secure Enclave / TPM.

DUK = Device User Key. It proves “this person on this device is asking to open Slack / Google / etc.”
Two badges, two storage places

Device badge (agent mTLS) → file in a locked drawer on disk.
User SSO stamp (JumpCloud Go DUK) → locked in the vault chip.

If you mix those two up, Secure Enclave “in JumpCloud” will never make sense.

6 One-time setup: creating the DUK (register)

When a user first enables JumpCloud Go on a laptop, JumpCloud creates the hardware key. This happens roughly once per user per device.

1

User is already logged into JumpCloud

Browser (or Safari SSO) has an ID token proving who the person is.

2

JumpCloud Go client asks: “Do we have a vault chip?”

Code calls keyStore.IsSupported(). Windows looks for TPM via Platform Crypto Provider. Linux tries to open TPM 2.0. Mac uses Secure Enclave path in the macOS DURT client.

3

If no chip → stop

Registration returns “No TPM found. JumpCloud Go not supported.” JumpCloud Go will not enroll without hardware backing.

4

If chip exists → create DUK inside the chip

Windows example: GenerateECDSAKey("jumpcloud-duk-{userId}", … nonExportable=true). The private key is born in TPM. App only receives the public key.

5

Send public key + proof of user to JumpCloud cloud

Cloud stores: “User Alice on device ABC has this public key.” Cloud cannot and does not get the private key.

6

Cloud returns a DURT (refresh token)

DURT is like a library card. It is not the stamp. It is stored encrypted in OS keyring (Linux) or registry+DPAPI (Windows) — software storage, not the vault chip.

DUK
Device User Key — the stamp in the vault chip. Hardware-backed.
DURT
Device User Refresh Token — long-lived “card” from the server. Encrypted on disk/registry, not in TPM.
DUST
Device User Session Token — short ticket cloud issues for one SSO session. Not stored as a permanent key.

7 Every day: opening an app with JumpCloud Go

This is the repeating flow. The vault chip is used for signing, not for storing the whole session.

1

You click an app that uses JumpCloud Go

Browser extension (or Safari SSO) asks the local JumpCloud Go client for a session.

2

Client loads the DURT

Looks up the saved refresh token for this user.

3

Client builds an access request

Includes what app you want, device signals, and the DURT.

4

Client asks the chip to stamp the request

“GetDUKSigner(username)” finds the named DUK in TPM/SE and asks it to sign. Private key never leaves the chip. Only the signature comes back.

5

Cloud verifies the stamp

Cloud already has your public key from registration. Signature matches + DURT valid + policy OK → cloud issues a short DUST/session for SSO.

6

You are signed into the app

No agent mTLS key was involved. This was the DUK vault stamp.

  participant Ext as Browser
  participant Go as JC Go client
  participant Chip as Vault chip
  participant Cloud as JumpCloud cloud
  participant App as Work app

  Ext->>Go: Need SSO session
  Go->>Go: Load DURT
  Go->>Chip: Sign this access request
  Chip-->>Go: Signature only
  Go->>Cloud: Signed request + DURT
  Cloud->>Cloud: Check public key + policies
  Cloud-->>Go: Short session (DUST)
  Go-->>Ext: Session
  Ext->>App: Log me in
Why use the vault here? Even if malware steals the DURT file, without the DUK stamp from this specific machine’s chip, it cannot prove “I am Alice on this trusted device.” Stealing the stamp itself is much harder because it cannot be copied out of the chip.

8 How each operating system does the vault

Same story, different chip name and code path.

Windows — TPM

  1. Client checks if Platform Crypto Provider (TPM) is available.
  2. Creates ECDSA key named jumpcloud-duk-{windowsUserId}, marked non-exportable.
  3. Signing goes through PCP / TPM APIs.
  4. Separately, the agent mTLS key is still loaded from the disk file client.key — not TPM.

Linux — TPM 2.0

  1. Client opens the TPM device.
  2. Creates an ECDSA key inside TPM with “fixed to this TPM” flags.
  3. TPM private blobs can be saved via local agent gRPC (SaveDUK) — these are sealed references, not a plain private key file.
  4. Signing happens by sending a digest into the TPM and getting a signature out.

macOS — Secure Enclave

  1. JumpCloud Go on Mac uses a separate Swift client: jumpcloud-durt-macos.
  2. Architecture docs define DUK as tied to Secure Enclave (or TPM on other platforms).
  3. Keys created against Secure Enclave cannot be exported as raw private material.
  4. Again: the main agent poll certificate is still the disk file, not Secure Enclave.

9 Other JumpCloud places that use hardware keys

JumpCloud Go is the biggest desktop example. Two more related ideas:

A

JumpCloud Protect (phone MFA)

Your phone stores a WebAuthn private key in its Secure Enclave / Android Keystore. Approving a push or challenge = signing with that hardware key.

B

Browser WebAuthn / Touch ID / Windows Hello

When you register a passkey for MFA, the private key often lives in SE (Mac) or TPM (Windows Hello). Same pattern: public key in JumpCloud Auth database, private key stays in the chip.

Desktop “Device Trust certificates” for Conditional Access can live in macOS Keychain. That is encrypted OS storage, but it is not the same thing as the JumpCloud Go DUK living in Secure Enclave.

10 The full story in order (one page)

You install the JumpCloud agent

Agent creates a software RSA key file (client.key), gets a certificate, and uses mTLS forever to prove “I am this managed device.” No Secure Enclave here.

Agent talks to cloud every day

Poll, policies, System Insights uploads — all authenticated with the disk certificate. Still the drawer key, not the vault.

You turn on JumpCloud Go

Client checks for TPM / Secure Enclave. Creates DUK inside the chip. Uploads only the public key. Cloud gives you a DURT. Now you have a vault stamp for SSO.

You open Slack / Google via JumpCloud Go

Client asks the chip to sign. Cloud verifies. You get a short session. Device identity (mTLS) and user SSO identity (DUK) stay separate.

Phone MFA / WebAuthn (if used)

Same vault idea on phone or Touch ID: hardware private key, cloud public key, signature proves presence.

One sentence to remember in an interview:
“Secure Enclave and TPM are hardware vaults. JumpCloud puts JumpCloud Go’s per-user DUK in that vault so the private key cannot be stolen from disk. The main agent mTLS key is still a software file on disk. Signing means the chip stamps a challenge; the private key never leaves.”
